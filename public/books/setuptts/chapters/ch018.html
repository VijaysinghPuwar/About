13 Settings, Logging and History

13.1 Where everything lives

AppPaths (app/utils/paths.py) asks platformdirs for per-user folders, creating them and falling back to a folder under the data directory or the system temp folder if creation fails. Setting the environment variable SETUPTTS_DATA_DIR puts everything under one folder instead; the tests and the stress script use it so they never touch real user data.

macOS Windows
Data ~/Library/Application Support/SetupTTS/ %LOCALAPPDATA%\SetupTTSApp\SetupTTS\
Logs ~/Library/Logs/SetupTTS/ %LOCALAPPDATA%\SetupTTSApp\SetupTTS\Logs\
Cache ~/Library/Caches/SetupTTS/ %LOCALAPPDATA%\SetupTTSApp\SetupTTS\Cache\

Verified by runtime experiment. platformdirs 4.9.4 on the analysis Mac returned exactly the three macOS folders above for ("SetupTTS", "SetupTTSApp"). The Windows column follows platformdirs’ documented layout and matches the paths in the README and the AppPaths docstring.

File Folder Purpose
settings.json data preferences
history.db (+ -wal, -shm) data recent conversions
staging/<job>/ data resumable jobs
setuptts.lock data single-instance lock
voices.json cache last voice list, for offline start
setuptts.log (+ .1 to .3) logs application log
crash.log logs native crash dumps

13.2 Settings

AppSettings (app/config/settings.py) is a thin wrapper around a dictionary that starts from _DEFAULTS:

Key Default Notes
voice en-US-AvaNeural last used voice
rate 5 percent, clamped to -50 to 100
volume 0 percent, clamped to -50 to 50; there is no UI control, so it stays 0 (+0%) unless settings.json is edited
language_filter, gender_filter en-US, All voice picker filters
recently_used_voices [] up to 5
auto_switch_recommended_voice false Settings ▸ Voice
output_dir "" empty means the Desktop
window geometry, show_history, history_panel_height restored at start-up, clamped to a real screen

Two choices keep a damaged or locked settings file from breaking the app:

  • Per-key validation on load. _coerce converts each value to the type of its default and clamps numbers. A bad value resets only its own key, with a warning in the log. Unknown keys from a newer version are dropped. A file that is not JSON at all is renamed settings.json.corrupt. Before v1.6.2 a hand-edited "rate": "abc" crashed the app at every launch until the file was deleted.
  • Atomic save. save() writes settings.json.tmp, fsyncs, then replaces, clearing a read-only flag and retrying briefly if antivirus or OneDrive holds the file. A plain write_text truncates first, so a crash mid-write would reset every preference.

Settings are saved on every Generate, when the Settings dialog is accepted, and at shutdown.

13.3 Logging

setup_logging (app/utils/app_logging.py:36-77) configures the root logger:

  • File: setuptts.log, DEBUG and above, rotating at 10 MB with 3 backups (at most about 40 MB).
  • stderr: WARNING and above, but only if a stderr exists; a windowed Windows build has none.
  • Third-party noise: edge_tts, aiohttp and friends are limited to WARNING.

install_crash_logging adds the parts a windowed app needs to leave evidence:

  • sys.excepthook and threading.excepthook route uncaught exceptions, including those in worker threads, into the log with a session id.
  • faulthandler writes native crash stacks (a segfault in Qt or a C extension) to crash.log, which Python logging cannot do because the interpreter is already dead.
  • A Qt message handler forwards Qt’s own warnings into the log.

At start-up log_environment writes one block: app version, build kind (source, macOS app, Windows installed or portable), executable path, OS, Python, Qt, edge-tts, aiohttp and certifi versions, and locale encoding. The same block, plus the log file and app data paths, is what Settings ▸ Copy Diagnostic Info copies.

Log lines are formatted as 2026-10-05 01:30:00 INFO app.workers.tts_worker <message>. During a job the most useful lines are:

Starting: job=... voice=... rate=... chars=701783 chunk_ceiling=9200 payload_limit=3600
          resume_chunk=0 resume_chars=0 output=...
chunk 12/214 succeeded (attempt 1) in 31.20s chars=3412 range=[37120,40532) bytes=...
          first_audio=1.02s receive=29.80s
chunk 13/214 failed on attempt 1: ... [kind=timeout_after_audio cause=... chars=... range=[...]]
Job summary [completed] job=... chunks_ok=214 attempts=229 retried_chunks=11 ...

The format strings are the real ones from tts_worker.py; the values are illustrative. The Job summary line, written however the job ends, exists so that one line answers “was the connection flaky, or did one chunk keep failing?” without reading hundreds of per-chunk lines.

The log file was called voicecraft.log before v1.6.0, “a leftover from the project’s old name”; it is renamed on first run.

13.4 History

HistoryService (app/services/history_service.py) stores one row per completed job in SQLite:

CREATE TABLE IF NOT EXISTS jobs (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    text_preview    TEXT    NOT NULL,      -- first 80 characters
    voice           TEXT    NOT NULL,
    rate            TEXT    NOT NULL,
    output_path     TEXT    NOT NULL,
    created_at      TEXT    NOT NULL,      -- ISO timestamp
    duration_secs   REAL    NOT NULL DEFAULT 0,   -- wall-clock generation time
    status          TEXT    NOT NULL DEFAULT 'completed',
    error_message   TEXT    NOT NULL DEFAULT ''
);
-- schema v2 adds: audio_secs REAL  (measured MP3 length)

The “Took” column is duration_secs, the generation time. The “Length” column is audio_secs, the measured length of the MP3, which shows as a dash for jobs recorded before 1.6.0.

The service is written so that history can never stop the app:

  • WAL mode lets readers and a writer coexist.
  • Migrations are numbered by PRAGMA user_version and additive only, so an older build can still read a newer table. If the version is up to date, start-up only reads, so it never needs the write lock.
  • A database newer than the build (an old portable copy launched after an upgrade) opens read-only.
  • A busy database (another process holds the lock) opens read-only for the session instead of being treated as corrupt, a v1.6.2 fix: before, Windows failed to start and macOS set the user’s history aside as damaged.
  • A genuinely corrupt database is moved to history.db.corrupt and a new one started.
  • Every call opens and closes its own connection. with sqlite3.connect(...) commits but never closes, which leaked a file handle on Windows per call.

Only completed jobs are written. The schema and the JobStatus enum allow failed and cancelled rows, and the panel knows how to show them, but at v1.6.2 OutputPanel only calls add_job from _on_job_completed. Failed jobs live on as resumable staging folders instead.

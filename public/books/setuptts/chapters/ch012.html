8 Failure and Recovery Architecture

8.1 Fail closed

A system fails open when, on error, it carries on and produces something. It fails closed when it stops and produces nothing it cannot vouch for. For an audiobook, failing open is the worst outcome: a file that plays, looks right, and is missing twenty minutes from the middle. The user discovers it, if at all, while listening, long after the source text has been closed.

SetupTTS fails closed at every level:

  • A chunk whose stream ended early is retried, never saved.
  • A chunk that cannot be produced after retries and splitting fails the job; it is never skipped.
  • A job whose saved chunks do not tile the text is not assembled.
  • An assembled file that is implausibly short does not replace the destination.

In every case, the work already done is kept and the job can be resumed.

8.2 How the project learned this

The commit history shows the principle being learned the hard way. Historical, from commit messages:

  1. April 2026, a53f1f5, shipped in v1.5.4: “skip irrecoverable no-audio sub-chunks instead of failing the whole job”. When a tiny recovery fragment kept returning no audio, the job had been aborting. The fix returned empty bytes for that fragment so the job could finish: “A few missing chars in the output is far better than aborting a multi-hour generation run.”
  2. May 2026, cfcc615, shipped in v1.5.5: “prevent truncated long-form exports and verify full text coverage”. That empty-bytes path turned out to be “the root cause of long-form audiobook exports landing at 2-3 hours when the source text should produce 7-12 hours”. The fix reversed the policy and built the coverage system: per-chunk source ranges and hashes in the manifest, coverage verification before assembly, recovery sub-ranges, the MP3 duration check, and “Irrecoverable sub-chunks raise instead of contributing b"" bytes.” The comment at tts_worker.py:2234-2243 still records it: “Long-form correctness wins over partial output.”
  3. September 2026, c1de6d7 (v1.6.0): silent stream truncation. Coverage proved every range had a chunk, but not that each chunk’s audio was complete. edge-tts “ends its stream quietly when the socket closes before turn.end”, so a dropped connection produced a short chunk that was recorded as whole. The per-chunk completeness check was added and validated “against 36 live voices”.
  4. October 2026, v1.6.2: slow voices. Healthy slow streams were being killed by a fixed 65-second deadline, retried, and eventually failed. Deadlines became proportional to expected audio.

Engineering lesson. Step 1 was a reasonable local decision (“finishing is better than crashing”) that was globally wrong, because it converted a visible failure into an invisible one. A visible, resumable failure costs the user a click. An invisible one costs them the product’s whole promise.

8.3 Detecting a stream that ended early

Here is the edge-tts receive loop that makes silent truncation possible (edge_tts/communicate.py, simplified):

async for received in websocket:
    if received.type == aiohttp.WSMsgType.TEXT:
        ...
        elif path == b"turn.end":
            self.__compensate_offset()
            break
    elif received.type == aiohttp.WSMsgType.BINARY:
        ...
        yield {"type": "audio", "data": data}
if not audio_was_received:
    raise NoAudioReceived(...)

If the socket closes before turn.end, the async for loop simply ends. If some audio had arrived, nothing is raised. The caller sees a normal end of stream.

_stream_incomplete_reason (tts_worker.py:796-873) closes that gap with two independent checks, “each tolerant of the other’s blind spot”:

  • Audio length. The service streams constant-bitrate 48 kbit/s MP3, so bytes convert exactly to seconds: 6,000 bytes per second. Each SentenceBoundary event carries an offset and a duration in 100-nanosecond ticks. The received audio must reach the end of the last announced sentence, with 0.35 s of tolerance for frame rounding. This catches a cut inside a sentence.
  • Text reach. The announced sentences, reduced to letters and digits and matched in order against the chunk’s text, must reach within 4 letters of the end. This catches a cut between sentences, before the next one was announced. If a sentence was rewritten by the service (numbers, symbols), the match anchors on its last 12 characters.

A stream with audio but no sentence events at all is also incomplete, because the service announces each sentence a few seconds before its audio finishes.

Verified by runtime experiment. A three-sentence text was streamed with en-US-AndrewNeural. The service returned 52,416 bytes (8.74 s of audio) and three sentence events ending at 8.71 s; _stream_incomplete_reason returned None. The same events with the audio cut to 60 % returned “received 5.2 s of audio but the speech runs to 8.7 s”. Dropping the last sentence event and cutting the audio just after the second sentence returned “the audio stopped with about 49 letters of this section unspoken”.

8.5 Recovery splitting

When retries run out, _subdivide_for_recovery (tts_worker.py:2271-2331) asks whether the chunk can be split: recursion depth below 3, more than 180 characters, more than 320 payload bytes. If so, _subdivide_range_for_recovery cuts the chunk’s source range into sub-ranges using the same boundary rules at half the limits, and guarantees the last sub-range ends exactly at the parent’s end. Each sub-chunk goes through the full retry machine, recursively.

The recovered audio is the concatenation of the sub-chunks’ audio, and the parent’s manifest entry records their ranges in sub_ranges. record_chunk refuses to save the entry unless those sub-ranges cover the parent range exactly (_ranges_exactly_cover, chunk_store.py:1022-1048).

8.6 Health tracking across chunks

_record_failure_pattern (tts_worker.py:2554-2583) remembers trouble across chunks. Any no-audio failure opens a conservative window of 4 chunks; a second timeout opens one of 3. While the window is open, chunk sizes are capped at 74 % of the plan’s ceiling. The idea is that provider-side trouble tends to persist for a while, so the next few requests should be smaller and cheaper to retry.

8.7 Telling the user

Failures end in _user_message (tts_worker.py:2819-2998), which writes a specific explanation for each failure kind: the chunk it happened on, whether finished audio was kept (“Completed audio up to chunk 81 has been preserved”), and a recommended voice where that helps. Raw exception text is appended after a Technical details: marker. In the UI, split_error (app/utils/errors.py) moves everything after that marker into the dialog’s Show Details… area, so a non-technical user reads a sentence they can act on, while the cause is one click away and always in the log.

10 Audio Assembly

10.1 Why concatenation is enough

An MP3 file is a sequence of independent frames, each with its own small header. The service streams constant-bitrate MP3 frames with no file-level header, so audio for chunk 1 followed by audio for chunk 2 is a valid MP3 of both. SetupTTS never decodes or re-encodes audio; assembly is a byte copy.

Historical. Commit cdd68a9 reports a live check of this assumption: “a real 3-chunk job assembles to a clean 24 kHz mono MP3 whose duration (1493.28 s) matches both CoreAudio and ffprobe, confirming multi-chunk assembly is frame-correct.”

10.2 Order and completeness

ChunkStore.finalize (chunk_store.py:694-791) sorts records by (start_char, index), so the audio order follows the text order even if indexes were ever out of step. It then passes a series of gates; any failure leaves the destination untouched.

  1. Coverage must be complete (previous chapter). Otherwise CoverageError.
  2. Write book.mp3.part by copying each chunk file in order, re-checking that it exists, is non-empty and has its recorded size.
  3. Byte total. The .part file’s size must equal the sum of the recorded audio_bytes.
  4. verify callback. The worker passes _verify_duration, which measures the .part file. If it raises, the .part file is moved to name (incomplete).mp3 for inspection.
  5. Replace. _replace_with_retry(part, book.mp3).
  6. The worker then marks the manifest completed and deletes the staging folder.

The order of steps 4 and 5 was a v1.6.0 fix. Previously the length check ran after the file had replaced the destination, so a suspect result could overwrite an existing good file. test_duration_sanity_failure_never_replaces_the_existing_output holds that line.

10.3 Measuring duration without FFmpeg

app/utils/mp3_duration.py walks MPEG frame headers. For each 4-byte header it reads the MPEG version, layer, bitrate index and sample-rate index, computes the frame size, adds the frame’s samples to a total, and jumps to the next frame. Unknown bytes are skipped one at a time, and an ID3v2 tag at the start is skipped by its declared size, even when it is larger than the first read block.

For SetupTTS’s format the arithmetic is simple. The service sends MPEG-2 Layer III at 24 kHz, which has 576 samples per frame, at 48 kbit/s:

frame size     = 576 x 48,000 / (8 x 24,000) = 144 bytes
frame duration = 576 / 24,000               = 0.024 s
bytes per second = 144 / 0.024              = 6,000

That 6,000 bytes per second is the same constant the per-chunk completeness check uses. The parser reads in 1 MiB blocks, because “a 12-hour audiobook is ~260 MB, and reading it whole doubled the app’s memory footprint at the very end of a long job”.

10.4 The duration window

_estimate_duration_range_seconds (tts_worker.py:668-700) converts the character count into a plausible range using wide characters-per-second bands per script (Latin 12 to 22 characters per second, Han 4 to 12, Devanagari 6.5 to 16) scaled by the speaking rate. _verify_duration fails only if the measured duration is below 55 % of the minimum.

Verified by runtime experiment. For 700,000 Latin characters at normal speed the window is 8.84 to 16.2 hours, so the check fails anything under about 4.9 hours.

The band is deliberately crude. Its stated job is to “catch catastrophic truncation (e.g. a 12-hour run ending up at 3 hours)”, exactly the failure the old empty-bytes bug produced. Small losses are caught earlier and more precisely, by the per-chunk completeness check. The two checks work at different scales: one per sentence, one per book.

10.5 Why “the file exists” proves nothing

Each of these produced a file that existed, had a plausible size and played without error:

  • a chunk whose stream was cut mid-sentence (per-chunk check);
  • a recovery fragment that contributed zero bytes (sub-range coverage);
  • a one-character gap between ranges (coverage report);
  • a chunk file replaced or zeroed on disk (size and hash checks);
  • an assembly that wrote fewer bytes than recorded (byte total);
  • a result hours shorter than the text (duration window).

10.6 When a job counts as successful

A job is complete only when all of the following hold:

  1. every chunk passed the stream-completeness check when it was synthesised;
  2. the recorded ranges tile the cleaned text exactly, with matching hashes;
  3. every chunk file exists with its recorded size;
  4. the assembled byte count equals the sum of chunk sizes;
  5. the measured duration is at least 55 % of the minimum estimate (or could not be measured, which is logged);
  6. the temporary file replaced the destination.

Only then does the worker emit completed, the UI write a history row, and the staging folder disappear.

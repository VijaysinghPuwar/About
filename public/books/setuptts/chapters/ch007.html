4 Application Architecture

4.1 The big picture

SetupTTS has three kinds of places where code runs or data lives: the UI thread, a handful of background threads, and the local disk. The fourth participant, Microsoft’s speech service, is outside the program. Figure 4.1 shows how they connect.

Two rules shape everything else:

  1. The UI thread never waits. It never opens a socket, never sleeps, and never reads a large file in a loop. Anything slow happens on a QThread.
  2. Background threads never touch widgets. They report through Qt signals, and Qt delivers those signals on the UI thread.

Breaking either rule produces the classic desktop-app failures: a window that freezes while a request is in flight, or a crash because a widget was modified from the wrong thread.

One detail surprises people: history is written by the UI, not by the worker. The worker only reports completed(path, elapsed). OutputPanel._on_job_completed builds a Job row and calls HistoryService.add_job. This keeps SQLite access on one thread and keeps the worker ignorant of how results are displayed.

4.3 Start-up, step by step

main.py at the repository root is three lines of code that call app.main.main(). That function (app/main.py:56-140) does the following, in this order, and the order matters:

  1. TLS environment. Sets SSL_CERT_FILE and REQUESTS_CA_BUNDLE to certifi’s bundle. In a PyInstaller bundle Python cannot otherwise find any CA certificates, and “voice loading and audio generation silently fail with SSL errors”.
  2. Self-test mode. If --selftest is on the command line, run app/selftest.py and exit. This happens before the single-instance check so CI can test a build while another copy is open.
  3. QApplication with name, version and organisation, and a platform font (13 pt system font on macOS, Segoe UI 10 pt on Windows).
  4. AppPaths() resolves the data, log and cache folders (Chapter 13).
  5. Single instance. SingleInstance(paths.data_dir).acquire(). If another copy holds the lock, this copy asks it to raise its window and exits before logging is configured, so the second copy never writes to the shared log.
  6. Logging. Rotating file log, exception hooks for the main thread and worker threads, a faulthandler crash log, a Qt message handler, and one block of environment details.
  7. Settings, icon, stylesheet, MainWindow.
  8. Safety nets. app.aboutToQuit is connected to window.ensure_workers_stopped and to instance.release, so even an exit that bypasses closeEvent stops the threads first.

Engineering lesson. Start-up ordering is a correctness concern. Each step above was placed to avoid a specific failure: TLS before any import that might open a connection, self-test before the lock, the lock before the log file, and shutdown hooks before the event loop starts.

4.4 Threads and event loops

Qt has its own event loop on the main thread (QApplication.exec()), and asyncio needs an event loop too. SetupTTS does not try to merge them. Instead, every worker thread creates a private asyncio loop, runs one coroutine to completion and closes the loop.

The core of TTSWorker.run (tts_worker.py:1174-1234), lightly shortened:

def run(self) -> None:
    start = time.monotonic()
    if sys.platform == "win32":
        self._loop = asyncio.ProactorEventLoop()
    else:
        self._loop = asyncio.new_event_loop()
    asyncio.set_event_loop(self._loop)
    try:
        self._loop.run_until_complete(self._run_with_task())
        # ... cancelled-before-output check ...
        self.completed.emit(self._output_path, elapsed)
    except asyncio.CancelledError:
        logger.info("Generation cancelled: %s", self._output_path)
    except Exception as exc:
        logger.exception("TTS generation failed: ...")
        if not self._cancelled:
            self.failed.emit(self._user_message(exc))
    finally:
        # release the staging dir, close the loop

Three details are worth understanding:

  • Why a private loop per thread. An asyncio loop belongs to one thread. Running the coroutine on the Qt thread would need a bridge library and would put network waits on the thread that paints the window. A private loop keeps all async code on the worker, where blocking is harmless.
  • Why the Proactor loop on Windows. ProactorEventLoop is asyncio’s Windows loop built on I/O completion ports, and it has been the default there since Python 3.8. Constructing it explicitly makes the choice independent of any event-loop policy set elsewhere in the process (Inference: the code does not say why). The spec files list asyncio.proactor_events and asyncio.windows_events as hidden imports so PyInstaller always includes them.
  • How cancel crosses threads. cancel() runs on the UI thread. It sets a flag, calls requestInterruption(), and schedules task.cancel() on the worker’s loop with loop.call_soon_threadsafe. Calling task.cancel() directly from another thread would not be thread safe. The CancelledError then unwinds through await points inside the worker, where _stream_generate marks the manifest cancelled and keeps finished chunks (tts_worker.py:1640-1659).

4.4.1 Signals as the only channel back

TTSWorker declares eight signals (tts_worker.py:1088-1097):

Signal Payload Used for
progress int 0 to 100 progress bar
status_changed short text status label
stage_changed kind, text, where kind is local, remote or waiting the LOCAL / REMOTE / RETRY badge
speed_updated characters per second speed readout
telemetry_updated JobTelemetry dataclass chunk N of ~M, ETA
completed output path, elapsed seconds success
failed user-facing message error dialog
job_resumable staging dir, chunks kept, failed chunk, total Resume button

JobQueue._start_job connects each one with a lambda that binds the job id (lambda v, j=jid: self._on_progress(j, v)) and re-emits a queue-level signal that carries the id. Because the worker emits from its own thread and the receiver lives on the UI thread, Qt’s default AutoConnection becomes a queued connection: the call is posted to the UI thread’s event queue and runs there. No locks appear in the UI code because none are needed.

4.5 Keeping thread objects alive

A Python QThread object that is garbage-collected while its OS thread is still running aborts the process with “QThread destroyed while still running”, which macOS reports as “quit unexpectedly”. SetupTTS guards against this in three places:

  • JobQueue._active_workers holds every started worker until its finished signal fires (job_queue.py:317).
  • JobQueue._finishing holds workers that were cancelled and removed from the running table but have not exited yet (job_queue.py:183).
  • OutputPanel._finishing_workers does the same for a voice loader replaced by a quick Retry click.

Shutdown is ordered (main_window.py:631-689): ask the user if jobs are running, then ensure_workers_stopped(), which calls OutputPanel.shutdown(). That cancels every job, waits up to 4 seconds per worker, and only then falls back to terminate(). Settings are saved last. ensure_workers_stopped is idempotent, so the aboutToQuit safety net can call it again harmlessly.

4.6 One running copy

Two copies of the app would share the same history database, log file and staging folder; a second copy could even resume a job the first is still writing. app/utils/single_instance.py prevents that with two Qt primitives:

  • A QLockFile named setuptts.lock in the data folder, with stale time 0 so a lock left by a crashed process is detected by PID and taken over.
  • A QLocalServer (a Unix socket on macOS, a named pipe on Windows) whose name is a hash of the data folder path. A second launch connects, writes activate, waits for the first copy to hang up, and exits.

That last wait was a Windows fix shipped in v1.6.0 (commit 0248489): a named-pipe client that disconnects immediately after writing can lose the message before the server reads it.

7 Long-Form Audiobook Architecture

7.1 Why a 10-hour book is a different problem

A two-minute request and a ten-hour book use the same service and the same code path, but they live in different regimes:

2-minute clip 12-hour book
Characters about 2,000 about 700,000
Requests 1 or 2 about 214
Output size about 0.7 MB about 260 MB at 6,000 bytes per second
Peak disk use negligible about 560 MB (staged chunks plus assembled file)
Wall-clock time seconds hours
Chance that every request succeeds first time, if each fails 1 % of the time 99 % 12 % (0.99^214)
Things that will probably happen nothing Wi-Fi changes, laptop sleeps, app is closed, voice streams slowly for an hour

That probability row is the whole argument. At book length, failures are not exceptions; they are expected several times per job. A long-form design therefore needs four properties that a short-request design can ignore:

  1. Every failure is local: one chunk is retried, not the job.
  2. Progress is durable: finished work survives a crash or a quit.
  3. Completeness is provable: the final file can be shown to cover the whole text.
  4. Memory is bounded: audio goes to disk as it arrives, not into a growing buffer.

7.2 The long-form pipeline

Large text (cleaned, ~700,000 chars)
   |
   v
Chunk planner: _chunk_plan_for + _retune_after_chunk
   |   warm-up 1,200 -> ramp 3,200 -> up to 3,600 payload bytes
   v
Chunk 0 [0, 1141)   Chunk 1 [1141, 4671)   Chunk 2 [4671, 7882)  ...  Chunk 213
   |
   v   (one at a time, per job)
Individual synthesis: fresh WebSocket, layered timeouts, retries, recovery split
   |
   v
Validation: audio reaches the last sentence; sentences reach the end of the text
   |
   v
Persistent chunk storage: chunk_NNNNNN.mp3 + manifest entry (fsync, atomic rename)
   |
   v
Coverage verification: ranges tile [0, 700,000) exactly; files and hashes match
   |
   v
Assembly: concatenate in source order -> .part -> duration check -> replace
   |
   v
12-hour audiobook

Within one job, chunks are synthesised sequentially, not in parallel. The cursor position for chunk n+1 depends on where chunk n ended, and the adaptive size for chunk n+1 depends on how chunk n went. Parallelism in SetupTTS exists only between jobs (Chapter 12).

7.3 Progress for a job you will not watch

For a job measured in hours, progress information has to stay truthful:

  • Chunk count. “Chunk 82 of ~194” uses _estimate_total_chunks (tts_worker.py:1034-1049): the chunks done plus the remaining characters divided by the size of the chunk being cut right now. That estimate reflects the payload limit and the adaptive ramp. The previous version clamped the remaining count to the current index, so the label read “11/11”, “16/16” for most of a job, and “a failure on chunk 150 of 210 was reported as chunk 150/150”.
  • Percentage. From characters, corrected to the committed range after each saved chunk.
  • Time left. Shown only after chunk 3 and 45 seconds, rounded to minutes.
  • Per-chunk timing in the stage line: wait for first audio, streaming time, write time.

7.4 Checkpoints

The checkpoint unit is one chunk. Immediately after a chunk passes validation, the main loop calls chunk_store.record_chunk(...) (tts_worker.py:1568-1598), which writes chunk_NNNNNN.mp3 and rewrites manifest.json, both atomically. For English prose that is about 3,300 characters, or roughly three and a half minutes of audio. The most a crash can cost is the chunk in flight.

Each chunk’s audio is held in memory only for its own attempt, then written and released. test_twelve_hour_job_does_not_accumulate_audio_in_memory checks with tracemalloc that peak memory stays bounded over a 12-hour simulated job.

If writing the chunk fails (disk full, a file locked by antivirus or a sync client), the OSError is converted into a _ChunkError of kind staging_io, which keeps every previous chunk and offers Resume with a plain explanation. Before this, a bare OSError escaped, left the manifest marked “running”, offered no Resume, and showed raw errno text.

7.5 Resume

When the app starts, and after every job ends, OutputPanel._refresh_resume_jobs asks ChunkStore.list_resume_candidates for staging folders that hold at least one valid chunk and are not complete. If any exist, Resume Unfinished Job appears. Choosing one resubmits the job with its saved text, voice, rate, volume and staging folder.

Inside the worker, a resume differs from a fresh run in four ways:

  1. The text comes from source.txt, verbatim. _build_profile (tts_worker.py:1143-1158) replaces the cleaned text with the staged one. Because cleanup is not idempotent, re-cleaning the already-clean text could change it, change its hash, fail the “same text?” check, and silently restart from chunk 1. That was a real bug fixed in v1.6.0 (test_resume_reuses_saved_chunks_even_when_cleanup_is_not_idempotent).
  2. ChunkStore.try_resume validates everything (Chapter 9) and returns the store positioned after the last trusted chunk.
  3. The cursor starts at resume_position, the end of the trusted prefix, with full-size chunks instead of the warm-up size: “the voice is already warmed up”.
  4. If validation fails, the old folder is left untouched and the job starts over under a new job id. Reusing the id used to overwrite the old manifest and destroy whatever progress it still held.

A resume also tolerates a destination that disappeared: if the original folder is gone or unwritable, the user is asked for a new location instead of the saved progress becoming unfinishable.

7.6 Multilingual voices on long jobs

The code treats multilingual voices as riskier for long English books, based on observed no-audio failures. It reduces their chunk ceiling, warns in the sidebar for English texts over 45,000 characters, logs a note in the stage line, and suggests a same-locale standard voice when a no-audio failure finally ends a job. test_multilingual_voice_uses_smaller_chunks_for_long_jobs pins the behaviour.

7.7 How long-form behaviour is tested

The network is the one thing a test cannot use, so tests/test_long_form_scale.py replaces Communicate with a stub that echoes each chunk’s text back as its “audio”. The assembled output is then a byte-exact transcript of what was sent, which makes truncation, duplication, gaps and ordering directly checkable:

  • test_book_length_job_reproduces_the_source_text_exactly runs 6- and 12-hour fixtures through the real chunker and real assembly.
  • test_failure_deep_into_a_long_job_preserves_prior_chunks simulates an outage 25 chunks in.
  • test_resume_does_not_duplicate_already_rendered_audio checks the seam between saved and new chunks.

For the real service there is scripts/stress_longform.py, which synthesises a multi-hour excerpt of Moby-Dick from Project Gutenberg with the exact worker the app uses, in an isolated data folder, and exits 0 only if the app’s own coverage and duration checks pass.

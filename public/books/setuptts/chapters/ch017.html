12 Multi-Job and Concurrency Architecture

12.1 The job queue

JobQueue (app/workers/job_queue.py) is a QObject on the UI thread. It holds three collections:

  • _pending: a FIFO list of JobItems waiting for a slot;
  • _running: a dictionary from job id to (JobItem, TTSWorker), at most MAX_CONCURRENT = 2 entries;
  • _finishing: cancelled workers that have left _running but whose threads have not exited yet.

submit appends to _pending and calls _try_start, which starts pending jobs while fewer than two are running. Every completion, failure and cancellation calls _try_start again, so the queue drains on its own.

12.2 What each job owns

Resource Per job? Detail
Thread yes its own TTSWorker (QThread)
asyncio loop yes created and closed inside run()
WebSocket yes a fresh one per attempt
Staging folder yes staging/<job_id>/; the queue’s 8-character id is used as the folder name, or a fresh 32-character id when a failed resume starts over
Output path yes no two active jobs may share one
Retry and health state yes _RollingHealthState, _JobStats live on the worker
Voice catalogue cache shared module-level in tts_service.py, 15-minute lifetime
Live-folder registry shared _LIVE_DIRS, protected by a threading.Lock
History and settings shared only touched on the UI thread

Isolation by construction is the main concurrency strategy. Two workers never write the same file because each has its own folder and its own output path, so almost no locking is needed. The one shared mutable structure that two threads really do touch, the set of live staging folders, has a lock.

12.3 Duplicate jobs

has_active_output_path refuses a second job for a destination that is running, pending, or still held by a finishing cancelled worker. Paths are compared after resolve() and normcase, and additionally lower-cased on macOS, whose default file system is case-insensitive. Before v1.6.2, Book.mp3 and book.mp3 were accepted as two jobs writing the same file (test_same_output_file_with_different_case_is_one_destination). The same text may be exported twice to different files; that is not a duplicate.

12.4 Cancellation

Cancelling a pending job removes it from the list. Cancelling a running job does four things immediately (job_queue.py:169-194): removes it from _running (freeing the slot), marks the item cancelled, calls worker.cancel(), and moves the worker to _finishing. Then _try_start fills the free slot.

There is one race worth knowing. Final assembly runs to the end once it starts. If Cancel arrives during assembly, the worker finishes writing a complete, verified file and emits completed. Rather than lose that, the queue keeps cancelled running items in _cancelled_running and reports the completion normally (“Cancelled too late to stop the final save; the file is done”).

12.5 Two jobs at once, concretely

Suppose chapter-1.mp3 and chapter-2.mp3 are submitted a second apart:

  1. Both start immediately, each in its own thread with its own loop.
  2. Both fetch the voice catalogue; the second probably gets it from the 15-minute cache.
  3. Each runs its own preflight, creates its own staging folder and streams its own chunks. Their requests interleave freely on the network.
  4. Signals from both arrive on the UI thread tagged with their job ids and update separate rows.
  5. If one fails, its error dialog is queued; the other job keeps running.
  6. When the first finishes, the slot goes to chapter-3.mp3 if one is pending.

Limitation found while preparing this book. The disk-space pre-flight (_check_free_space) compares a job’s estimated need with the free space now. It does not subtract what other running jobs are about to use, so two large jobs started together can each pass the check and still fill the disk between them. The failure is handled safely (a resumable staging_io error), but the up-front check is per job, not global.

12.6 Shutdown with jobs running

Quitting asks first (“Audio is still being generated … the audio finished so far is kept”). If the user quits, cancel_all cancels pending items, cancels running workers and waits up to 4 seconds for each, then waits for finishing workers the same way. A worker still alive after that is terminate()d as a last resort. Because chunks are checkpointed, even that loses at most the chunk in flight.

16 GitHub Actions and CI/CD

16.1 When it runs

.github/workflows/build.yml has two triggers:

  • Pushing a tag that matches v*, such as git push origin v1.6.2. This builds, tests and publishes a release.
  • workflow_dispatch, a manual run from the Actions tab with an optional version label. It builds and tests every artifact but does not publish.

A concurrency group keyed on the ref, with cancel-in-progress: true, stops a re-pushed tag from racing an earlier run of the same tag.

Observation. The workflow has no push or pull_request trigger for ordinary commits, so the tests run in CI only when a release is tagged or a run is started by hand. The project’s run history shows the habit that compensates: both pull-request branches (fix/windows-voice-loading-1.6.1 and release/1.6.2) were validated with manual workflow_dispatch runs before they were merged. Nothing enforces that habit; it is a convention.

16.2 The pipeline

16.2.1 build-macos (macos-latest, Apple Silicon)

  1. Check out, set up Python 3.12.
  2. Resolve the version from the tag (v1.6.2 becomes 1.6.2).
  3. Check the tag matches APP_VERSION and that release_notes/v1.6.2.md exists. A release can never be published with the wrong version inside it or without notes.
  4. Install requirements.txt, PyInstaller and the test tools; run pytest -q with QT_QPA_PLATFORM=offscreen.
  5. Install create-dmg; run PyInstaller.
  6. Verify bundle assets are in Contents/Resources.
  7. Verify the declared minimum macOS. A Python snippet walks every Mach-O file in the bundle, runs otool -l, finds the highest minos any binary requires, and fails if LSMinimumSystemVersion is lower. This is the guard against repeating the v1.5.8 mistake.
  8. Self-test the .app with --network, and check the reported version.
  9. Create the DMG and hdiutil verify it. (create-dmg exits non-zero for unsigned apps even on success, so its exit code is ignored and the file is verified instead.)
  10. Mount the DMG read-only and self-test the app inside it; check the Applications link exists.
  11. Zip with ditto, extract and self-test that copy.
  12. Upload the DMG and zip as workflow artifacts.

16.2.2 build-windows (windows-latest)

  1. Check out, Python 3.12, version and tag checks, install, pytest -q.
  2. PyInstaller onedir; verify the EXE and assets exist.
  3. Self-test the onedir build with --network. A small PowerShell helper launches the windowed EXE, waits, reads the JSON, and fails the step if ok is false or the version differs.
  4. Build the installer with ISCC.exe, passing the version and source folder.
  5. Install it silently (/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CURRENTUSER), check the installed EXE exists at %LOCALAPPDATA%\Programs\SetupTTS\SetupTTS.exe, check its ProductVersion equals APP_VERSION, and self-test the installed app with --network.
  6. PyInstaller onefile for the portable build; zip it.
  7. Extract the zip and self-test the extracted EXE with --network.
  8. Upload the installer and the portable zip.

16.2.3 create-release (ubuntu-latest)

Runs only for tag pushes and only after both build jobs succeed (needs: [build-macos, build-windows]). It has contents: write permission, downloads the four artifacts, and calls softprops/action-gh-release@v2 with:

  • name SetupTTS v1.6.2;
  • body from release_notes/v1.6.2.md;
  • the four files, with fail_on_unmatched_files: true;
  • make_latest: true, so the README’s “Latest release” link points to it.

Verified from the project’s GitHub Actions history. The v1.6.2 tag run succeeded in 12 minutes 28 seconds and published the release at 05:42 UTC on 5 October 2026. The history also shows the gate working: on 27 August 2026 the v1.5.8 tag was pushed five times, and four of those runs failed (in the runs inspected, test_ui_layout.py assertions on the Windows runner, where the default font is wider) before the fifth succeeded and published. v1.6.1 was never published; its fixes shipped inside v1.6.2.

16.3 Versioning

The version lives in app/__init__.py as APP_VERSION, and everything reads it from there: the spec (bundle version, Windows VERSIONINFO), the build scripts (file names), the window title, Settings, the self-test JSON and the CI checks. pyproject.toml repeats it and must be bumped by hand; the README’s release steps say to change both. The release ritual is:

# 1. set APP_VERSION in app/__init__.py and version in pyproject.toml
# 2. add release_notes/vX.Y.Z.md
git tag vX.Y.Z && git push origin vX.Y.Z

Engineering lesson. “Tested as shipped” is the idea behind this workflow. Unit tests run against source code, but users run a frozen bundle, a mounted disk image, an installed copy and an unzipped EXE. Each of those has failed differently in this project’s history. The workflow tests each one, and the network self-test catches TLS and proxy problems that only appear outside a developer’s environment.

19 Engineering Lessons

Each section names a concept, shows where SetupTTS uses it, and says why it matters beyond this project.

19.1 Asynchronous programming

The idea. Code that mostly waits on I/O can wait cooperatively: an await hands control back to an event loop, which runs something else until the data arrives. In SetupTTS. edge-tts’s stream() is an async generator. The worker consumes it inside asyncio.wait_for so that every wait has a deadline, and cancellation arrives as a CancelledError at the next await. Why it matters. Async code makes timeouts and cancellation composable. _consume_stream expresses three different timeouts in a few lines because each await is a natural place to stop.

19.2 GUI architecture and the event loop

The idea. A GUI is a loop that processes events: input, timers, repaints, posted calls. Anything slow inside a handler freezes the window. In SetupTTS. Widgets only read inputs, validate them and submit jobs. Work happens elsewhere; results come back as events. Heavy UI-side computations are debounced (250 ms editor settle, 150 ms search) or sampled (120,000-character guidance profile). Why it matters. Responsiveness is an architectural property, not an optimisation. It comes from deciding what may run on the UI thread at all.

19.3 Worker threads

The idea. Move blocking or long-running work to another thread and communicate with messages, not shared state. In SetupTTS. Each QThread owns its own asyncio loop, its own staging folder and its own output path. The only shared mutable structure, the live-folder set, has a lock. Thread objects are kept alive until their OS thread exits. Why it matters. Most threading bugs come from sharing. Designing for isolation removes whole classes of bugs before locks are even considered.

19.4 Event-driven programming

The idea. Components announce what happened and others react, instead of calling each other directly. In SetupTTS. Qt signals connect worker to queue to panel to row widget. The worker never knows a progress bar exists. Queued connections make cross-thread delivery safe automatically. Why it matters. Loose coupling made it possible to rebuild the Active Jobs display in v1.6.0 without touching the worker.

19.5 Network programming

The idea. Networks fail partially: connections succeed then stall, servers accept requests and never answer, streams end early. In SetupTTS. Layered timeouts for connect, first byte, idle gap and whole operation; a fresh connection per attempt; failure classification into kinds that each get a different response. Why it matters. A single “timeout = 30 s” is wrong for every request except the one it was tuned on. The 65-second floor that killed slow voices is the cautionary tale.

19.6 Retries and exponential backoff

The idea. Retry transient failures, waiting longer each time so a struggling service gets room to recover. In SetupTTS. Five attempts with 2, 4, 8, 16 s waits; early exit after two for failures that repetition rarely fixes; a longer deadline after a mid-stream cut; and, when retrying stops helping, a different request (a split) rather than the same one again. Why it matters. A retry policy is a set of decisions about which failures are transient. Treating all failures the same either gives up too early or wastes minutes on hopeless requests.

19.7 Fault tolerance and failing closed

The idea. A fault-tolerant system keeps working through faults, and when it cannot, it stops in a safe state. In SetupTTS. Recoverable faults are absorbed at the smallest scope: an attempt, a chunk, a sub-range. Unrecoverable ones stop the job with all finished work kept. Nothing incomplete is ever published under the user’s file name. Why it matters. The project’s history (Chapter 8) shows a well-meant fail-open choice producing 3-hour audiobooks from 10-hour texts. Visible failures are cheap; invisible ones destroy trust.

19.8 Checkpointing

The idea. Save progress at boundaries so that a crash loses only the work since the last checkpoint. In SetupTTS. Every validated chunk is written with its manifest entry before the next begins; resume continues from the last trusted chunk. Why it matters. The cost of a crash becomes “one chunk” instead of “the job”, which is what makes multi-hour work on consumer machines practical.

19.9 Data integrity

The idea. Record enough metadata to prove that data is complete and correct, and check it rather than assume it. In SetupTTS. Absolute source ranges, per-chunk text hashes, byte counts, sub-range coverage, a coverage report, a byte-total check during assembly, a duration window, and atomic writes with fsync. Why it matters. “The file exists” proves nothing (Chapter 10). Integrity comes from invariants that are cheap to check and checked at every boundary.

19.10 Working with a service you do not control

The idea. A remote service can change, slow down, or answer in ways its client library does not report. In SetupTTS. The service is used unofficially through a library that ends streams silently. SetupTTS verifies completeness from the service’s own metadata (sentence timing) and the physics of the format (6,000 bytes per second), instead of trusting “no exception” to mean “success”. Why it matters. When you cannot fix the other side, verify its output using information it already gives you. This is a small instance of a general distributed-systems truth: the absence of an error is not an acknowledgement.

19.11 Chunking

The idea. Split large work into units small enough to retry, verify and checkpoint individually. In SetupTTS. Chunks are sized to map one-to-one onto provider requests, cut at natural boundaries, and sized adaptively. Why it matters. The unit of work decides the unit of failure, progress and recovery. Choosing it is one of the most consequential design decisions in any batch system.

19.12 State machines

The idea. Model a lifecycle as named states with explicit transitions. In SetupTTS. The manifest status (running, completed, failed, cancelled, interrupted), the JobItem status in the queue, and the attempt machine of Figure 8.2. Why it matters. Explicit states make it possible to ask “what should resume do with a manifest that says running?” and get a single, testable answer.

19.13 Persistence

The idea. Choose the storage format that matches the data’s shape and failure modes. In SetupTTS. JSON for small documents rewritten whole (settings, manifests) with atomic replace; SQLite for an appendable, queryable table (history) with WAL, migrations and read-only fallbacks; plain files for bulk binary data (chunks). Every store is designed to survive being damaged, being newer than the code, or being locked by another process. Why it matters. User data outlives versions of your program. Plan for reading files your past and future selves wrote.

19.14 Packaging

The idea. Ship the runtime with the program so users need nothing else. In SetupTTS. PyInstaller with explicit data files and hidden imports; different shapes for different delivery channels (bundle, installer folder, single EXE); fixes for things that only break when frozen. Why it matters. For desktop software, the packaged artifact is the product. Packaging decisions (onefile versus onedir) have user-visible consequences such as a 30-second start-up.

19.15 CI/CD

The idea. Automate build, test and release so every release is produced the same way. In SetupTTS. Tag-triggered builds on both platforms, consistency checks on versions and notes, and self-tests of every artifact, including live network checks, before publishing. Why it matters. The workflow encodes lessons as gates: the minimum-macOS check exists because a release once lied about its requirement.

19.16 Cross-platform development

The idea. “Works on my machine” hides platform differences. In SetupTTS, platform differences that needed code: Windows forbids certain file names and characters; paths over 260 characters fail; antivirus and sync clients briefly lock new files; proxies and trusted certificates live in the registry and the Windows store; the default UI font is wider on Windows; macOS’s default file system is case-insensitive; named pipes behave differently from Unix sockets; a windowed Windows app has no stderr. Why it matters. Each of these was a real bug. Cross-platform code is mostly a catalogue of such differences, discovered by testing on each platform.

19.17 Measure before you tune

The 65-second deadline was replaced because a user’s log showed “22 of 29 such failures … hit exactly 65 s”. The streaming-speed constants (15.8 characters per second, 0.45x slowest) and the completeness tolerances (0.35 s, 4 letters, validated on 36 voices) are all measured. Good reliability work in this project starts from logs, not guesses, which is why the per-job summary line exists.

14 Security and Privacy

This chapter describes what the implementation does. It is not a privacy policy and makes no promises the code does not keep.

14.1 What leaves your computer

Data Sent to When
The full cleaned text, chunk by chunk speech.platform.bing.com (Microsoft) every generation
A sample of about 220 characters from the start of the text same startup check, texts of 4,000+ characters
A fixed preview sentence (“Hello! This is a preview…”) same Preview Voice
Voice name, rate, volume same every request
A request for the voice list same start-up, Retry, and before each job (cached 15 minutes)
Your IP address, and request headers that edge-tts sets to resemble the Edge browser, including a randomly generated muid cookie same every connection

Nothing else is sent anywhere. A search of app/ finds no other host names, no analytics, no crash reporting and no update check.

What this means in practice. Anything you convert is transmitted to Microsoft’s service and processed there. How Microsoft handles that text is governed by Microsoft, not by SetupTTS, and SetupTTS uses the service without an official API agreement. Do not convert text you are not willing to send to a third party.

14.2 What stays local

  • The text in the editor, and the cleaned text in staging/<job>/source.txt, in plain text, until the job completes (folder deleted) or is swept: 7 days for non-resumable folders, 60 days for resumable ones. Discarding saved progress from the Resume menu deletes it immediately.
  • The first 80 characters of each completed job’s text, its voice, rate and output path, in history.db, until removed from history.
  • Logs, which record file paths, voice names, character counts and ranges, timings and error causes. SetupTTS’s own log statements do not write the text itself.
  • Generated audio: chunk files in staging, the final MP3 in the folder you chose, and, if the duration check fails, a name (incomplete).mp3 beside it.
  • The preview’s temporary MP3, created in the system temp folder and deleted after playback or on stop.

None of this is encrypted by SetupTTS; it is protected only by your operating-system account.

14.3 Credentials

SetupTTS has no API keys, accounts or secrets of its own, and stores none. The edge-tts library contains a public client token constant that identifies it as an Edge-style client, and computes a short-lived Sec-MS-GEC value from the current time. Neither belongs to the user, and this book deliberately does not reproduce them.

14.4 Network security

  • TLS is always verified. build_ssl_context starts from certifi’s CA bundle and adds the operating system’s store. Verification is never turned off. tests/test_network_setup.py checks that edge-tts uses this context for both the voice list and synthesis, and the packaged self-test checks it again inside each built app.
  • The trade-off of trusting the system store. It means trusting any root the machine already trusts, including the roots that antivirus HTTPS scanners and corporate proxies install to inspect traffic. That is what makes SetupTTS work in those environments, and it also means such software can read the text in transit, exactly as it can for the user’s browser.
  • Proxies. If no proxy environment variables are set, system_proxy reads the operating system’s proxy settings (on Windows, the registry via urllib), skips it if the speech host is on the bypass list, and passes only http:// proxies to aiohttp, which cannot tunnel through SOCKS. A broken proxy setting is logged and ignored rather than stopping the app.

14.5 Distribution security

The macOS app is not signed or notarised and the Windows installer and EXE are not code-signed, so macOS Gatekeeper and Windows SmartScreen warn on first launch and users must override them. Practically, this means a user cannot verify the publisher cryptographically; trust rests on downloading from the project’s GitHub Releases page. The release workflow builds from the tagged source on GitHub-hosted runners with pinned dependency versions, which narrows but does not remove supply-chain risk. scripts/entitlements.plist exists for a future signed build but is not referenced by setuptts.spec (entitlements_file=None).

14.6 Local safety measures

A few smaller choices reduce local risk: output names that Windows reserves for devices (CON, NUL, COM1…) are refused; writes go through temporary files so an interrupted write never corrupts an existing file; the single-instance socket is local-only and named after a hash of the data folder; and an existing output file is never replaced without asking.

SetupTTS is a pure-Python desktop application. Every dependency below was found in requirements.txt, pyproject.toml, an import statement or a build file. Anything not in this chapter is not used. In particular there is no FFmpeg, no audio library and no web framework.

2.1 Python

What it is. A general-purpose interpreted language. Why here. The best available client for the Edge voices, edge-tts, is a Python library, and Python with Qt bindings gives a native-looking desktop UI on both target platforms from one codebase. What it costs. End users do not have Python, so the app must ship its own interpreter (Chapter 15), and Python’s single interpreter lock means “background work” must be either I/O-bound or in native code. SetupTTS’s background work is almost entirely waiting on the network, which suits Python well.

2.2 PySide6 and Qt

What it is. PySide6 is the official Python binding for Qt 6, a C++ application framework. Why here. Qt supplies the widgets, the event loop, a thread class with safe cross-thread messaging (signals and slots), a stylesheet system, a lock file and a local socket server. SetupTTS uses all of these. The pinned version matters: PySide6 6.10 and later ship binaries that need macOS 15, which is why the app’s minimum macOS version is 15.0 and why CI checks every bundled binary against it (Chapter 16).

Where. app/main.py creates the QApplication; app/ui/ holds the widgets; app/workers/ subclasses QThread; app/utils/single_instance.py uses QLockFile and QLocalServer; app/assets/styles/app.qss is a 1,078-line dark theme.

2.3 edge-tts

What it is. An open-source Python library that talks to the speech endpoint the Edge browser uses. It fetches the voice list over HTTPS and synthesises speech over a WebSocket, yielding a stream of events: binary audio frames and SentenceBoundary metadata with timing. Why here. It is the provider. Where. Only app/services/tts_service.py imports it by design (“This module is the only place that imports edge_tts directly”), with two narrow exceptions in tts_worker.py: its exception classes and two text helpers (escape, remove_incompatible_characters) used to measure the exact payload size edge-tts will send.

The version pin is deliberate. The comment in requirements.txt says edge-tts 7.x compensates SentenceBoundary offsets for CBR audio, “which the per-chunk completeness check relies on”. Chapter 8 explains why that matters.

2.4 asyncio and aiohttp

What they are. asyncio is Python’s event loop for cooperative concurrency: code that waits on the network yields control instead of blocking. aiohttp is an asyncio HTTP and WebSocket client. Why here. edge-tts is an async library; its stream() is an async generator. SetupTTS never runs asyncio on the UI thread. Instead each worker thread creates its own event loop (Chapter 4). aiohttp matters to SetupTTS in two ways: its exception types (ClientConnectorDNSError, ServerTimeoutError and others) are how failures are classified, and it only reads proxy settings from environment variables, which is why SetupTTS reads the Windows proxy itself (Chapter 14).

2.5 TLS: ssl and certifi

Why here. In a frozen app Python cannot find a certificate bundle on its own, so app/main.py points SSL_CERT_FILE at certifi’s bundle before anything else runs. In v1.6.1 the app also learned to trust the operating system’s certificate store, because antivirus “HTTPS scanning” and corporate proxies re-sign traffic with a root that exists only in the Windows store (build_ssl_context, tts_service.py:26-44).

2.6 platformdirs, JSON and SQLite

platformdirs answers “where do per-user files go on this OS?” (Chapter 13). Settings live in a JSON file written atomically. Resumable job state lives in a JSON manifest per job, also written atomically. Completed jobs are recorded in a small SQLite database in WAL mode. None of these need a server, which is the point: everything stays on the user’s machine.

2.7 PyInstaller, Inno Setup and the macOS tools

PyInstaller analyses main.py, follows the imports, and copies the interpreter, the libraries, Qt’s plugins and the app’s data files into a bundle. On macOS the result is SetupTTS.app, wrapped in a DMG by create-dmg and in a zip by ditto. On Windows there are two builds: a folder build packaged by Inno Setup into an installer, and a single-file portable EXE. Chapter 15 explains why both exist.

2.8 GitHub Actions

A single workflow, .github/workflows/build.yml, runs on every pushed tag that starts with v. It tests on macOS and Windows, builds every artifact, launches each packaged app in a self-test mode (four of those runs contact the live speech service), and only then publishes a GitHub Release. Chapter 16 walks through it.

Engineering lesson. Notice how little the stack contains. Audio is never decoded or re-encoded: the service already streams MP3, and MP3 frames can be concatenated byte for byte. The only “audio processing” in the project is a 171-line frame-header parser used to measure duration (app/utils/mp3_duration.py), which exists precisely so the app does not need to ship FFmpeg.

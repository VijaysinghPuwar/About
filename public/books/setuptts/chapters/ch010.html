6 The Text-to-Speech Pipeline

This chapter follows one job from the moment the worker starts to the moment the MP3 exists. Figure 6.1 is the map; the sections below take it one box at a time.

6.1 Text import

Text arrives either from the editor or from a file decoded by decode_text_file (Chapter 5). Either way the worker receives a Python str. Nothing downstream knows or cares where it came from.

6.2 Text normalization

The first thing the worker does with that string is clean it, via build_text_profile → normalize_text_for_tts (app/services/tts_quality.py:467-515). The goal stated in its docstring is narrow: “Clean punctuation and noisy unicode without changing the meaning.” In order, it:

  1. Applies Unicode NFKC normalisation, which folds compatibility forms (full-width Latin letters, ligatures) into their ordinary equivalents.
  2. Maps typographic punctuation to plain ASCII: curly quotes to straight quotes, all dash variants to -, … to ..., CJK corner quotes to ", CJK lenticular and tortoise-shell brackets to [ ], non-breaking spaces to spaces.
  3. Normalises line endings and removes invisible characters: zero-width space, direction marks, BOM, and the soft hyphen (U+00AD), which e-books scatter through words so that “inter­national” would otherwise be read as two words.
  4. Removes Markdown bullets, replaces Unicode bullets with commas, and drops decorative symbols (stars, hearts, card suits).
  5. Collapses !!!! to !! and long ellipses to ....
  6. Replaces control characters and unspoken symbols with spaces, but keeps the symbols voices actually read: ° © ® ™ ℃ ℉ № ℗.
  7. Keeps zero-width joiners (ZWNJ, ZWJ) inside words, where they change how Persian and Indic words are shaped, and after a virama, where they select a letter form. Elsewhere, such as the leftovers of an emoji family, they become spaces.
  8. Cleans each line: separator lines such as ----- vanish, [Narrator] Hello becomes Narrator: Hello, arrows become ” to “, pipes become commas.
  9. Collapses more than two consecutive blank lines.

An important property: this cleanup is not idempotent. Cleaning already-clean text can change it again. The docstring of _build_profile (tts_worker.py:1148) gives the example "Stop ! ! !" → "Stop!!!" → "Stop!!". That fact caused a real bug, covered in Chapter 7.

Code that never runs. normalize_text_for_tts contains a rule meant to turn runs of Unicode dashes into - (_EXTRA_DASH_RE, tts_quality.py:22, applied at :482). It never matches, because step 2 has already converted every Unicode dash to an ASCII -. Running the function on two em-dash characters between letters returns two ASCII hyphens, not -. Nothing breaks, but it is a small example of why behaviour should be checked by running code rather than by reading it.

6.3 Language and voice selection

build_text_profile (tts_quality.py:619-735) then guesses what the text is:

  • Script by counting letters per Unicode range (Latin, Devanagari, Arabic, Cyrillic, Han, Hiragana, Katakana, Hangul, Thai and sixteen more). Any Hiragana or Katakana means Japanese.
  • Mixed if a second script has at least 4 letters and at least 18 % of all letters.
  • Language for Latin and a few other scripts by counting common function words (“the”, “and”, “der”, “und”, “है”, “это”…), plus character hints such as þ ð for Icelandic and і ї є ґ for Ukrainian.

assess_voice_compatibility compares that profile with the selected voice’s locale and returns a severity: ok, warning (for example a multilingual voice reading a different language in the same script) or mismatch (wrong script entirely, “likely to produce poor pronunciation or gibberish”). It also proposes a voice via recommend_voice, preferring the exact locale, then the language, then the script, matching the current voice’s gender.

This runs twice. In the UI, build_guidance_profile profiles at most 120,000 characters (start, middle and end samples) so the warning card can update while typing without freezing the window. In the worker, the full text is profiled on the worker thread, and a mismatch stops the job before any audio is requested unless the user chose Generate Anyway (allow_voice_mismatch) or the job is a resume, which was already confirmed when it first started (tts_worker.py:1319-1343).

6.4 Why chunking exists

The service, as reached through edge-tts, accepts text in requests of bounded size. edge-tts itself splits any text longer than 4,096 bytes (after XML escaping) into several requests inside a single Communicate object (edge_tts/communicate.py:351). SetupTTS keeps every chunk below that limit on purpose. The comment at tts_worker.py:68-70 says why: “so each SetupTTS chunk maps to one actual provider request”. If SetupTTS sent a 20,000-byte chunk, edge-tts would quietly turn it into five requests, and SetupTTS could no longer tell which of the five failed, retry just that one, or record exactly which characters the audio covers.

Even if the service accepted a whole book in one request, a single request would be the wrong design:

  • Failure cost. A dropped connection at hour 9 of a single 10-hour stream loses 9 hours. With chunks it loses one chunk, about three and a half minutes of audio.
  • Verification. A short request can be checked against the service’s own sentence timing. A 10-hour stream could only be checked at the end.
  • Resumability. Progress can only be saved at boundaries the program controls.
  • Proportionate timeouts. A deadline can be sized for 3,000 characters. It cannot sensibly be sized for 700,000.

6.5 How chunk size is decided

6.5.1 The plan

_chunk_plan_for (tts_worker.py:167-232) returns a _ChunkPlan from the job’s length, script and voice:

Job length (cleaned chars) Max chars Max payload bytes
under 12,000 10,500 3,750
12,000 to 44,999 10,000 3,700
45,000 to 89,999 9,600 3,650
90,000 and over 9,200 3,600

Every plan also has a warm-up size for the first chunk (1,200 chars / 1,350 bytes) and a ramp size for the second (3,200 / 2,600). Complex scripts get much smaller limits from _COMPLEX_SCRIPT_LIMITS: Han text, for example, is capped at 3,100 chars and 2,150 bytes, because each Han character is three bytes in UTF-8. Multilingual voices on jobs of 45,000+ characters are shrunk to 78 % or 84 % of the normal ceiling, because, in the code’s words, multilingual voices “are more resource-intensive on the provider side”.

6.5.2 Characters versus bytes

A chunk must fit both limits. The byte measure is what edge-tts will actually send: _edge_payload_size applies edge-tts’s own remove_incompatible_characters and XML escape, then counts UTF-8 bytes (tts_worker.py:255-258). For English prose the byte limit binds long before the character limit, so the 9,200-character ceiling is mostly theoretical.

Verified by runtime experiment. The test suite’s own 12-hour fixture (_build_book(12) in tests/test_long_form_scale.py, 701,783 characters after cleanup) was cut with the production plan. It produced 214 chunks averaging 3,277 characters, the largest 3,595 characters. The 6-hour fixture produced 107.

Docs and code disagree. The docstring of tests/test_long_form_scale.py estimates “~35 production chunks” for 6 hours and “~70” for 12 hours. That assumes chunks near the character ceiling. Because the payload limit binds first, the real counts are about three times higher. The tests’ assertions are about coverage and bounds, so they still pass; only the comment is off.

6.5.3 Adaptive sizing during the job

The size is not fixed. After each chunk, _retune_after_chunk (tts_worker.py:2487-2552) adjusts the limits for the next one:

  • First chunk at the warm-up size, second at the ramp size.
  • Healthy chunks grow both limits by x1.18, up to the plan’s ceiling.
  • A chunk that needed a retry, needed recovery, or streamed slower than real time shrinks the next one by x0.82.
  • After any no-audio failure (a window of 4 chunks) or a second timeout (3 chunks), a conservative window caps sizes at 74 % of the ceiling; each clean chunk counts the window down.

The definition of “slow” was a v1.6.2 fix. Before, any chunk that took longer than 32 seconds counted as slow, which kept slow-streaming voices such as Andrew pinned at 1,000 to 2,000-character chunks: “3-5x more requests, each one a failure risk”. Now a chunk is slow only if it took over 32 seconds and produced less audio than the time it took, or if its first audio arrived very late.

6.6 Where to cut

Knowing the limit is half the job; the other half is choosing a boundary that does not split a sentence or a word. _take_chunk_at (tts_worker.py:491-544) searches the window in tiers and takes the largest candidate that fits:

  1. Paragraph breaks (\n\n).
  2. Sentence ends: . ! ? followed by space, also after a closing quote or bracket, and the full-width 。！？, which are not followed by spaces in Chinese and Japanese.
  3. Clause marks: ，、；： and , ; : followed by space, but only if the resulting chunk is at least 40 % of the window. Otherwise “Well, <3,000 words>” would become a 5-character request.
  4. Whitespace.
  5. A hard split by binary search, for pathological text such as a long URL.

Before v1.6.2, the CJK sentence marks were only recognised when followed by whitespace, so every Chinese or Japanese chunk fell through to the hard splitter and was cut mid-sentence (test_cjk_chunks_end_at_sentence_boundaries).

Finding “the largest prefix that fits” also used to be slow. The payload of a prefix grows with its length, so _largest_fitting_boundary binary-searches the sorted candidates instead of trying them one by one; the commit message reports about 150x faster cutting on text without paragraph breaks.

6.6.1 The cursor and the gap bug

Chunks are taken by a _ChunkCursor (tts_worker.py:440-488) that walks the cleaned text by absolute position and returns (text, payload, start, end). The spoken text is stripped of surrounding whitespace, but the recorded range is not:

def take_next(self, max_chars, max_payload_bytes):
    """...The range starts at the cursor, *not* at the first non-whitespace
    character: whitespace between two chunks belongs to the later one."""
    start = self.position
    chunk, _, end, payload = _take_chunk_at(
        self.source_text, start, max_chars, max_payload_bytes)
    self.position = end
    return chunk, payload, start, end

The docstring records why. When the range began at the first non-whitespace character, a split that landed inside a blank line left a one- or two-character gap between two recorded ranges. The final coverage check (Chapter 9) then refused to assemble the file on every attempt and every resume, because the same text always cut the same way. The v1.6.2 notes say this “affected many Andrew audiobooks”. test_paragraph_break_on_the_warmup_boundary_still_completes is the regression test.

6.7 Before the first chunk: preflight

Several cheap checks run before any chunk, so a doomed job fails in seconds instead of hours:

  • Voice catalogue. _list_voices_with_retry fetches the voice list (cached for 15 minutes) with up to three attempts and 2 s / 4 s waits, and confirms the selected voice still exists. A single failed DNS lookup used to end the job here with raw aiohttp text.
  • Compatibility gate. As described above.
  • Startup synthesis. For texts of at least preflight_threshold characters (4,000 for Latin script, lower for complex scripts), a sample of about 220 characters is synthesised with a 45-second limit, up to twice. If it returns no audio, the voice list is refreshed to tell “voice removed” apart from “voice cannot read this text”.
  • Disk space. _check_free_space estimates the output at 350 bytes per character, doubles it because chunks are staged before being concatenated, adds 15 %, and refuses the job if either the staging or the output volume has less free space. A 700,000-character book needs about 564 MB.

6.8 The request lifecycle

Each attempt at a chunk calls _synthesise_attempt (tts_worker.py:2333-2454), which builds a fresh edge_tts.Communicate through build_communicate. Reusing one after a failure could carry “half-dead websocket/session state” into the next attempt.

Inside edge-tts 7.2.8, one request looks like this:

  1. Open a WebSocket to wss://speech.platform.bing.com/consumer/speech/synthesize/readaloud/edge/v1 with a connection id and a time-based Sec-MS-GEC token computed by the library. TLS uses SetupTTS’s context; the proxy is SetupTTS’s system_proxy().
  2. Send a speech.config message asking for audio-24khz-48kbitrate-mono-mp3 with sentence-boundary metadata enabled.
  3. Send the text wrapped in SSML with the voice, rate and volume.
  4. Receive messages: text frames for turn.start, response, audio.metadata (one per sentence: offset, duration, text) and finally turn.end; binary frames carrying MP3 audio.
  5. On turn.end, stop. If no audio arrived at all, raise NoAudioReceived.

SetupTTS consumes that stream with its own watchdog:

async def _consume_stream() -> None:
    stream = communicate.stream().__aiter__()
    deadline = stats.started_at + timeout_s
    while True:
        if self._cancelled:
            raise asyncio.CancelledError()
        now = time.monotonic()
        if now >= deadline:
            raise asyncio.TimeoutError()
        if stats.audio_bytes == 0:
            wait_timeout = min(deadline - now, first_audio_wait)
        else:
            wait_timeout = min(deadline - now, idle_wait)
        try:
            event = await asyncio.wait_for(stream.__anext__(),
                                           timeout=max(wait_timeout, 1.0))
        except StopAsyncIteration:
            break
        # audio -> append to an in-memory buffer
        # SentenceBoundary -> record (offset, duration, text), update progress

Audio goes into an io.BytesIO buffer for this attempt only. Nothing is written to disk until the whole attempt has succeeded and passed the completeness check, so “failed retries never poison the final MP3” (module docstring).

6.9 Timeouts

A streaming request can fail in different ways at different moments, so there are layered timeouts rather than one.

Timeout Formula (tts_worker.py:2464-2485, tts_service.py:84) Catches
Connect 20 s service unreachable
First audio base + payload/220, clamped to 18-40 s service accepted the request but is not producing audio
Idle between events 12 + payload/260, clamped to 12-40 s stream stalled mid-way
edge-tts socket read deadline minus 15 s, clamped to 60-180 s same, at the aiohttp level
Whole attempt 30 + expected_audio / 0.45, clamped to 90-600 s everything else

The whole-attempt deadline is the interesting one. Expected audio is len(text) / (15.8 x rate multiplier) seconds, where 15.8 characters per second was measured at normal speed, and 0.45 is the slowest observed streaming speed relative to real time. So the deadline is generous enough for the slowest voice to stream the whole chunk, at the speed the user chose: slower speech means more audio for the same text.

Verified by runtime experiment. Calling the real _chunk_timeout_for gives 198 s for a 1,200-character chunk and 536 s for 3,600 characters at normal speed; at -50 % speed the 1,200-character deadline becomes 367 s. The idle timeout for a 3,600-byte chunk is 25 s and the first-audio timeout 40 s.

This formula replaced a fixed floor of 65 seconds. The comment at tts_worker.py:110-115 records the evidence: Andrew and the multilingual voices “often stream at ~1.5x real time and dip below 0.5x”, and in one user’s log “22 of 29 such failures … hit exactly 65 s”. The old deadline was killing healthy streams. Real stalls are caught by the idle timeout, which is short.

6.10 Retries and back-off

_process_chunk (tts_worker.py:1991-2269) allows up to 5 attempts per chunk. Before attempt n (for n = 2 to 5) it waits 2 x 2^(n-2) seconds: 2, 4, 8 and 16 s. After a failure where audio had started and then stalled (timeout_after_audio), the next deadline is multiplied by 1.5 per attempt, up to the 600-second cap, because “the same limit just failed on this text”.

Two failure kinds stop early and go straight to splitting after 2 attempts instead of 5: no audio (no_audio, metadata_without_audio) and timeouts before any audio (timeout_waiting_for_audio). Hammering the same doomed request five times wastes about 30 seconds of back-off and rarely helps; a smaller request often does.

The back-off has no random jitter. With at most two concurrent jobs per machine, the classic reason for jitter (thousands of clients retrying in lockstep) does not really apply (Inference).

6.11 Failure classification

Every exception from an attempt passes through _classify_attempt_failure (tts_worker.py:2718-2817), which turns it into an _AttemptFailure with a kind. The kind decides the retry policy, the health tracking and the final user message.

Kind Raised when Typical cause
timeout_waiting_for_audio timeout, no audio and no metadata yet service slow or overloaded
metadata_without_audio sentence metadata arrived but no audio provider-side failure for this text or voice
timeout_after_audio timeout after some audio, or a stream that ended early connection dropped mid-stream
no_audio edge-tts raised NoAudioReceived voice cannot read this text, or provider hiccup
dns ClientConnectorDNSError or “getaddrinfo failed” offline, DNS broken
invalid_voice ValueError mentioning voice voice removed from catalogue
network aiohttp connection errors, WebSocket errors, “503”, “ssl”, “invalid response status” network or service outage, TLS interception
service_response edge-tts UnexpectedResponse / UnknownResponse protocol change
unexpected anything else bug

HTTP-level problems surface in this table indirectly. A 503 or 429 during the WebSocket handshake arrives as an aiohttp error whose text contains the status, and is classified as network. A 403 is handled inside edge-tts itself: stream() catches ClientResponseError with status 403, adjusts its clock-skew correction for the token, and retries once.

6.12 Audio validation

When an attempt ends without an exception, SetupTTS still does not trust it. Two questions are asked:

  1. Did any audio arrive? If not, the attempt fails as no_audio or metadata_without_audio.
  2. Is the audio complete? _stream_incomplete_reason compares the received audio and the announced sentences with the chunk’s text. If either check fails, the attempt is discarded and treated as timeout_after_audio, which is retried like any mid-stream stall.

The second check is the most important reliability mechanism in the project, and the reason is historical. Chapter 8 tells that story.

9 Manifest and Coverage System

9.1 The staging folder

Every job gets a folder staging/<job_id>/ inside the app’s data folder (Chapter 13):

staging/4f1c9e.../
|-- source.txt           the cleaned text, exactly as chunked
|-- manifest.json        job metadata and one record per saved chunk
|-- chunk_000000.mp3
|-- chunk_000001.mp3
`-- ...

source.txt is the reference against which everything is checked. Storing the cleaned text, instead of the user’s original, is what makes the ranges meaningful: a range [4671, 7882) refers to characters of source.txt.

9.2 The manifest

ChunkStore._save_manifest (chunk_store.py:810-838) writes this structure (schema version 2):

{
  "schema_version": 2,
  "job_id": "4f1c9e...",
  "voice": "en-US-AndrewNeural",
  "rate": "+0%",
  "volume": "+0%",
  "output_path": "/Users/you/Desktop/book.mp3",
  "text_hash": "<sha256 of source.txt, first 16 hex chars>",
  "total_chars": 701783,
  "chars_consumed": 268114,
  "chunks": [
    { "index": 0, "start_char": 0, "end_char": 1141,
      "text_hash": "<sha256[:16] of source[0:1141]>",
      "file": "chunk_000000.mp3", "audio_bytes": 433152,
      "retries": 0, "used_recovery": false, "sub_ranges": [[0, 1141]],
      "completed_at": 1759650000.0 }
  ],
  "chunks_completed": [0],
  "status": "running",
  "failed_at_chunk": null,
  "failed_at_chunk_total": null,
  "expected_duration_min_s": 31899.2,
  "expected_duration_max_s": 58481.9,
  "measured_duration_s": null,
  "created_at": 1759649000.0,
  "updated_at": 1759650000.0
}

The field names and structure are real; the values are illustrative. Note sub_ranges: even a chunk that succeeded first time records its own range as a single sub-range, because _process_chunk reports the ranges “that actually produced audio”.

9.3 The invariants

The manifest is only useful because a few rules always hold, and are checked rather than assumed:

Invariant Enforced in
0 <= start_char < end_char <= total_chars record_chunk refuses to save otherwise
sub-ranges start at start_char, touch end to end, stop at end_char record_chunk, coverage_report, _validate_chunk_records
a chunk’s file exists and is exactly audio_bytes long coverage_report, resume validation, finalize
a chunk’s text_hash equals the hash of source[start:end] coverage_report, resume validation
source.txt has total_chars characters and the job’s text_hash coverage_report (both); try_resume (hash)
chars_consumed never exceeds the end of the trusted prefix update_chars_consumed

Hashes are SHA-256 truncated to 16 hex characters (64 bits). They are not a security measure; they detect accidental mismatch, such as a resume against a different text.

9.4 Coverage: what happens when chunk 2 fails

Coverage is a question about intervals: do the recorded ranges tile [0, total_chars) exactly, with no gaps and no overlaps? Figure 9.1 shows the normal case and the recovery case together.

Suppose chunk 2, covering [4671, 7882), keeps failing:

  1. Retries. Up to five attempts (two for no-audio), with back-off. Nothing is written.
  2. Split. The range is subdivided at sentence or clause boundaries into, say, [4671, 5760), [5760, 6830), [6830, 7882). Each runs the full attempt machine.
  3. If all three succeed, their audio is concatenated and saved as chunk_000002.mp3, with used_recovery: true and those three sub_ranges. The range of record is still [4671, 7882). Coverage is unaffected; chunk 3 starts at 7882 as before.
  4. If a sub-range still fails and cannot be split further, _ChunkError is raised. Chunks 0 and 1 stay on disk, the manifest becomes failed with failed_at_chunk: 3 (one-based, as displayed), and Resume is offered.
  5. On resume, chunks 0 and 1 validate, the cursor restarts at 4671, and chunk 2 is attempted again from scratch, often successfully a few minutes later.

The old bug would have saved chunk 2 with only the audio of the two sub-ranges that worked. Its recorded range would still say [4671, 7882), so coverage would have looked complete while about a thousand characters were never spoken. Recording sub_ranges and requiring every sub-range to have produced audio is what makes that impossible now. test_irrecoverable_subchunk_fails_closed_instead_of_skipping is the regression test.

9.5 The coverage report

ChunkStore.coverage_report (chunk_store.py:544-643) sorts records by start position and walks them, collecting:

  • gaps and overlaps between consecutive ranges, plus a trailing gap if the last range stops short;
  • missing_files (absent or empty) and invalid_files (size differs from audio_bytes);
  • invalid_ranges (out of bounds, empty, or bad sub-ranges);
  • duplicate_indexes and text_hash_mismatches;
  • source_errors if source.txt is missing, the wrong length, or the wrong hash.

is_complete (chunk_store.py:105-119) is true only if every list is empty, covered_chars == total_chars, every recorded chunk has audio, and at least one chunk exists. The worker checks it right after the last chunk; finalize checks it again before writing a byte.

9.6 Resume validation

Resume uses a stricter rule than coverage, because it must decide what to trust after a crash. _validate_chunk_records (chunk_store.py:914-1003) walks records in index order and stops at the first one that has the wrong index, does not start where the previous one ended, has an empty or out-of-bounds range, bad sub-ranges, a missing or wrong-sized file, or a text hash that does not match. Everything from that point on is dropped, even records that look fine.

Throwing away apparently good chunks costs a few minutes of regeneration. In return the resume position is a single, simple number, _trusted_cursor_from_records, and there is never a question of what lies between two trusted islands.

9.7 Manifest status

The running → interrupted relabelling has a subtlety. The resume listing runs on the UI thread every time a job starts, finishes or fails, and it “repairs” manifests still marked running. For a job that is running in this process, that used to flip its manifest to interrupted underneath the worker and offer it for resume while it was being generated. The fix is a process-wide set of live staging folders, _LIVE_DIRS, guarded by a lock (chunk_store.py:189-210). create and try_resume add a folder; terminal states and release() remove it; the listing skips live folders.

9.8 Atomic writes

Every manifest and chunk write goes through _atomic_write_bytes (chunk_store.py:1055-1076):

tmp = path.with_name(f"{path.name}.{uuid.uuid4().hex[:8]}.tmp")
with open(tmp, "wb") as fh:
    fh.write(payload)
    fh.flush()
    os.fsync(fh.fileno())
_replace_with_retry(tmp, path)

Each line prevents a specific failure:

  • Write to a temporary file, then rename. os.replace is atomic on the same filesystem: a reader sees either the old file or the new one, never half of one.
  • A unique temporary name per call. The UI thread (listing resume candidates) and a worker can both rewrite the same manifest. A shared .tmp name let one writer rename the other’s half-written file.
  • fsync before the rename. Without it, a power cut can leave a file of the right size containing zeros, which resume validation (size-based) would accept as a real chunk.
  • Rename with retries on Windows. Antivirus scanners, search indexers and sync clients open new files for a moment; a rename in that window fails with a sharing violation. Up to five tries with growing short sleeps turn that into a non-event.

9.9 Legacy manifests and cleanup

Manifests from before the coverage system (schema version 1) have a list of completed indexes but no ranges. _load_manifest discards their progress rather than “silently trusting unverifiable history” (chunk_store.py:896-911).

Old staging folders are swept by cleanup_stale_staging at the start of each job: folders that cannot be resumed go after 7 days, resumable ones after 60 days, and the folder being resumed is never touched. Before v1.6.0 the limit was a week for everything, which “silently discards generated audio the user can still see and expects to continue”.

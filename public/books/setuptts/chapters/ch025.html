18 How to Debug SetupTTS

18.1 Where the evidence is

The fastest route through most problems:

  1. Read the dialog, then Show Details… for the raw cause.
  2. Open Settings ▸ Logs & Troubleshooting ▸ Open Current Log, or the log folder from the Help menu.
  3. Search the log for the job’s Job summary line, then for failed on attempt lines with their kind=.
  4. If the problem is about saved progress, open staging/<job>/manifest.json.
  5. For a crash with nothing in the log, read crash.log.

Useful commands on macOS:

# follow the log while reproducing a problem
tail -f ~/Library/Logs/SetupTTS/setuptts.log

# the one-line outcome of every job
grep "Job summary" ~/Library/Logs/SetupTTS/setuptts.log

# what each unfinished job has saved
ls ~/Library/"Application Support"/SetupTTS/staging/
python3 -m json.tool ~/Library/"Application Support"/SetupTTS/staging/<job>/manifest.json

# run the packaged app's own end-to-end check (works while the app is open)
/Applications/SetupTTS.app/Contents/MacOS/SetupTTS --selftest ~/Desktop/selftest.json --network

On Windows the log is %LOCALAPPDATA%\SetupTTSApp\SetupTTS\Logs\setuptts.log, and the same --selftest flag works on SetupTTS.exe; it writes a JSON file instead of printing because the app has no console.

18.2 By symptom

18.2.1 The voice list does not load

  1. Is it offline mode? A note beginning “Offline” that says your saved voice list is shown means the live fetch failed three times and voices.json from the cache was used. The picker works; generation needs the connection.
  2. Read the cause in the log (Voice loading failed (attempt n/3)). A name-resolution error means DNS or no connection. SSL or CERTIFICATE means TLS: check the computer’s date and time, and on Windows check antivirus HTTPS scanning. Builds before v1.6.1 ignored the Windows certificate store and failed behind such scanners.
  3. Proxies. Environment variables (HTTPS_PROXY) take precedence. Otherwise the system proxy is used only if it is an http:// proxy; SOCKS proxies are not passed to aiohttp.
  4. Run --selftest --network. Its tls and voices entries say exactly which layer failed.
  5. If everything else works, the service may have changed its protocol. Look for UnexpectedResponse or UnknownResponse from edge-tts; the fix is usually a newer edge-tts pin.

18.2.2 Generation is slow

  1. Read the Job summary. retried_chunks, failures[...], and the first_audio and receive distributions show whether time went into retries, waiting for first audio, or streaming.
  2. Which voice? Andrew and the multilingual voices stream much slower than others; that is the service, not the app. A same-language standard voice is often faster.
  3. Is the chunk size shrinking? Stage lines reading “Reducing upcoming chunk size” or “using safer smaller chunks” mean failures pushed the job into conservative mode, which means more requests.
  4. Is a second job running? Two jobs share the connection and the service.
  5. Network stability, not bandwidth. Frequent network or timeout_after_audio failures point to an unstable connection. A faster plan will not help; a wired connection or a different network might.

18.2.3 “No audio received”

  1. During the startup check? The message says the voice “may not be compatible with this text”. Check that the voice’s language and script match the text; accept the recommended voice if one is offered.
  2. Has the voice been removed? The worker refreshes the voice list to distinguish this; the message then says the voice “is no longer available”.
  3. Mid-job on one chunk? SetupTTS already retried and split the chunk. Look at that chunk’s text (its range is in the log) for something unusual: a line of symbols, a very long token, mixed scripts.
  4. Multilingual voice on a long English job? The message suggests a standard voice; use it.
  5. Otherwise the service may be having a bad period. Resume later; finished chunks are kept.

18.2.4 The final audio is shorter than expected

  1. Is there a name (incomplete).mp3? Then the duration check refused the result. The log line Duration sanity check failed ... measured=... expected_min=... gives both numbers.
  2. Check the speed setting. +100 % halves the audio length; the expected range accounts for it, but your own expectation might not.
  3. Check what cleanup removed. Decorative lines, bullets, symbols and bracketed labels are rewritten or dropped (Chapter 6). Compare the job’s source.txt with your original if the difference matters.
  4. Check the coverage line. File written: ... coverage=chunks=214 covered=701783/701783 proves every character had audio.
  5. Old builds. v1.5.4 could silently drop failed fragments, and every version before 1.6.0 could accept a chunk cut short by a dropped connection. Re-generate with a current build.

18.2.5 A job fails at the very end, or Resume always fails the same way

  1. “Part of the text has no audio yet”. The coverage check found a gap. Click Resume; it regenerates from the first unverified chunk.
  2. The same failure on every resume was the whitespace-gap bug fixed in v1.6.0. On a current build, inspect manifest.json: consecutive end_char and start_char values must be equal.
  3. “could not save the finished MP3” means the output folder is unwritable, full, or the file is open in a player. Fix that and Resume; the audio is kept.

18.2.6 Resume is missing or starts from the beginning

  1. The text or voice changed. Resume requires the same text hash and voice. The log says Source text changed or Voice changed.
  2. The folder was swept. Resumable progress is kept for 60 days.
  3. The saved data failed validation. Could not resume from ... starting fresh is logged, and the old folder is left untouched. Dropping un-resumable chunk record lines show where trust ended.

18.2.7 The Windows build fails

  1. Which step? CI names it. A failing Run tests on Windows only is usually layout under Windows font metrics; the August 2026 v1.5.8 runs failed exactly this way.
  2. ModuleNotFoundError in the self-test means PyInstaller missed a module: add it to hiddenimports or use collect_all in both spec files.
  3. Failed to load Python DLL means a onedir build was run without its _internal folder, usually from inside a zip. The portable download must come from setuptts_portable.spec.
  4. Installer step fails if Inno Setup is not at C:\Program Files (x86)\Inno Setup 6\ISCC.exe or /DAppVersion is missing.
  5. Version mismatch errors mean the tag and APP_VERSION differ, or the installed EXE’s ProductVersion did not match.

18.2.8 macOS blocks the application

  1. First launch of an unsigned app. Open System Settings ▸ Privacy & Security and click Open Anyway. The app is not notarised, so this is expected.
  2. macOS older than 15, or an Intel Mac. The bundled Qt requires macOS 15 on Apple Silicon; the app will not start on anything older.
  3. A zip extracted with a third-party tool. The release zip is made with ditto; tools that drop symlinks or extended attributes can break the bundle. Use the DMG or Finder’s built-in unzip.
  4. “Damaged” warnings on downloaded unsigned apps are usually Gatekeeper’s quarantine attribute. Removing it with xattr -dr com.apple.quarantine /Applications/SetupTTS.app is a general macOS technique, not something the project documents; prefer Open Anyway.

18.2.9 The app will not start, or opens and closes

  1. Another copy is running. A second launch brings the first window forward and exits. Check the Dock or taskbar.
  2. Read crash.log for native faults and the end of setuptts.log for uncaught exceptions with a session id.
  3. Settings problems reset per key with a warning; a file that is not JSON becomes settings.json.corrupt.

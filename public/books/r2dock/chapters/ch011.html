6 The Transfer Scheduler

When a user drops a folder of four thousand photos into R2Dock and then one urgent document, some code must decide which file moves next, how many move at once, how many requests each may open, and how the window learns about it without being flooded. That code is the transfer scheduler in crates/r2dock-transfer/src/engine/mod.rs. Chapter 7 (Backpressure and Resource Management) follows the same machinery from the angle of memory, disk, and compression, Chapter 13 (Transfer State Machines) owns the job states, and Chapter 5 (Tokio and Asynchronous Execution) defines the Tokio vocabulary used here.

Why a Transfer Engine Needs a Scheduler

The simplest design would start one task per file the moment it is added. Tokio tasks are cheap, but each upload holds an open file and an HTTPS connection to Cloudflare R2. Four thousand at once would exceed the open file limit on many systems, split one uplink so every file finishes late, and provoke HTTP 429 (Too Many Requests) or 503 (Service Unavailable) responses whose retries add load exactly when the service asked for less.

So the engine needs a limit on jobs running at once, a policy for which waiting job runs next, and a limit on requests in flight overall, because one large file is split into parallel requests (Chapter 9, Multipart Uploads in Depth). R2Dock implements the first two with a queue and a counting loop under a mutex, and the third with a Tokio semaphore.

The Data the Scheduler Works On

EngineConfig::new sets the defaults: concurrency 3 (jobs active at once), parts_per_job 4 (parts of one multipart upload in flight), global_parts 8 (part requests in flight across all jobs), a multipart_threshold of 100 MiB, and a progress_interval of 250 milliseconds. The desktop app, in src-tauri/src/lib.rs, overrides only concurrency, multipart_threshold, and home from the user’s settings. The setting Preferences::concurrency in crates/r2dock-core/src/settings.rs defaults to 3 and is clamped to 1 to 8 by Preferences::sanitized, and the engine clamps again in Engine::start and set_concurrency.

Everything else lives in one structure, Inner, shared through an Arc by the Engine handle, the background tasks, and every running job:

Source: crates/r2dock-transfer/src/engine/mod.rs, lines 114 to 131

#[derive(Default)]
struct Jobs {
    order: Vec<JobId>,
    map: HashMap<JobId, Entry>,
    queue: VecDeque<JobId>,
}

struct Inner {
    jobs: Mutex<Jobs>,
    wake: Notify,
    progress_wake: Notify,
    sink: RwLock<Option<EventSink>>,
    delivery: Mutex<()>,
    provider: Arc<dyn ClientProvider>,
    part_slots: Arc<Semaphore>,
    concurrency: AtomicUsize,
    threshold: Mutex<u64>,
    slow_until: Mutex<Option<Instant>>,
    // ...

map is the authoritative record: one Entry per job with its spec, snapshot (including state), byte counter, run control for pause and cancel, and a sequence number seq that preserves insertion order across restarts. order is the display order. queue is a VecDeque of only the waiting jobs, so a pass never walks finished work and a job can be placed at either end.

All three sit behind one synchronous parking_lot::Mutex. Every critical section is short and performs no input or output, so a synchronous lock is cheaper and cannot be held across an .await by accident. concurrency is atomic so settings can change it without the jobs lock, and part_slots is the engine’s only semaphore.

The Scheduler Loop

Engine::start loads the journals (Chapter 14, Journals and Persistent Queues), restores saved jobs, and spawns two long-lived tasks, scheduler and progress_ticker. Restored jobs enter map in the Interrupted state and never the run queue; the comment on restore says “Nothing restarts on its own.” The scheduler task (lines 1009 to 1028) is a loop that runs one pass, then awaits wake.notified(). There is no polling. The only timed wake is a select! against a sleep until slow_until, because when an overload slowdown ends the limit rises and waiting jobs could start with no other event. Everything that can free a slot or add work calls notify_one: enqueue, resume and retry, the end of every run_job and compression run, and settings changes. The Tokio documentation for Notify states that with no waiter “a permit is stored in this Notify value”, and that “Many sequential calls to notify_one will result in a single permit being stored.” A burst of a thousand finishing jobs causes at most one extra pass, and since each pass examines the whole queue, no wake-up is lost.

Work arrives through Engine::enqueue, called from src-tauri/src/commands/transfers.rs. Each JobSpec is one upload or download, a folder becomes many specs sharing a GroupInfo, and each new job enters queue at the back in the Queued state. The jobs are saved to the persistent queue file while the jobs lock is still held, so a job that finishes instantly cannot remove its record before the record was written (the test a_job_finished_while_it_is_saved_is_not_kept in engine/tests.rs forces that race). The window is told in Added events of at most 500 jobs, so a folder of 50,000 files does not become one giant Inter-Process Communication (IPC) message. enqueue starts nothing; it wakes the scheduler.

One Scheduling Pass

Inner::schedule first lets the compression stage start encodes (Chapter 7), computes the limit, and takes the jobs lock (lines 598 to 625). It first drops queued identifiers whose job is no longer Queued. A “slot” is not an object anyone holds; it is a count of jobs whose state is active, which JobState::is_active in crates/r2dock-transfer/src/model.rs defines as Preparing, Running, Retrying, or Verifying. A job in a retry backoff keeps its slot. A Compressing job does not hold one, which is the key idea of Chapter 7. While counting, the pass builds per_group, the number of active jobs per group (ungrouped jobs share the None entry), and busy, the set of (connection, bucket, key) triples currently being uploaded. The pick loop follows:

Source: crates/r2dock-transfer/src/engine/mod.rs, lines 626 to 656

while active < limit {
    // Look at the first jobs that can upload now; prefer the
    // group with the fewest running jobs. Jobs waiting for the
    // encoder are passed over without counting, so a long line
    // of them never keeps idle upload slots from other files.
    let pick = queue
        .iter()
        .enumerate()
        .filter(|(_, id)| {
            map.get(id).is_some_and(|e| {
                let compressing = matches!(
                    &e.spec,
                    JobSpec::Upload(u) if u.needs_compression()
                );
                !compressing
                    && (e.snap.direction == Direction::Download
                        || !busy.contains(&(
                            e.snap.connection_id,
                            e.snap.bucket.clone(),
                            e.spec.key().to_string(),
                        )))
            })
        })
        .take(256)
        .min_by_key(|(i, id)| {
            let g = map
                .get(id)
                .and_then(|e| e.snap.group.as_ref().map(|g| g.id));
            (per_group.get(&g).copied().unwrap_or(0), *i)
        })
        .map(|(i, id)| (i, *id));
    let Some((index, id)) = pick else { break };
    queue.remove(index);

While fewer jobs are active than the limit, the loop walks the queue from the front: it skips uploads that still need compression or whose key is being written, considers at most the first 256 jobs that pass, and chooses the one whose group has the fewest active jobs, breaking ties by queue position.

Queue order and fairness

Without groups every job has the same group count, so the tie-break makes the pass first in, first out (FIFO). Resumed and retried jobs return to the back (push_back in Inner::control and set_state). The one exception is requeue_front in engine/compress.rs, which returns a job that just finished compressing to the front, “keeping its turn”. The test bulk_controls_keep_per_job_behavior in tests/bulk_controls.rs checks that after pausing and resuming 1,000 queued downloads, “The first three (by original order) are started again.”

With groups, the rule gives cheap fairness. If a 4,000 file folder holds all three slots and the user drops one ungrouped file, the next free slot goes to the new file (group count 0 against 3), provided it is within the 256-job window. Two folders alternate the same way. PLAN.md section 12.3 calls this “round-robin between group jobs”; the code is close but not identical. It is “fewest active first” within a window, so a file behind more than 256 eligible jobs is not seen until the window shrinks, and all ungrouped jobs share one bucket, so two separately dropped files compete as one group. Both are trade-offs for a pass that stays cheap on very long queues.

The filter runs before take(256), and that order is a 0.5.0 fix recorded in docs/benchmarks/2026-10-18-compression-at-scale.md. Previously, with 300 audiobooks waiting to compress at the front of the queue, the window held only unpickable jobs, and 50 small text files behind them “did not start within 30 s”; after the change they “finished in 0.11 s”. The test a_long_encode_does_not_hold_back_other_uploads in tests/compress_scale.rs reproduces this with a fake FFmpeg that sleeps for ten minutes.

Writes to the same key

The busy set prevents two uploads to the same key on the same connection and bucket from running at once. Without it, under a “Keep both” conflict policy, two jobs could both decide the name was free. A newly picked upload is added to busy immediately (lines 662 to 668), so a second upload to that key later in the same pass is also held back. Downloads are not entered into busy; local destination conflicts belong to the download path and the path guard (Chapter 10, Downloads and HTTP Range Requests, and Chapter 23, Filesystem Security).

Launching a Job

For the chosen job, still under the lock, the pass sets the state to JobState::Preparing, clears the error, installs a fresh RunControl, inserts the key into busy if it is an upload, and increments active and the group count. After the lock is released, it emits an Updated event, wakes the progress ticker, and calls tokio::spawn(run_job(...)) (lines 657 to 682).

Because the state becomes Preparing inside the critical section, a pause arriving a microsecond later sees Preparing and reaches the job through its RunControl instead of racing the scheduler; Inner::control says “Check and change state under one lock so the scheduler cannot start a job between the check and the change.” Events and spawns happen outside the lock, a pattern used throughout the engine, so event delivery never blocks other engine operations.

At most limit run_job tasks exist, plus jobs that are finishing. run_job gets an R2 client from the ClientProvider, builds a JobCtx (crates/r2dock-transfer/src/ctx.rs), calls upload::run or download::run, records the outcome, and calls wake.notify_one() so the freed slot is refilled.

Adaptive slowdown after overload

The limit is effective_concurrency(), not always the configured value. When a job ends with an error code of RateLimited or ServerError, run_job sets slow_until to 60 seconds ahead (lines 1223 to 1225), and during that window the limit is half the configured concurrency, never below one. Running jobs are not stopped; the pass just does not refill above the reduced limit. This is PLAN.md section 13’s “concurrency reduced on 429/503” in its simplest form: one global window, extended by each new overload error, with no gradual ramp. The part semaphore is not resized during the window.

Semaphores, From the Problem to R2Dock’s Use

Job slots limit files, not requests: three jobs uploading four parts each mean twelve requests. The engine needs a limit across all jobs.

A counting semaphore is a counter of permits: acquire takes one, waiting if none is left, and release returns one and wakes a waiter. tokio::sync::Semaphore waits by suspending the task, not blocking a thread. Its documentation states that it “is fair, which means that permits are given out in the order they were requested”, that “Cancelling a call to acquire makes you lose your place in the queue”, and that dropping a permit releases it. acquire_owned on an Arc<Semaphore> returns an OwnedSemaphorePermit that holds its own reference to the semaphore, so it can live inside a stored future.

Inner::part_slots is created as Arc::new(Semaphore::new(config.global_parts.max(1))), so 8 permits by default and never fewer than one. Every job receives it through JobCtx::part_slots, and exactly one place acquires it, the multipart loop in crates/r2dock-transfer/src/upload.rs:

Source: crates/r2dock-transfer/src/upload.rs, lines 451 to 474

loop {
    // Queue parts up to the per-job limit. Each part waits for a global
    // slot inside its own future, so waiting never stops this job from
    // polling (and finishing) the parts it already started.
    while failure.is_none()
        && ctx.control.stop() == Stop::None
        && in_flight.len() < ctx.parts_per_job
    {
        let Some(part) = pending.next() else { break };
        let slots = ctx.part_slots.clone();
        let control = ctx.control.clone();
        let fut = upload_part(ctx, spec, &snapshot, source.clone(), part);
        in_flight.push(async move {
            let Ok(permit) = slots.acquire_owned().await else {
                return None;
            };
            if control.stop() != Stop::None {
                return None;
            }
            let r = fut.await;
            drop(permit);
            Some(r)
        });
    }

Each multipart job keeps a FuturesUnordered named in_flight of at most parts_per_job futures, which is the per-job limit. Each future acquires a global permit, rechecks for pause or cancel, runs upload_part, and drops the permit. The permit is acquired inside the future for a reason. If the job’s loop itself awaited a permit before pushing the next part, then while suspended it would not poll in_flight, so parts already holding permits could not finish and release them. With several jobs doing this, every permit could be held by a part whose owner is waiting for another permit: a hold-and-wait deadlock. Acquiring inside each future keeps the job polling all its parts. The regression test concurrent_multipart_jobs_do_not_deadlock in tests/engine.rs runs three 40 MiB multipart uploads, four parts per job, with only two global permits, and requires all three to complete with correct bytes.

Fairness means one job cannot starve another of permits. When in_flight is dropped on cancel, pause, or failure, every future and any permit it holds is dropped, so permits cannot leak. R2Dock never closes the semaphore, so the AcquireError branch (else { return None; }) is defensive; as far as the code shows, it cannot occur. Single-request uploads (below the 100 MiB threshold) and downloads (one ranged GET per job) take no permit. The total number of simultaneous R2 data requests is therefore active single uploads and downloads plus at most global_parts part requests, bounded in every configuration. Figure 6.1 shows the two layers.

Job slots are not a second semaphore because a semaphore serves waiters in arrival order, while the scheduler must choose by group, skip encoder waits and busy keys, and change its limit at runtime. A count derived from job states under the jobs lock does all of that and cannot drift. The cost is that each pass walks every job in map and the whole queue. The 0.5.0 benchmarks do not measure a scheduling pass separately, so this book does not claim a number for it.

Progress Without Flooding the Window

Counter in crates/r2dock-transfer/src/progress.rs holds two AtomicU64 values: committed for finished parts or ranges and in_flight for running requests. Upload bodies add each 64 KiB chunk to in_flight as it is handed to the HTTP client; settle removes those bytes when the request ends and commits the part on success, and a retried request first subtracts what its previous attempt counted, so nothing is double counted. Downloads call set_committed after each write. Relaxed atomics are cheap enough per chunk.

Reporting is progress_ticker. It sleeps on progress_wake while nothing is active. Once woken, it samples every active job each progress_interval (250 ms), updates bytes, speed, and estimated time remaining, and sends one TransferEvent::Progress holding a ProgressUpdate for each job whose bytes changed or whose speed is known. Speed comes from SpeedMeter, an exponentially weighted moving average over about five seconds (WINDOW_SECS), hidden for the first three seconds (ETA_WARMUP); the unit test speed_hidden_until_warm checks both. PLAN.md section 12.4 speaks of “at most every 250 ms per active job” and hiding the estimate “when variance is high”. The code sends one batched event per interval for all jobs, which is stricter, and has no variance check; it hides the estimate only during warm-up or at speeds of at most one byte per second.

State changes are not throttled: set_state emits TransferEvent::Updated immediately, because “Paused” or “Failed” must appear at once. A compressing job is not active, so the ticker skips it; the on_fraction closure in engine/compress.rs sends its Updated events at most every PROGRESS_EVERY (250 ms).

Every event goes through Inner::emit, which takes the delivery mutex before calling the sink. That gives all events one total order, so a stale Progress can never overtake the Updated that says “Completed”. Engine::subscribe holds the same lock while sending the initial Snapshot and installing the sink. In the app, the sink from transfer_subscribe in src-tauri/src/commands/transfers.rs records activity rows and forwards each event over a Tauri Channel<TransferEvent>; because it runs under the delivery lock, it must never block. Chapter 26 (React and Tauri IPC) and Chapter 28 (UI Performance and Large Queues) follow the events into the frontend.

What the Tests and Benchmarks Show

many_small_files_respect_concurrency in tests/engine.rs uploads 30 files at concurrency 2, sampling every 5 ms, and asserts no more than two jobs were ever active. cancel_queued_job_is_final checks that a job cancelled while queued never runs. For the stress test in tests/stress.rs, as recorded in docs/benchmarks/2026-10-17-stress.md (not re-run for this book), on an Apple silicon Mac, release build, against the in-process local S3 server, single runs: 404 files (96.9 MB) uploaded in 0.75 s and downloaded in 1.89 s, and 3,012 files (1,306.5 MB) uploaded in 3.21 s and downloaded in 15.28 s, all bytes matching. These say nothing about internet throughput or R2’s own limits.

Working on This Code

Job selection is Inner::schedule in crates/r2dock-transfer/src/engine/mod.rs; overload handling is effective_concurrency and the error branch of run_job; reporting is progress_ticker. Part concurrency lives in the multipart function of upload.rs. The user setting reaches the engine through Engine::set_concurrency from src-tauri/src/commands/settings.rs.

Run cargo test -p r2dock-transfer for tests/engine.rs, tests/bulk_controls.rs, and the unit tests in engine/tests.rs, and cargo test -p r2dock-transfer --release --test stress -- --include-ignored for the stress run. FFmpeg tests skip unless R2DOCK_TEST_FFMPEG points at a binary.

Keep every fan-out bounded and acquire part_slots only inside a part’s own future. Make racing state checks and changes under one acquisition of the jobs lock, never hold that lock across an .await, and never emit or touch the disk under it except for the ordered queue-file saves of Chapter 14. Keep the sink non-blocking, and keep compression waits out of the 256-job window. A common pitfall is adding a state that should hold a slot without adding it to JobState::is_active, which lets the scheduler oversubscribe.

29 Automated Testing Strategy

A desktop client for object storage fails in ways that are expensive to discover by hand. A crash in the middle of a multipart upload, a key that contains ../, a second client that replaces an object while a move is half done, an FFmpeg process that stops printing and never exits: none of these show up on the happy path. R2Dock answers with a layered test suite in which each layer is chosen for the kind of failure it can reproduce cheaply and deterministically. This chapter walks through the layers, the fault injection tools the project built for itself, and the results of running the default suites for this book.

The Layers

Fast unit tests prove one function; integration tests prove collaboration at higher cost; tests against real external systems prove the most but need credentials, network, and possibly private data. R2Dock follows that economic shape, with boundaries drawn around its own risks. Figure 29.1 maps each layer to real suites.

PLAN.md section 18 also lists an end to end layer with WebdriverIO and tauri-driver, axe-core accessibility scans, and a fault-injecting proxy such as Toxiproxy; none exists at the audited commit. The section ends with “No test results are claimed in this plan. None have been run.”, which is now out of date.

Rust Unit and Property Tests

Pure logic lives in crates that do not depend on Tauri precisely so it can be unit tested. The densest suites guard boundaries described elsewhere: the path guard in crates/r2dock-core/src/path_guard.rs (Chapter 23, Filesystem Security), part planning in parts.rs (Chapter 9, Multipart Uploads in Depth), log redaction in redact.rs, the journal in crates/r2dock-transfer/src/journal.rs (Chapter 14, Journals and Persistent Queues), compression planning and FFmpeg argument building in crates/r2dock-media, and the CSV activity log in src-tauri/src/activity/.

Property based tests check a rule against inputs the developer did not think of. The proptest documentation describes “Hypothesis-like property-based testing and shrinking”: random inputs come from a strategy, and a failure is shrunk toward a minimal case. Four files in r2dock-core use it: keys.rs, parts.rs, path_guard.rs, and redact.rs. The most important property is that no key maps to a local path that escapes the download folder.

Source: crates/r2dock-core/src/path_guard.rs, lines 464 to 476

        #[test]
        fn never_escapes_root(key in "(?s).{0,60}") {
            // ...
            {
                if let Ok(p) =
                    key_to_relative_path(&key, Platform::current())
                {
                    prop_assert!(p.is_relative());
                    for c in p.components() {
                        prop_assert!(
                            matches!(c, Component::Normal(_)),
                            "bad component in {:?}",
                            p
                        );
                    }
                }
            }
        }
    }

The strategy generates any string of up to 60 characters, including newlines, slashes, dots, and arbitrary Unicode. The function may refuse a key, but whenever it accepts one the result must be a relative path of normal components only: no root, no prefix, no .., no .. Sibling properties cover the lossy mapping and Unicode normalization collisions; plans_are_contiguous_and_within_limits in parts.rs checks part plans for sizes up to 64 GiB, and known_account_is_always_masked checks that an account identifier never survives redaction. Path rules depend on the host platform (a Windows reserved name such as CON is only exercised on Windows), which is one reason the suite runs on all three operating systems.

Mocks That Act at Request Boundaries

A move in R2 is a copy, a verification, and a delete (Chapter 11, Object Management and Consistency). The dangerous moments are between those requests, and a real server cannot be paused there. crates/r2dock-r2/tests/support/mock_s3.rs is a deliberately tiny S3 server whose module comment says “a hook runs after each request is applied and before the response is sent, so tests can change objects at exact request boundaries.”

Source: crates/r2dock-r2/tests/support/mock_s3.rs, lines 55 to 66

#[derive(Debug, Default)]
pub struct Model {
    pub objects: BTreeMap<String, Obj>,
    pub requests: Vec<Req>,
    /// Answer every DeleteObject with a server error.
    pub fail_deletes: bool,
    /// Apply every CopyObject but answer with a server error, as when the
    /// response is lost after the copy happened.
    pub lose_copy_responses: bool,
    next_version: u64,
    uploads: BTreeMap<String, (String, Vec<(String, String)>)>,
}

Every write gets a fresh ETag ("v1", "v2", and so on) and every request is recorded. lose_copy_responses models the worst network failure: the copy happened, but the client was told it did not. The mock honors R2’s conditional headers on CopyObject and, like R2, ignores the source condition on UploadPartCopy; a mock more forgiving than the real service would let bugs through.

The suite crates/r2dock-r2/tests/move_races.rs has 14 tests under one contract: “every case must keep the changed data.”

Source: crates/r2dock-r2/tests/move_races.rs, lines 80 to 96

/// T21 case 1: the source changes right after the copy. The new version
/// must not be deleted.
#[tokio::test]
async fn source_changed_after_copy_is_kept() {
    let hook: Hook = Arc::new(|r: &Req, m: &mut Model| {
        if r.is("PUT", "dst") && r.status == 200 {
            m.put("src", b"NEW!");
        }
    });
    let (s3, report) = run_move(with_source(), 4, false, hook).await;
    let m = s3.model.lock().unwrap();
    assert_eq!(m.body("src"), Some(&b"NEW!"[..]), "{:?}", m.sequence());
    assert_eq!(report.moved, 0);
    assert_eq!(report.copied_not_deleted.len(), 1, "{report:?}");
    assert!(!m.requests.iter().any(|r| r.is("DELETE", "src")));
}

Figure 29.2 shows the resulting sequence. Once the copy into dst succeeds, the hook writes new content to src, giving it a new ETag. The private function move_one in crates/r2dock-r2/src/bulk.rs checks the destination and then the source after the copy, sees the source ETag changed, and reports the item as copied but not deleted. The test asserts that the new data survives, the report is correct, and no DELETE for the source was sent.

Other cases cover a destination created after the existence check, a same-length replacement of the destination, a failed delete, a lost copy response, and multipart copies of objects faked as larger than 5 GiB. For the Cloudflare REST API, MockCloudflare in crates/r2dock-testkit/src/cloudflare.rs returns canned bodies or Reply::Hang, which never answers, so crates/r2dock-r2/src/cfapi/tests.rs can prove timeouts and token-free errors (Chapter 12).

The Local S3 Server and Network Shaping

Architecture decision record (ADR) 0005 records that tests must never touch production buckets and that crates/r2dock-testkit “starts an in-process S3-compatible server (s3s with s3s-fs) on a random local port backed by a temporary folder.” LocalS3::start creates a temporary directory with one folder per bucket, serves it with fixed test credentials on 127.0.0.1 port 0, and aborts the server when the value is dropped. object_path exposes an object’s data file so a test can corrupt stored bytes. The client, bulk operations, engine, and connection service are therefore tested with real Signature Version 4 signing, HTTP, multipart uploads, and ranged reads. It is only a development dependency. ADR 0005 states the cost: “R2-specific behaviour (conditional writes, error codes, checksum defaults, scoped token responses) is not proven by these tests.” Those items stay marked [Verify] in PLAN.md.

Loopback hides bugs that only appear when uploads are slow or aborts take seconds, so the test kit’s Network layer adds “a shared upload bandwidth limit and a delay before multipart aborts are answered.” Its before hook recognizes an AbortMultipartUpload (a DELETE with an uploadId query), counts it, and optionally sleeps, so a test can assert through Network::aborts that a cancel reached the server without making the user wait. When a limit is set, request bodies are wrapped in Throttled, an http_body::Body that reserves time for each frame on one shared clock behind a mutex, so concurrent requests share a single uplink of a chosen speed. The compression-at-scale benchmark notes that an earlier version of this limiter waited per request instead of reading at the limited rate (Chapter 30, Performance Benchmarking).

What the Integration Suites Prove

The transfer suites in crates/r2dock-transfer/tests/ build an R2Client against the local server, use an EngineConfig with small thresholds, and wait with helpers such as wait_state, which fails with the job’s last state after a timeout. engine.rs (14 tests) covers byte round trips, every conflict policy, cancel and pause of multipart uploads, the concurrency limit, and restarts on the same data directory. traversal_keys_never_escape_destination stores an object under ../evil.txt, asks the engine to download it into a subfolder, insists on JobState::Failed, and checks that nothing appeared in the parent; it proves the engine actually routes destinations through the path guard. wrong_credentials_fail_without_retry_storm asserts ErrorCode::SignatureMismatch with fewer attempts than retry::MAX_ATTEMPTS, and exactly one attempt only off Windows, because there the server can reset the connection while rejecting the body and the first failure surfaces as retryable.

recovery.rs (7 tests) supports Chapter 15 (Crash Consistency and Recovery). Instead of killing a process, it writes a journal by hand with Journal and JournalEntry and starts an engine on it, reproducing exact post-crash states: a partial without a finalization record, a record that proves completion (with the user’s file backdated, because Windows timestamps can tie), a record for a different file, and 5,000 paused downloads.

compress.rs (11 tests) runs compression before upload with real FFmpeg. In compress_scale.rs, copies_waiting_for_upload_stay_bounded limits the link to 600,000 bytes per second, watches the work folder, and asserts at most 4 copies on disk (“3 upload slots + 1 encoder”), the bound Chapter 7 (Backpressure and Resource Management) explains. a_long_encode_does_not_hold_back_other_uploads substitutes a script named ffmpeg that runs exec sleep 600, queues 300 files behind it and 50 that skip compression, requires the 50 to finish within 30 seconds, and then uses pgrep -P to wait until no FFmpeg child remains. Similarly, watchdog_stops_a_silent_process in crates/r2dock-media/tests/ffmpeg.rs runs /bin/sleep 10 as a stuck FFmpeg and expects RunError::Stalled, and preserve.rs proves that compression never drops audio, video, subtitle streams, or channels (Chapters 18 and 19).

Tests that skip silently

FFmpeg tests return early when no binary is found. Most fall back to ffmpeg on the PATH; the scale suite is stricter.

Source: crates/r2dock-transfer/tests/compress_scale.rs, lines 54 to 65

fn ffmpeg_bin() -> Option<PathBuf> {
    let bin = std::env::var_os("R2DOCK_TEST_FFMPEG").map(PathBuf::from)?;
    let ok = Command::new(&bin)
        .arg("-version")
        .output()
        .is_ok_and(|o| o.status.success());
    if !ok {
        eprintln!("R2DOCK_TEST_FFMPEG does not run; skipping");
        return None;
    }
    Some(bin)
}

Without the variable the test returns silently, and Rust’s harness, which has no “skipped” outcome, reports it as passed. A green compress_scale line therefore does not prove the behavior was exercised. CI sets R2DOCK_TEST_FFMPEG only on Windows, so the two portable default tests that need it (copies_waiting_for_upload_stay_bounded and cancel_all_mid_compress_and_mid_upload) exercise FFmpeg only there; the fourth, pause_on_a_slow_link_is_prompt_and_resume_completes, uses no FFmpeg. a_long_encode_does_not_hold_back_other_uploads is #[cfg(unix)], so the code shows no CI job where it runs with FFmpeg. That is a gap worth closing; the recorded scale results were produced by hand with the variable set.

Ignored, Heavy, and Live Tests

The Rust book describes #[ignore] for expensive tests, -- --ignored to run only them, and -- --include-ignored to run all. R2Dock’s 15 ignored tests carry reasons that serve as documentation. Heavy and timing runs include many_files_with_pause_and_resume_heavy, bulk_controls_timing, and realistic_long_audiobooks. installs_the_pinned_package_and_compresses in crates/r2dock-media/tests/live_tools.rs downloads the pinned FFmpeg package; CI runs it explicitly on every operating system. Manual checks need inputs that cannot be committed: the read-only crates/r2dock-r2/tests/live_r2.rs needs real R2 credentials, the real media tests need local files, and one r2dock-secrets test touches the real OS credential store. The principle is that cargo test --workspace must be safe anywhere: offline, credential-free, no private files, no writes outside temporary directories.

Frontend Tests

Vitest is configured in vite.config.ts with environment: "jsdom" and a setup file, src/test/setup.ts. The Vitest documentation describes jsdom as a browser-like environment. Because jsdom has no layout engine, the setup gives elements a fixed size “so virtualized lists render rows” and stubs browser methods. renderWithProviders in src/test/utils.tsx wraps components in a TanStack Query client with retries disabled.

The frontend never talks to Rust in tests, so the Inter-Process Communication (IPC) layer is mocked: nine files replace src/ipc/commands.ts (Chapter 26, React and Tauri IPC) with vi.mock, swapping commands for spies. The connection form test checks that a secret crosses IPC only on submit and is cleared from React state afterwards.

Cross-Platform Validation

Path rules, file identity, process control, TCP behavior, and credential stores differ by operating system, so the test job in .github/workflows/ci.yml runs the default suite on ubuntu-22.04, macos-latest, and windows-latest with fail-fast: false (Chapter 31, CI/CD and Desktop Releases). Each runner installs FFmpeg. On Windows the workflow exports the real ffmpeg.exe as R2DOCK_TEST_FFMPEG because, as its comment says, cancel and Job Object tests must “act on FFmpeg itself”, not on a Chocolatey shim that launches it as a child. The live_tools step downloads and verifies each platform’s pinned FFmpeg package in every run, so a changed or missing release asset fails CI.

No cloud account is needed to run any default test. Toolchain setup, the full local checklist, and running the app against the local-s3 test server are covered in Chapter 34 (Your First Contribution).

Results of Running the Default Suites for This Book

The default suites were run for this book at the audited commit on an Apple silicon Mac laptop with Rust 1.94.0 and FFmpeg 9.0.1 from a package manager on the PATH, with no credentials or network services and R2DOCK_TEST_FFMPEG unset for the first run.

cargo test --workspace exited with status 0: 463 tests passed, 0 failed, and 15 were ignored, across 32 test binaries. Wall-clock time was 113.7 seconds, 32.1 of them compilation. The table breaks the passing tests down by crate.

Crate Passed Ignored Largest suites
r2dock-core 91 0 path guard, keys, redaction
r2dock-secrets 3 1 credential store wrapper
r2dock-r2 53 1 unit 31, move_races 14, local_s3 8
r2dock-transfer 82 5 unit 44, engine 14, compress 11
r2dock-media 125 5 unit 89, ffmpeg 16, preserve 14
r2dock (src-tauri) 109 3 unit 107, activity_stress 2

Because three of the four default compress_scale.rs tests returned early in that run, the suite was run again for this book with R2DOCK_TEST_FFMPEG set: cargo test -p r2dock-transfer --test compress_scale -- --nocapture --test-threads=1. All four passed in 35.5 seconds of test time; Chapter 30 discusses their timings.

npm test (which runs vitest run) passed all 158 tests in 22 files in 2.67 seconds as reported by Vitest. Together that is 621 passing tests, consistent with the README’s “about 600 automated tests”. Linting, type checking, formatting, Clippy, and the ignored tests were not run for this book.

Working on This Code

Start with the test file nearest your change; add a table case for every bug and a proptest! property when a rule holds “for all inputs”. Move and copy changes belong in crates/r2dock-r2/tests/move_races.rs; add a flag to Model for a new failure rather than weakening the mock’s R2 rules. Engine and restart changes go in engine.rs or recovery.rs, writing journals by hand for crash states. Slow links use LocalS3::network with set_upload_bps and set_abort_delay.

Run one suite with cargo test -p r2dock-transfer --test recovery or cargo test -p r2dock-r2 --test move_races, and the frontend with npm test. For media and scale tests, set R2DOCK_TEST_FFMPEG to an absolute path and pass --nocapture to see skips.

Keep the default run offline and credential-free, use fictional names such as media-library, never commit media files or their names, and keep every test passing on all three platforms. A test that returns early must say so with eprintln!, and every #[ignore] needs a reason that says how to run it.

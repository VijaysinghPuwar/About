19 Video Compression Internals

Video is where compression pays off most and where it can go wrong in the most ways: a careless conversion can turn a phone recording sideways, wash out its colors, drop an audio language, lose subtitles, or produce a file some browsers cannot play. This chapter covers how R2Dock probes a video, detects and picks an encoder, sets its options, and decides which files to leave alone. Process handling belongs to Chapter 17 (How FFmpeg Integrates with Rust), and the skip and verification ideas reused here come from Chapter 18 (Audio Compression Internals). The code is in crates/r2dock-media/src/video/.

Video Concepts for Newcomers

A video is a sequence of frames with a resolution (1920 by 1080 is “1080p”) and a frame rate. Phones and screen recorders often use a variable frame rate; forcing a fixed rate duplicates or drops frames.

Codecs such as H.264 (Advanced Video Coding, AVC), HEVC (High Efficiency Video Coding), VP9, and AV1 store a few complete keyframes and describe the frames between them as changes. The span between keyframes is the group of pictures (GOP); a longer GOP saves bits but makes seeking coarser.

Encoders either target a bitrate or target a quality. x264 and SVT-AV1 call their quality knob the constant rate factor (CRF), where lower means higher quality. The FFmpeg codecs documentation gives the libsvtav1 CRF range as 0 to 63 and its preset as a “quality-speed tradeoff, in the range 0 to 13,” where “higher values are faster but lower quality.”

Bit depth is bits per color component; yuv420p is the widely playable 8 bit 4:2:0 pixel format and yuv420p10le its 10 bit form. The transfer function maps stored numbers to brightness: standard dynamic range (SDR) uses a gamma curve, while high dynamic range (HDR) uses PQ (smpte2084 in FFmpeg) or hybrid log gamma, HLG (arib-std-b67). HDR to 8 bit SDR needs tone mapping, or pictures look washed out. Phones also record the intended rotation as a “display matrix” that a converter must honor. R2Dock always writes MP4 with +faststart, which moves the index to the front so playback can start before the download completes.

Routing a File to the Video Path

pipeline::prepare in crates/r2dock-media/src/pipeline.rs is the entry point for audio and video. A file whose extension is in VIDEO_EXTENSIONS (defined in video/run.rs: mp4, mov, mkv, webm, and six others) is probed with ffprobe first, because the in-process Symphonia probe may see only the audio track of an MP4. An MP4 with no main video stream continues down the audio path.

video::probe::probe_video runs ffprobe -print_format json -show_format -show_streams with the usual -protocol_whitelist file and file: path rules, a 60 second timeout, and kill_on_drop; any failure returns None, meaning “not something we can compress”. parse uses #[serde(default)] so missing fields become empty or zero, and builds a StreamInfo per stream with codec, size, pixel format, color transfer, bitrate, channels, cover art flag, rotation (from display matrix side data, else the older rotate tag), frame rate, tag, and language. The unit test parses_a_phone_video checks an HEVC, 10 bit, HLG phone recording with a minus 90 degree rotation. VideoProbe::video_bitrate falls back to the container bitrate minus audio, because Matroska files often lack per stream bitrates.

Which Encoders Exist on This Computer

According to THIRD_PARTY_NOTICES.md and the plan, the pinned Windows and Linux builds include SVT-AV1, OpenH264, and the hardware H.264 encoders. The macOS build from tools/ffmpeg/build-macos.sh enables SVT-AV1 and VideoToolbox but not OpenH264, so a Mac has no software H.264 fallback.

H264Encoder::PRIORITY in video/plan.rs orders seven H.264 encoders: VideoToolbox, NVENC, Quick Sync, AMF, Media Foundation, VA-API, and the software libopenh264, last because, as the plan puts it, it has lower quality per bit. Being listed by ffmpeg -encoders does not mean an encoder works (an NVENC build runs on laptops without NVIDIA cards), so video::encoders::detect tests every listed candidate.

Source: crates/r2dock-media/src/video/encoders.rs, lines 26 to 51

/// Test the listed encoders (`listed` comes from `ffmpeg -encoders`).
pub async fn detect(ffmpeg: &Path, listed: &[String]) -> VideoEncoders {
    let has = |name: &str| listed.iter().any(|e| e == name);
    let mut found = VideoEncoders::default();
    if has("libsvtav1") {
        found.av1 = works(ffmpeg, VideoEncoder::SvtAv1).await;
    }
    for e in H264Encoder::PRIORITY {
        if !has(e.name()) {
            continue;
        }
        if works(ffmpeg, VideoEncoder::H264(e)).await {
            if e == H264Encoder::OpenH264 {
                found.openh264 = true;
            }
            if found.h264.is_none() {
                found.h264 = Some(e);
            }
            // Keep looking only for the software fallback.
            if found.openh264 || !has(H264Encoder::OpenH264.name()) {
                break;
            }
        }
    }
    found
}

VideoEncoders records the best working H.264 encoder, whether OpenH264 works (for the retry described later), and whether SVT-AV1 works. On Windows with an NVIDIA card, NVENC becomes h264, but the loop keeps testing until OpenH264 passes, so intermediate hardware tests cost time without changing the result. On a Mac, VideoToolbox passes and the loop stops.

Each test (works) encodes three frames of FFmpeg’s testsrc2 pattern through the lavfi input to the null muxer, using args::test_encode, which shares the real job’s encoder settings. A 20 second timeout with kill_on_drop bounds a hung driver. Detection runs once per FFmpeg in CompressionService::refresh (Chapter 17). Figure 19.1 shows detection and the per file choice.

Choosing the Encoder for a File

VideoSettings in crates/r2dock-core/src/compression.rs holds a codec (VideoCodec::Av1 by default, or H264, shown as “Most compatible”) and a size (Small720, Balanced1080 by default, Keep, or Off). plan_video turns these into one choice.

Source: crates/r2dock-media/src/video/plan.rs, lines 214 to 231

    // AV1 when chosen and available; otherwise H.264.
    let encoder = match (settings.codec, encoders.av1, encoders.h264) {
        (VideoCodec::Av1, true, _) => VideoEncoder::SvtAv1,
        (_, _, Some(h)) => VideoEncoder::H264(h),
        (VideoCodec::Av1, false, None) | (VideoCodec::H264, _, None) => {
            return Err(SkipReason::NoVideoEncoder);
        }
    };
    let source = video.codec.as_str();
    let already_efficient = match encoder {
        VideoEncoder::SvtAv1 => source == "av1",
        VideoEncoder::H264(_) => EFFICIENT.contains(&source),
    };
    if already_efficient {
        return Err(SkipReason::AlreadyEfficient {
            codec: video.codec.clone(),
        });
    }

A user who asked for AV1 on a machine where SVT-AV1 failed still gets H.264; the test encoder_choice_and_fallbacks covers each arm. “Already efficient” depends on the encoder: HEVC, AV1, VP9, or VVC (Versatile Video Coding) sources are skipped for H.264, which would usually grow them, while AV1 skips only AV1 sources, so an HEVC phone video can become AV1. The plan’s video section says an “HEVC or AV1 source” is uploaded unchanged; that predates AV1 as the default, and the code is narrower.

AV1 is the default because of docs/benchmarks/2026-10-17-video-encoders.md. On a 60 second slice of a 1080p30 H.264 web video, on an Apple silicon Mac with FFmpeg 9.0.1, scored with VMAF (Video Multimethod Assessment Fusion, a perceptual metric where 95 and above is described as indistinguishable for most viewers), SVT-AV1 at CRF 35 and preset 8 produced 29.6 percent of the source size at VMAF 96.7, while VideoToolbox H.264 at -q:v 60 produced 89.3 percent at VMAF 94.8. These are single runs on one source, as recorded in that file (not re-run for this book). The cost is compatibility: the comment in compression.rs says AV1 plays in current Chrome, Edge, Firefox, and Safari on recent Apple devices; older devices need “Most compatible”.

Skips: HDR, Tracks, Size, and Bitrate

Before the encoder is chosen, plan_video runs cheap checks.

Size and duration minimums (1 MB, 10 seconds) match audio. HDR is detected only from the transfer function name, because there is no tone mapping; hdr_and_off_are_left_alone expects SkipReason::Hdr for a file tagged smpte2084. So a file missing its HDR metadata is treated as SDR. And 10 bit SDR is not skipped: the plan says “HDR or 10-bit” is skipped by default, but the code keeps 10 bit for AV1 and converts to 8 bit yuv420p for H.264.

The stream rules keep every track or leave the file alone. Subtitles must be text based (TEXT_SUBTITLES, such as subrip or webvtt) so they can become MP4’s mov_text. Data tracks are allowed only if they are timecode (tmcd) or Apple camera metadata (mebx), which are dropped safely; GoPro telemetry (gpmd) or Matroska font attachments cause a skip. Tests in crates/r2dock-media/tests/preserve.rs exercise these with real files.

Resolution and the Bitrate Model

scaled_size scales the short side down to the size setting, so portrait and landscape are treated alike; it never enlarges and rounds to even numbers, since most encoders reject odd sizes with 4:2:0 color. expected_bps starts from a 1080p30 reference (reference_bps): 1.1 Mbps for SVT-AV1, 3.5 Mbps for hardware H.264, 4 Mbps for OpenH264. The comment calls these measured; the SVT-AV1 figure matches the 1.06 Mbps in the benchmark, but the code does not show where the H.264 figures came from. The model scales by picture area to the power 0.75 (four times the pixels needs about 2.8 times the bits) and by the square root of the frame rate over 30. These exponents are heuristics with no derivation in the repository, and the plan’s Progress table says “the sample test makes the final call.”

If the picture is not being scaled and the source video bitrate is at most 3 percent above the expected bitrate, the file is skipped as AlreadyCompressed. Otherwise the expected bitrate is capped at the source bitrate, audio and 1 percent container overhead are added, and a saving below the user’s minimum produces SavingTooSmall. The test h264_target_is_decided_by_the_sample_test shows that for “Most compatible” a typical web video is skipped at about 10 percent saving, while a 16 Mbps phone recording is planned.

Encoder Settings and Filters

video::args::encoder_args holds the encoder settings. SVT-AV1 runs at CRF 35, preset 8, -g 240 (a keyframe at least every 8 seconds at 30 frames per second). VideoToolbox uses -q:v 60 with the High profile. The test hardware_encoders pins the others: NVENC -rc vbr -cq 23 -b:v 0, Quick Sync -global_quality 23, AMF constant quantizers, Media Foundation -quality 60, VA-API -qp 23. Apart from VideoToolbox the repository has no quality measurements for these, so their equivalence is an assumption. OpenH264 “has no constant-quality mode”, so it gets a bitrate target (at least 300 kbps) with a 1.5 times maximum and a 3 times buffer.

video_filter builds the filter chain. Its scale expression sets the short side to the target and the other side to -2; reading -2 as “keep the aspect ratio, round to a multiple of 2” comes from the expression and the unit test av1_snapshot_parts, since this book could not fetch that section of the filters documentation. The pixel format is 10 bit for AV1 with a 10 bit SDR source, NV12 uploaded to the graphics processor (GPU) for VA-API (with the fixed device /dev/dri/renderD128), and yuv420p otherwise.

Streams and Rotation

Every audio track is kept (audio_plan): mono gets 96 kbps AAC, stereo 128 kbps, surround 64 kbps per channel up to 384 kbps. No -ac is passed, so channel counts survive, and an AAC track within 32 kbps above its target is copied to avoid a second lossy generation.

The arguments map streams by absolute input index (-map 0:N), so they encode only the main video stream (not cover art), then each planned audio track and text subtitle (converted with -c:s mov_text), and copy tags and chapters with -map_metadata 0 -map_chapters 0. The ffmpeg documentation describes -dn as disabling “data recording”, which drops timecode and Apple metadata, and says that with -fps_mode passthrough “each frame is passed with its timestamp from the demuxer to the muxer,” so variable frame rate timing survives. A .mov or .mkv input gets the .mp4 extension and therefore a new object key. Cover art inside a video is not mapped, a deliberate exception in the plan.

R2Dock passes no rotation option: FFmpeg applies the display matrix while decoding, so the scale filter sees the upright picture. The test phone_rotation_and_scaling accepts a portrait output or a landscape one with the rotation tag kept (short side exactly 720), so which form a given FFmpeg version produces is not pinned down.

Sample, Encode, Retry, Verify

video::run::prepare_video follows the audio sequence: files longer than 300 seconds get a 30 second sample encode from the middle (too little saving uploads the original with SampleSavedTooLittle), a free space check requires 1.2 times the estimate, and then the real encode runs. A hardware encoder can still fail mid-file, for example when a driver resets, so it gets one software retry.

Source: crates/r2dock-media/src/video/run.rs, lines 194 to 211

    // A hardware encoder that fails mid-file gets one retry in software.
    if let (Err(e), VideoEncoder::H264(h)) = (&size, encoder)
        && !e.is_cancelled()
        && h.is_hardware()

    {
        encoder = VideoEncoder::H264(H264Encoder::OpenH264);
        size = encode_once(

            &job,
            &output,
            &target,
            encoder,
            cancel,
            &mut on_fraction,
        )
        .await;

A cancellation never becomes a second encode, SVT-AV1 has no retry, and with the macOS tools (no OpenH264) the retry cannot happen. The test broken_hardware_encoder_falls_back_to_software checks for the preset h264-libopenh264.

encode_once deletes the output on any failure. On success, ffprobe must show the expected codec (av1 or h264) and a duration within 1 second or 0.5 percent, and crate::streams::check must find one video track, every planned audio track with its channel count and language in order, and the planned subtitles. A mismatch uploads the original as TracksNotKept, which is not a failure. The recorded preset is av1-crf35 or h264- plus the encoder name.

The benchmark file records one full run on a real 31 minute video: 936 MB to 285 MB (69.5 percent smaller) in 355 seconds, with VMAF 97.1 on the first 30 seconds (not re-run for this book). The scale benchmark cautions that software video encoders, which can use every core, were not measured at scale.

Working on This Code

Decisions live in video/plan.rs (skips, encoder choice, bitrate model, audio plans), with arguments in video/args.rs, detection in video/encoders.rs, parsing in video/probe.rs, the pipeline in video/run.rs, and stream inventory rules in crates/r2dock-media/src/streams.rs. A new hardware encoder needs an H264Encoder variant, a place in PRIORITY, arguments in encoder_args, and an extended hardware_encoders test; a new kept subtitle or data format needs a real file test in tests/preserve.rs.

cargo test -p r2dock-media runs the unit tests. With FFmpeg and ffprobe available (through R2DOCK_TEST_FFMPEG or PATH), cargo test -p r2dock-media --test video runs real encodes; tests skip with a printed reason when an encoder is missing, so a green run without OpenH264 has not tested the retry.

Never drop a track without returning “unchanged”, never convert HDR without tone mapping, never force a frame rate, and keep test_encode sharing encoder_args. Do not change a quality value without re-measuring; the benchmark file warns that seeking two files by time can compare frames one apart.

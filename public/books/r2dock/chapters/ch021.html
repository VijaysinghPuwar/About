14 Journals and Persistent Queues

A user who drops ten thousand files into R2Dock and closes the laptop lid expects the work to be there in the morning. This chapter explains how transfer state is written, synced, read back, and kept small. The state machine this data feeds belongs to Chapter 13 (Transfer State Machines), and Chapter 15 (Crash Consistency and Recovery) uses this foundation to walk through crash scenarios.

Work That Outlives the Process

Three kinds of information matter after a restart: the accepted work that has not finished; resumable progress (for a multipart upload, the multipart upload identifier, or upload ID, and the stored parts; for a download, the partial file and its object’s entity tag, or ETag), whose loss would restart a 20 GB upload from zero; and a history of what happened. Progress changes often but exists only for running jobs, the accepted list can be huge but changes rarely, and history only grows, so R2Dock uses a different strategy for each.

Three Files Under the Transfers Folder

Engine::start (lines 160 to 167 of engine/mod.rs) opens three files under a transfers folder in the application data directory. The resume journal, journal.json, is a “plain” Journal: one JSON file rewritten completely and atomically on every save. The queue, queue.json plus queue.log, is a “logged” Journal: a snapshot plus an append-only change log. History, history.jsonl, is a separate type. The module comment of journal.rs explains: the resume journal “changes often but stays small”, while the queue “can hold a very large number of jobs”. Each journal has a background writer with its own batch interval: JOURNAL_BATCH is 200 milliseconds and QUEUE_BATCH one second, because uploaded parts are more expensive to lose than the fact that a job exists.

The Record Format

Both journals store JournalEntry, serialized as JSON with serde and serde_json:

Source: crates/r2dock-transfer/src/journal.rs, lines 41 to 52

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct JournalEntry {
    pub id: JobId,
    pub spec: JobSpec,
    pub group: Option<GroupInfo>,
    pub resume: ResumeState,
    pub created_at: String,
    /// Order the job was added in (0 in older journals).
    #[serde(default)]
    pub seq: u64,
}

JobSpec is the full upload or download description, and #[serde(default)] on seq lets older journals without the field load with zero.

ResumeState in ctx.rs has three variants, None, Multipart, and Download, serialized as an internally tagged enum (#[serde(tag = "kind")]), as is JobSpec. Serde buffers internally tagged enums through an intermediate representation that cannot carry 128-bit integers or numeric map keys, and two code comments record the consequences: the modification time in a Fingerprint (source.rs) is a u64 of nanoseconds rather than a u128, and a multipart upload’s completed parts, a BTreeMap<i32, PartDone> in memory, are serialized as a list through the custom module parts_as_list. The unit test multipart_and_compressed_entries_reload exists because, as its comment says, every journal with a multipart upload once failed to load.

A snapshot (JournalFile) is a JSON object of the form {"version":1,"generation":7,"entries":[...]}. A log line (LogLine) is one JSON object per line: {"generation":7,"id":"...","entry":{...}} adds or replaces an entry, and "entry":null removes one. Replay is “last writer wins” per identifier. There is no per-line checksum; a line is valid if it parses. JournalFile uses #[serde(default)], so an older pretty-printed queue.json without generation loads with generation zero (test old_pretty_queue_files_still_load). JOURNAL_VERSION is 1 and is written into every snapshot, but at the audited commit the loader never inspects it; compatibility relies entirely on serde defaults.

Batching Writes Off the Async Runtime

A blocking write on a Tokio worker would stall every task on it (Chapter 5, Tokio and Asynchronous Execution), so callers only change memory. upsert_many inserts entries into a BTreeMap behind a parking_lot::Mutex, pushes each change onto a pending list for a logged journal, and calls dirty.notify_one(). The task started by spawn_writer waits on dirty, sleeps one batch interval so a burst of updates (say, eight parts finishing within milliseconds) becomes one write, then runs flush on the blocking pool with spawn_blocking. Because Notify stores a permit when no one is waiting, a change arriving mid-flush triggers another flush.

That creates a deliberate window: a change reaches disk up to one batch interval plus the write time after it happens in memory. JobHooks::persist_now flushes synchronously for code that cannot accept the window; its only caller is download finalization (Chapter 15). Both journals are also flushed synchronously on normal exit, from the Tauri RunEvent::Exit handler in src-tauri/src/lib.rs.

Appending to the Log

For the queue, a flush normally appends a few lines:

Source: crates/r2dock-transfer/src/journal.rs, lines 236 to 279

pub fn flush(&self) {
    let Some(log) = &self.log else {
        self.compact();
        return;
    };
    let _writing = self.writing.lock();
    let (lines, generation) = {
        let mut state = self.state.lock();
        if state.needs_snapshot
            || state.log_bytes >= LOG_COMPACT_MIN.max(state.snapshot_bytes)
        {
            drop(state);
            drop(_writing);
            self.compact();
            return;
        }
        (std::mem::take(&mut state.pending), state.generation)
    };
    // ...
    let appended = log
        .parent()
        .map_or(Ok(()), std::fs::create_dir_all)
        .and_then(|()| {
            std::fs::OpenOptions::new()
                .create(true)
                .append(true)
                .open(log)
        })
        .and_then(|mut f| {
            f.write_all(&bytes)?;
            f.sync_data()
        });

A plain journal has no log, so its flush is a full snapshot (compact). For a logged journal, the second lock, writing, serializes every disk write, so an append and a snapshot never overlap and, in the field comment’s words, “an older snapshot never lands after a newer one”. If compaction is not due, the pending changes are encoded as JSON lines with the current generation, written with one write_all, and followed by sync_data.

That is the queue’s durability point. The Rust documentation for File::sync_data says it is like sync_all “except that it might not synchronize file metadata to the filesystem”. An appended file’s length is metadata; on Unix the data sync call is generally expected to persist it, but the Rust documentation does not promise this and this book did not verify it per platform. What the code does guarantee is that log_bytes grows only after the sync succeeds.

Snapshots, Atomic Replace, and fsync

Snapshots go through write_bytes_atomic in r2dock-core, shared with the settings and connection files:

Source: crates/r2dock-core/src/storage.rs, lines 49 to 63

pub fn write_bytes_atomic(
    path: &Path,
    bytes: &[u8]
) -> Result<(), StorageError> {
    let dir = path
        .parent()
        .ok_or(StorageError::Io(io::ErrorKind::InvalidInput))?;
    fs::create_dir_all(dir)?;
    let mut tmp = tempfile::Builder::new()
        .prefix(".r2dock-")
        .suffix(".tmp")
        .tempfile_in(dir)?;
    tmp.write_all(bytes)?;
    tmp.as_file().sync_all()?;
    tmp.persist(path)
        .map_err(|e| StorageError::Io(e.error.kind()))?;
    Ok(())
}

This is the classic write, sync, rename pattern, with the temporary file in the same folder so the rename stays on one file system. The tempfile documentation for persist states that it “will atomically replace” an existing target, and warns that “neither the file contents nor the containing directory are synchronized”. R2Dock covers the contents with sync_all, but no code at the audited commit syncs the parent directory after the rename. A reader therefore always sees a complete old or complete new snapshot, never a half-written one; what is not guaranteed under power loss is that the new one is permanent when persist returns, since on some POSIX file systems the old name can survive. Chapter 15 considers what that means for the queue.

Generation Numbers

A snapshot and its log must agree on which lines the snapshot already contains. R2Dock uses a generation counter stored in the snapshot and copied onto every log line. Each compaction of a logged journal writes a snapshot with the generation increased by one, then empties the log, and on load any line from another generation is skipped. This matters because “write snapshot, then truncate log” is two system calls, and a crash between them leaves a new snapshot next to a log full of changes it already contains. Replaying most of them would be harmless, but an old “add” line for a job later removed would resurrect it. The test logged_journal_compacts_and_skips_older_lines appends a stale generation-zero removal for a job that should survive and checks that it does. A plain journal’s generation never changes.

Replay at Startup

Loading reads the snapshot, replays the log, and compacts at once if the log was not empty:

let file = match read_json::<JournalFile>(&path) {
    Ok(Loaded::Found(f)) => f,
    _ => JournalFile::default(),

if let Some(log) = &log
    && let Ok(f) = std::fs::File::open(log)
{

        let Ok(line) = line else { break };
        if line.trim().is_empty() {
            continue;

        let Ok(change) = serde_json::from_str::<LogLine>(&line) else {
            break;

            continue;
        }
        match change.entry {
            Some(e) => {
                state.entries.insert(change.id, e);
            }
            None => {
                state.entries.remove(&change.id);
            }
        }
    }
}
// ...
if replayed {
    journal.compact();
}

A missing or unreadable snapshot counts as empty with generation zero, lines apply in order, lines from another generation are skipped, and the first unreadable line ends the replay. Figure 14.1 shows these rules.

The immediate compaction makes “stop at the first bad line” safe. Without it, new appends would follow a torn line, and the next load would stop there and silently drop the whole following session. The doc comment on load_logged says: “Anything in the log is folded into a new snapshot at once, so later appends never follow a line cut short by a crash.”

Engine::restore then merges the two journals. Resume journal entries win for the same identifier because they carry resumable state, and every restored job is Interrupted (“Nothing restarts on its own.”). Jobs are sorted by (seq, created_at). The test accepted_queue_survives_restart in tests/recovery.rs enqueues 5,000 downloads, pauses, flushes, restarts, and checks all 5,000 return as Interrupted in their original order.

Compaction: When and How

The rule is the condition at the top of flush: compact when a previous snapshot failed (needs_snapshot) or when the log reaches LOG_COMPACT_MIN.max(state.snapshot_bytes), with LOG_COMPACT_MIN at 1 MiB. So the log is folded in once it is at least 1 MiB and at least as large as the snapshot. Disk use stays under roughly twice the live data, a snapshot of size S is rewritten only after S bytes of log, and the floor keeps a nearly empty queue from compacting on every change.

The function compact (lines 297 to 345 of journal.rs) takes the write lock, discards pending changes (the map already reflects them), builds a snapshot with the next generation, writes it atomically with one retry after 50 milliseconds (the comment cites antivirus or indexers briefly holding the file on Windows), records the new generation and sizes on success, and truncates the log. A failed truncation is ignored: old lines carry the old generation and will be skipped, though the next compaction then comes later than intended. Changes arriving after the state lock is released are pushed to pending without a generation; the later flush that encodes them needs the same write lock, so they get the new generation. Figure 14.2 shows the cycle.

Damage and Disk Failures

A torn log tail ends the replay and is removed by the load-time compaction, so a crash loses at most the batch in progress plus unflushed changes. A corrupt middle line is treated the same way: without a checksum it cannot be told from a cut tail, and continuing could apply a removal without its addition. Since the code only appends, such damage needs a hardware or file system fault.

A corrupt snapshot is handled by read_json in storage.rs: it is renamed to queue.json.corrupt-<timestamp> (or the journal.json equivalent), a warning is logged, and the journal starts empty (test corrupt_journal_is_ignored, for a plain journal). For the queue, the empty replacement has generation zero, so every log line written against the lost snapshot is skipped and then truncated; the log is not backed up. Any other read error, such as a permission problem, also yields an empty journal, without a backup.

Persistence is best effort: a failed save never fails a transfer and is only logged with tracing::warn! and retried. A failed append makes flush release its write lock and call compact. The benchmark notes in docs/benchmarks/2026-10-18-compression-at-scale.md explain why the release matters: an earlier version fell back while holding the lock and deadlocked in a fresh data folder without a transfers directory. The tests a_failed_append_writes_a_snapshot_without_hanging and logged_journal_starts_in_a_missing_folder cover the fix. If the snapshot also fails, compact sets needs_snapshot, keeps the old log (still consistent with the old snapshot), and notifies the writer, so the journal retries every batch interval while memory keeps everything. The cost is that a full disk can silently leave the journals stale for as long as it stays full.

Ordering Between Memory, Disk, and the Network

The hard correctness questions are about ordering. First, adding versus finishing: Engine::enqueue saves accepted jobs to the queue while holding the jobs lock, so a job that finishes at once removes its record only after the save and “never comes back as interrupted”. The tests a_job_finished_while_it_is_saved_is_not_kept and a_retried_job_finished_while_it_is_saved_is_not_kept in engine/tests.rs force that race with the hook before_queue_save, and save_intent refuses to save a finished job.

Second, cleanup versus announcement: Inner::finish removes the resume entry and compressed copy before set_state announces the final state and removes the queue entry. The resume entry is kept for Failed, so a failed download keeps its partial file for Retry (the “partial kept for retry” row in PLAN.md section 13), and, as Chapter 13 notes, such a job returns as Interrupted after a restart.

How This Compares With a Write-Ahead Log

The queue resembles a database write-ahead log (WAL), but a WAL makes the log record durable before the change is applied. R2Dock cannot: the changed data is mostly remote, an upload ID exists only after CreateMultipartUpload succeeds, and batching means changes reach the network before disk. The journal is a checkpoint of progress, not a log of intent. It is safe because recovery never trusts it alone: a resumed multipart upload lists its parts on the server and keeps only matching ETags, a download re-checks its partial file and uses If-Match, and a compressed copy is verified by SHA-256. With no multi-record transactions and no directory sync, the journal gives crash safety and fast recovery, not transactional durability.

What the Log Saves in Practice

As recorded in docs/benchmarks/2026-10-18-compression-at-scale.md (not re-run for this book), the ignored test draining_a_huge_queue_keeps_disk_writes_small in tests/queue_scale.rs queued 100,000 jobs and drained 50,000 over about 15 seconds on an Apple silicon Mac with release builds, estimating bytes written by polling file sizes. The earlier design, a pretty-printed queue.json rewritten up to once a second, wrote 59.4 MB per save and about 636 MB while draining. With snapshot and log, the first save was 50.1 MB and draining wrote about 45 MB including one compaction. These are single-run estimates; the test also checks that exactly the unfinished jobs return after a restart.

The other persistent logs choose differently. History (history.rs) appends one JSON line per finished job without syncing and skips malformed lines when reading. The activity log in src-tauri/src/activity/ writes daily comma-separated values (CSV) files from a dedicated thread with a bounded queue (200,000 rows and 64 MiB), dropping and counting rows when full, without syncing, because “callers never wait on disk”. The journals sync because they drive recovery; history and activity only describe the past.

A Crash Recovery Walkthrough

The user enqueues 1,000 downloads, and a second later the writer appends 1,000 lines with, say, generation 4 and syncs. Three downloads start and each saves a Download resume state to journal.json within about 200 milliseconds. As downloads finish, removal lines are appended; the log stays far below 1 MiB.

Then the power fails. On restart, Journal::load reads the last complete journal.json and finds three resume entries. Journal::load_logged reads the generation 4 snapshot and replays 1,000 additions, a few hundred removals, and perhaps half a line, where it stops. The queue is compacted at once into generation 5 and the log emptied. restore shows the remaining jobs as Interrupted, in order. Jobs that finished in the last second may reappear because their removal lines were never written; PLAN.md section 12.3 accepts this, since resuming them is safe under the conflict policy and verification. Chapter 15 follows each resumed job.

Working on This Code

crates/r2dock-transfer/src/journal.rs holds Journal, its formats, replay, compaction, and unit tests. crates/r2dock-core/src/storage.rs holds write_bytes_atomic and read_json, shared with settings and connections, so changes there reach beyond transfers. The engine’s use is in engine/mod.rs (Engine::start, restore, enqueue, save_intent, finish, persist_now), and resume types are in ctx.rs.

When adding a field to JobSpec or ResumeState, give it #[serde(default)], avoid u128 and non-string map keys inside tagged enums, and add a reload test beside multipart_and_compressed_entries_reload. Keep queue saves under the jobs lock and cleanup before final announcements, and never call flush from async code without spawn_blocking. Run cargo test -p r2dock-transfer, cargo test -p r2dock-transfer --test recovery, and cargo test -p r2dock-core; the large queue measurement is cargo test -p r2dock-transfer --release --test queue_scale -- --ignored --nocapture. Do not test persistence only through clean shutdowns; build files by hand with stale and torn lines, as logged_journal_compacts_and_skips_older_lines does.

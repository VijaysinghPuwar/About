11 Object Management and Consistency

Desktop users expect instant renames, all-or-nothing folder moves, and a trash can. R2 offers none of these; every file-like action is assembled from HTTP requests that can each fail on their own. This chapter shows how R2Dock builds copy, move, rename, folders, and bulk delete from them, which races it closes, and which it cannot. Protocol basics belong to Chapter 8 (The S3-Compatible Protocol) and multipart mechanics to Chapter 9 (Multipart Uploads in Depth).

Why a Move Is Hard on R2

Cloudflare’s consistency reference states that reads after writes and listings are strongly consistent, and that when two clients write or delete the same key, the last writer to complete wins. Last writer wins means that if a user moves covers/cover.webp while a script elsewhere uploads a new version of it, nothing in the service stops one from silently destroying the other’s work.

A local move is one atomic rename. R2 has no rename, no move, and no transaction across two keys, so a move is a server-side copy followed by a delete. Between them the source can be overwritten, the destination created, the copy’s response lost, or the delete can fail, so a naive copy then delete can destroy data it never copied. R2Dock binds each step to a specific version of each object, identified by its entity tag (ETag), and keeps the source whenever the outcome is uncertain. Here an ETag is only a version identifier, never a content hash. The helper same_etag in crates/r2dock-r2/src/ops.rs strips quotes, which some responses omit, and never calls two empty strings equal.

Simulated Folders

The module comment in crates/r2dock-core/src/keys.rs says a “folder” is the part of a key before a /. A folder with nothing in it therefore does not exist, and a folder operation is an operation on every key under its prefix, with cost growing accordingly. To create an empty folder, create_folder in ops.rs writes a zero-byte folder marker whose key ends in /, with If-None-Match: *. A 412 counts as success, since the folder already exists, and the condition guarantees the marker never replaces a real object; listing_hides_marker_and_paginates creates the same folder twice. Markers come from the folder_create command (which validates names with validate_name) and from uploads of empty local folders. collect_objects in crates/r2dock-r2/src/bulk.rs lists without a delimiter, “including folder markers,” so folder moves and deletes include nested markers.

Server-Side Copy

In a server-side copy R2 duplicates the bytes internally, so moving a 4 GiB video takes seconds. A CopySpec names source and destination keys, the size, an optional source_etag that pins the source version, and a create_only flag that refuses to overwrite the destination. copy_object turns them into headers.

Source: crates/r2dock-r2/src/ops.rs, lines 251 to 275

let source = format!("{}/{}", bucket, percent_encode_key(spec.src_key));
if spec.size <= MAX_SINGLE_PUT {
    let mut req = self
        .inner
        .copy_object()
        .bucket(bucket)
        .key(spec.dst_key)
        .copy_source(source)
        .set_copy_source_if_match(spec.source_etag.map(str::to_string))
        .metadata_directive(MetadataDirective::Copy)
        .customize();
    if spec.create_only {
        // R2 extension: evaluated when the copy is committed, so a
        // destination created after any earlier check is not replaced.
        req = req.mutate_request(|r| {
            r.headers_mut().insert(COPY_DESTINATION_IF_NONE_MATCH, "*");
        });
    }
    let out = req.send().await.map_err(R2Error::from_sdk)?;
    return Ok(out
        .copy_object_result()
        .and_then(|r| r.e_tag())
        .map(str::to_string));
}
self.multipart_copy(bucket, &source, spec).await

The AWS CopyObject reference requires the copy source to be URL-encoded, so percent_encode_key (Chapter 12) encodes it; otherwise a key with a space, ?, or # would name the wrong object. x-amz-copy-source-if-match, which R2 lists as supported on CopyObject, makes the copy fail with 412 if the source was replaced after R2Dock inspected it. cf-copy-destination-if-none-match: * is an R2 extension: the R2 extensions page says the cf-copy-destination-if-* headers are checked when the object is committed, are not atomic relative to the source conditions, and are beta. The AWS software development kit (SDK) has no builder for it, hence mutate_request; the non-atomicity is harmless because each condition guards a different object. MetadataDirective::Copy is already the default per AWS but documents intent; whether it preserves storage class on R2 is [Verify] in PLAN.md section 8.7.

Copies larger than 5 GiB

MAX_SINGLE_PUT is 5 GiB, and AWS says CopyObject copies “up to 5 GB in size in a single atomic action.” Above that, multipart_copy pins the source’s ETag and size, plans parts with the upload engine’s plan_parts, and copies them sequentially with UploadPartCopy. This path is weaker: R2’s compatibility page lists every x-amz-copy-source-if-* header as unsupported on UploadPartCopy and no conditional headers on CompleteMultipartUpload. So just before completing, R2Dock re-reads the source and fails if its ETag or size changed, and fails if a create_only destination now exists. Any error aborts the upload. The doc comment admits “A change in that short window is not detected,” and PLAN.md adds that a source changing and changing back to the same ETag between parts would also go unnoticed. Without a metadata directive, the create request copies the source’s content headers, storage class, and custom metadata, as multipart_copy_keeps_metadata checks.

R2Dock exposes no stand-alone copy command in this version; copy_object is called only from the move path and tests.

Move as Copy, Verify, Delete

move_one in bulk.rs moves one object. Its contract: copy exactly the inspected source version, confirm the destination is that copy, confirm the source is still that version, and only then delete it. Figure 11.1 shows every branch.

The first HeadObject, skipped when overwriting, gives a clear conflict message cheaply; the copy condition is what makes the move safe. The second reads the source’s size and ETag; without an ETag the move refuses, since no later check would mean anything. The third is the conditional copy. A 412 does not say which condition failed, so the code asks whether the destination exists to choose the message, and reports the item as failed with the source untouched.

The fourth request requires the destination ETag to equal the ETag the copy returned, because another client could write different bytes of the same length right after the copy. If the copy returned no ETag, or the read itself errors, the outcome is unknown and the item is “copied, original kept.” If the destination is missing or different, someone replaced it; the source is kept and the item is reported as not moved. The last two requests protect the source.

Source: crates/r2dock-r2/src/bulk.rs, lines 308 to 331

// The source must still be the version that was copied.
match client.head_object(bucket, &item.src).await {
    Ok(d)
        if d.size == source.size
            && d
                .etag
                .as_deref()
                .is_some_and(|e| same_etag(e, source_etag)) => {}
    Ok(_) => {
        // ...
    }
    // Someone else already removed it; the verified copy is in place.
    Err(R2Error::NoSuchKey { .. }) => return ItemResult::Moved,
    // ...
}
match client.delete_object(bucket, &item.src).await {
    Ok(()) => ItemResult::Moved,
    Err(e) => kept(&format!(
        "Copied, but the original was not removed. {}",
        e.to_app_error().message
    )),
}

A changed source would lose its newer version if deleted, so it is kept, as it is when the check fails. A source already gone means another client removed it and the verified copy stands. Only an unchanged source is deleted.

Three outcomes instead of two

move_items collects one ItemResult per object into a MoveReport with a moved count and two lists: failures (not copied, destination already existed, or destination changed right after copying; the source is kept) and copied_not_deleted (copied, but the original was kept because it could not be removed, changed during the move, or the copy could not be confirmed). The split tells the user what is in the bucket. A failed item exists only at its old location; a copied-but-kept item exists in both places. moveProblems in src/features/manage/moveRunner.ts turns the report into plain sentences, and OpResultDialog lists keys under “Failed” and “Copied but not deleted,” passing them through visibleText so invisible or bidirectional characters cannot disguise a key (Chapter 23). PLAN.md section 8.7 promises a “Retry delete” action, but no flow passes the dialog’s optional onRetry callback, so users must delete originals by hand.

Proving the Ordering With a Mock Server

Interesting interleavings happen within milliseconds, so the tests in move_races.rs use an in-process S3 mock (crates/r2dock-r2/tests/support/mock_s3.rs) that applies each request to an in-memory model and then runs a test hook before responding. A hook can change an object at an exact request boundary. Following the R2 documentation, the mock honors x-amz-copy-source-if-match and cf-copy-destination-if-none-match on CopyObject, ignores source conditions on UploadPartCopy, and accepts no conditions on DeleteObject or CompleteMultipartUpload.

source_changed_after_copy_is_kept overwrites the source with same-length bytes right after the copy and asserts that the new bytes survive, no delete is sent, and the item is copied-not-deleted. destination_created_after_check_is_not_overwritten creates the destination after the existence check returned 404. destination_replaced_after_copy_keeps_source writes same-length content to the destination after the copy, which only the ETag comparison catches. Others cover failing deletes, a source removed after the copy, and multipart cases. lost_copy_response_keeps_source applies the copy but answers with a server error; the SDK’s retry meets the destination condition and gets 412, so the item is reported as failed with “Something with that name already exists at the destination.” No data is lost, but the user may not realize the existing object came from this move.

PLAN.md states the limit plainly: these tests “prove the client’s sequencing, not R2’s enforcement.” Whether R2 returns 412 for an existing destination, and whether CopyObject’s ETag always equals a later HeadObject’s, is [Verify] against a disposable test bucket. If the ETags ever differed, every move would err on the safe side and keep its source.

Rename Is a Move in Place

A rename is a move whose destination is the item’s own parent, with a new last segment. plan_move plans both before any request that changes data: each object under a selected prefix keeps its relative path below the new prefix. Moving a/ into a/deeper/ would copy its own output, so it is refused with “A folder cannot be moved into itself.” A move to the same place produces no work. Every new key goes through validate_key, since a longer prefix can push a key past 1,024 bytes. A set of destination keys catches two items landing on one name, such as a/x.txt and b/x.txt moved into dest/, returning DuplicateDestination. Unit tests such as refuses_moving_into_itself and rejects_colliding_destinations cover these; the frontend repeats cheap checks, but Rust is authoritative. The dialogs describe the mechanism honestly: “Renaming copies the file to the new name, then deletes the original,” and for folders, “R2 has no real folders.”

Bulk Delete and Confirmation Tokens

A move can leave extra copies; a delete destroys data with no way back, since R2 has no trash and, per PLAN.md section 8.6, no bucket versioning. Every delete is therefore a two-step exchange in which the backend decides what is deleted. Figure 11.2 shows it.

delete_preview in src-tauri/src/commands/manage.rs validates its arguments (an empty prefix cannot select a whole bucket), calls collect_objects, and stores a PendingDelete holding the connection, bucket, exact key list, and typed phrase. The frontend gets a token, count, bytes, five sample keys, and the phrase. Typed confirmation is required for any folder delete and for more objects than typed_confirm_threshold (default 50, clamped to 1 to 10,000). The phrase is the folder name for a single folder, otherwise delete N.

The token comes from Registry<T> in src-tauri/src/state.rs: version 4 UUIDs, expiry after TOKEN_TTL (15 minutes), at most REGISTRY_CAP (256) entries per kind with the oldest evicted.

Source: src-tauri/src/state.rs, lines 65 to 69

/// Remove and return a value (single use).
pub fn take(&self, id: &str) -> Option<T> {
    let (t, v) = self.items.lock().remove(id)?;
    (t.elapsed() < TOKEN_TTL).then_some(v)
}

delete_execute takes the token first and checks the phrase second, so a wrong phrase also consumes the token. It accepts no keys and deletes exactly those recorded at preview time; objects added later are not deleted. The AWS DeleteObjects reference reports a missing key as deleted; the code assumes R2 behaves the same, which this book could not confirm from an R2 page. An object overwritten after the preview is deleted in its new version, because there is no conditional delete.

SECURITY.md says bulk and folder deletes require a backend token; in the code every delete does, even of one file. The token pins the key list so a frontend bug cannot widen a delete. But the phrase is returned to the frontend, so it guards against accidental clicks, not a compromised webview. PLAN.md section 9.8 states the residual risk as deleting “one object per call within confirmation rules”; since the webview has the phrase, the honest reading is that a compromised webview could delete anything the connection’s key may delete, one preview and execute pair at a time (Chapter 25, Threat Modeling and Remaining Risks).

Deletion uses DeleteObjects in quiet mode, which reports only failed keys. AWS allows 1,000 keys per request; PLAN.md marks R2’s limit [Verify], and DELETE_BATCH uses the S3 value, with delete_batch refusing larger batches. delete_keys runs batches through buffer_unordered(BULK_CONCURRENCY). A per-key error becomes a KeyFailure for that key; a whole-request failure, such as a timeout, marks every key in the batch failed, conservatively, since some may be gone. Progress reaches the dialog as OpProgress { done, total }.

Concurrency, Cancellation, and Gaps

BULK_CONCURRENCY is 4, so at most four delete batches or four object moves are in flight (Chapter 6, The Transfer Scheduler, owns bounded concurrency). Both paths build the full vector of boxed futures before streaming, so every item’s future state is allocated up front. MAX_BULK_OBJECTS caps an operation at one million objects; memory at that scale was not measured for this book. Both loops honor a CancellationToken, but the commands pass a fresh one that nothing cancels, so a confirmed operation runs to completion.

PLAN.md section 8.7 describes folder moves as “Journaled,” with “Finish move” offered after a restart. The code has no move journal; the journal of Chapter 14 (Journals and Persistent Queues) serves transfers only. After a mid-move exit, every object is moved, not moved, or in both places, but nothing records which. The same section says conflicts are checked by listing the destination first; the code checks each key with HeadObject as it goes.

The remaining windows are properties of the service. R2 lists no conditions on DeleteObject, so a source overwritten between the final check and the delete loses its new version, as move_one’s doc comment and PLAN.md section 9.8 state; every other conflicting change keeps the source. A folder move is never all-or-nothing, and the confirmation text says so: “If something fails, some objects may exist in both places.”

Working on This Code

Single requests live in crates/r2dock-r2/src/ops.rs (copy_object, multipart_copy, delete_batch, create_folder) and bulk work in bulk.rs (collect_objects, plan_move, move_one, delete_keys). Commands in src-tauri/src/commands/manage.rs stay thin; dialogs are in src/features/manage/. Start a move change with a new hook case in move_races.rs. Run cargo test -p r2dock-r2 --test move_races, cargo test -p r2dock-r2 --test local_s3, cargo test -p r2dock-r2 --lib, cargo test -p r2dock manage, and npm test.

Never delete a source unless the destination was verified by ETag and the source re-checked; when unsure, report the item in copied_not_deleted. Keep fan-out bounded, never let an execute command accept keys from the frontend, validate every computed key, and compare ETags with same_etag, not ==. Before relying on a new conditional or cf-* header, check R2’s compatibility page: a header R2 ignores weakens a guarantee that the mock would still report as working.

15 Crash Consistency and Recovery

Chapter 14 (Journals and Persistent Queues) described the files R2Dock writes so that work survives a restart. Crash consistency is the stronger property that, whatever instant the process or the machine stops, the state on disk and on the server can be brought back to something correct without losing user data and without silently doing the wrong thing. This chapter checks that property scenario by scenario at the audited commit, condenses the results into a failure matrix, and lists the remaining gaps. Job states such as Interrupted are defined in Chapter 13 (Transfer State Machines).

Two Kinds of Crash

In a process crash (a panic, a forced quit, kill -9) the operating system keeps running, so every byte passed to write survives in the page cache. Only process memory is lost, such as pending journal changes, and the Tauri RunEvent::Exit handler that calls Engine::flush is skipped.

In a power loss or operating system crash, the page cache is lost too. The Rust documentation for File::sync_all says it “will attempt to ensure that all in-memory data reaches the filesystem before returning”; without it, a recent file can come back shorter, with a tail of zeros, or not at all. R2Dock’s recovery mostly avoids caring which kind of crash happened: it re-checks evidence instead of trusting it.

Where R2Dock Forces Data to Disk

The non-test transfer code has exactly three sync points. Journal::flush appends the queue log and calls sync_data. Every snapshot of queue.json and journal.json is written to a temporary file, synced with sync_all, and renamed into place by write_bytes_atomic in crates/r2dock-core/src/storage.rs. A finished download’s partial file is synced in download.rs before verification.

Not synced are a streaming partial download, compressed copies, the history and activity logs, and every directory after a create, rename, or delete; the tempfile documentation for persist warns that “neither the file contents nor the containing directory are synchronized” by a rename.

The Startup Sequence

Engine::start loads and replays both journals, and Engine::restore merges them, marks every job Interrupted, and computes bytes already done: recorded parts for a multipart upload, the partial file’s length for a download. A compressed copy that is missing, or lacks a digest from an older version, sends the job back to compressing. Hashing the copy is deferred until upload because, as PLAN.md section 12.5 says, “Nothing is read at startup, so a restart with many copies is instant.”

No job restarts automatically; the user chooses to resume or discard. That is a safety property: files may have changed since the crash, and an unrequested transfer could overwrite something or spend bandwidth. A resumed job runs the normal code path, which consults its saved resume state first. Figure 15.1 summarizes the decisions.

Partial Downloads

A download streams into a hidden file beside the target, named by temp_path_for: a dot, the file name, eight hex characters of the job identifier, and .r2dock-part. PLAN.md section 8.5 gives the name as .<name>.r2dock-part; the code adds the job tag so two jobs never share a partial. Chapter 10 (Downloads and HTTP Range Requests) owns the request mechanics.

Recovery does not trust the partial’s length. The doc comment on RESUME_BACKOFF (one mebibyte) says: “After a crash or power loss the file can be longer than the data that reached the disk (the tail reads as zeros), so the last stretch is fetched again.” open_temp truncates to the length minus one mebibyte, and the request sends Range with If-Match set to the recorded entity tag (ETag), so a changed object (412 Precondition Failed) or an ignored range restarts the download from zero.

The margin is a heuristic, not a file system guarantee. At the end, the file’s MD5 is compared with the ETag only when the ETag is a single-part MD5 and the object is not encrypted with a customer key (SSE-C). For multipart objects only the length is checked, so after a power loss a zero-filled hole before the last mebibyte would go undetected. This is an analysis of the code, not an observed failure.

The resume state naming the partial is saved through the 200 millisecond journal batch. If the process dies first, a resume still picks the same temporary name (it depends only on target and job) and truncates the orphan. It survives only if the user dismisses the job or “Keep both” picks another target; nothing scans for stray .r2dock-part files.

Finishing a Download Exactly Once

The rename that moves a finished file into place is the delicate moment. If the process stops right after it, the next start finds a resume entry whose partial is gone, and a file of the right size at the destination proves nothing: it could be one the user had all along. R2Dock writes a finalization record synchronously before the rename.

Source: crates/r2dock-transfer/src/download.rs, lines 362 to 385

// Record the finished, synced file before moving it, so recovery can
// tell this file from any other one at the destination.
let check = temp.clone();
let written = blocking(move || {
    std::fs::symlink_metadata(&check)
        .map(|m| WrittenFile::of(&m))
        .map_err(|e| JobError::io(&e, "save the download"))
})
.await?;
ctx.save_resume(ResumeState::Download(DownloadState {
    etag: remote_etag.clone(),
    temp: temp.clone(),
    final_path: final_path.clone(),
    finalized: Some(written),
}));
// On disk before the move, not in the next batched save: after a crash
// right after the move, this record is what tells the moved file apart
// from someone else's file at the destination.
let hooks = ctx.hooks.clone();
blocking(move || {
    hooks.persist_now();
    Ok(())
})
.await?;

WrittenFile (in source.rs) holds the length, the modification time in nanoseconds, and on Unix the device and inode numbers, all preserved by a rename; on Windows only length and time exist, which can collide for two quick writes. persist_now performs a full atomic snapshot with sync_all, the one place in the engine that follows the write-ahead rule from Chapter 14: intent is durable before the effect.

On resume, a present partial means the move never happened, so the download resumes. If the partial is gone and find_finalized matches the record against the target or one of up to 1,000 “Keep both” names, the job completes with no network traffic. Otherwise it starts over through resolve_target, and an existing file meets the conflict policy: “Ask” yields NeedsDecision, “Skip” skips, only “Replace” overwrites. Tests in crates/r2dock-transfer/tests/recovery.rs pin this, including finalized_download_completes_after_restart, finalization_record_must_match_the_file (a same-size record from another file forces a repeat), and missing_partial_without_proof_keeps_a_user_file.

One residual case: non-Replace placement uses persist_noclobber, which per its documentation may leave a second hard link if the process “crashes mid-operation”. Recovery would then resume from the partial, and “Keep both” could create a duplicate. This is inferred, not tested.

Uploads That Completed but Were Not Recorded

Uploads have the mirror problem. A single-request upload (below the 100 MiB default multipart threshold) has no resume state, and its queue entry is removed through the one second queue batch. After a crash in that window it returns as Interrupted and runs again: “Replace” writes the same bytes, “Ask” or “Skip” find the job’s own object and report a conflict or skip, and “Keep both” creates a second copy. PLAN.md section 12.3 calls this safe “because the conflict policy and verification apply”; safe means nothing is overwritten without permission, not that no duplicate appears.

A multipart upload records its upload ID, part size, source fingerprint, and each part’s ETag and MD5. On resume, upload::multipart first runs reconcile, which calls ListParts (Chapter 9, Multipart Uploads in Depth). If the upload no longer exists, finished_before_restart decides whether “the object is already ours”, in the words of the code comment, and if so the job completes. It requires that every planned part was recorded, that the object has the source’s size, and that its ETag equals the multipart ETag computed from the recorded part MD5s (PLAN.md section 8.10). The weak spot is the first condition: parts are recorded through the batched journal, and there is no persist_now before CompleteMultipartUpload. If the last part was not yet recorded, the job starts over under the conflict policy as if the object were someone else’s. The steps between the last part and completion usually take longer than 200 milliseconds, but nothing enforces it.

Multipart Uploads Interrupted Midway

With parts in flight at a crash, reconcile keeps only parts that the journal and server both hold with the same ETag; the rest are sent again under the same part number, which replaces them. A source whose fingerprint (size and modification time) changed aborts the old upload. The test paused_multipart_resumes_after_restart in tests/engine.rs covers a restart.

Inner::finish removes the resume entry only for Completed, Cancelled, and Skipped, but removes the queue entry for Failed too. A multipart upload that exhausted its retries keeps its parts in journal.json, so after a restart restore brings it back as Interrupted. That supports Retry from saved parts, but “failed” is not terminal across restarts. The test finished_jobs_are_not_restored covers only a failed download without resume state.

The upload ID from CreateMultipartUpload is also saved through the batch. A crash before it lands leaves an unknown upload on R2, and the job creates a new one. Cloudflare’s multipart documentation states that “incomplete multipart uploads are automatically aborted after 7 days by default”. PLAN.md section 13 proposes a ListMultipartUploads cleanup tool; no code calls that operation.

Orphans and Interrupted Compression

Snapshot temporaries (.r2dock-<random>.tmp) left by a crash are never removed, but they are small and never read. Compressed copies are the only orphans with an explicit sweep: Engine::sweep_work_dir in engine/compress.rs deletes every regular file in R2Dock’s own work folder that no restored job references. Its doc comment says “Call once at startup, before any encode”, yet the app starts the FFmpeg check that enables encoding in parallel and does not wait for the sweep. A compressed upload added within moments of launch could, in principle, race a slow sweep; the code does not settle that.

After a crash mid-encode, on Windows a Job Object ends FFmpeg with R2Dock; on macOS and Linux it “exits on the next progress write after R2Dock is gone (the pipe is closed)”, per crates/r2dock-media/src/ffmpeg/run.rs (Chapter 17, How FFmpeg Integrates with Rust). The sweep deletes the partial output, and a resume encodes from the start.

A finished encode is recorded by Hooks::checkpoint (path, size, time, SHA-256 in the resume journal) and save_intent (updated spec in the queue), so it is not repeated. The copy was never synced, so before every upload attempt gate_copy runs check_copy, which re-verifies the original and the copy’s length, time, and SHA-256. A mismatch sends the job back to be recompressed or uploaded as the original: a damaged copy costs time, never a corrupted upload. Chapter 20 (Compression Scheduling and Data Integrity) covers the digest.

Crash During Compaction

Queue compaction writes and syncs a snapshot, renames it over queue.json, and truncates queue.log. A process crash at any step is safe: before the rename the old files are intact, after it the old log’s generation is skipped. Power loss leaves a theoretical gap, because neither the directory nor the truncation is synced: a file system that persisted the truncation but not the rename would yield the old snapshot and an empty log, losing every change since. This book did not test whether any file system reorders them that way. The resume journal has no log, so a lost rename there only restores an older snapshot, which recovery re-checks.

The Failure Matrix

The table lists each scenario, what recovery does, and the result for the user.

Scenario Recovery does Result
Kill mid-download Drop 1 MiB, Range with If-Match Resumes
Power loss mid-download Same; MD5 if single-part ETag Resumes; multipart hole possible
Crash after placing download Match finalization record Completed, no transfer
Crash mid multipart upload ListParts, keep matching parts Sends missing parts
Multipart done, fully recorded HEAD size and multipart ETag Completed, no transfer
Done, last part unrecorded Start over under policy Conflict, skip, or duplicate
Single PUT done, unrecorded Run again under policy Same bytes, conflict, or duplicate
Crash before upload ID saved New multipart upload R2 aborts orphan later
Crash mid-encode Sweep deletes output Encode runs again
Crash after encode recorded SHA-256 check before upload Uses copy or re-encodes
Power loss in compaction Nothing detects it Recent changes may be lost
Corrupt queue snapshot Empty queue, log discarded Queued jobs lost

The pattern is consistent. Where the server or file system can prove what happened (a matching ETag, file identity, or digest), recovery completes or continues the job without waste. Without proof, the work is repeated under the conflict policy, which may waste bandwidth, prompt, or duplicate, but never silently overwrites. State is lost only in the last two rows, which concern the queue file itself.

Gaps and Possible Improvements

These are suggestions, not plans in the repository. Syncing the parent directory after each snapshot rename closes the compaction gap. Calling persist_now after CreateMultipartUpload and before CompleteMultipartUpload closes both upload windows. Cleaning up .r2dock-*.tmp files and stale multipart uploads at startup removes the remaining orphans. Keeping queue.log beside a corrupt queue.json preserves evidence. Recomputing per-part MD5s for multipart downloads, when the part size is known, covers the hole the margin cannot.

Working on This Code

Startup recovery is Engine::start and Engine::restore in crates/r2dock-transfer/src/engine/mod.rs. Download recovery is at the top of run in download.rs with find_finalized and place; multipart recovery is reconcile and finished_before_restart in upload.rs; check_copy and sweep_work_dir are in engine/compress.rs; WrittenFile is in source.rs.

Recovery tests build a crashed state by hand: write a journal with Journal::load and flush, then start a fresh engine on the same folder against the in-process S3 server from r2dock-testkit. That is far more reliable than killing a process at the right moment. Run cargo test -p r2dock-transfer --test recovery and cargo test -p r2dock-transfer --test engine.

Never replace a file at a download destination unless the policy is Replace, even in recovery; a shortcut must prove the file is the job’s own. Re-validate destinations through the path guard (revalidate, Chapter 23) before reusing a partial or moving a file. Never start transfers automatically. Give every new temporary file an owner that removes it, or a sweep that proves it is unreferenced.

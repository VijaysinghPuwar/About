3 A Guided Tour Through the Repository

The R2Dock repository holds about 450 tracked files. This chapter walks through each directory and Rust module, shows how they depend on each other, and ends with a reading order. Line counts come from wc -l on the audited commit.

The Top Level

Cargo.toml declares the Rust workspace: seven members, version 0.5.0, edition 2024, minimum Rust 1.94, shared dependency versions, lints, and the release profile. package.json defines the frontend, which uses npm (docs/adr/0004-frontend-libraries.md). .cargo/config.toml sets TS_RS_EXPORT_DIR so generated TypeScript types land in src/ipc/bindings. The workspace lints shape all the Rust code you will read.

Source: Cargo.toml, lines 59 to 67

[workspace.lints.rust]
unsafe_code = "forbid"

[workspace.lints.clippy]
unwrap_used = "warn"
expect_used = "warn"
panic = "warn"
dbg_macro = "warn"
todo = "warn"

Per Cargo’s workspace documentation, members opt in with [lints] workspace = true; every crate except the test kit does. forbid cannot be overridden locally, so those crates contain no unsafe block. The Clippy warnings become errors in continuous integration (CI), which runs with -D warnings; library crates relax them only for tests with #![cfg_attr(test, allow(clippy::unwrap_used, clippy::expect_used, clippy::panic))].

PLAN.md (about 1,100 lines) is the technical plan and DESIGN.md (about 1,000 lines) specifies the interface; SECURITY.md, CONTRIBUTING.md, and CHANGELOG.md cover reporting, ground rules, and releases. The license is MIT.

Documentation, Tools, and Workflows

docs/adr/ holds five Architecture Decision Records: the Tauri architecture, the keyring crate, ts-rs for IPC types, the frontend libraries, and testing against a local S3 server. docs/plans/ holds two approved feature plans, media-compression.md and logs-and-csv.md, each with a progress table listing deviations.

tools/ffmpeg/build-macos.sh builds a static FFmpeg for macOS under the GNU Lesser General Public License (LGPL) from pinned, checksummed sources. The manually triggered .github/workflows/tools.yml runs it and publishes the packages the app downloads, and the URLs and SHA-256 sums the app trusts live in crates/r2dock-media/src/tools/manifest.rs (Chapter 17, How FFmpeg Integrates with Rust).

.github/workflows/ci.yml runs the frontend and Rust checks on Ubuntu, macOS, and Windows for every push to main and every pull request, plus a live check of the platform’s FFmpeg package, a Linux check that generated bindings are committed, and npm audit and cargo audit. .github/workflows/release.yml builds installers for v* tags (Chapter 31, CI/CD and Desktop Releases).

The Rust Crates, Module by Module

Chapter 2 (Complete Software Architecture) introduced the crates and their dependency graph. Here we open each one.

r2dock-core

Its twelve modules are small. app_error.rs defines the IPC error type and io_error, which describes a local I/O error without the path. keys.rs validates object keys (at most 1,024 bytes, no control characters) and provides helpers such as parent_prefix and keep_both_name. path_guard.rs (477 lines, the largest here) maps untrusted keys to safe local paths. parts.rs plans multipart part sizes, policy.rs defines ConflictPolicy, and settings.rs holds versioned settings. storage.rs writes JSON atomically (temporary file, flush, rename) and backs up corrupt files. redact.rs strips secrets, signatures, account hosts, and home paths from text. With no network I/O and no async runtime, this is where property tests live: parts.rs and path_guard.rs use proptest.

r2dock-secrets and r2dock-r2

r2dock-secrets is one file, src/lib.rs (225 lines), defining the SecretStore trait (set, get, delete), SecretError, KeyringStore for the operating system store, and MemoryStore for the session-only fallback. Chapter 21 (Credential Storage and Authentication) owns it.

In r2dock-r2, client.rs builds an aws_sdk_s3::Client for R2: region auto, path-style addressing, checksums only when required, three attempts per request in the AWS software development kit (SDK), a 10 second connect timeout, and stalled stream protection with a 60 second grace period. error.rs maps SDK errors to R2Error and then AppError, list.rs paginates listings, and ops.rs (488 lines) covers single-object operations and ranged reads. bulk.rs (462 lines) implements bulk delete and the copy, verify, then delete move. cfapi.rs is the read-only Cloudflare REST client. Tests run against the local S3 server, a mock that reproduces move races (move_races.rs), and, only with credentials in environment variables, a real bucket read-only (live_r2.rs, ignored by default).

r2dock-media

This crate has the most files (34 tracked). probe.rs reads audio metadata in process with the Symphonia library, plan.rs holds the bitrate ladder and reasons to skip, streams.rs and verify.rs check that an encoded copy dropped nothing promised, and pipeline.rs runs the whole decision for one file, cheapest checks first. ffmpeg/ holds fixed argument arrays (never a shell), a progress parser, and the runner with cancellation and a watchdog; tools/ installs and detects FFmpeg; video/ holds the video equivalents. Part V covers this crate.

r2dock-transfer

This is the heart of the application, and its public surface is a short lib.rs.

Source: crates/r2dock-transfer/src/lib.rs, lines 9 to 24

mod body;
pub mod ctx;
mod download;
pub mod engine;
pub mod history;
pub mod journal;
pub mod model;
pub mod progress;
pub mod retry;
pub mod scan;
pub mod source;
mod upload;

pub use download::human_bytes;
pub use engine::{BoxFuture, ClientProvider, Engine, EngineConfig,
    EventSink};
pub use model::*;

The modules without pub (body, download, upload) are private, so the application cannot call upload::run directly; it must enqueue a job with Engine::enqueue. That privacy is a design statement: every transfer goes through the queue, the journal, and the concurrency limits.

model.rs defines jobs, states, and frontend events. engine/mod.rs (1,272 lines, the largest Rust file) holds the queue, scheduler, controls, progress ticker, and job runner, and engine/compress.rs (714 lines) schedules compression. upload.rs and download.rs implement the two directions, body.rs builds streaming, retryable request bodies, source.rs opens local files and remembers their identity, journal.rs persists resumable state, and retry.rs classifies failures.

Two plan discrepancies live here. scan.rs walks a local selection, skipping links and special files, and collects it into memory in one pass up to MAX_FILES (200,000), while PLAN.md section 12.3 describes a lazy walk with child jobs added in batches; Chapter 5 (Tokio and Asynchronous Execution) discusses this. PLAN.md section 12.6 also proposed separate queue, scheduler, upload_single, and upload_multipart modules, but the code keeps the queue and scheduler in engine/mod.rs and both upload kinds in upload.rs, a reasonable target for a future split.

Its integration tests in tests/ range from engine.rs (end-to-end transfers) and recovery.rs (restarts) to stress.rs (thousands of transfers, partly ignored by default).

r2dock-testkit

crates/r2dock-testkit/src/lib.rs starts an S3-compatible server built on the s3s and s3s-fs crates, on a random local port backed by a temporary folder. Its Network type can throttle request bodies and delay multipart aborts to imitate a slow uplink, and cloudflare.rs mocks the Cloudflare domain endpoints. cargo run -p r2dock-testkit --bin local-s3 -- <port> <bucket>... runs the server for manual testing, and a debug build of the app can target it through R2DOCK_DEV_ENDPOINT; per setup in src-tauri/src/lib.rs, only http://127.0.0.1: addresses are accepted and the override is compiled out of release builds.

The Tauri Application: src-tauri

src-tauri/ holds the r2dock package, its build.rs, tauri.conf.json, capabilities/main.json, and generated permissions. In src-tauri/src/, main.rs calls r2dock_lib::run(), lib.rs (293 lines) performs startup wiring, state.rs defines AppState, the expiring Registry<T>, and commit_json (save settings atomically before publishing them), and commands/ holds the seven command modules.

The other modules are app services: connections.rs (998 lines) for connection lifecycle and the client cache, planning.rs for turning selections into jobs, compression.rs for the pinned FFmpeg, media.rs for the preview protocol, public_links.rs for public URLs with caching and request coalescing, logging.rs for rotating redacted logs, and activity/ for the comma-separated values (CSV) activity log, whose background writer thread has a bounded queue (stressed by src-tauri/tests/activity_stress.rs).

The Frontend: src

src/app/ holds the shell, the TanStack Query client (queries.ts), and Zustand stores. src/ipc/ holds commands.ts, the only module that calls invoke, and bindings/, 74 generated type files; never edit a binding by hand. src/features/ groups screens by domain: browser/, connections/, manage/, preview/, settings/, and transfers/ (dock, event subscription, store, compression notices). src/components/ holds shared Radix-based components and src/styles/tokens.css the design tokens; Vitest tests sit beside their code. Part VII covers the frontend.

How the Pieces Depend on Each Other

The Rust crates form the strict layering of Figure 2.2, so a type change in r2dock-core causes compile errors in the crates above it and nowhere else. The frontend depends on Rust through exactly two artifacts, the generated bindings and the command names in commands.ts, so npm run typecheck finds every component affected by a changed Rust type.

Other files must agree by convention rather than compiler. The command list appears in src-tauri/src/lib.rs, src-tauri/build.rs, src-tauri/capabilities/main.json, and src/ipc/commands.ts. The version appears in the workspace Cargo.toml, package.json, and src-tauri/tauri.conf.json. The FFmpeg sums in manifest.rs must match what tools.yml published. Some strings are matched across languages: failure_error in engine/compress.rs notes that the interface matches its “Compression failed:” prefix in compressionNotice.ts.

A Recommended Reading Order

Reading in dependency order means each step uses only what earlier steps introduced. Figure 3.1 summarizes the order.

In r2dock-core, read app_error.rs, keys.rs, parts.rs, storage.rs, then path_guard.rs, using the tests at the bottom of each file to learn edge cases. Read r2dock-r2 in the order client.rs, error.rs, list.rs, ops.rs, bulk.rs. For the wiring, read src-tauri/src/lib.rs, state.rs, commands/mod.rs, commands/browse.rs, and connections.rs.

The engine is the most demanding step: read model.rs and ctx.rs, then engine/mod.rs from Engine::start through scheduler and run_job, then upload.rs, body.rs, download.rs, and journal.rs; Chapters 5, 6, 9, 10, 13, and 14 accompany it. Then read r2dock-media/src/pipeline.rs with engine/compress.rs, the frontend entry points with src/ipc/commands.ts, and finally the tests as specifications, starting with crates/r2dock-transfer/tests/engine.rs and recovery.rs.

Working on This Code

A rule with no I/O (a key format, a size limit) belongs in r2dock-core with a table or property test. S3 requests belong in r2dock-r2, anything that queues, retries, or persists a transfer in r2dock-transfer, and FFmpeg work in r2dock-media. Code that needs Tauri types belongs in src-tauri and stays thin, and interface work calls Rust only through src/ipc/commands.ts.

Each crate tests on its own: cargo test -p r2dock-core, -p r2dock-secrets, -p r2dock-r2, -p r2dock-media, -p r2dock-transfer, and -p r2dock, plus npm test and npm run typecheck. Some media tests need FFmpeg; on Windows, CI supplies it through R2DOCK_TEST_FFMPEG. The usual pitfalls are the convention links above. engine/mod.rs and connections.rs are already candidates for splitting, so avoid growing them.

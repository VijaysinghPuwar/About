23 Filesystem Security

Downloading looks like the safe direction of a file manager, yet it is where classic desktop vulnerabilities live. R2Dock turns an object key, chosen by whoever wrote the object, into a path on the user’s disk. A key like ../../.bashrc, a planted symbolic link at the destination, or two keys differing only in case can each make a careless program write in the wrong place. This chapter covers the path guard in crates/r2dock-core/src/path_guard.rs, the download code in crates/r2dock-transfer/src/download.rs that uses it, and the upload side, where the danger is reading the wrong file. The network side of downloads belongs to Chapter 10 (Downloads and HTTP Range Requests).

Object Keys Are Untrusted Input

R2 has no folders: a key is one string of up to 1,024 bytes, and R2 stores keys with .. segments, empty segments, leading slashes, colons, backslashes, right-to-left override characters, or Windows device names, from shared buckets, other tools, or an attacker with write access. The OWASP path traversal guidance recommends accepting known good input and not letting the user control the whole path. The guard builds the path itself one validated component at a time, then checks it against the real file system.

The module comment lists the rules, mirroring PLAN.md section 9.6. Figure 23.1 shows how they combine for one download.

Stage One: Turning a Key Into a Relative Path

key_to_relative_path splits the key on /, skips empty and . segments, and pushes each sanitized segment onto a fresh PathBuf. Splitting first defeats absolute paths: /etc/passwd yields an empty segment (dropped), etc, and passwd. Since no sanitized segment contains a separator, PathBuf::push can never replace the whole path, as it does in Rust when given an absolute path. The test absolute_looking_keys_stay_relative also turns C:/Windows/system.ini under Windows rules into a relative path starting with C_. The heart of the stage is sanitize_component.

pub fn sanitize_component(
    segment: &str,
    platform: Platform
) -> Result<String, PathGuardError> {
    if segment == ".." {
        return Err(PathGuardError::Traversal);
    }
    let mut out: String = segment
        .chars()
        .filter(|c| !is_deceptive_char(*c))
        .map(|c| {
            if c.is_control()
                || (platform == Platform::Windows
                    && WINDOWS_INVALID.contains(&c))
            {
                '_'
            } else {
                c
            }
        })
        .collect();

    if platform == Platform::Windows {
        let trimmed_len = out.trim_end_matches(['.', ' ']).len();
        out.truncate(trimmed_len);
        let stem = out.split('.').next().unwrap_or("");
        if is_windows_reserved(stem.trim_end()) {
            out.insert(0, '_');
        }
    }
    // ...

The elided tail rejects an empty or . result (Empty), a result that became .. (Traversal), and a component over MAX_COMPONENT_BYTES (255 bytes) with ComponentTooLong. Each part answers a specific attack.

Traversal. A .. segment is rejected, not dropped; silently saving a/../b as a/b would hide a strange key. The check runs again after filtering, because removing an invisible character between two dots could produce ... The test rejects_traversal covers ../etc/passwd, a/../../b, and similar keys under both rule sets.

Characters the platform cannot store. Control characters become _ everywhere, and on Windows so do the nine characters in WINDOWS_INVALID (<, >, :, ", |, ?, *, \, /), matching Microsoft’s Naming Files, Paths, and Namespaces. The backslash matters because the segment ..\..\x would otherwise become two traversal steps on Windows; it becomes .._.._x. The colon matters because it introduces a drive letter or alternate data stream. On Unix both are ordinary characters; as the property test never_escapes_root says, “Paths are interpreted by the host, so only the host platform’s rules apply.”

Trailing dots, spaces, and device names. Windows silently strips trailing spaces and periods, so the guard trims them there. Microsoft’s guide also reserves device names (CON, PRN, AUX, NUL, COM1 to COM9, LPT1 to LPT9, and superscript digit forms), even “followed immediately by an extension” as in NUL.txt. is_windows_reserved checks the stem before the first dot and the guard prefixes an underscore (_CON), so the download still succeeds. The code also reserves COM0, LPT0, CONIN$, and CONOUT$, an over-match that costs only an underscore; tests include near misses such as COM10 and computer.txt.

Invisible and deceptive characters. report\u{202E}fdp.exe displays as reportexe.pdf in many file managers, because U+202E (RIGHT-TO-LEFT OVERRIDE) reverses what follows. is_deceptive_char in crates/r2dock-core/src/keys.rs matches zero-width characters, directional marks, bidirectional embeddings, overrides, and isolates, invisible operators, the byte order mark, and the soft hyphen. The guard removes them, the interface’s display_name shows them as placeholders such as ⟨U+202E⟩, and strips_bidi_and_replaces_controls checks the example becomes reportfdp.exe.

Lossy Mapping and the Traversal Exception

One odd key should not fail a folder download, so key_to_relative_path_lossy replaces an unsanitizable segment with _ and shortens overlong ones on a UTF-8 boundary. The planner in src-tauri/src/planning.rs falls back to it, except for Traversal, where it keeps the raw path “so the job fails in the path guard and the user sees why”: ensure_dir_under_root rejects the ParentDir component and the job fails with “The name contains”..” and cannot be saved safely”. Tests traversal_keys_keep_raw_path_so_the_job_fails_safely and lossy_never_escapes_root cover both paths.

Stage Two: Walking the Real File System

A clean string can still lead outside the root if a folder along the way is a symbolic link, so stage two walks the destination one component at a time without following links.

Source: crates/r2dock-core/src/path_guard.rs, lines 180 to 194

pub fn ensure_dir_under_root(
    root: &Path,
    rel_dir: &Path
) -> Result<PathBuf, PathGuardError> {
    let root = root.canonicalize()?;
    if !root.is_dir() {
        return Err(PathGuardError::NotADirectory);
    }
    let mut current = root.clone();
    for component in rel_dir.components() {
        let Component::Normal(name) = component else {
            return Err(PathGuardError::Traversal);
        };
        current.push(name);
        match std::fs::symlink_metadata(&current) {
            Ok(meta) if meta.file_type().is_symlink() =>
                return Err(PathGuardError::SymlinkInPath),
            Ok(meta) if !meta.is_dir() =>
                return Err(PathGuardError::NotADirectory),
            Ok(_) => {}
            // ...

Canonicalizing the root resolves links in the user’s chosen folder itself, which is correct: the user picked it. Below the root, symlink_metadata reports on a link rather than its target, so a linked component fails with SymlinkInPath and a file in the way of a folder with NotADirectory. The tests refuses_symlinked_directory (which also checks nothing was written at the link’s target) and file_in_the_way_of_folder cover both.

The elided remainder creates missing folders with std::fs::create_dir and defends against time-of-check to time-of-use (TOCTOU) races, where something changes between a check and an action. If create_dir fails with AlreadyExists, something appeared after the check, possibly a planted link, so the entry is inspected again and a link or file is refused. The function finally confirms the path still starts with the canonical root. resolve_file_under_root then refuses a target name that already exists as a link or directory (refuses_symlinked_target_file), since writing through a link at the target would overwrite whatever it points to.

Stage Three: Writing and Placing

The download writes to a hidden temporary file beside the target, named by temp_path_for from a dot, the name, eight hex digits of the job ID, and .r2dock-part. An existing temporary path that is not a regular file is refused, and open_temp sets O_NOFOLLOW on Unix, so the operating system refuses to open a final component that is a link. That flag covers only the last component, which is why the folder walk is still needed. On Windows the audited code sets no equivalent flag on this open, so a link planted at the temporary name between the check and the open would be followed; the window is short and needs write access to the folder, but it is a platform difference.

When the data is complete and verified, revalidate re-runs resolve_file_under_root, and resumed jobs revalidate saved state the same way, discarding a partial file if a folder in its path became a link. Then place enforces the conflict policy from crates/r2dock-core/src/policy.rs: Ask by default, or Skip, Replace, or KeepBoth.

Every policy except Replace uses persist_noclobber, whose documentation says: “If a file exists at the target path, fail.” Check and move are one file system operation, so no other program can slip a file in between. Skip and Ask stop at an existing file; KeepBoth tries name (1).ext, name (2).ext, and so on up to KEEP_BOTH_LIMIT (1,000), each attempt no-clobber. It cannot cross file systems, which never happens here because the temporary file shares the target’s folder. Only Replace overwrites, and earlier lines of place still refuse a target that is a link or directory before std::fs::rename. The test place_never_overwrites_without_replace checks contents under Skip, KeepBoth, and Replace.

Collisions Between Two Remote Names

Two harmless keys can also map to one local file: Cover.jpg and cover.jpg on default APFS and NTFS volumes; é as one code point (U+00E9) or as e plus a combining accent, which Unicode Standard Annex 15 calls canonically equivalent (composed form NFC, decomposed form NFD); or a:b and a_b after Windows sanitizing. Under Replace, the second download would silently replace the first.

R2Dock detects this at planning time with collision_key in path_guard.rs, which normalizes a path to NFC and, when CASE_INSENSITIVE_BY_DEFAULT is true (Windows and macOS), decomposes, lowercases, and recomposes it first. The key never touches disk or object keys. rename_collisions in src-tauri/src/planning.rs gives any later item with a taken key a “Keep both” name, so the downloads land as cover.jpg and cover (1).jpg. The tests collision_keys_match_equivalent_names and the property test collision_key_ignores_normalization_form cover this.

The comparison is a heuristic. Folding may add an unneeded suffix on case-sensitive volumes, which the code accepts, and to_lowercase is not full case folding, so rare pairs (for example with the German sharp s) may reach place, where only Replace would lose data. Collisions with files already on disk are handled at placement. Uploads convert each component to NFC in key_from_components, so a folder uploaded from macOS gets the same keys as one from Windows.

The Upload Side: Reading the Right File

Uploads can read the wrong file. If photos/a.jpg is replaced by a link to ~/.ssh/id_ed25519 after the scan, a naive uploader would publish the private key; PLAN.md section 9.6 calls this a “swap-after-scan race”. The scanner in crates/r2dock-transfer/src/scan.rs walks with follow_links(false) and reports links as “Shortcut (symbolic link)”, and every open for upload goes through one function.

Source: crates/r2dock-transfer/src/source.rs, lines 42 to 58

fn open_nofollow(path: &Path) -> std::io::Result<File> {
    let mut opts = OpenOptions::new();
    opts.read(true);
    #[cfg(unix)]
    {
        use std::os::unix::fs::OpenOptionsExt;
        opts.custom_flags(libc::O_NOFOLLOW);
    }
    #[cfg(windows)]
    {
        use std::os::windows::fs::OpenOptionsExt;
        // ...
        const FILE_FLAG_OPEN_REPARSE_POINT: u32 = 0x0020_0000;
        opts.custom_flags(FILE_FLAG_OPEN_REPARSE_POINT);
    }
    opts.open(path)
}

On Unix a link fails with ELOOP, which map_open_error reports as “This is a shortcut (symbolic link), so it was skipped.” On Windows the flag opens “a link itself instead of its target”, per the elided comment, and SourceFile::open refuses anything that is a link or not a regular file.

The second layer is identity. At scan time R2Dock records a FileIdentity (device and inode on Unix); a swapped file has a different inode even with the same name, size, and time. SourceFile::open compares it and fails with “file changed” on a mismatch, then keeps a same_file::Handle that reopen, used for every multipart part and retry, compares again. With the size and time check in ensure_unchanged, a file replaced during a long upload is detected rather than uploaded. On Windows FileIdentity::of returns None, so the scan-time check is skipped, but the handle comparison still applies.

What the Guard Does Not Do

Several PLAN.md section 9.6 items are not implemented. Downloads get neither the macOS quarantine attribute nor the Windows Mark of the Web, so the usual warnings on opening a downloaded program do not appear; R2Dock itself never opens files. Total path length is not limited, only components; an overlong path fails with an I/O error, which is safe. And the guard defends against hostile names, not a hostile local user, so the TOCTOU defenses matter mainly for shared or synchronized folders.

Working on This Code

Key-to-name rules live in crates/r2dock-core/src/path_guard.rs and, for character classes, keys.rs; placement in download.rs (resolve_target, open_temp, place); planning and collision renaming in src-tauri/src/planning.rs; upload checks in source.rs and scan.rs. Run cargo test -p r2dock-core for the guard’s table and property tests, cargo test -p r2dock-transfer for placement, identity, and scanning (several Unix only, since they create links), and cargo test -p r2dock for planning. CI runs on Windows, macOS, and Linux, which matters because Windows rules only apply on Windows.

Every key-to-path mapping goes through the guard, never PathBuf::from(key) or join on a raw key; every write below the root goes through resolve_file_under_root; no write follows a link below the root; and nothing is overwritten unless the policy is Replace. New writers should use a temporary file beside the target and persist_noclobber. Pitfalls: std::fs::metadata or Path::exists, which follow links (the download code has exists_no_follow), and “fixing” a traversal key by dropping ...

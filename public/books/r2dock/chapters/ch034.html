25 Threat Modeling and Remaining Risks

The four previous chapters described individual defenses: credential storage, the Tauri boundary, the path guard, and the preview scheme. A list of defenses is not a security argument. The argument comes from asking what is worth protecting, who can attack it, through which doors, and what still gets through. This chapter builds that model from the audited code, compares it with the threat model in PLAN.md section 9.8, and states plainly where the two disagree and which risks remain.

Scope, Assets, and Attackers

SECURITY.md defines the scope. In scope are leaks of secrets, path traversal or overwrite through object keys, the webview gaining access it should not have, and unsafe rendering of names or previews. Out of scope are “a compromised operating system or user account, malware running as the same user, and issues in Cloudflare R2 itself”. No user-space design can defend against a program running as the same user. PLAN.md section 9.8 says of the store: “Malware running as the same user can usually query the store or memory. Not defended.”

The most valuable asset is the R2 secret access key with its access key ID: together they grant read, overwrite, and delete on everything the key reaches, from anywhere. The optional Cloudflare API token is a second credential; R2Dock needs only read access to bucket domain settings. PLAN.md says the form recommends a read-only token, but the audited Connect form’s helper text does not mention read-only access, so that advice lives only in the plan. The other assets are bucket data (R2 has no trash or versioning, so a delete is final), the user’s local files, privacy (account IDs, bucket names, keys, and local paths stay out of logs and exports), and the app’s availability against memory or disk exhaustion.

The five trust boundaries are the webview to Rust core (Chapter 22, Tauri Security Architecture), the core to the network (R2, the Cloudflare REST API, GitHub for FFmpeg), the core to the local file system, the core to FFmpeg as a child process (Chapter 17, How FFmpeg Integrates with Rust), and the operating system credential store. The attackers are a bucket content author who chooses keys, bytes, and metadata (the most realistic, since buckets are shared and filled by other tools); a network attacker; a local co-tenant or sync client with write access to the download folder; and a supply chain attacker. A compromised webview is not a separate attacker but an escalation: a content author who found a script injection could call R2Dock’s commands.

Entry Points and Their Defenses

The table below lists each entry point, who controls it, and its main defense; the subsections explain each.

Object bytes in previews Content author Media scheme limits, type allowlist
Object bytes in downloads Content author No-clobber placement, no auto-open

Object Keys and Bytes

Names are rendered as React text nodes; the audited src/ has no dangerouslySetInnerHTML. Invisible and bidirectional control characters become visible placeholders through display_name in crates/r2dock-core/src/keys.rs. Every key-to-path mapping goes through the path guard (Chapter 23, Filesystem Security). In the activity log, the CSV writer in src-tauri/src/activity/csv.rs neutralizes formula-like cells (test formula_injection_is_neutralized) and writes names as short hashes unless the user opts in. The residual risk is heuristic: the collision check uses Unicode normalization and lowercase mapping, which may miss rare case-folding pairs, and under the Replace policy such a pair leaves one file instead of two.

Preview bytes pass through the defenses of Chapter 24 (The Custom Media Preview Protocol). Text previews come from preview_text, which reads at most 1 MiB (TEXT_PREVIEW_BYTES) and is shown as text in a <pre>. What remains is the browser engine’s own image and audio decoders parsing hostile bytes; R2Dock relies on the operating system to patch its webview, a choice the Tauri security overview defends because platform maintainers patch faster. Downloaded bytes are written to disk and never opened. PLAN.md section 9.6 plans to apply the platform download marker (the macOS quarantine attribute and the Windows Mark of the Web), but the audited code does not, so a hostile executable downloaded through R2Dock carries no operating system warning.

What a Compromised Webview Can Do

If an attacker ran script in the webview, the IPC boundary is what remains. The capability allows 56 application commands and five core permissions, no plugins, and no command accepts a local path. PLAN.md section 9.8 says such an attacker “could still delete one object per call within confirmation rules”. The code allows more. Deletes take two steps: delete_preview enumerates the objects and stores a pending delete under a single-use token, and delete_execute performs it. The preview’s return value is the key detail.

Source: src-tauri/src/commands/manage.rs, lines 73 to 80

    Ok(DeletePreview {
        token,
        objects: count,
        bytes,
        needs_typed,
        typed_phrase: phrase,
        sample,
    })

The token and the typed confirmation phrase both go to the page, because the page must show the phrase. Page code can therefore read the phrase and send it back. check_sources refuses an empty prefix, but any non-empty prefix is allowed, and a loop over a listing’s prefixes would reach most of a bucket. The token defends against interface mistakes, double clicks, and stale dialogs; it cannot defend against a compromised page without a confirmation step outside the webview.

Such an attacker could also read any object through preview_text, media_token, or a download into the configured folder; open any https:// URL through open_external; write up to 1 MiB to the clipboard; and set the conflict policy to Replace. They could not read the secret, read local files beyond what the user selected in the last 15 minutes, or choose where files are written. The honest residual risk is “a compromised webview can read and delete bucket data”, not “one object per call”.

Local Races, Network, and Supply Chain

A co-tenant can plant symbolic links or files in the download folder. The path guard checks each folder below the root without following links, re-checks just before placement, and places with persist_noclobber; on Unix the temporary file is opened with O_NOFOLLOW. The remaining windows are narrow: Windows opens the temporary file without a no-follow flag, and a folder could be swapped between the final check and the rename.

R2Dock connects only over HTTPS. The S3 client uses the AWS SDK’s default HTTPS client (the default-https-client feature in the workspace Cargo.toml), and the Cloudflare client in crates/r2dock-r2/src/cfapi.rs builds reqwest with redirects disabled and with https_only whenever its base URL is an https:// address (always, outside local tests), capping bodies at 1 MiB and validating domain names (Chapter 12, Public URLs and Cloudflare REST API Integration). No code uses danger_accept_invalid_certs. As PLAN.md states, an organization root certificate for traffic inspection can still read traffic, and a domain the account owner configured is trusted as theirs.

FFmpeg is downloaded from a pinned release and checked against SHA-256 sums compiled into the app, with redirects limited to GitHub hosts and binaries re-hashed when size or modification time changes (Chapter 17). What remains is an FFmpeg decoder vulnerability, running with the user’s privileges, and the integrity of the R2Dock build itself.

Code Compared With PLAN.md Section 9.8

Most rows match the code. The differences below were found while auditing commit 2bdc8a6. None is a demonstrated exploitable vulnerability within scope, but several are places where documentation promises more than the code delivers.

The “Updates” row describes Tauri updater signature verification. The code has no updater plugin in src-tauri/Cargo.toml, and .github/workflows/release.yml publishes what its release notes call an “Unsigned preview build” with a SHA256SUMS.txt file. Published beside the installers, that file catches corruption but not a compromised release, so the real risk is the integrity of the GitHub account and release process, plus users learning to click through unsigned-app warnings. The “IPC” row understates the delete exposure, as shown above.

PLAN.md section 9.2 says types holding secrets do not implement Debug without redaction, yet ConnectionInput in src-tauri/src/dto.rs derives Debug with the secret and API token as plain strings. Nothing formats it today, but the type does not enforce the rule. The same section says the secret is cleared from React state “immediately after the call”; the code clears it after a successful save and keeps it after a failure so the user can retry (Chapter 21, Credential Storage and Authentication).

Section 9.4 lists dialog, notification, clipboard, opener, and updater permissions; the code grants the page no plugin permissions, which is stricter. Conversely, it grants core:app:allow-version, core:window:allow-is-focused, and core:path:default, which the frontend does not appear to use; the last lets page code resolve paths such as the home folder. Section 9.6 plans download markers and marks Windows long paths “[Verify]”; neither is implemented. Range handling (9.5) and SVG scripts in <img> (9.4) remain “[Verify]” with no real-webview test. Section 9.7 describes log rotation as “5 files, 5 MB each”; the code rotates daily and keeps five files with no size limit.

Two observations are absent from the plan. Values loaded from connections.json are not re-validated, including the account ID that becomes part of the endpoint host; editing that file needs the user’s own privileges, but re-validation would be cheap defense in depth. And style-src 'unsafe-inline', which the plan says to “try to remove”, is still present.

Remaining Risks, Ranked

The highest risk is the user’s own key management. R2Dock cannot enforce least privilege; the Connect form advises a bucket-scoped token, but a broad key stolen from anywhere gives full access until revoked in the Cloudflare dashboard, and deleting a connection in R2Dock does not revoke it.

Second is a webview compromise through a decoder vulnerability in the browser engine, reached by previewing a hostile object. Its impact includes reading and deleting bucket data, but not reading the secret or arbitrary local files.

Third is an FFmpeg decoder vulnerability during optional compression. Compression is off by default and runs only on selected files, but the process is not sandboxed. Fourth are the narrow download folder races and the missing download markers. Lowest are log leaks: the redaction filter, typed errors, and hashed activity names make them unlikely, leaving mainly future code printing a secret in a form the pattern filter does not recognize.

Possible future improvements, not committed plans, follow from these gaps: a native Rust confirmation dialog for bulk deletes, a redacting Debug for ConnectionInput, removing unused core permissions, download markers, re-validating configuration on load, signed releases with a verifying updater, and a real-webview test for ranges and SVG.

Working on This Code

The project rule is that a change affecting the threat model updates PLAN.md section 9.8 in the same change. When you add a command, write in the pull request what a compromised page could do with it. When remote data gains a new route to disk, the webview, or a child process, add a row and route it through the existing defenses: the path guard, the preview scheme, text rendering, and AppError.

The tests that guard the model live in crates/r2dock-core/src/path_guard.rs, crates/r2dock-core/src/redact.rs, src-tauri/src/logging.rs, src-tauri/src/connections/tests.rs, src-tauri/src/media.rs, and src-tauri/src/activity/csv.rs; cargo test --workspace runs them, as continuous integration does on all three platforms. CI also runs cargo audit and npm audit --omit=dev. PLAN.md mentions cargo deny, but there is no deny.toml and no workflow runs it.

The invariants: secrets never cross back over IPC; local paths come only from Rust pickers and drag and drop; remote content is never rendered as HTML; the CSP never gains unsafe-eval, remote scripts, or a broad connect-src; every fan-out is bounded; nothing is overwritten or deleted without policy or confirmation. Weakening any of these needs an ADR. Report vulnerabilities privately through the repository’s Security tab, as SECURITY.md describes.

27 Frontend State Management

Most of R2Dock’s truth is not in the user interface: listings live in R2, credentials in the credential store, and transfer state in the Rust engine. The React code is a view onto these sources, so its state management is mostly about keeping copies honest. Chapter 26 (React and Tauri IPC) covered how data crosses the boundary; Chapter 28 (UI Performance and Large Queues) covers how the transfer stream is applied quickly.

Four Kinds of State

Server state has its truth outside the webview and is fetched on demand: listings, object details, buckets, connections, settings, transfer history, compression tool status. The frontend holds a cache that can be stale. UI state exists only because someone is looking at the screen: the open folder, the selection, open dialogs, the search text; losing it on restart is acceptable. The transfer queue is a streamed read model: PLAN.md section 6.6 says “Transfer state is owned by Rust. The frontend holds a read model updated from a progress channel.” It changes too often to fetch, so the frontend keeps a projection rebuilt from a snapshot and patched by events. Finally, component-local state should not outlive one component; the main example is the secret in the Connect form’s useState.

PLAN.md section 6.6 assigns “TanStack Query for IPC-backed server state (listings, details) with caching and invalidation after uploads and deletes,” “Zustand (tiny) for UI state,” and “No Redux, no global event bus.” Architecture decision record (ADR) 0004 confirms it. Figure 27.1 shows the resulting ownership map.

The frontend never edits a cached listing to pretend an upload happened; it waits for Rust or overlays a clearly marked temporary row.

TanStack Query as the Cache of Rust Answers

TanStack Query is a cache keyed by arrays whose entries know how to fetch themselves and whether they are stale. R2Dock creates one QueryClient in src/app/App.tsx with this factory.

Source: src/app/queries.ts, lines 18 to 29

export function createQueryClient(): QueryClient {
  return new QueryClient({
    defaultOptions: {
      queries: {
        retry: false,
        refetchOnWindowFocus: false,
        staleTime: 30_000,
      },
      mutations: { retry: false },
    },
  });
}

Each setting overrides a default that the important defaults page documents: data is stale immediately, stale queries refetch when “The window is refocused,” and failures are “silently retried 3 times, with exponential backoff delay”. Retries are off because the Rust client already classifies errors and backs off (Chapter 16, Retries, Cancellation, and Idempotency); a second loop in JavaScript would multiply attempts against a server that may be rate limiting and delay messages such as “The keys for this connection no longer work.” Focus refetching is off because every listing refetch is a ListObjectsV2 call, which PLAN.md section 8.3 says R2 bills as a Class A operation (a claim the plan marks [Verify]), and because a list that reloads on focus can reorder under the cursor. The cost is that changes by other tools need a manual refresh.

Some queries override the 30 second default: appInfo and settings use Infinity, connections 60 seconds, buckets 5 minutes, and media tokens 4 minutes. Settings never go stale because every settings command returns the new SettingsView for setQueryData. Folder sizes (prefixSize) use enabled: false: the query is only a cache slot, filled when the user presses Calculate, because sizing a folder lists every object under it. useConnections is the one place the frontend polls: refetchInterval returns 5 seconds while any connection is unknown or offline, and false otherwise. connection_list reads in-memory state in Rust with no network request, so the poll only asks what Rust learned from other traffic. PLAN.md section 14 lists “no polling” as a strategy; this is a small, commented exception.

Query Keys as a Hierarchy

The query keys guide says a key “should include every variable the query function uses that can change.” R2Dock defines every key in one object, qk, in src/app/queries.ts. Keys follow [kind, connectionId, bucket, prefix or key], so a shorter key is a prefix of every longer key in its family, and the invalidation guide matches “multiple queries by their prefix.” qk.objectsBucket invalidates every listing in a bucket; qk.objectsAll every listing of a connection, which ConnectDialog uses after keys are edited. Putting connectionId before the bucket is a correctness decision: two accounts can each have a bucket named media-library, and without the connection in the key one account’s listing could appear under the other.

Optimistic Preferences

The one useMutation is for preferences, where a toggle must apply instantly while the save happens in the background and may fail.

Source: src/app/queries.ts, lines 138 to 166

/** Change one or more preferences. Applies immediately, then saves. */
export function useUpdatePreferences() {
  const client = useQueryClient();
  const mutation = useMutation({
    mutationFn: (prefs: Preferences) => settingsSet(prefs),
    onMutate: async (prefs) => {
      const change = ++preferenceChanges;
      await client.cancelQueries({ queryKey: qk.settings });
      const previous = client.getQueryData<SettingsView>(qk.settings);
      if (previous) client.setQueryData<SettingsView>(qk.settings,
        { ...previous, preferences: prefs });
      return { previous, change };
    },
    onError: (err, _prefs, ctx) => {
      toast.danger(errorMessage(err));
      // A newer change is on its way and carries the full preferences.
      if (ctx?.change !== preferenceChanges) return;
      if (ctx.previous) client.setQueryData(qk.settings, ctx.previous);
      void client.invalidateQueries({ queryKey: qk.settings });
    },
    onSuccess: (view, _prefs, ctx) => {
      // A late reply to an older change must not undo a newer one.
      if (ctx.change === preferenceChanges)
        client.setQueryData(qk.settings, view);
    },
  });
  // ...
}

The shape follows the optimistic updates guide: cancel in-flight fetches, snapshot, write, roll back on error. R2Dock adds the counter preferenceChanges. If a user moves concurrency from 3 to 4 and quickly to 6, two settings_set calls are in flight; writing the late reply to the first would flip the slider back to 4 while disk ends at 6. Older replies are therefore ignored, and older failures do not roll back, because each call sends the complete Preferences. The tests “ignores a late reply to an older change” and “a failed older change does not roll back a newer one” in src/app/queries.test.tsx reproduce both orderings.

Here the code and PLAN.md disagree. Section 6.6 lists “theme” as Zustand UI state, and section 10 says theme and density live in “Zustand, persisted via settings commands.” The code keeps all preferences in the settings query; the comment on useUiStore says “Preferences live in the settings query.” One copy cannot disagree with itself after a failed save. The plan has not been updated.

Invalidation After Changes

Uploads are the hardest case: they complete one by one, sometimes thousands in a burst, and each changes a listing, search results, details, previews, and the size of every ancestor folder. invalidateObjectChanges handles a batch.

Source: src/app/objectChanges.ts, lines 55 to 66

export function invalidateObjectChanges(client: QueryClient,
  changes: Iterable<ObjectChange>): void {
  for (const g of group(changes).values()) {
    void client.invalidateQueries({
      queryKey: qk.objectsBucket(g.connectionId, g.bucket) });
    void client.invalidateQueries({
      queryKey: ["search", g.connectionId, g.bucket] });
    void client.invalidateQueries({
      predicate: (q) => OBJECT_KINDS.has(String(q.queryKey[0]))
        && inBucket(q, g) && g.keys.has(String(q.queryKey[3])),
    });
    void client.resetQueries({
      predicate: (q) => q.queryKey[0] === "prefixSize" && inBucket(q, g)
        && g.prefixes.has(String(q.queryKey[3])),
    });
  }
}

Changes are grouped by bucket with their keys and ancestor prefixes, so the number of cache operations per bucket is fixed. Listings and search are invalidated by prefix; per-object views (head, text, media) by a predicate that touches only changed keys. Folder sizes are reset, not invalidated. The QueryClient reference says invalidateQueries “Marks queries matching the given filters as invalidated” (refetching only active ones), while resetQueries returns them “back to their initial state”. For a disabled size query a reset empties it, so the Details panel shows Calculate again instead of a wrong number. The transfer subscription calls this once per burst with an 800 millisecond debounce (Chapter 28); the test “refreshes every view of an uploaded object once the burst settles” in subscription.test.ts checks that unrelated keys, accounts, and sibling folder sizes are left alone.

Deletes and moves invalidate more coarsely. DeleteFlow.tsx invalidates the bucket’s listings, search, and sizes after deleteExecute resolves. runMove in src/features/manage/moveRunner.ts also invalidates every head entry, inside finally, because an R2 move is copy then delete and can leave objects in both places (Chapter 11, Object Management and Consistency). DeleteFlow invalidates only on success; the code does not show whether a rejected delete can have removed some objects first, so check delete_execute_inner before assuming nothing changed.

The explicit refresh, refreshCurrentView in src/app/refresh.ts, resets the open folder’s listing and search rather than invalidating them. The infinite queries guide explains that a stale infinite query refetches every loaded page in sequence; after scrolling ten pages, invalidation would cost ten requests, a reset costs one. useGlobalShortcuts.ts intercepts F5 and Ctrl or Command with R so the page itself never reloads and wipes every store. Switching connections clears selection and resets navigation; the old account’s cache entries stay under their own key until garbage collected.

Zustand for State Without a Server

The Zustand README sums up its model: “Your store is a hook!” and “Select your state and the component will re-render on changes.” Code outside React reads “non-reactive fresh state” with getState(). R2Dock has about ten small stores beside the features that use them; the main ones are below.

Store File Holds
useNavStore src/app/navStore.ts View, bucket, prefix, history stacks
useUiStore src/app/uiStore.ts Sidebar, panels, dock, dialogs
useBrowserStore browser/browserStore.ts Selection, focus, search, sort
useTransferStore transfers/transferStore.ts Transfer read model
usePendingStore transfers/pendingStore.ts Cancel or pause clicks awaiting the engine

Smaller ones are useToastStore, useUploadStore, usePreviewStore, useOpsStore, and useDragStore. Navigation is a store rather than a router because non-React code (a toast’s “Show” action, the drop handler) also changes location. navigate caps the back stack at 100 (HISTORY_LIMIT), clears the forward stack, and ignores navigation to the current location. PLAN.md section 11 describes history as “(connection, bucket, prefix)”, but Location holds view, bucket, and prefix; the code compensates by calling reset on every connection switch, so history never leads into another account’s bucket. Components subscribe with narrow selectors; event handlers read with getState(), so the keyboard handler’s Effect is installed once and still sees current values.

The Transfer Read Model and Pending Intent

The transfer queue arrives as a push stream, which fits a store with a pure reducer better than a fetch-oriented cache. TransferState in src/features/transfers/transferStore.ts holds jobs by id, an order array, a seen flag, and the last authFailed connection; Chapter 28 dissects the reducer. The ownership rules are what matter here: a snapshot replaces everything, added and updated replace whole job snapshots, progress touches only byte counts and rates, and the frontend never invents a job state.

The one deliberate exception lives in a separate store. Stopping a transfer can take seconds. usePendingStore records the click so the row shows “Cancelling…” at once, and settlePending clears it only when the engine reports a state outside the moving set; a job going from running to verifying keeps its pending cancel. The marker states intent, never a claim about the engine.

Ghost Rows: Joining Two Sources

When a user uploads into the open folder, the files should appear at once with progress, though R2 will not list them until they finish. useExplorerData joins the query cache and the transfer store.

Source: src/features/browser/useExplorerData.ts, lines 54 to 70

  const jobs = useTransferStore((s) => s.jobs);
  const order = useTransferStore((s) => s.order);
  const listedAt = listing.dataUpdatedAt;
  const ghosts: GhostRow[] = useMemo(() => {
    if (bucketSearch || term) return [];
    const listedKeys = new Set(listed.map((r) => r.id));
    const out: GhostRow[] = [];
    for (const id of order) {
      const j = jobs[id];
      if (!j || j.direction !== "upload" || j.connectionId !== connectionId
        || j.bucket !== bucket) continue;
      if (parentPrefix(j.key) !== prefix || listedKeys.has(j.key)) continue;
      const done = j.state === "completed" && j.finishedAt !== null
        && Date.parse(j.finishedAt) >= listedAt;
      if (isTerminal(j.state) && !done) continue;
      // ... push { kind: "ghost", ... }
    }
    return out;
  }, [jobs, order, listed, listedAt, connectionId, bucket, prefix,
    bucketSearch, term]);

The subtle line is done. Between completion and the debounced refetch, the object exists in R2 but not in the cached list; dropping the ghost at completion would make the file vanish and reappear. So a completed upload keeps its ghost, marked “Uploaded”, if it finished after the listing loaded (dataUpdatedAt), and listedKeys.has(j.key) removes it once the refetched list contains the key. The tests “keeps a finished upload visible until the listing refresh shows it” and “does not show uploads that finished before the listing loaded” cover both paths. One hidden assumption: finishedAt comes from the Rust clock and dataUpdatedAt from the webview’s, which is sound only because both run on the same machine.

Ordering races appear elsewhere too: showInBucket serializes requests through a promise chain and checks request !== latest after every await, so a slow account switch from an older click cannot navigate last. It uses fetchQuery, which the current TanStack reference marks deprecated; this book did not verify whether that applies to the locked 5.104.3 release.

On failure these choices behave predictably: an unreachable R2 fails queries at once with code network; a webview reload loses every store, but listings refetch and the transfer store rebuilds from a new snapshot.

Working on This Code

Add new keys to qk in the [kind, connectionId, bucket, rest] shape so prefix invalidations cover them, and choose staleTime deliberately: anything costing R2 operations should not refetch on its own. For operations that change many objects, reuse invalidateObjectChanges. Prefer resetQueries when stale data would mislead or refetching every page would waste requests.

Never put secrets in a store or the query cache. Never write a job state the engine did not send; intent goes in usePendingStore. Preferences live in the settings query. Tests include src/app/queries.test.tsx, src/features/transfers/subscription.test.ts, transferStore.test.ts, useExplorerData.test.tsx, refresh.test.ts, and showInBucket.test.ts; run them with npm test or one file with npx vitest run src/app/queries.test.tsx. In tests, use testQueryClient() from src/test/utils.tsx (with gcTime: Infinity), not the app’s factory.

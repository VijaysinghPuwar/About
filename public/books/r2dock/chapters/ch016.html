10 Downloads and HTTP Range Requests

A download looks easy: one GetObject request, written to a file. But the connection can drop after 30 GB of a 40 GB file, the object can be replaced while a paused download waits overnight, the app can be killed just before the file is moved into place, and a file with the same name can appear in the destination at any moment. A careful download never leaves a corrupted file where the user expects a good one and never overwrites a file without permission. This chapter follows crates/r2dock-transfer/src/download.rs: the hidden partial file, resuming with Range and If-Match, validating and verifying the data, and the ordered finalization. Chapter 15 (Crash Consistency and Recovery) builds the full failure matrix on it.

Network Success Is Not Completion

Receiving the last byte is not finishing. The bytes must reach the disk, match the promised count and, where possible, the object’s checksum; the file must move to its final name without replacing someone else’s file; and the app must record enough to explain a crash at any point. Only then does the job report Completed, after passing through Preparing, Running, and Verifying (Chapter 13, Transfer State Machines).

The Partial File

Bytes never go directly into the destination. temp_path_for names a temporary file in the same folder: for report.pdf and a job identifier beginning 0123abcd, it is .report.pdf.0123abcd.r2dock-part, as the test temp_name_is_hidden_unique_and_beside_target checks. The dot hides it, the job tag makes it unique per job, and the name is truncated if needed to fit the path guard’s per-component limit. PLAN.md section 8.5 describes the name as .<name>.r2dock-part; the job tag was added after the plan was written.

The partial file lives beside its target because a rename is atomic only within one file system; a move from /tmp to an external drive would be a copy that a crash could truncate.

open_temp opens the partial file with write and create. With keep of zero it truncates; with a positive keep it cuts the file to exactly that length and seeks to the end, so new data continues after the trusted prefix. On Unix it adds O_NOFOLLOW, so a temporary path replaced by a symbolic link cannot redirect the download into another file, and run already refuses a temporary path that exists but is not a regular file.

Starting or Resuming

For a new download, resolve_target asks the path guard (resolve_file_under_root) to map the destination root and the key-derived relative path into a path that cannot escape the root, then checks without following links whether something exists there. Replace uses the path; Skip ends as Skipped; Ask ends as NeedsDecision; Keep both tries name (1).ext and onward, up to 1,000 names. conflict_policies_for_downloads covers these, and traversal_keys_never_escape_destination checks that a key trying to climb out of the destination fails without writing outside it. Before any request, fs4::available_space turns a too-small volume into a DiskFull error. The check is advisory.

A job that ran before has a saved DownloadState (crates/r2dock-transfer/src/ctx.rs): the entity tag (ETag) from the first response, the temporary path, the final path, and an optional finalization record. The saved temporary path is trusted only if it equals what temp_path_for computes for this job and the final path still passes the path guard; otherwise, for example if a folder was replaced by a symbolic link while the app was closed, the partial file is removed (after confirming its folder is still the validated one) and the job starts over.

The resume offset is the partial file’s length minus RESUME_BACKOFF, 1 MiB. Its doc comment explains: “After a crash or power loss the file can be longer than the data that reached the disk (the tail reads as zeros), so the last stretch is fetched again.” The margin is a heuristic: the code does not show how 1 MiB was chosen, and an operating system can cache more than that, so zeros further back are possible. The MD5 check below would catch that for single part objects; for multipart objects it is a residual risk. The offset is also discarded if no ETag was saved or it exceeds the expected size.

HTTP Range and If-Match

RFC 9110 defines both mechanisms. Range: bytes=1048576- asks for “the remainder of the representation” from that byte (section 14.1.2); success is 206 Partial Content with a header such as Content-Range: bytes 42-1233/1234. If-Match asks the server to proceed only if the representation still has the given ETag, which the server “MUST” compare strongly (section 13.1.1), answering 412 (Precondition Failed) otherwise. Without If-Match, resuming after the object was replaced would yield a file that is half old and half new. The R2 S3 API compatibility page lists Range and If-Match for GetObject, and PLAN.md section 8.5 marks conditional GET as confirmed.

Source: crates/r2dock-transfer/src/download.rs, lines 229 to 261

// ...
let mut response = None;
for _ in 0..2 {
    let mut req = ctx
        .client
        .sdk()
        .get_object()
        .bucket(&spec.bucket)
        .key(&spec.key);
    if offset > 0 {
        req = req.range(format!("bytes={offset}-"));
        if let Some(e) = &etag {
            req = req.if_match(e);
        }
    }
    let sent = tokio::select! {
        () = ctx.control.cancel.cancelled() => return stopped(ctx, &temp),
        r = req.send() => r.map_err(R2Error::from_sdk),
    };
    match sent {
        Ok(out) => {
            response = Some(out);
            break;
        }
        Err(R2Error::PreconditionFailed { .. })
        | Err(R2Error::Service { status: 416, .. })
            if offset > 0 =>
        {
            offset = 0;
            etag = None;
        }
        Err(e) => return Err(e.into()),
    }
}

A 412 means the object changed; a 416 (Range Not Satisfiable) means the offset no longer fits, most likely because the object shrank. Either way the loop forgets the offset and ETag and tries once from byte zero. The 416 is matched as Service { status: 416, .. } because Chapter 8 (The S3-Compatible Protocol) maps that status to the catch-all variant. The loop runs at most twice; any other error goes to the engine’s retry policy (Chapter 16, Retries, Cancellation, and Idempotency). The ETag in If-Match is the one from the first response, not from a separate HeadObject, so the version is pinned by the response whose bytes are already on disk.

Validating the response

RFC 9110 section 14.2 says “A server MAY ignore the Range header field.” A server or proxy that does so replies 200 OK with the whole object, and appending it would duplicate the start of the file. So if a resumed response lacks a Content-Range starting exactly at bytes {offset}-, the code sets the offset to zero and open_temp truncates before writing. The check reads only the first byte position; the expected total is the offset plus Content-Length, which agrees with the full range for an open-ended request. Only after a valid response does the job reset or reopen the partial file and then save a DownloadState with the new ETag, so the saved state always describes the file actually on disk.

Streaming and Verifying

The body is consumed chunk by chunk, each read raced against cancellation and written with write_all; the committed count updates after every write, so throttled progress (Chapter 6, The Transfer Scheduler) reflects bytes written, not merely received. The body is never collected, so memory is bounded by a chunk. A body error, such as a reset or the 60 second stall guard of the AWS software development kit (SDK) (Chapter 8), flushes the file and returns a retryable “Connection lost during download,” keeping the partial file for resume. A pause keeps the partial file and returns Outcome::Paused; a cancel deletes it and clears the saved state. Downloads stop at once on pause, since every written byte is kept.

When the stream ends, the job calls flush and sync_all, so a “completed” file cannot still be in memory when power fails, and enters Verifying. If the bytes written differ from the expected total, it returns a retryable “Download ended early,” keeping the partial file. If the ETag passes is_single_part_md5, the only case where an ETag is the object’s MD5 (Chapter 8), and no customer-provided encryption (SSE-C) is reported, md5_file hashes the whole file on a blocking thread with a 1 MiB buffer. A mismatch deletes the partial file and clears the saved state before returning a retryable “Downloaded data did not match the file in R2,” so the retry starts from zero rather than resuming bad data.

Objects uploaded with multipart, including everything R2Dock uploads above its 100 MiB default threshold (Chapter 9, Multipart Uploads in Depth), have <hash>-<parts> ETags and are verified by size only. HTTPS protects the wire, so the residual risk is local, such as the crash tail above. Comparing per-part MD5s through GetObject’s PartNumber parameter, which R2 supports, is a possible future improvement the code does not implement.

Finalizing the File

Figure 10.1 shows the path from request to a completed job.

Before moving the file, the job records it as a WrittenFile (source.rs): size, nanosecond modification time, and on Unix the device and inode. It saves this as the finalized field of DownloadState and, unlike normal batched journal updates (Chapter 14, Journals and Persistent Queues), writes it immediately through persist_now on a blocking thread. The code comment explains why: “after a crash right after the move, this record is what tells the moved file apart from someone else’s file at the destination.” A same-folder rename keeps these values; an unrelated file almost certainly does not.

At the top of run, a saved download with no partial file on disk has two possible histories: the app placed the file and stopped before clearing state, or the partial file was lost. find_finalized looks for a file matching the record at the target, then at the Keep both names beside it, stopping at the first missing name. A match completes the job without downloading again. No record, or no match, means starting over and applying the conflict policy again, “so an existing file is never replaced without permission.” Tests in crates/r2dock-transfer/tests/recovery.rs, such as finalized_download_completes_after_restart and missing_partial_without_proof_keeps_a_user_file, confirm that a matching record completes the job and that a same-size file alone is never proof.

Just before the move, the job revalidates the destination with the path guard, since folders may have changed, then calls place.

Source: crates/r2dock-transfer/src/download.rs, lines 501 to 545

fn place(
    temp: &Path,
    target: &Path,
    policy: ConflictPolicy
) -> Result<Placed, JobError> {
    if policy == ConflictPolicy::Replace {
        // ... refuse a symlink or directory at the target
        std::fs::rename(temp, target)
            .map_err(|e| JobError::io(&e, "save the download"))?;
        return Ok(Placed::Done(target.to_path_buf()));
    }
    // ... candidate starts as the target
    for n in 0..=KEEP_BOTH_LIMIT {
        // ... from n = 1, candidate is "name (n).ext"
        let tmp = tempfile::TempPath::try_from_path(temp)
            .map_err(|e| JobError::io(&e, "save the download"))?;
        match tmp.persist_noclobber(&candidate) {
            Ok(()) => return Ok(Placed::Done(candidate)),
            Err(err) => {
                // Keep the temp file: we still need it.
                let _ = err.path.keep();
                // ... other I/O errors are returned
                match policy {
                    ConflictPolicy::Skip => return Ok(Placed::Skipped),
                    ConflictPolicy::Ask => return Ok(Placed::Ask),
                    _ => {}
                }
            }
        }
    }
    // ... "Too many files with this name already exist."

With Replace, a plain rename replaces the target in one step, after refusing a target that is a symbolic link or directory. Every other policy uses persist_noclobber from tempfile, which per its documentation persists “if and only if no file exists there.” A file that appeared since resolve_target, perhaps hours earlier, makes the persist fail with AlreadyExists instead of being overwritten. Skip then ends as Skipped and deletes the partial file; Ask ends as NeedsDecision and keeps it, so resolving later refetches only the last mebibyte; Keep both tries the next name. The test place_never_overwrites_without_replace checks all three branches.

The tempfile documentation warns that persist_noclobber “is not atomic” and “can leave the original link to the temporary file behind.” Where it links a second name and then removes the first, a crash between the steps leaves both. On restart the job would resume and place the file again, which under Keep both could create a second copy. This is inferred from the code and library documentation; no test exercises it.

After placement the job clears its state and reports Completed. The folder is not synced after the rename, and on some file systems a rename may not survive power loss until it is. If it is lost, the partial file reappears and the resume path handles it: extra work, not a corrupted file.

Ranged reads also serve text previews (read_head_bytes in crates/r2dock-r2/src/ops.rs, which wraps the body in take so an ignored range cannot make it read more) and media previews (Chapter 24, The Custom Media Preview Protocol).

Working on This Code

Nearly everything is in crates/r2dock-transfer/src/download.rs, with saved state in ctx.rs, WrittenFile in source.rs, and path validation in crates/r2dock-core/src/path_guard.rs. Run cargo test -p r2dock-transfer --test engine for round trips, conflicts, traversal, and resume, cargo test -p r2dock-transfer --test recovery for finalization and restart, and cargo test -p r2dock-transfer for unit tests; all use the in-process S3 server.

Keep the finalization order: write, flush, sync_all, size check, MD5 where the ETag allows, persist the record, revalidate, place. Reordering opens crash windows. Never write to the final path directly, never overwrite without Replace, and never follow symbolic links. Keep the partial file beside its target. Always pair a resumed range with If-Match and the first response’s ETag, treat a response without a matching Content-Range as a full body, keep bodies streaming, and never treat a multipart ETag as an MD5.

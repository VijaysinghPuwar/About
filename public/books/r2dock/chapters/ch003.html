How to Read This Book

R2Dock is a desktop application for managing Cloudflare R2 object storage through a file manager interface. It is built with Tauri 2, a Rust core split into several workspace crates, and a React and TypeScript frontend. It has no server of its own and no telemetry: people bring their own R2 credentials, and every request goes directly from their machine to their storage. Behind that simple description sit a surprising number of hard engineering problems. Uploads of many gigabytes must survive network failures and crashes. Thousands of queued transfers must not exhaust memory, disk, or the network. A web view must be allowed to display media without being trusted with the file system. Secrets must never leak into logs or into JavaScript. Media files can be compressed with FFmpeg before upload without risking the original.

This book explains how the code solves those problems. It was written by reading the source code itself, not by restating the project’s planning documents, and it is meant for two kinds of readers. The first is an engineer who wants to learn practical Rust, asynchronous programming, storage protocols, and application security from a real, medium sized codebase. The second is someone who wants to contribute to R2Dock and needs a guided path from a fresh clone of the repository to understanding what they are changing and how to test it.

How the book is organized

Part I describes the problem and gives a map of the whole system and the repository. Part II teaches the Rust and Tokio concepts the code relies on, then uses them to explain the transfer scheduler and how it applies backpressure. Part III covers the S3 compatible protocol that R2 speaks: listing, multipart uploads, ranged downloads, object management, and public URLs. Part IV is about reliability: the state machines that describe every transfer, the journal that persists them, crash recovery, retries, and cancellation. Part V covers media compression with FFmpeg. Part VI is about security: credentials, the Tauri trust boundary, file system safety, the media preview protocol, and a threat model. Part VII covers the React frontend. Part VIII covers testing, benchmarking, continuous integration, releases, the main engineering trade-offs, and a complete end to end walkthrough of one upload. Part IX is for new contributors: how to set up the project, make a first change, and where to read next.

Each chapter ends with a section called Working on This Code, which names the files you would change for common tasks in that area, the tests that protect it, and the rules you must not break. A glossary, a list of references, and the License Notice close the book.

How claims are labeled

A book about a codebase can easily blur the line between what the code does, what its documents intend, and what the author believes. This book tries hard to keep those apart, and the wording tells you which is which. When the text says the code does something, that behavior was read in the source at the audited commit, and a pinned source link usually follows. When it says a plan, an architecture decision record, or the changelog states something, that is a documented intention or claim, which may or may not match the code; where they differ, the text says so. When it says a test demonstrates something, the named test exercises that behavior. When it cites official documentation from Tokio, Tauri, Cloudflare, Amazon Web Services, FFmpeg, or another project, the link goes to the page that was consulted. Benchmark numbers come from the repository’s own benchmark records, together with the conditions under which they were measured, and they are labeled as recorded rather than re-measured unless the text says otherwise. Suggestions for future work are always presented as suggestions.

Conventions

Code excerpts are copied from the audited commit. A line containing only // ... marks an omission, and a few long lines have been re-wrapped at whitespace so they fit the page. Every excerpt is preceded by a source note that names the file and line range and links to the exact lines on GitHub. Identifiers and file names in running text, such as upload.rs, are set in a monospace font. Figures are described fully in the surrounding text and carry text descriptions for screen readers, so you can follow the book without looking at a single diagram, for example when listening to it with text to speech.

17 How FFmpeg Integrates with Rust

R2Dock compresses audio and video with FFmpeg, a large C media toolkit that parses untrusted files for a living. This chapter explains how R2Dock installs and verifies it, starts it without a shell (a command interpreter such as sh), reads its output, follows progress, stops it on cancel or hang, and cleans up. The media decisions belong to Chapter 18 (Audio Compression Internals) and Chapter 19 (Video Compression Internals). The code lives in the r2dock-media crate, which does not depend on Tauri, plus a thin service in src-tauri/src/compression.rs.

Why FFmpeg Runs as a Separate Program

R2Dock runs the ffmpeg program as a child process instead of linking its libraries. A child process is an isolation boundary: if a malformed file crashes FFmpeg, R2Dock sees a non-zero exit status and keeps running, whereas a linked library would corrupt R2Dock’s own memory. PLAN.md’s threat model row “Malicious media file attacks FFmpeg or the probe” lists the mitigations (separate process, fixed argument array, file: inputs with a protocol whitelist, watchdog, kill on exit) and the residual risk: an FFmpeg vulnerability could still run code as the user during compression, one reason compression is off by default.

Licensing points the same way: the downloaded builds use the GNU Lesser General Public License (LGPL) version 3, and THIRD_PARTY_NOTICES.md states that FFmpeg runs as a separate program not included in the installers, so R2Dock stays MIT licensed. Everything R2Dock learns from FFmpeg arrives as text and an exit code. Simple audio probing is the exception: it runs in process with the pure Rust Symphonia library (Chapter 18).

Finding the Tools

R2Dock never runs a bare ffmpeg from PATH. The ToolsSource enum in crates/r2dock-media/src/tools/mod.rs has two cases: Bundled, the pinned package R2Dock downloaded and verified, and System, a binary the user chose with a native file picker (pick_ffmpeg in src-tauri/src/dialogs.rs), so the path never comes from a string typed in the web view.

CompressionService::refresh in src-tauri/src/compression.rs validates the chosen tools (detect::use_system or install::check_installed, then detect::inspect) at startup, after install or removal, and when the source changes. detect::inspect runs -version and -encoders, and parse_license classifies the build as LGPL, GPL, or nonfree for Settings to show; a system FFmpeg must also include libmp3lame and have ffprobe beside it. On success the engine receives a MediaRuntime holding an Ffmpeg value; on failure it gets none, and files that asked for compression upload as originals with Unchanged::ToolsMissing.

The Pinned Manifest

crates/r2dock-media/src/tools/manifest.rs compiles the package description into the app. Each platform has an ffmpeg and an ffprobe Asset with a file name, a download size, and two SHA-256 sums (a cryptographic hash: any change to the bytes changes the 256 bit value), one of the compressed download and one of the unpacked binary. PACKAGES covers Windows and Linux on x86_64 and macOS on both architectures; other platforms get ToolsError::UnsupportedPlatform. VERSION is 9.0.2, and RELEASE_URL points at the tag tools-ffmpeg-9.0.2-2 on the project’s GitHub repository, with the rule that a new build gets a new tag and assets are never replaced.

Downloading Without Trusting the Network

crates/r2dock-media/src/tools/install.rs assumes the network, a proxy, or a redirect could deliver the wrong bytes. HttpFetch::new builds a reqwest client with https_only(true), 20 and 60 second connect and read timeouts, and a redirect policy that stops after five hops or at any host outside ALLOWED_HOSTS: github.com plus the objects.githubusercontent.com and release-assets.githubusercontent.com storage hosts that release downloads redirect to. The final URL is checked against the list again.

The body is streamed, hashed, and written in one loop, so the binary never sits whole in memory. Anything more than 1 MiB over the pinned size is rejected at once, so a hostile server cannot fill the disk. A tokio::select! with biased; checks cancellation before each chunk (the Tokio select! documentation explains that biased; polls branches in written order). The download sum is compared before decompression, so a tampered archive never reaches the zstd decoder.

unpack then streams the .zst file through a zstd decoder into a HashingWriter on a blocking thread and deletes a binary whose sum differs from binary_sha256. Everything happens in a .staging- folder from tempfile::Builder, which deletes itself on any error or cancel. When both binaries and an installed.json record are ready, swap_in renames the folder into place; an older install is first renamed aside under .old- and restored if the swap fails. rename_retry retries renames that a Windows virus scanner can briefly block. Tests in crates/r2dock-media/src/tools/install/tests.rs use an in-memory fetcher, including refuses_a_tampered_download_before_unpacking, refuses_an_oversized_download, cancel_leaves_nothing, and a_failed_swap_keeps_the_old_install. Figure 17.1 summarizes the path.

Checking Before Use

Installed binaries could later be replaced by another program or malware. check_installed in install.rs validates every binary that installed.json names, without trusting the record blindly. A recorded name with a path separator or a leading dot is refused. symlink_metadata does not follow links, so a planted link is not a plain file. If size and modification time match the record, the binary is not rehashed, which keeps startup fast; otherwise its full SHA-256 must match. Finally the recorded sum must equal the compiled-in sum, so editing both binary and record still fails. The tests detects_a_replaced_binary, pinned_sums_win_over_the_record, edited_records_are_refused, and symlinked_binaries_are_refused cover each rule.

CHANGELOG.md for 0.3.0 overstates this, saying the tools are “checked by SHA-256 before it is unpacked and before each use”. The code checks at each refresh, not before each encode, so a binary replaced while the app runs is noticed only at the next refresh, and a replacement that preserves size and modification time is not rehashed. The plan’s wording (“re-checked if their size or modification time changes”) is the accurate one.

Provenance: Where the Bytes Come From

The packages come from .github/workflows/tools.yml, run only by hand (workflow_dispatch) with a build number. For Windows and Linux it mirrors a specific BtbN FFmpeg-Builds release (autobuild-2026-09-30-13-08, LGPL variant of the 9.0 branch), checking each archive against a SHA-256 written in the workflow. For macOS, where BtbN publishes nothing, tools/ffmpeg/build-macos.sh compiles FFmpeg 9.0.2, LAME 3.100, Opus 1.5.2, and SVT-AV1 4.2.0 from source archives each pinned by SHA-256. Its configure line uses --enable-version3, --disable-autodetect, and --disable-network (the binary cannot open network URLs), and the script fails if otool -L shows a non-system library, if the build is GPL, or if libsvtav1 is missing. The Windows and Linux jobs run the same GPL check and an encoding smoke test.

A publish job writes a MANIFEST.txt with the sums and sizes copied into manifest.rs, refuses to reuse a tag, and creates a pre-release with --latest=false. Per PLAN.md’s row “Tampered or replaced FFmpeg download”, a compromised GitHub account could publish new assets, but the app accepts only its compiled-in sums. Two limits remain: BtbN binaries are trusted as BtbN built them, and nothing shows the macOS build is reproducible.

Building a Command Line Without a Shell

A command string handed to a shell turns a file name containing a quote or $(...) into code. The Rust documentation for Command::arg states that “the argument is not passed through a shell, but given literally to the program.” Every FFmpeg invocation is a Vec<OsString>, one element per argument, so even a non UTF-8 file name passes through unchanged.

FFmpeg has its own mini language in arguments, though. An input named concat:a|b.mp3 would use the concat protocol, which the FFmpeg protocols documentation describes as reading “many resources in sequence”; http: could open a connection; -i.mp3 could look like an option. Two habits close these holes.

Source: crates/r2dock-media/src/ffmpeg/args.rs, lines 72 to 87

/// `file:` URL for an absolute path.
pub fn file_url(path: &Path) -> Result<OsString, ArgsError> {
    if !path.is_absolute() {
        return Err(ArgsError::RelativePath);
    }
    let mut s = OsString::from("file:");
    s.push(path.as_os_str());
    Ok(s)
}

fn common_start() -> Vec<OsString> {
    ["-hide_banner", "-nostdin", "-y", "-loglevel", "error"]
        .into_iter()
        .map(OsString::from)
        .collect()
}

Every path is absolute, so it cannot start with -, and carries the file: protocol prefix. Every input is preceded by -protocol_whitelist file, so even nested protocols are unreachable. The unit test hostile_names_stay_files checks the arrays, and the integration test hostile_file_names_are_plain_files in crates/r2dock-media/tests/ffmpeg.rs encodes files named concat:a|b.mp3, http:x.mp3, and -i.mp3 and checks the output is real MP3.

The common prefix removes every way FFmpeg could wait for a human. Per the ffmpeg documentation, -y means “overwrite output files without asking” and -nostdin disables interaction on standard input; -loglevel error keeps stderr to real errors. The output format is always named with -f, and outputs always go into R2Dock’s work folder under a name derived from the job identifier, so the original is never an output.

Spawning the Process

Almost every line of the spawning function answers a failure mode.

Source: crates/r2dock-media/src/ffmpeg/run.rs, lines 100 to 133

fn command(bin: &Path, args: &[OsString]) -> CommandWrap {
    // A missing FFmpeg is started directly, so it fails as a spawn error
    // and not as an exit code from `nice`.
    #[cfg(unix)]
    let mut cmd = match NICE
        .iter()
        .map(Path::new)
        .find(|p| p.is_file())
        .filter(|_| bin.is_file())
    {
        Some(nice) => {
            let mut c = tokio::process::Command::new(nice);
            c.args(["-n", "10"]).arg(bin);
            c
        }
        None => tokio::process::Command::new(bin),
    };
    #[cfg(not(unix))]
    let mut cmd = tokio::process::Command::new(bin);
    cmd.args(args)
        .stdin(Stdio::null())
        .stdout(Stdio::piped())
        .stderr(Stdio::piped());
    // CREATE_NO_WINDOW | BELOW_NORMAL_PRIORITY_CLASS
    #[cfg(windows)]
    cmd.creation_flags(0x0800_0000 | 0x0000_4000);
    let mut wrap = CommandWrap::from(cmd);
    #[cfg(unix)]
    wrap.wrap(process_wrap::tokio::ProcessGroup::leader());
    #[cfg(windows)]
    wrap.wrap(process_wrap::tokio::JobObject);
    wrap.wrap(KillOnDrop);
    wrap
}

Encoding is CPU heavy, so on macOS and Linux the command runs through nice -n 10 from a fixed path (/usr/bin/nice or /bin/nice), never from PATH; nice replaces itself with FFmpeg through exec, so the process and group belong to FFmpeg. The Linux-only test runs_below_normal_priority checks this (its comment notes the macOS CI runner reports 0 for the child). On Windows the flags request below normal priority and no console window. CHANGELOG.md for 0.5.0 records that macOS and Linux gained lower priority in that release, and the benchmark notes say “the effect under contention was not measured.” PLAN.md’s threat model row still says “below-normal priority on Windows” only, which is out of date.

The process-wrap wrappers put FFmpeg in its own process group on Unix, so a kill reaches the whole group, and in a Job Object on Windows. KillOnDrop matters because, as the Tokio documentation warns, “a spawned process will, by default, continue to execute even after the Child handle has been dropped.”

If R2Dock itself crashes, Windows closes the Job Object and kills its processes. Unix has no equivalent without unsafe code, which the project avoids, so FFmpeg exits at its next write to the progress pipe, which has lost its reader; the plan’s Progress table puts that at about twice a second.

Reading Two Pipes at Once

A child writing to a pipe nobody reads blocks forever once the small kernel buffer fills, so reading only stdout while FFmpeg fills stderr would hang both. The function forward in run.rs spawns one task per pipe that reads raw bytes up to each newline, converts them with from_utf8_lossy (so a non UTF-8 name in an error cannot break parsing), and sends them into one bounded channel of 256 lines tagged Line::Out or Line::Err. Each task exits when its pipe closes or the receiver is gone. Stderr lines go into a ring of keep_lines entries (50 by default), so the last error is available without an unbounded log.

Parsing Progress

R2Dock passes -progress pipe:1 -nostats. The ffmpeg documentation says progress is written as key=value lines whose blocks end with progress=continue or progress=end; pipe:1 is standard output, and -nostats keeps stderr for real errors. The parser in crates/r2dock-media/src/ffmpeg/progress.rs accumulates fields and, at each progress key, returns the block and resets with std::mem::take. It reads out_time_us and the historically misnamed out_time_ms both as microseconds, and tolerates N/A, negative times, speed=infx, and Windows line endings (tests parses_blocks, tolerates_missing_and_odd_values, windows_line_endings).

Ffmpeg::encode divides the output time by the probed duration and clamps it to 0 to 1; the engine throttles these updates to one per 250 milliseconds per job (PROGRESS_EVERY).

Timeouts, Cancellation, and Exit Status

The runner’s main loop waits for a cancel request, the next line from either pipe, or too long without any line.

Source: crates/r2dock-media/src/ffmpeg/run.rs, lines 155 to 183

loop {
    tokio::select! {
        biased;
        () = cancel.cancelled() => {
            let _ = Box::into_pin(child.kill()).await;
            return Err(RunError::Cancelled);
        }
        line = tokio::time::timeout(opts.watchdog, rx.recv()) =>
            match line {
            Err(_) => {
                let _ = Box::into_pin(child.kill()).await;
                return Err(RunError::Stalled);
            }
            Ok(None) => break,
            Ok(Some(Line::Out(l))) => {
                if let Some(p) = parser.line(&l) {
                    on_progress(p);
                }
            }
            Ok(Some(Line::Err(l))) => {
                if !l.trim().is_empty() {
                    if tail.len() == opts.keep_lines {
                        tail.pop_front();
                    }
                    tail.push_back(l);
                }
            }
        },
    }
}

With biased; the cancellation token (Chapter 5, Tokio and Asynchronous Execution) is checked first, so a flood of progress lines cannot starve a cancel. The Tokio Child documentation says kill “forces the child to exit” and waits for it, so no zombie remains, and the process group carries the signal to the group. The plan originally proposed sending q and waiting 3 seconds; its Progress table explains the immediate kill: the output is deleted anyway, and -nostdin means FFmpeg would never read the key. The test cancel_stops_ffmpeg_and_removes_the_output cancels an hour long encode and checks the output is gone within 30 seconds.

Each recv is wrapped in tokio::time::timeout, so any line resets the watchdog. Since FFmpeg writes progress regularly, 120 seconds of silence (the RunOptions default) means it is stuck, perhaps on a corrupt file or a hung hardware encoder, and the runner kills it with RunError::Stalled. The test watchdog_stops_a_silent_process covers it. When both pipes close, the runner waits for the exit status, again racing cancel and the watchdog. Success returns the kept stderr lines; failure becomes RunError::Failed with the exit code (or None for a signal) and the last stderr line. Figure 17.2 shows the lifecycle.

Short helper runs (ffprobe with a 60 second limit, and version and encoder checks with 20 seconds) use plain tokio::process::Command with kill_on_drop(true), bypassing nice and the process group wrapper.

Safe Messages and Cleanup

An FFmpeg error line usually contains the full input path, and R2Dock’s rules forbid showing or logging full local paths. Ffmpeg::run_clean passes the last line through sanitize in run.rs, which replaces each known input and output path with its bare file name, giving messages like “FFmpeg exited with 1: part 1.mp3: Invalid data found”. The test failures_are_reported_without_folders checks that a folder named private folder never appears. The limit: only paths it was given, in the exact form display() produces, are removed.

The runner never deletes files; its callers do. Ffmpeg::encode deletes its output on any error, including cancel and failed verification; Ffmpeg::sample_saving always deletes its sample, as does video::run::encode_once. Outputs are named <job id>.<ext> or <job id>.sample.<ext> in compress inside the app cache folder. A killed process cannot clean up, so a crash can leave a partial file; the startup sweep and the life of a finished copy belong to Chapter 20 (Compression Scheduling and Data Integrity).

Working on This Code

Audio arguments are in crates/r2dock-media/src/ffmpeg/args.rs and video arguments in crates/r2dock-media/src/video/args.rs; update their snapshot tests (speech_mp3_snapshot, av1_snapshot_parts) deliberately rather than loosening them. Process behavior is in ffmpeg/run.rs, parsing in progress.rs, installation in tools/install.rs, and pinned values in manifest.rs. A new FFmpeg build means running tools.yml with a new build number, copying every sum from MANIFEST.txt, and running manifest_is_consistent.

Run cargo test -p r2dock-media. The integration tests in tests/ffmpeg.rs need a real FFmpeg via R2DOCK_TEST_FFMPEG or PATH (tests only) and skip otherwise, so check cargo test -p r2dock-media --test ffmpeg output for “skipping” lines.

Never build a command string or call a shell. Pass every path through file_url and every input after -protocol_whitelist file. Never let FFmpeg write outside the work folder. Keep both pipes drained, keep the watchdog fed, and never drop a child without the kill wrappers. Never put a full local path in a message, never fall back to PATH, and never loosen the host allowlist or skip a hash check.

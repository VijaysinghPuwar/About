8 The S3-Compatible Protocol

Cloudflare R2 does not have its own wire protocol for object access. It speaks the Amazon Simple Storage Service (S3) application programming interface (API), the HTTP interface that thousands of tools already understand. This chapter follows one request from a Rust method call to R2 and back, separates what the AWS software development kit (SDK) does from what R2Dock does itself, and explains the error classification that later chapters rely on. Chapter 9 (Multipart Uploads in Depth) and Chapter 10 (Downloads and HTTP Range Requests) build on it.

Why R2Dock Uses the AWS SDK

Every R2 call goes through the aws-sdk-s3 crate. The workspace Cargo.toml pins it to major version 1 with default features off and three features on: behavior-version-latest, rt-tokio, and default-https-client. The lock file resolves it to version 1.102.0. Turning default features off keeps the dependency tree to what the code uses and makes the choice of Tokio (Chapter 5) explicit.

A hand-written client would have to get signing, S3’s URI encoding, XML, error documents, and retries exactly right; the SDK carries that work, and R2Dock keeps the product decisions. The r2dock-r2 crate owns the SDK. Its crate documentation in crates/r2dock-r2/src/lib.rs states that it is the only place, besides the secret store, that ever sees a secret. The transfer crate reaches the configured client through R2Client::sdk(); React and the Tauri commands never build S3 requests.

Endpoints and Jurisdictions

The Cloudflare page on R2 S3 API tokens gives the endpoint as https://<ACCOUNT_ID>.r2.cloudflarestorage.com and lists separate endpoints for jurisdictions, adding that “Jurisdictional buckets can only be accessed via the corresponding jurisdictional endpoint.” endpoint_url in crates/r2dock-core/src/connections.rs encodes this with a match on the Jurisdiction enum, which has three variants: Default, Eu (inserting .eu. into the host), and Fedramp (inserting .fedramp.). The same Cloudflare page also lists a United States endpoint (.us.) that the enum lacks, so a bucket in that jurisdiction cannot be reached at the audited commit. That is a gap against current documentation, not a bug in what the code supports.

Because the jurisdiction is part of the host, R2Dock builds one client per saved connection. ConnectionService::client in src-tauri/src/connections.rs caches it, guarded by a generation counter so a client built from an outdated secret is never stored. ClientParams also has an endpoint_override for tests; the desktop app sets it only in debug builds, from R2DOCK_DEV_ENDPOINT, and only for http://127.0.0.1: values, so an environment variable can never send a release build’s signed requests elsewhere.

The client sets force_path_style(true), so the bucket is the first path segment (.../media-library/photos/cover.webp) rather than a sub-domain. PLAN.md section 8.1 marks this [Verify], noting that both styles likely work on R2; the local test server expects path style, which keeps tests and production on one code path.

Credentials and Signing

R2 accepts static S3 credentials. The Cloudflare token page explains that the Access Key ID is “The id of the API token,” and the Secret Access Key is “The SHA-256 hash of the API token value.” There is no session token. Chapter 21 (Credential Storage and Authentication) covers storing the secret.

R2Client::new in crates/r2dock-r2/src/client.rs builds static credentials with Credentials::new (no session token, no expiry). The secret arrives as a secrecy::SecretString and is exposed once, at this call. ClientParams has a hand-written Debug that prints only the account identifier and jurisdiction and ends with finish_non_exhaustive(), so a stray {:?} cannot print the secret.

Requests are authenticated with AWS Signature Version 4 (SigV4), and the secret never crosses the network. As the AWS guide to creating a signed request describes, the client hashes a canonical form of the request (method, encoded path, query, signed headers, payload hash), combines it with a timestamp and a credential scope of the form YYYYMMDD/region/service/aws4_request, and signs the result with HMAC-SHA256 using a key derived from the secret, date, region, and service. The region is therefore part of the signature. The server recomputes the signature from what it received, so a wrong secret produces SignatureDoesNotMatch rather than a generic denial. PLAN.md section 8.2 records this as confirmed against real R2 on 2026-10-17, and the ignored test live_read_only_connection_check in crates/r2dock-r2/tests/live_r2.rs asserts it with real credentials. The AWS SigV4 overview says a request must usually arrive “within five minutes of the time stamp”; whether R2 enforces the same window is not stated in the R2 pages fetched for this book, so clock skew tolerance on R2 is unverified.

The R2 S3 API compatibility page states that “the region for an R2 bucket is auto,” with an empty value and us-east-1 accepted as aliases. R2Dock sets Region::new("auto"). Since the endpoint is explicit, the region’s only job is to appear in the credential scope.

For S3 the canonical request ends with a payload hash in x-amz-content-sha256, or the literal UNSIGNED-PAYLOAD. The code does not show which mode the SDK picks for R2Dock’s streaming bodies, so this book claims neither; upload integrity rests on a Content-MD5 header that R2Dock computes itself (Chapter 9).

The Life of One Request

Each attempt in the retry loop is signed afresh before it is sent. All of these layers are configured in one place.

let timeouts = TimeoutConfig::builder()
    .connect_timeout(CONNECT_TIMEOUT)
    .build();
let config = aws_sdk_s3::Config::builder()

    .region(Region::new("auto"))
    .endpoint_url(endpoint)
    .credentials_provider(credentials)

            .build(),
    )
    .build();

Beyond the settings already covered, the lines decide checksums, retries, and timeouts, where an S3-compatible service can differ from Amazon S3.

Checksums only when required

The SDK documentation for RequestChecksumCalculation describes the default WhenSupported as calculating a checksum “for all request payloads” on operations that model one, while WhenRequired limits it to operations that require one or where the caller chose an algorithm. ResponseChecksumValidation works the same way for responses. PLAN.md section 8.1 explains the choice (several S3-compatible services rejected the new default checksums) and marks it [Verify on R2]. R2’s per-operation tables for PutObject and UploadPart list only Content-MD5. With this setting the SDK adds no checksums and validates none on GetObject bodies; Chapter 10 describes R2Dock’s own download verification.

Two layers of retries

RetryConfig::standard().with_max_attempts(3) enables standard retry mode. The RetryConfig documentation counts max attempts “including the initial attempt,” so this is one try plus up to two retries with backoff and jitter, invisible to R2Dock code. The transfer engine adds a slower job-level layer of up to three attempts, with waits of about 2 and then 8 seconds (crates/r2dock-transfer/src/retry.rs). Chapter 16 (Retries, Cancellation, and Idempotency) owns how the layers interact. Here the key point is that SDK retries require a replayable body, which is why uploads use a rebuildable body (Chapter 9).

Timeouts and stall protection

client.rs defines a 10 second CONNECT_TIMEOUT, a 30 second METADATA_ATTEMPT_TIMEOUT, and a 60 second STALL_GRACE. A per-attempt timeout suits a listing, where a healthy server answers in well under a second, but not a transfer, where a 4 GiB part on a slow link can take many minutes. So metadata_timeouts() returns a config override, applied with .customize().config_override(...) only to ListObjectsV2, ListBuckets, and HeadObject. Transfers and mutating calls get only the connect timeout plus stall protection.

Stall protection replaces a total timeout with a progress rule. The StalledStreamProtectionConfig documentation says that “When a stream stalls for longer than this grace period, the stream will return an error.” A transfer can run for hours while bytes move, but a connection that silently stops is abandoned after a minute as a retryable error.

Division of Labor

The SDK owns protocol mechanics: SigV4 signing, URI encoding, XML, the per-request retry loop, and timeouts once configured. R2Dock owns every decision with product meaning: job-level retries, Content-MD5 on upload bodies (upload.rs), listing pagination and its guards (list.rs), conditional headers (ops.rs, upload.rs, download.rs), and error classification (error.rs). R2Dock avoids the SDK’s paginators and transfer utilities so every step can be journaled, checked, or cancelled.

The non-test source uses exactly fourteen S3 operations, all on R2’s supported list: ListBuckets, ListObjectsV2, HeadObject (also behind exists, which treats NoSuchKey as false), GetObject, PutObject, the five multipart operations of Chapter 9, and CopyObject, UploadPartCopy, DeleteObject, and DeleteObjects, which belong to Chapter 11 (Object Management and Consistency). R2Dock never sends ACL or tagging headers.

Keys and Prefixes

A key such as photos/2026/cover.webp is one flat string. The module documentation of crates/r2dock-core/src/keys.rs says it plainly: “R2 has no folders.” validate_key rejects empty keys, keys over MAX_KEY_BYTES (1,024), and control characters. key_from_components, used for folder uploads, rejects . and .. and normalizes names to Unicode Normalization Form C (NFC), because macOS may report decomposed names that would otherwise yield a second key for the same visible name.

Keys from R2 are untrusted. display_name replaces control and invisible formatting characters, such as the right-to-left override, with visible placeholders like ⟨U+202E⟩ (tested by display_name_reveals_bidi_override), and is_unusual_key flags empty segments and leading slashes. Mapping a key to a local path is the path guard’s job (Chapter 23, Filesystem Security). Where R2Dock builds a header or URL itself, percent_encode_key encodes every byte except unreserved characters and /, matching the AWS signing guide.

Listing and Pagination

A folder view is a ListObjectsV2 call with a prefix (the folder path) and a delimiter of /. The ListObjectsV2 reference explains that CommonPrefixes “lists keys that act like subdirectories,” each counting as a single return. list_page in list.rs asks for PAGE_SIZE keys (1,000, the S3 maximum; PLAN.md section 8.3 marks R2’s limit [Verify]) and returns FolderEntry and ObjectEntry values, hiding the folder itself and its zero byte folder marker (Chapter 11).

Pages continue with an opaque token that, per the AWS reference, “is sent when isTruncated is true.” R2Dock never interprets the token, but it refuses a response that breaks the paging contract.

Source: crates/r2dock-r2/src/list.rs, lines 153 to 171

/// Fail on a truncated page without a token, or a token that repeats.
pub(crate) fn check_next_token(
    is_truncated: Option<bool>,
    next: Option<&str>,
    previous: Option<&str>,
) -> Result<Option<String>, R2Error> {
    if !is_truncated.unwrap_or(false) {
        return Ok(None);
    }
    match next {
        None | Some("") => Err(R2Error::Protocol {
            detail: "listing was truncated without a continuation token"
                .to_string(),
        }),
        Some(t) if Some(t) == previous => Err(R2Error::Protocol {
            detail: "listing repeated a continuation token".to_string(),
        }),
        Some(t) => Ok(Some(t.to_string())),
    }
}

Without these guards, a truncated page with no token would silently show an incomplete folder, and a repeating token would make a folder delete or size calculation loop forever, paying for a list call per page. Both become Protocol errors. A missing IsTruncated reads as “not truncated.” The unit test pagination_guards covers every branch, and listing_hides_marker_and_paginates in crates/r2dock-r2/tests/local_s3.rs pages through a folder two keys at a time and checks that the marker is hidden and nothing is lost or duplicated.

search_prefix_page omits the delimiter to list every key under a prefix. for_each_object builds on it, checking a CancellationToken before each page and racing each request against it with tokio::select!, and holds one page at a time, so memory stays flat. Listing happens only on user action; PLAN.md section 8.3 notes that list calls are billed as Class A operations.

Metadata

A listing gives each object’s key, size, last modified time, entity tag (ETag), and storage class. HeadObject gives more, and R2Client::head_object in ops.rs maps it into ObjectDetails, adding content type, Cache-Control, Content-Encoding, user metadata from x-amz-meta-* headers, and a storage class that defaults to STANDARD.

It also computes etag_is_md5. An ETag is an opaque version identifier; the AWS CompleteMultipartUpload reference says it “may or may not be an MD5 digest.” For a single part upload without customer-provided encryption keys (SSE-C) it is the content MD5. For a multipart object, Cloudflare’s multipart documentation describes it as “the hash of the concatenated binary MD5 sums of all parts, followed by a hyphen and the number of parts.” So is_single_part_md5 in crates/r2dock-core/src/etag.rs accepts exactly 32 hexadecimal characters after removing quotes and a weak marker, and head_object also requires that no SSE-C algorithm is reported.

Uploads set Content-Type from the extension with mime_guess (falling back to application/octet-stream), and compressed copies (Chapters 18 to 20) add r2dock-original-size, r2dock-original-name, and r2dock-compression. compression_metadata percent-encodes the original name, because a newline in a file name could otherwise inject a header; percent_encoding_keeps_headers_ascii tests this.

Conditional Requests

Conditional headers are R2Dock’s main defense against races. The R2 S3 extensions page says PutObject conditions “are evaluated atomically, as part of the same write that commits the object,” and competing writers lose with 412 PreconditionFailed. R2Dock uses If-None-Match: * on PutObject for folder markers and for single uploads when the conflict policy is not Replace (Chapter 9); If-Match on GetObject to pin a resumed download (Chapter 10); and x-amz-copy-source-if-match plus the beta R2 extension cf-copy-destination-if-none-match on CopyObject (Chapter 11).

The same page warns that “A negative read (NoSuchKey) is not proof that a prior write failed if that write’s outcome is unknown.” Chapter 16 discusses such uncertain outcomes.

Error Classification

The SDK returns SdkError<E, R>, which separates where a failure happened, and R2Error::from_sdk in error.rs maps it in two steps. First the kind: a timeout, reported directly or as a dispatch failure, becomes Timeout; any other dispatch failure (DNS, refused connection, TLS) becomes Network; an unparseable response becomes Protocol; an unbuildable request becomes Construction; and a wildcard arm maps future kinds to Network, since SdkError is non-exhaustive. Only a ServiceError carries an S3 error code, and it goes to the second step, which reads the code first and falls back to the HTTP status.

Source: crates/r2dock-r2/src/error.rs, lines 82 to 105

fn from_service<E: ProvideErrorMetadata + RequestId>(
    err: &E,
    status: u16
) -> Self {
    let detail = detail_of(err, status);
    match err.code() {
        Some("InvalidAccessKeyId") => Self::InvalidAccessKey { detail },
        Some("SignatureDoesNotMatch") => Self::SignatureMismatch { detail },
        Some("AccessDenied") | Some("Unauthorized") =>
            Self::AccessDenied { detail },
        Some("NoSuchBucket") => Self::NoSuchBucket { detail },
        Some("NoSuchKey") | Some("NotFound") => Self::NoSuchKey { detail },
        Some("PreconditionFailed") => Self::PreconditionFailed { detail },
        Some("SlowDown") | Some("TooManyRequests") =>
            Self::RateLimited { detail },
        _ => match status {
            401 | 403 => Self::AccessDenied { detail },
            404 => Self::NoSuchKey { detail },
            412 => Self::PreconditionFailed { detail },
            429 => Self::RateLimited { detail },
            500..=599 => Self::Server { status, detail },
            _ => Self::Service {
                code: err.code().unwrap_or("Unknown").to_string(),
                status,
                detail,
            },
        },
    }
}

The order matters. A HeadObject error has no body and often no code, so a bare 404 becomes NoSuchKey through the fallback. NoSuchUpload, a 404 for an unknown multipart upload, also lands in NoSuchKey, which Chapter 9 relies on. A 416 for a bad range becomes Service with status 416, which Chapter 10 matches explicitly. The test missing_bucket_maps_cleanly accepts either NoSuchBucket or NoSuchKey, a sign that codes vary between implementations. PLAN.md section 8.11 says R2’s exact codes still need capturing against a test bucket, and Architecture Decision Record (ADR) 0005 states that R2-specific behavior, error codes included, “is not proven by these tests.”

is_retryable is true for RateLimited, Server, Network, Timeout, and Protocol. is_auth_failure is true only for InvalidAccessKey and SignatureMismatch; the engine uses it to stop every job of a connection at once, as wrong_credentials_fail_without_retry_storm in crates/r2dock-transfer/tests/engine.rs tests. Two choices differ from PLAN.md section 8.11: the plan lists TLS failures as not retryable, but the code maps them to retryable Network; and Protocol is retryable, so a listing whose token repeated may fail again. Retries are bounded, so neither is dangerous.

to_app_error converts an R2Error into the AppError sent over Inter-Process Communication (IPC) to the frontend (Chapter 26), with a fixed plain message per variant and a detail holding only the code, status, and request identifier. The server’s free-text message is never included, because a server or proxy might echo anything into a log or screenshot; app_error_has_no_raw_message tests this.

Working on This Code

Protocol changes start in crates/r2dock-r2/src: client.rs for construction, timeouts, retries, and checksums; list.rs for listing; ops.rs for single-object calls; error.rs for mapping; dto.rs for the shapes exported to TypeScript. Key, ETag, and endpoint helpers live in crates/r2dock-core/src (keys.rs, etag.rs, connections.rs). Run cargo test -p r2dock-r2 (against an in-process S3 server) and cargo test -p r2dock-core; neither needs network access. The ignored live check in live_r2.rs needs R2DOCK_LIVE_* variables for a dedicated test account.

Keep the invariants: secrets go only into the SDK; no error carries server text, signatures, or presigned URLs; metadata calls use metadata_timeouts() and transfers never get a total timeout; every page loop goes through check_next_token and honors cancellation; keys from R2 are displayed through display_name and mapped to paths only through the path guard. Local tests prove sequencing, not R2 behavior; anything marked [Verify] in PLAN.md section 8 needs a test bucket.

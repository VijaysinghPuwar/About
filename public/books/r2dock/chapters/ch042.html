31 CI/CD and Desktop Releases

A desktop application ships as installers that users run with their own privileges, so each must come from a checked commit, the file set must be unambiguous, and users must be able to verify downloads. This chapter follows R2Dock’s three GitHub Actions workflows: ci.yml, which checks every push and pull request; release.yml, which builds and publishes installers from a version tag; and tools.yml, which builds the pinned FFmpeg packages. It also states which parts of a trustworthy release are not done yet, most importantly code signing.

Toolchain setup for contributors (Rust 1.94 or newer, Node.js 22, and the Tauri prerequisites) is covered in Chapter 34 (Your First Contribution); the continuous integration (CI) workflow below is the most precise record of what each platform needs. One constraint belongs here because it broke a release: the Rust tauri crate and the JavaScript @tauri-apps/api package must share a minor version. The CHANGELOG entry for 0.1.1 records that release builds failed until the crate moved to 2.12 “matching the JavaScript API package”, and at the audited commit both lock files hold 2.12.4.

The Continuous Integration Workflow

The CI workflow, ci.yml, runs on every push to main and every pull request. Figure 31.1 shows its two jobs.

Source: .github/workflows/ci.yml, lines 8 to 25

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:
  CARGO_TERM_COLOR: always

jobs:
  test:
    name: Test (${{ matrix.os }})
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-22.04, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}

permissions: contents: read limits the automatic GITHUB_TOKEN to reading, as GitHub’s token documentation recommends (“grant the GITHUB_TOKEN the least required access”); CI runs code from pull requests, so a read-only token limits what a malicious change could do. The concurrency group with cancel-in-progress: true cancels a branch’s older run when a new push arrives. GitHub’s matrix documentation explains that fail-fast cancels the other jobs when one fails; fail-fast: false keeps them running, so one run shows whether a failure is platform-specific.

The test job

The job installs system packages and FFmpeg (on Windows exporting the real ffmpeg.exe rather than a Chocolatey shim, as Chapter 29, Automated Testing Strategy, explains), the Netwide Assembler (NASM) on Windows, stable Rust with rustfmt and clippy, a Rust build cache through Swatinem/rust-cache, and Node.js 22. The workflow does not say which dependency needs NASM, and this book has not traced it. Because it uses dtolnay/rust-toolchain@stable, CI checks the newest compiler, and no job builds with exactly Rust 1.94, so the rust-version floor is declared but not tested.

Source: .github/workflows/ci.yml, lines 65 to 90

      - run: npm ci

      - name: Frontend lint, types, tests, build
        run: |
          npm run lint
          npm run typecheck
          npm test
          npm run build

      - name: Rust format
        run: cargo fmt --all -- --check

      - name: Rust lint
        run: cargo clippy --workspace --all-targets -- -D warnings

      - name: Rust tests
        run: cargo test --workspace

      # Downloads this OS's pinned FFmpeg package from the tools release,
      # verifies it, and compresses a file with it.
      - name: Compression tools install on this OS
        run: cargo test -p r2dock-media --test live_tools -- --ignored

      - name: Generated IPC types are up to date
        if: runner.os == 'Linux'
        run: git diff --exit-code -- src/ipc/bindings

The Rust lint step interacts with the workspace lint table in Cargo.toml, which sets unsafe_code = "forbid" and Clippy’s unwrap_used, expect_used, panic, dbg_macro, and todo to warn. Warnings alone do not fail a build, but -D warnings turns them into errors, so a stray unwrap() in application code fails CI on every platform. Test files opt out with a crate-level #![allow(...)], so an allow in non-test code stands out in review. The tools step runs the ignored live_tools test, so a missing or altered FFmpeg release asset breaks CI rather than a user’s download.

Checking the generated TypeScript bindings

Architecture decision record (ADR) 0003 records the typed Inter-Process Communication (IPC) contract: “Rust DTOs derive ts_rs::TS; cargo test writes TypeScript definitions to src/ipc/bindings/. CI fails if the generated files differ from the committed ones.” Each exported type carries #[ts(export)] (74 occurrences at the audited commit), and .cargo/config.toml sets TS_RS_EXPORT_DIR to src/ipc/bindings. After the test step regenerates every binding, git diff --exit-code fails if a contributor changed a Rust data transfer object without committing the new TypeScript, protecting the rule from Chapter 26 (React and Tauri IPC) that frontend IPC types come only from generated definitions. The workflow does not say why the check runs only on Linux. ADR 0003 also notes the gap: command names and arguments are still listed by hand in src/ipc/commands.ts, src-tauri/build.rs, and the capability file.

Dependency Audits

The audit job runs on Linux: npm audit --omit=dev, then cargo install cargo-audit --locked and cargo audit. The npm check covers only packages that ship in the app. cargo audit checks Cargo.lock against the RustSec database, “a repository of security advisories filed against Rust crates published via crates.io” according to its project site, and --locked pins the auditor’s own dependencies.

Three limitations follow from the code. The audit has no scheduled trigger, so an advisory against an unchanged lock file is noticed only at the next push. Nothing in the release workflow depends on it. And PLAN.md section 19 and the contribution rules mention cargo deny, but no deny.toml is tracked and no step runs it; its license check would suit an MIT-licensed project that distributes tools under the GNU Lesser General Public License (LGPL). PLAN.md also mentions Dependabot or Renovate; neither is configured.

The Release Workflow

release.yml turns a version tag into a GitHub release with five installers and a checksum file. It starts on a pushed v* tag, or through workflow_dispatch with an existing tag, which allows rebuilding after a failed build. Figure 31.2 shows its three jobs.

Verifying the tag

The verify job runs a script under set -euo pipefail. It rejects any tag that is not v plus three dot-separated numbers, requires git rev-parse "refs/tags/$TAG^{commit}" to equal the checked-out HEAD, requires the versions in Cargo.toml, package.json, and src-tauri/tauri.conf.json to equal the tag, and requires a ## [X.Y.Z] heading in CHANGELOG.md. It then outputs the commit hash as sha. A mismatched manifest would produce installers reporting the wrong version, and passing the hash rather than the tag means every build checks out the same commit even if the tag moves mid-run.

What the workflow does not do is run tests. Nothing in release.yml runs cargo test or npm test or requires a green CI run, so a tested release depends on the maintainer tagging a commit whose CI passed. A needs dependency on a test job or a check of the commit’s CI status would make that mechanical.

Building four targets

The build job is a four-entry matrix with fail-fast: false.

Source: .github/workflows/release.yml, lines 54 to 76

      matrix:
        include:
          - name: macOS Apple Silicon
            os: macos-latest
            target: aarch64-apple-darwin
            args: --target aarch64-apple-darwin
            bundles: dmg
          - name: macOS Intel
            os: macos-latest
            target: x86_64-apple-darwin
            args: --target x86_64-apple-darwin
            bundles: dmg
          - name: Windows x64
            os: windows-latest
            target: x86_64-pc-windows-msvc
            args: ""
            bundles: nsis
          - name: Linux x64
            os: ubuntu-22.04
            target: x86_64-unknown-linux-gnu
            args: ""
            bundles: appimage,deb
    runs-on: ${{ matrix.os }}

Both macOS builds use one runner image with an explicit --target, so one is a cross-compilation, and two disk images ship instead of a universal binary. The command is npm run tauri build -- ${{ matrix.args }} --bundles ${{ matrix.bundles }}; --bundles narrows the formats because tauri.conf.json sets "targets": "all", and a comment explains “One clearly named file per platform (no MSI, RPM, or updater archives).” Building Linux on Ubuntu 22.04 likely keeps the AppImage compatible with newer glibc versions, but the workflow does not state that reason. In tauri.conf.json, macOS requires version 11.0 and the installMode of the Nullsoft Scriptable Install System (NSIS) installer is currentUser, so Windows installation needs no administrator rights. A bash step renames each bundle to a fixed name such as R2Dock-0.5.0-Windows-Setup.exe and uploads it as an artifact.

Publishing with a fixed file set and checksums

Only the publish job has contents: write. It downloads all artifacts (GitHub’s artifact documentation says each upload’s SHA-256 digest is recalculated on download), sorts the file names with LC_ALL=C sort, and compares them with an expected list of exactly five versioned names. A missing or extra file fails the release, which stops a partially failed matrix from publishing an incomplete set. The job then writes SHA256SUMS.txt, builds notes from a fixed “Which file do I download?” table, the line “Unsigned preview build.”, and the CHANGELOG section, and runs gh release create ... --verify-tag, which per the GitHub CLI manual aborts if the tag does not exist remotely.

The checksum file confirms that a download matches what the workflow published. It does not prove who published it, because the checksums sit on the same release page as the files; authenticity needs a signature.

PLAN.md section 19 planned to use tauri-apps/tauri-action, which can also generate updater manifests. The implemented workflow instead calls the Tauri CLI and does naming, checks, and publishing in visible shell, at the cost of maintaining that logic itself. Here PLAN.md and the code differ, and the code is the source of truth.

Signing, Notarization, and Distribution Limits

Code signing attaches a signature from an identity the operating system trusts. R2Dock’s installers are not signed: the release notes say “Unsigned preview build”, PLAN.md section 17.1 says “Code signing, notarization, and the updater are not done”, and nothing in release.yml or tauri.conf.json configures a certificate. The README tells Windows users to choose More info > Run anyway and macOS users to right-click and choose Open.

The Tauri macOS signing guide says distribution outside the App Store uses a Developer ID Application certificate and “Notarization is required when using a Developer ID Application certificate”, with the certificate supplied to CI through secrets. This book did not inspect the published disk images for an ad-hoc signature. The Windows guide explains that signing reduces SmartScreen warnings, though reputation builds over time; PLAN.md section 15 marks Windows certificate options [Verify cost/options]. The Linux guide says signing “is not required”, and that GPG-signed AppImages are not validated automatically (“AppImage does not validate the signature”).

For users today, the operating system cannot say who made the app, and checksums help only if users check them and trust the release page. There is no auto-updater (the Tauri plugins in src-tauri/Cargo.toml do not include it), so a fixed vulnerability reaches users only when they download a new version; SECURITY.md says “Only the latest release receives fixes while the project is in 0.x.” PLAN.md Phase 7 lists signed macOS and Windows builds, a signed updater, and release smoke tests as future deliverables.

The Compression Tools Pipeline

R2Dock downloads FFmpeg on first use; Chapter 17 (How FFmpeg Integrates with Rust) covers installation and verification in the app. The packages come from tools.yml, triggered by hand with a build number and published as tools-ffmpeg-9.0.2-<build>. Its header states “A release tag is never reused; a new build gets a new tag, and the app pins the new SHA-256 sums in crates/r2dock-media/src/tools/manifest.rs”, and the publish job refuses to continue if the tag exists. Because the app pins download and binary digests per platform and points RELEASE_URL at one tools release (build 2 at the audited commit), a rebuilt package can never silently replace a trusted one.

For Windows and Linux, the mirror job downloads a dated LGPL build from the BtbN FFmpeg-Builds project, verifies its SHA-256, fails if ffmpeg -version shows --enable-gpl, and runs smoke encodes. For macOS, tools/ffmpeg/build-macos.sh builds FFmpeg 9.0.2 with LAME, Opus, and SVT-AV1 from sources verified against pinned SHA-256 values, with --disable-autodetect and --disable-network, and fails if otool -L shows any library outside /usr/lib/ or /System/Library/, if GNU General Public License (GPL) code is enabled, or if the AV1 encoder is missing. The publish job writes the digests a maintainer copies into manifest.rs and marks the release as a prerelease. The CI live_tools step closes the loop by installing exactly what manifest.rs pins.

Versioning and the Changelog

R2Dock uses Semantic Versioning and a CHANGELOG that “follows Keep a Changelog”. The version lives in the workspace Cargo.toml, package.json, and src-tauri/tauri.conf.json, all 0.5.0 at the audited commit; the release workflow refuses a tag that does not match all three or lacks a CHANGELOG section, which becomes the release notes.

Working on This Code

Workflows live in .github/workflows/ci.yml, release.yml, and tools.yml; packaging in the bundle section of src-tauri/tauri.conf.json; tool pins in crates/r2dock-media/src/tools/manifest.rs and tools/ffmpeg/build-macos.sh. Before pushing, run the CONTRIBUTING.md checklist (Chapter 34 lists it), which mirrors the test job. If you change a Rust type that crosses IPC, commit the regenerated src/ipc/bindings/ files. After dependency changes, run cargo audit and npm audit --omit=dev.

To release, bump all three manifests, add a ## [X.Y.Z] CHANGELOG section, confirm CI is green on all three platforms for that commit (the release workflow does not test), and push a vX.Y.Z tag. Never reuse a tools tag. Keep tokens read-only outside publish jobs, keep fail-fast: false, never add GPL or nonfree FFmpeg components, never put credentials in workflows or logs, and keep tauri and @tauri-apps/api on the same minor version. Adding a bundle format without updating the publish job’s expected file list fails the release by design.

21 Credential Storage and Authentication

R2Dock asks for keys that can read, overwrite, and delete everything in a user’s buckets. This chapter follows those keys from the Connect form to the signed request: where a secret may live, who may see it, and how it is destroyed. Request signing with the Amazon Simple Storage Service (S3) protocol is in Chapter 8 (The S3-Compatible Protocol), and the optional Cloudflare API token in Chapter 12 (Public URLs and Cloudflare REST API Integration).

Which Credentials Exist

A connection is described by four values, two of them secret. The account ID is not secret but is masked in logs; it becomes part of the endpoint host (<account>.r2.cloudflarestorage.com, with eu or fedramp for those jurisdictions), so validate_account_id accepts only ASCII letters and digits, at most 64 bytes. The test account_id_cannot_inject_host checks that evil.com/x is refused, since a dot or slash could steer requests to another host. The access key ID is the public half of the key pair, stored in plain JSON and shown only as a shortened hint. The secret access key signs requests with the key’s full permissions; it is the asset this chapter protects. The optional Cloudflare API token is a second secret, used only to discover public domains.

The data model makes the split visible: a saved connection holds only a description of where its secret is kept.

Source: crates/r2dock-core/src/connections.rs, lines 46 to 68

/// Where a connection's secret lives.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase", tag = "kind")]
pub enum SecretLocation {
    /// OS credential store entry, keyed by a random id.
    Keychain { reference: String },
    /// Held in memory for this session only (credential store unavailable).
    Session,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct ConnectionConfig {
    pub id: Uuid,
    pub name: String,
    pub account_id: String,
    pub access_key_id: String,
    pub jurisdiction: Jurisdiction,
    pub secret: SecretLocation,
    /// Optional Cloudflare API token, used only to read a bucket's public
    /// domains. Stored like the secret; absent in older config files.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub api_token: Option<SecretLocation>,
    // ...

Keychain carries a random reference to an operating system credential store entry; Session carries nothing, because a session secret lives only in process memory. The configuration is serialized to connections.json, and the derived serializer can only write the reference or the word session. There is no field into which a secret could be serialized: the leak is unrepresentable rather than prevented by a rule every writer must remember.

Operating System Credential Stores

Desktop systems ship a per-user secret store: the Keychain on macOS, Credential Manager on Windows, and the freedesktop Secret Service over D-Bus on Linux. Unlike a configuration file, they encrypt secrets at rest and stay out of casual reads and backups.

R2Dock uses the keyring crate (pinned at 3.6.3). Its documentation says entries are named by a service and a user name and that “there are no default features in this crate”; without a platform feature it uses a mock store that keeps nothing. crates/r2dock-secrets/Cargo.toml therefore selects apple-native, windows-native, or sync-secret-service with crypto-rust per target, as Architecture Decision Record (ADR) 0002 records (Linux needs libdbus-1). Because the documentation warns some stores are unsafe for concurrent or rapid access, every call is a short blocking operation in spawn_blocking (Chapter 5).

The program sees only the SecretStore trait (set, get, and a delete that ignores missing entries). KeyringStore uses the service name app.r2dock.credentials; MemoryStore keeps secrets in a mutex-protected map and lets the connection tests run without a keychain. Each entry is named by a fresh UUID from new_reference, so the keychain reveals no account or bucket and a replacement never overwrites the old entry. map_keyring_error folds errors into SecretError (NotFound, Unavailable, or Other; the Denied variant exists but this function never produces it) with fixed messages, so platform text naming a service or account goes no further; these map to the CredentialMissing and CredentialStoreUnavailable codes of AppError.

Probe, Then Fall Back

A store can exist and still fail, for example with no Secret Service daemon or a locked keyring. At startup KeyringStore::probe writes, reads back, compares, and deletes an entry named probe- plus a UUID; only if that succeeds is the store used, otherwise every secret goes to session memory. The backend label (“macOS Keychain”, “Memory for this session only”) appears in Settings and in the activity log’s app_start row.

When there is no safe place for a secret, many tools quietly write it to a file. R2Dock refuses: the crate comment says “There is no plaintext fallback”, PLAN.md section 9.2 agrees, and no code path writes a secret to disk. After a restart the user pastes the secret again; session_only_when_keychain_unavailable shows the summary reporting SecretStorage::Missing and client construction failing with ErrorCode::CredentialMissing. The form warns that the secret “will be kept in memory until R2Dock closes”.

Secret Values in Memory

In memory a secret is a secrecy::SecretString (0.10.3). The secrecy documentation says the crate wipes secrets on drop through zeroize, makes access explicit through ExposeSecret, and prevents leaks through debug logging; R2Dock’s test secret_debug_is_redacted checks the last point. It also says the crate does not lock pages with mlock, so a secret can still reach swap or a core dump.

The expose_secret() calls are the audit trail: the store adapter, the connection service, the Cloudflare API client’s bearer header, and the S3 client constructor. The comment in crates/r2dock-r2/src/lib.rs says this crate “is the only place (besides the secret store) that ever sees a secret”, which holds for request construction.

Source: crates/r2dock-r2/src/client.rs, lines 52 to 58

        let credentials = Credentials::new(
            params.access_key_id.clone(),
            params.secret.expose_secret().to_string(),
            None,
            None,
            "r2dock",
        );

The protection has gaps worth stating exactly. First, .to_string() makes an ordinary String moved into the SDK’s credential type; whether it is wiped depends on the AWS types, which the R2Dock code does not show. Second, the secret arrives over Inter-Process Communication (IPC) in ConnectionInput (src-tauri/src/dto.rs), whose secret and api_token are plain Option<String> dropped without zeroization after being copied into a SecretString. Third, ConnectionInput derives Debug, so format!("{input:?}") would print the secret. No code does that, and commands log only booleans such as new_secret, but PLAN.md section 9.2 says secret-holding types do not implement Debug “without redaction”. This type does not meet that rule; a custom Debug like the one ClientParams has in client.rs would close the gap.

Saving, Using, and Rotating a Secret

The Connect form sends a ConnectionInput to connection_test or connection_save in src-tauri/src/commands/connections.rs, thin commands that call ConnectionService::test or save in src-tauri/src/connections.rs. Figure 21.1 shows the path of a secret.

prepare validates every field. validate_secret requires non-empty visible ASCII of at most 256 bytes and cannot echo the value into an error. When editing with the secret field closed, the stored secret is used, so “Replace secret” never displays the old one. run_test then calls R2, so rejected credentials are never saved; save_edit_replace_remove_lifecycle shows a wrong replacement refused without the value in the message, while the old secret keeps working.

After the test, save writes the secret under a new UUID with store_new_reference, or holds it as a pending session secret. commit_then, the service’s transactional core, applies the change to a copy of the configuration, writes the copy atomically, and only then swaps it in and runs a publish closure under the write lock that stores session secrets and invalidates cached clients. As PLAN.md section 9.3 says, no reader can pair new settings with an old secret. If the write fails, nothing is published and new keychain entries are removed by discard_reference (failed_saves_leave_the_committed_state).

ConnectionService::client returns a cached R2Client or reads the secret on a blocking thread and builds one, caching it only if a per-connection generation counter is unchanged; invalidate bumps it on edit, removal, or authentication failure, so a client built from an old secret is never cached after a replacement. A missing secret yields a location-specific message (secret_removed_outside_app_is_reported).

PLAN.md section 9.3 describes rotation as write, test, switch, delete the old entry. The code tests first, so a rejected secret never touches the store, then writes, switches, and deletes. The configuration never points at nothing, and a crash between steps never loses the working secret.

Deleting the old entry can fail, for example on a locked keyring, so the old reference is added to a secret_cleanup list in the same atomic save that stops using it. ConnectionsFile::add_cleanup refuses a reference still in use (cleanup_never_records_a_reference_in_use). cleanup_secrets runs at startup and after every change; if even the configuration save fails, the reference goes to connections-cleanup.json (orphaned_secret_survives_a_restart_until_deleted). Both files hold only UUIDs. Deleting R2Dock’s copy does not revoke the key at Cloudflare; an exposed key must be revoked in the dashboard.

The Secret in the Webview

The secret crosses IPC once, from the form to the save command. Per PLAN.md section 9.2 it never enters TanStack Query or Zustand, and the command logs nothing about inputs.

Source: src/features/connections/ConnectForm.tsx, lines 136 to 156

  const runSave = async () => {
    setSubmitted(true);
    if (!valid || busy) return;
    setBusy("save");
    let saved: ConnectionSummary | null = null;
    try {
      // Saving always runs a connection test in Rust first.
      if (!passed) setTest({ kind: "testing" });
      saved = await connectionSave(buildInput());
    } catch (e) {
      fail(e);
    } finally {
      // Clear the secret and the API token once they have been saved.
      if (saved) {
        setSecret("");
        setApiToken("");
      }
      setBusy(null);
    }
    if (saved) await onSaved(saved);
  };

PLAN.md says the field “is cleared from React state immediately after the call”; the code clears it only after a successful save, so a user can fix another field and retry. The secret thus lives in JavaScript memory for the dialog’s lifetime, and JavaScript strings cannot be wiped. SecretField in src/components/Fields.tsx is a password input with autoComplete="new-password", spelling correction off, and copy and cut blocked while masked.

Once saved, the secret never comes back. ConnectionSummary carries access_key_hint (such as a1b2…9f0e), secret_storage, and the boolean has_api_token, and the lifecycle test asserts that neither the configuration file nor the serialized summaries contain the secret. The summary does carry the full account ID, which the edit form needs.

Redaction in Logs and Errors

Text about requests can still carry secrets, such as an echoed header or a presigned URL. RedactingWriter in src-tauri/src/logging.rs passes each log event through redact_text, and the filter keeps the AWS SDK and hyper at warning level. redact_text in crates/r2dock-core/src/redact.rs blanks everything after authorization on a line, the values after markers such as x-amz-signature, signature=, secret, and token=, and the account part of r2.cloudflarestorage.com hosts. Property tests (redaction_is_total_over_utf8, known_account_is_always_masked) and fake_secret_never_reaches_log_output cover it.

Pattern redaction is a safety net: a secret printed without a recognizable marker would pass. The primary defenses remain SecretString, fixed SecretError messages, and AppError, whose doc comment says messages never contain secrets, signatures, raw server responses, or full local paths. One discrepancy: PLAN.md section 9.7 says logs rotate at “5 files, 5 MB each”, but logging::init rotates daily and keeps five files with no size limit. The code is the authority.

Working on This Code

crates/r2dock-secrets/src/lib.rs owns the store abstraction, crates/r2dock-core/src/connections.rs the non-secret configuration and validators, src-tauri/src/connections.rs the lifecycle (test, save, replace, remove, cleanup), and ConnectForm.tsx the only interface that touches a secret. Run cargo test -p r2dock-secrets, cargo test -p r2dock-core for validators and redaction, and cargo test -p r2dock for the lifecycle tests, which use the local S3 server from r2dock-testkit and an in-memory store. The real keychain test is ignored; run it per platform with cargo test -p r2dock-secrets -- --ignored.

No command may return a secret and no serialized type may hold one; if you add a field to ConnectionSummary, confirm the lifecycle test still proves the secret absent. Keep secrets in SecretString, justify every expose_secret, run store calls in spawn_blocking, never add a plaintext fallback, and record old references for cleanup in the same save that stops using them. Pitfalls: logging a ConnectionInput with {:?}, and formatting a store error’s text into a message.

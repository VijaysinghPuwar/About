33 Complete End-to-End Execution Walkthrough

Earlier chapters each opened one subsystem. This chapter follows a single real upload through all of them, in the order the code runs, naming every function and file on the way. Then it kills the application in the middle of that upload and follows what happens on the next launch. The goal is to show how the pieces hand work to each other, so that a contributor can set a breakpoint anywhere on the path and know what came before and what comes next. The chapters that own each concept are named along the way.

The Scenario

A user has a connection open on the fictional bucket media-library and is looking at the folder videos/ in the explorer. They click Upload and pick one file, lecture.mp4, which is 200 mebibytes (MiB). The settings are the defaults: three concurrent jobs, a multipart threshold of 100 MiB, the conflict policy “Ask”, and compression turned off (the enabled field of the compression settings defaults to false in crates/r2dock-core/src/compression.rs). The optional compression stage is described as a detour at the end.

Figure 33.1 shows the whole conversation between the four actors: the React interface, the Tauri commands, the transfer engine, and Cloudflare R2.

Step 1: Picking the File in Rust

The Upload button in src/features/browser/Explorer.tsx calls pickAndUpload in src/features/browser/upload.ts, which calls pickUploadFiles from src/ipc/commands.ts, the typed wrapper for the command pick_upload_files. In src-tauri/src/commands/transfers.rs, that command opens an activity record and calls dialogs::pick_files in src-tauri/src/dialogs.rs, which opens the native picker and bridges its callback into async Rust with a tokio::sync::oneshot channel. The chosen paths go to register_selection, which stores them in the selections registry of AppState and returns a Selection: an opaque identifier, a count, and up to three display names. The path never reaches the webview (Chapter 22, Tauri Security Architecture). The registry is a map from random identifiers to values, with an expiry and a size cap.

Source: src-tauri/src/state.rs, lines 47 to 70

impl<T> Registry<T> {
    pub fn insert(&self, value: T) -> String {
        let id = Uuid::new_v4().simple().to_string();
        let mut items = self.items.lock();
        let now = Instant::now();
        items.retain(|_, (t, _)| now.duration_since(*t) < TOKEN_TTL);
        if items.len() >= REGISTRY_CAP
            && let Some(oldest) = items
                .iter()
                .min_by_key(|(_, (t, _))| *t)
                .map(|(k, _)| k.clone())
        {
            items.remove(&oldest);
        }
        items.insert(id.clone(), (now, value));
        id
    }

    /// Remove and return a value (single use).
    pub fn take(&self, id: &str) -> Option<T> {
        let (t, v) = self.items.lock().remove(id)?;
        (t.elapsed() < TOKEN_TTL).then_some(v)
    }
}

Every insert drops entries older than TOKEN_TTL (15 minutes) and evicts the oldest when 256 (REGISTRY_CAP) are present, so a looping page cannot grow memory without bound, and a random universally unique identifier (UUID) cannot be guessed. get, used for selections, leaves the entry in place; take, used for plans, removes it, which makes a plan single use.

Step 2: Planning the Upload

pickAndUpload then calls uploadSelection, which calls uploadPrepare(selection.id, connectionId, bucket, prefix). The command upload_prepare validates the bucket and prefix with bucket_arg and prefix_arg from src-tauri/src/commands/mod.rs and runs upload_prepare_inner. That function looks up the paths with state.selections.get and calls scan from crates/r2dock-transfer/src/scan.rs inside tokio::task::spawn_blocking, because walking the disk blocks (Chapter 5, Tokio and Asynchronous Execution). The scan skips symbolic links and names R2 cannot store, stops at MAX_FILES (200,000), and records each file’s size and FileIdentity (device and inode on Unix), which later lets the upload refuse a file replaced between planning and sending (Chapter 23, Filesystem Security).

upload_items in src-tauri/src/planning.rs builds each destination key with key_for (here videos/lecture.mp4). With compression off, no estimate is computed. count_conflicts asks R2 which keys exist: one existence check per key, eight at a time, for up to 100 keys (HEAD_LIMIT), or a listing of the top-level folders beyond that. It runs through with_client, which takes the cached R2Client from ConnectionService and records the outcome for the connection status.

needs_review is true for folders, more than 20 files, conflicts, skipped items, a too-large selection, or a compression estimate; none applies here. The plan is stored with state.uploads.insert(PreparedUpload { ... }), and the webview receives an UploadPlan with counts, the review flag, and default_policy (“Ask” here), but no local path. An upload_prepare row goes to the activity log.

Step 3: Starting the Plan

With no review needed, startPlan calls uploadStart(plan.planId, policy, compress). upload_start_inner takes the plan out of the registry (a second call fails with “This upload expired. Choose the files again.”), creates any empty-folder markers, and builds one JobSpec::Upload(UploadSpec { ... }) per file with the connection, bucket, key, local path, size, policy, scanned identity, and compression request (None here). Several files or a folder would also get a GroupInfo, which the scheduler uses for fairness. It calls state.engine.enqueue(specs, group) and returns the job count; the frontend toasts “Uploading 1 file to …” and the activity log records upload_start.

Step 4: Enqueue and the Queue Journal

Engine::enqueue in crates/r2dock-transfer/src/engine/mod.rs takes the jobs lock once for the batch. Per spec it creates a UUID, a Queued snapshot (new_snapshot marks it pausable because it will be multipart), and an Entry with an empty ResumeState, a progress Counter, and the next sequence number, and pushes the identifier onto order and queue. Still under the lock it calls queue.upsert_many(intents), where each intent from Entry::intent holds the spec without resume data. The queue journal only records the change in memory; within one second (QUEUE_BATCH) its writer appends a line to queue.log and calls sync_data (Chapter 14, Journals and Persistent Queues). Saving under the lock guarantees that an instantly finished job cannot remove its record before it is written. After the lock, enqueue emits TransferEvent::Added in chunks of at most 500 jobs and wakes the scheduler. It starts nothing itself.

Step 5: The Scheduler Picks the Job

The scheduler task calls Inner::schedule. schedule_compression in engine/compress.rs finds nothing to encode. The pass then counts active jobs, builds per-group counts and the busy set of keys being uploaded, and picks the first eligible job within the 256-entry window (Chapter 6, The Transfer Scheduler). Under the same lock it sets Preparing, creates an Arc<RunControl> (the cancellation tokens and stop flag used by pause and cancel), and marks the key busy. After the lock it emits Updated, wakes the progress ticker, and calls tokio::spawn(run_job(...)).

Step 6: run_job Builds the Context

run_job first calls gate_copy, which for a compressed copy re-verifies its SHA-256 and the original’s fingerprint before every attempt; with no copy it returns CopyGate::Go. It then asks the ClientProvider for a client, racing the request against the cancel token with tokio::select!. In the app the provider is EngineClients in src-tauri/src/state.rs, an adapter over ConnectionService::client, so transfers reuse the cached client and the secret stays in Rust. It builds a JobCtx (crates/r2dock-transfer/src/ctx.rs) with the client, the run control, the byte counter, the shared part_slots semaphore, parts_per_job, the threshold, the job’s resume slot, and a Hooks object, and calls upload::run. The hooks (state, parts, renamed, total, checkpoint, persist_now) are the only way upload code reports back to the engine, which is why upload.rs can be tested without the scheduler.

Step 7: Deciding Between Resume, Single, and Multipart

upload::run in crates/r2dock-transfer/src/upload.rs sets Preparing (needed again after a retry) and opens the file with SourceFile::open on a blocking thread. That uses O_NOFOLLOW on Unix, accepts only a regular file, fails with a file-changed error if the identity differs from the scan, and records a Fingerprint of length and modification time. Then comes the decision.

Source: crates/r2dock-transfer/src/upload.rs, lines 153 to 173

// Continue a saved multipart upload when the file is unchanged.
let saved = ctx.resume.lock().clone();
if let ResumeState::Multipart(state) = saved {
    if state.fingerprint == source.fingerprint && state.key == spec.key {
        return multipart(ctx, spec, source, Some(state)).await;
    }
    let _ = ctx
        .client
        .abort_multipart(&spec.bucket, &state.key, &state.upload_id)
        .await;
    ctx.clear_resume();
}

if let Err(outcome) = resolve_key(ctx, spec).await? {
    return Ok(outcome);
}
if use_multipart(size, ctx.multipart_threshold) {
    multipart(ctx, spec, source, None).await
} else {
    single(ctx, spec, source).await
}

With no saved state, resolve_key applies the policy: for “Ask” one HeadObject request (HEAD) through client.exists finds the key free. (An existing object would end the run as NeedsDecision under “Ask” or Skipped under “Skip”; “Keep both” would pick a new name and report it through hooks.renamed.) use_multipart in crates/r2dock-core/src/parts.rs is true at or above the threshold or above the 5 GiB single-request limit, so the file goes multipart. A smaller file would go to single: one PutObject with Content-MD5 and, unless the policy is “Replace”, If-None-Match: *, which R2 evaluates atomically; it takes no part permit and cannot pause (Chapter 9, Multipart Uploads in Depth). The first branch of the excerpt returns in the recovery scenario.

Step 8: Creating the Upload and Saving Resume State

multipart calls create_upload. part_size_for picks the larger of 16 MiB and the size divided by 9,000, rounded up to a whole MiB: 16 MiB. It sends CreateMultipartUpload, builds a MultipartState holding the multipart upload identifier (upload ID), the key, the part size, the source fingerprint, and an empty map of finished parts, and calls ctx.save_resume. That stores the state in the job’s resume slot and calls Hooks::checkpoint, which upserts a full JournalEntry into the resume journal. Within 200 milliseconds (JOURNAL_BATCH) the journal rewrites journal.json atomically: temporary file, sync_all, rename (write_bytes_atomic in crates/r2dock-core/src/storage.rs). That short window before the ID is durable is one of the gaps listed in Chapter 15 (Crash Consistency and Recovery).

Step 9: Sending Parts Under Two Limits

plan_parts yields 13 parts, twelve of 16 MiB and a last of 8 MiB. multipart reports parts(0, 13), sets Running, and keeps at most parts_per_job (4) part futures in a FuturesUnordered. Each future first takes one of the 8 global part_slots permits with acquire_owned, re-checks for pause or cancel, and runs upload_part; acquiring inside the future prevents hold-and-wait deadlocks between jobs (Chapter 6; test concurrent_multipart_jobs_do_not_deadlock). upload_part computes the part’s MD5 on a blocking thread through a 1 MiB buffer, then sends UploadPart with Content-MD5 and a retryable body from range_body in body.rs that streams 64 KiB chunks, reopening the file with an identity check on each attempt (Chapter 8, The S3-Compatible Protocol). Memory per part is bounded by those buffers, not the part size. Chunks add to the counter’s in_flight bytes, and settle commits the part’s length on success or removes the uncounted bytes on failure, so a retry never counts twice.

Each finished part returns as (number, PartDone { etag, md5, len }); the loop inserts it into state.done, checkpoints again with save_resume, and reports the count. On a part failure the loop stops queueing, lets started parts finish, and returns the first error to run_job, whose retry rules Chapter 16 (Retries, Cancellation, and Idempotency) owns.

Step 10: Progress Over the Channel

While parts run, the progress ticker in engine/mod.rs wakes every 250 milliseconds, reads each active job’s counter.total() under the jobs lock, updates speed and remaining time with SpeedMeter, and emits one TransferEvent::Progress holding a ProgressUpdate for each job that changed. Every event passes through Inner::emit, which holds the delivery lock and calls the sink installed by transfer_subscribe in src-tauri/src/commands/transfers.rs. The webview called that command once at startup from startTransferSubscription (invoked in Bootstrap in src/app/App.tsx), passing a Tauri Channel<TransferEvent>. The sink runs under the delivery lock, so it stays quick: for Updated events it calls record_job, which writes an activity row only for states worth keeping (completed, failed, cancelled, skipped, needs decision, paused, retrying, interrupted), and note_transfer, which updates the connection’s online status; it counts finished jobs so a background notification can be sent when the engine goes idle; and it forwards every event with on_event.send, which serializes it to JSON for the webview. There, the channel’s handler only buffers events.

Source: src/features/transfers/subscription.ts, lines 163 to 184

/** Subscribe to transfer events once for the app's lifetime. */
export function startTransferSubscription(client: QueryClient): void {
  if (started) return;
  started = true;
  // ...
  let pending: TransferEvent[] = [];
  const flush = () => {
    const events = pending;
    pending = [];
    const before = useTransferStore.getState().jobs;
    useTransferStore.getState().applyMany(events);
    for (const event of events) afterEvent(client, before, event);
  };
  transferSubscribe((event) => {
    if (pending.length === 0) setTimeout(flush, FLUSH_MS);
    pending.push(event);
  }).catch((e: unknown) => {
    started = false;
    toast.danger(`Transfer updates are not available. ${errorMessage(e)}`);
  });
}

The first event of a burst schedules a flush 50 milliseconds later (FLUSH_MS). The flush applies the batch with applyMany, which calls reduceTransferBatch in transferStore.ts; that reducer copies the job map and order at most once per batch, puts Added and Updated snapshots, and overwrites only the byte, speed, time, and part fields for Progress (Chapter 28, UI Performance and Large Queues). Meanwhile useExplorerData in src/features/browser/useExplorerData.ts shows a ghost row for the upload, because its key is in the open folder but not yet in the listing (Chapter 27, Frontend State Management).

Step 11: Verifying and Completing

With all 13 parts recorded, multipart sets Verifying and calls ensure_unchanged, which compares the fingerprint (length and modification time) again; a file edited meanwhile aborts the upload and fails the job with a file-changed error instead of publishing mixed content. Because R2 has no conditional CompleteMultipartUpload, it repeats the existence check under “Ask”, checks once more for a cancel, and sends CompleteMultipartUpload with every part number and entity tag (ETag). It compares the returned ETag with the multipart ETag computed from the part MD5s and only logs a warning on a mismatch (Chapter 9). ctx.clear_resume() then removes the job from the resume journal, and run returns Outcome::Completed.

Step 12: Finishing in the Engine

Back in run_job, Outcome::Completed leads to Inner::finish.

Source: crates/r2dock-transfer/src/engine/mod.rs, lines 882 to 893

/// Record a final state, history, and journal cleanup.
fn finish(&self, id: JobId, state: JobState, error: Option<AppError>) {
    // Clean up before announcing the final state, so anyone who sees
    // "completed" never finds the job's copy or journal entry still there.
    if matches!(
        state,
        JobState::Completed | JobState::Cancelled | JobState::Skipped
    ) {
        self.journal.remove(id);
        // The copy is no longer needed; a finished job keeps its result.
        self.drop_compressed(id, state != JobState::Completed);
    }

Cleanup comes before the announcement. set_state(Completed) then sets finished_at, removes the job from the queue journal (a removal line within a second), and emits the final Updated; finish appends a HistoryEntry to history.jsonl on a blocking thread; and run_job clears its run control and wakes the scheduler. In the sink, record_job writes a transfer_completed row with the job tag, direction, key (a short hash code unless names are turned on), bytes, attempt, and parts=13/13, handed to the activity writer thread so no caller waits for the disk. If the window is in the background, the user gets the notification “1 file transferred.”

Step 13: Refreshing the Listing

In the webview, afterEvent sees a job that has just become terminal, sets historyChanged, records { connectionId, bucket, key } in changedObjects, and calls scheduleRefresh, which debounces for 800 milliseconds (REFRESH_MS) so a burst of completions causes one refresh. invalidateObjectChanges in src/app/objectChanges.ts then invalidates every listing of the bucket through the prefix key ["objects", connectionId, bucket], bucket searches, cached details and previews of the changed keys, and resets folder sizes that contain them. Only mounted queries refetch, so the open videos/ listing calls object_list again, and the ghost row, kept and marked done while its finishedAt is newer than the listing’s dataUpdatedAt, gives way to the real row. When no job of the batch is still moving, summarize toasts “Uploaded 1 file to …” with a Show action.

That is the whole path: three commands, one enqueue, one spawned task, eighteen requests to R2 when nothing has to be retried (the planning HEAD, a HEAD for the policy, a create, 13 parts, a second HEAD, and the completion), and a stream of events that the webview batches and reduces.

The Compression Detour

With compression on and an audio or video file, the path takes a detour owned by Chapters 17 to 20. upload_prepare_inner computes an estimate on a blocking thread, which forces the review dialog, and upload_start_inner attaches a CompressionRequest, so needs_compression is true. schedule_compression moves the job from Queued to Compressing when the encoder gate allows and spawns compress_job; a compressing job holds no upload slot. When the encode ends, compress_job checkpoints the result, saves the intent, and calls requeue_front. From there the job follows steps 5 to 13, except that gate_copy verifies the copy’s SHA-256 before every attempt and finish deletes the copy.

Second Scenario: Killed Mid-Upload

Now replay the same upload, but terminate the process forcibly (for example with kill -9, or by the operating system) after six of the 13 parts have been sent and two more are in flight.

What the kill leaves behind

The normal exit path, the RunEvent::Exit handler in src-tauri/src/lib.rs that calls state.engine.flush() and gives the activity writer two seconds, does not run. Pending journal batches (up to about 200 milliseconds of resume updates and one second of queue changes) and unwritten activity rows are lost. On disk, the queue files hold the accepted job, and journal.json holds its MultipartState with the upload ID and the parts recorded by the last batch, probably all six. On R2, the upload exists with six to eight parts, since the two in flight may or may not have been stored. Nothing is visible at the key.

Startup: loading and restoring

On the next launch, run in src-tauri/src/lib.rs builds the EngineConfig and calls Engine::start. Figure 33.2 summarizes everything that follows.

Engine::start loads journal.json with Journal::load and replays the queue with Journal::load_logged, which stops at a line cut short by the crash and compacts at once (Chapter 14). Engine::restore merges both, letting the resume entry win, sorts by sequence number, puts every job in Interrupted, and restores visible progress.

Source: crates/r2dock-transfer/src/engine/mod.rs, lines 230 to 242

The row shows 96 MiB and six parts done. Restored jobs do not enter the run queue. In parallel, lib.rs runs sweep_work_dir on a blocking thread and locates the compression tools. When the webview subscribes, Engine::subscribe sends a Snapshot under the delivery lock, the reducer replaces its state, and InterruptedBanner in src/features/transfers/InterruptedBanner.tsx says “1 transfer did not finish before R2Dock closed. Started downloads and large uploads continue where they stopped; the rest start again.”, offering Resume all, Review, and Discard.

Resuming

Resume all calls controlMany in src/features/transfers/actions.ts, which invokes transfer_control for one job (or transfer_control_many for several). Inner::control moves the job from Interrupted to Queued under the jobs lock, appends it to the run queue, emits Updated, and wakes the scheduler. Steps 5 and 6 repeat, but the JobCtx now carries the saved MultipartState.

In upload::run, SourceFile::open checks the identity again, so a file replaced during the downtime fails cleanly. Then the first branch of the step 7 excerpt applies: if fingerprint and key match the saved state, multipart continues it; otherwise the old upload is aborted and the job starts fresh under the conflict policy.

multipart first calls reconcile, which pages through ListParts (with a guard against a repeated marker) and keeps only recorded parts that R2 still lists with the same ETag. Parts R2 holds but the journal never recorded, like the two in flight, are uploaded again under the same numbers, replacing them. The counter restarts from the kept bytes, the remaining parts run through the same permit-limited loop, and verification and completion follow step 11.

The other recovery branches

reconcile returns false when ListParts says the upload is gone (R2Error::NoSuchKey or R2Error::Service): someone aborted it, R2 removed it (Cloudflare aborts incomplete uploads after 7 days by default), or the app completed it just before dying. finished_before_restart detects the last case: if every planned part was recorded and HEAD shows the source size and exactly the multipart ETag computed from the recorded MD5s, the job completes with no bytes sent. Otherwise the conflict policy applies and a new upload starts. Other ListParts errors go through the retry path in run_job.

Discard sends cancel instead; Inner::control moves the job to Cancelled and discard_partial aborts the saved upload in a background task.

What this scenario does not cover

The repository’s restart tests do not kill a process. paused_multipart_resumes_after_restart in crates/r2dock-transfer/tests/engine.rs pauses a multipart upload after a part, calls engine.flush(), starts a new engine on the same folder against the same local S3 server, and checks that the job returns as Interrupted with parts done and then completes with the right bytes; tests/recovery.rs writes crashed journals by hand. They exercise the same restore and reconcile code, but two windows that only a real kill opens remain analysis: an upload ID created but not yet saved (a new upload is made and the orphan waits for R2’s cleanup), and a completed upload whose last part was not recorded (the conflict policy decides). Chapter 15 lists them in its failure matrix.

Working on This Code

This chapter is also a debugging map. Problems before a job appears live in src-tauri/src/commands/transfers.rs, src-tauri/src/planning.rs, or crates/r2dock-transfer/src/scan.rs; a job stuck in Queued points to Inner::schedule and schedule_compression; failures while sending point to upload.rs and the run_job error branch; a listing that does not refresh points to afterEvent and invalidateObjectChanges. The activity log, a comma-separated values (CSV) file, shows how far an upload got.

End-to-end behavior is covered by cargo test -p r2dock-transfer --test engine (the round trip, multipart, conflict, pause, and restart tests), cargo test -p r2dock-transfer --test recovery, cargo test -p r2dock for the command layer and planning, and npm test for the reducer, subscription, and ghost rows. To watch the real app follow this path without a cloud account, run it against the local S3 server described in Chapter 34 (Your First Contribution).

The invariants along the path are the ones every earlier chapter insisted on: paths stay in Rust behind opaque identifiers; queue saves happen under the jobs lock; cleanup precedes announcement; parts acquire permits inside their own futures; the sink never blocks; and recovery never restarts work on its own or trusts the journal without asking R2.

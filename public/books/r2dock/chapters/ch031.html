22 Tauri Security Architecture

A Tauri application pairs a Rust core with full operating system access and a web page rendered by the system webview. R2Dock’s page is not hostile by design, but it renders data R2Dock does not control (object names, image bytes, text files, server error messages), and web pages have a long history of being turned against their hosts. This chapter explains where R2Dock draws the line: which commands the page may call, which plugins are reachable, what the Content Security Policy (CSP) permits, and how commands treat arguments as untrusted. How the frontend calls commands is taught in Chapter 26 (React and Tauri IPC).

Two Trust Groups and One Bridge

The Tauri security overview says Tauri’s model “differentiates between Rust code written for the application’s core and frontend code”. Core code can use system resources freely; webview code “has only access to exposed system resources via the well-defined IPC layer”, the Inter-Process Communication (IPC) layer that “is the bridge for communication between these two trust groups”. Capabilities decide which commands the webview may invoke, and each command enforces finer rules itself.

SECURITY.md states R2Dock’s consequences: secrets live only in Rust, no command returns a secret, the webview has no file system, shell, or HTTP plugin access, commands are allowlisted, and local paths are opaque identifiers. Read the rest of this chapter with one question in mind: if an attacker ran arbitrary JavaScript in the webview, what could they do? Figure 22.1 shows the boundary.

Only invoke calls, r2dock-media requests (Chapter 24, The Custom Media Preview Protocol), and events cross it; the credential store, file system, and network are reachable only from Rust.

The Command Allowlist

By default every command registered with tauri::generate_handler! can be called by every window; the capabilities documentation points to AppManifest::commands in the build script to restrict this, and R2Dock uses it.

Source: src-tauri/build.rs, lines 63 to 70

fn main() {
    let attributes = tauri_build::Attributes::new()
        .app_manifest(tauri_build::AppManifest::new().commands(COMMANDS));
    if let Err(e) = tauri_build::try_build(attributes) {
        println!("cargo:warning=tauri build failed: {e}");
        std::process::exit(1);
    }
}

COMMANDS lists 56 names. From it tauri-build generates, under src-tauri/permissions/autogenerated/, one committed TOML file per command defining allow-<name> and deny-<name> permissions “without any pre-configured scope”. Tauri scopes can restrict command arguments such as allowed paths; R2Dock’s commands use none and check arguments themselves. A permission grants nothing until, per the permissions documentation, it is referenced in a capability.

Three lists must therefore agree: the handlers in src-tauri/src/lib.rs, COMMANDS in build.rs, and the capability file, as the module comment in src-tauri/src/commands/mod.rs reminds contributors. In the audited commit all three contain the same 56 names.

The Capability File

R2Dock has one capability for one window.

Source: src-tauri/capabilities/main.json, lines 1 to 16

{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main",
  // ...
  "windows": [
    "main"
  ],
  "permissions": [
    "core:app:allow-version",
    "core:event:allow-listen",
    "core:event:allow-unlisten",
    "core:window:allow-is-focused",
    "core:path:default",
    "allow-app-info",
    "allow-clipboard-write",
    // ...

The elided description promises “only the listed app commands and minimal core features” and “no fs, shell, or http plugin access”; the rest of the array is the 56 allow- entries. The capability is bound to main, the only window in tauri.conf.json. There is no remote section, which the capabilities documentation says is needed to give a remote origin command access; even a webview somehow navigated to a remote page would have none.

Of the five core permissions, the core permissions reference shows core:event:allow-listen and allow-unlisten enable event subscriptions, which the drag and drop bridge in src/features/browser/useDragDrop.ts needs. The other three enable version, is_focused, and the path helpers (resolve_directory, join, basename, and others). The audited src/ imports only @tauri-apps/api/core and @tauri-apps/api/event, so those three appear unused. They grant no file access, but core:path:default lets page code learn directory paths such as the home folder, which contains the account name. Removing them would be a possible least-privilege improvement, not a demonstrated vulnerability, and should be confirmed with a build.

src-tauri/src/lib.rs initializes single instance, dialog, notification, clipboard manager, and opener plugins, but grants none of their permissions to the page. Dialogs, clipboard writes, notifications, and URL opening happen only through R2Dock’s own commands, which call the plugins from Rust after validation; pickers in src-tauri/src/dialogs.rs keep their paths in Rust. PLAN.md section 9.4 lists plugin permissions and an updater in the capability; the code is stricter, and there is no updater in src-tauri/Cargo.toml at all, so the plan’s threat model row for updater signature verification describes a feature that does not exist in this version. The dangerous fs, shell, and http plugins are not even dependencies.

The Webview Configuration and CSP

tauri.conf.json sets withGlobalTauri to false, so the API is not injected as window.__TAURI__ (per the configuration reference) and script injected through cross-site scripting (XSS) has a harder time finding it. freezePrototype is true, running Object.freeze(Object.prototype) to block prototype pollution. And it defines the CSP.

Source: src-tauri/tauri.conf.json, lines 27 to 42

    "security": {
      "csp": {
        "default-src": "'self'",
        "script-src": "'self'",
        "style-src": "'self' 'unsafe-inline'",
        // ...
        "media-src": "'self' r2dock-media: http://r2dock-media.localhost",
        "font-src": "'self' data:",
        "connect-src": "ipc: http://ipc.localhost",
        "object-src": "'none'",
        "frame-src": "'none'",
        "base-uri": "'none'",
        "form-action": "'none'"
      },
      "freezePrototype": true
    }

The elided img-src allows 'self', blob:, data:, and both media scheme spellings. A CSP tells the engine which origins may supply scripts, images, styles, and connections, limiting the damage of an injection bug. Scripts come only from the bundle, with no unsafe-eval, so injected text cannot become code. Connections are limited to the IPC transport (ipc: and http://ipc.localhost), so page code cannot fetch data to an attacker’s server. The Tauri CSP guide says Tauri adds hashes and nonces at build time (“local scripts are hashed, styles and external scripts are referenced using a cryptographic nonce”), which R2Dock does not disable, and its advice to “avoid loading remote content such as scripts served over a CDN” is followed.

Two relaxations remain. style-src includes 'unsafe-inline', which PLAN.md section 9.4 says to “try to remove”; inline styles cannot run script, so the risk is CSS tricks such as overlaying interface elements. How it interacts with Tauri’s injected style nonces was not verified; under the CSP specification a nonce makes browsers ignore 'unsafe-inline', so the effective policy may be stricter. data: and blob: in img-src do not allow script in an image context. The code also differs from the plan’s policy by adding data: to font-src and the http://r2dock-media.localhost spelling. The latter is required: the Tauri Builder documentation says custom schemes are served as http://<scheme>.localhost/ on Windows and Android, so previews would otherwise break on Windows.

PLAN.md requires developer tools off in release builds. The configuration reference says devtools “requires devtools feature flag to enable it in release builds”, and src-tauri/Cargo.toml enables no Tauri features, so release builds have no inspector.

Validating Every Argument

Capabilities say nothing about arguments; the capabilities documentation says they do not protect against “incorrect scope checks in commands”. R2Dock’s handlers are thin: “validate input, call a service, map errors”. Serde deserialization is the first filter, so an invalid Uuid or an unknown ConflictPolicy variant never reaches R2Dock code, and Preferences::sanitized in crates/r2dock-core/src/settings.rs clamps numbers (concurrency to 1 to 8). Strings get dedicated validators in src-tauri/src/commands/mod.rs: bucket_arg (3 to 63 lowercase letters, digits, and hyphens), key_arg (non-empty, at most 1,024 bytes, no control characters), and prefix_arg (empty or ending in /). These keep S3 requests well formed; local path safety is a separate matter for Chapter 23 (Filesystem Security).

Higher-risk strings get specific treatment. Opening arbitrary URLs is dangerous on a desktop, since file: and custom scheme handlers can launch applications.

Source: src-tauri/src/commands/app.rs, lines 77 to 87

fn open_external_inner(
    app: &tauri::AppHandle,
    url: String
) -> CmdResult<()> {
    let ok = url.starts_with("https://")
        && url.len() < 4096
        && !url.chars().any(|c| c.is_control() || c.is_whitespace());
    if !ok {
        return Err(AppError::invalid_input(
            "Only https links can be opened."
        ));
    }
    app.opener()
        .open_url(url, None::<&str>)
        .map_err(|_| AppError::internal("Could not open the link."))
}

The host is not restricted, so a compromised page could open any HTTPS site in the browser, a phishing aid at most. clipboard_write caps text at 1 MiB and logs only its length. open_log_folder, open_activity_folder, and transfer_show take no path; Rust already knows it, or looks up a job by UUID. validate_public_base_url accepts only https:// plus a host of letters, digits, dots, hyphens, and colons, rejecting ?, #, spaces, and @; the unit test public_urls checks that https://user@evil.com is refused. The @ rule blocks a trick such as https://trusted.example@evil.example, which looks like one host but connects to another.

Local Paths Never Come From the Page

If a command accepted a path from the page, a compromised page could upload ~/.ssh/id_ed25519 or download over a startup script. The OWASP path traversal guidance recommends to “use indexes rather than actual portions of file names”, and R2Dock applies the same idea to local paths. Local paths come only from native pickers in src-tauri/src/dialogs.rs, operating system drag and drop (WindowEvent::DragDrop in src-tauri/src/dragdrop.rs), and the Settings folder pickers, all in Rust. register_selection in src-tauri/src/commands/transfers.rs stores the paths and gives the page an identifier, a count, and up to three display names (with control characters shown as placeholders), never a full path. Uploads go from selection identifier to upload_prepare to a plan identifier to upload_start; downloads go to the configured folder or one picked at that moment.

The identifiers live in a generic Registry in src-tauri/src/state.rs: random UUIDs that expire after 15 minutes (TOKEN_TTL), at most 256 per kind (REGISTRY_CAP, oldest evicted). take makes plans and delete confirmations single use, while get lets selections be retried; registry_is_single_use_and_capped tests both. Page code cannot forge an identifier, only use ones created for a real dialog or drop. settings_get returns folders with the home directory shown as ~ (redact_path), Preferences has no path fields, and “Copy path” is performed by Rust.

What Remains in Reach of a Compromised Page

Such an attacker could not read local files, run programs, contact arbitrary hosts, obtain stored secrets, or write to chosen paths. They could still call any of the 56 commands with valid arguments: listing and previewing objects, downloading into the configured folder, uploading files selected in the last 15 minutes, and deleting objects. delete_preview returns both the confirmation token and the typed phrase, because the page must display the phrase, so tokens guard against interface mistakes, not a compromised page. PLAN.md section 9.8 says a compromised webview “could still delete one object per call within confirmation rules”; in fact the bulk path could delete whatever delete_preview enumerates, including whole prefixes. Chapter 25 (Threat Modeling and Remaining Risks) weighs this. The defenses against compromise itself are the CSP, no remote content, rendering remote data as React text (the frontend has no dangerouslySetInnerHTML), and showing SVG only through <img>.

Working on This Code

A new command touches four places: the handler under src-tauri/src/commands/, generate_handler! in src-tauri/src/lib.rs, COMMANDS in src-tauri/build.rs, and allow-<name> in src-tauri/capabilities/main.json; commit the regenerated permission file. A forgotten capability entry fails safely at runtime. Validate every string with the helpers in commands/mod.rs or r2dock-core, never accept a local path from the page, and never return a secret or full path (use AppState::display_path).

Review tauri.conf.json changes closely: no unsafe-eval, remote script hosts, broad connect-src, or withGlobalTauri; no fs, shell, or http plugins; no plugin permissions for the page when a Rust command can do the job; and a stated reason for any new permission. cargo test -p r2dock covers the registry and settings, cargo test -p r2dock-core the validators, and npm test the frontend; CI also runs clippy with -D warnings and checks that the TypeScript bindings in src/ipc/bindings are current.

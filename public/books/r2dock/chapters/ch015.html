9 Multipart Uploads in Depth

Uploading a 40 GB video archive in one HTTP request would be fragile, and S3-compatible services do not accept a single request that large anyway. Multipart upload splits an object into numbered parts that are sent independently and in parallel, then assembled by the server in one final step. It is the most stateful protocol R2Dock speaks, and pause, resume after a crash, and retry without starting over all depend on it. This chapter follows planning, sending, completing, and resuming. It builds on Chapter 8 (The S3-Compatible Protocol); the scheduler is Chapter 6 (The Transfer Scheduler) and the journal is Chapter 14 (Journals and Persistent Queues).

The Protocol and R2’s Limits

CreateMultipartUpload announces the key and metadata and returns a multipart upload identifier (upload ID). UploadPart sends one numbered part and returns an entity tag (ETag) for it. CompleteMultipartUpload sends the part numbers with their ETags, and only then does the object appear at its key. AbortMultipartUpload discards the parts, and ListParts reports which parts the server holds. The AWS UploadPart reference adds two rules R2Dock relies on: part numbers run “from 1 to 10,000, inclusive,” and uploading the same part number again means “the previously uploaded part is overwritten.”

Cloudflare’s multipart objects page sets R2’s limits: at most 10,000 parts, a minimum part size of 5 MiB “except for the last part,” a maximum of 5 GiB, and “All parts except the last must be the same size.” Multipart objects can reach 5 TiB; single uploads stop at 5 GiB. “Incomplete multipart uploads are automatically aborted after 7 days by default.” The equal-size rule is stricter than Amazon S3’s and is why R2Dock plans one part size per file. These limits are constants in crates/r2dock-core/src/parts.rs, a crate with no AWS software development kit (SDK) or Tauri dependency, so planning can be property tested in isolation.

Single Upload or Multipart

use_multipart in parts.rs chooses multipart when the file is at least the threshold or larger than MAX_SINGLE_PUT. The threshold is raised to at least 5 MiB, since a smaller multipart upload would have a single part below the minimum; the test multipart_threshold checks both boundaries. The threshold comes from multipart_threshold_mib in crates/r2dock-core/src/settings.rs: default 100, clamped by sanitized() to 16 to 4,096 MiB, and copied into the engine at startup and on settings changes. Because the clamp stays at or below 4 GiB, the MAX_SINGLE_PUT clause never decides anything in the shipped app; it is a backstop for other configurations such as tests. Multipart has fixed costs (extra requests, a journal write per part), and PLAN.md section 8.4 records 100 MiB as a default to tune, not a measured optimum.

The single request path

single in crates/r2dock-transfer/src/upload.rs hashes the file with MD5 on a blocking thread, then sends PutObject with Content-MD5 and the same streaming body used for parts. Unless the conflict policy is Replace, it adds If-None-Match: *. The R2 extensions page says such conditions “are evaluated atomically, as part of the same write that commits the object,” so a file that appeared at the key after the earlier check is not overwritten. A 412 becomes Outcome::Skipped under Skip and Outcome::NeedsDecision otherwise. A single request cannot pause midway (single_put_cannot_pause).

After success, ensure_unchanged fails the job with “File changed while uploading” if the size or modification time changed. R2 has already stored bytes matching the digest; the error means the stored copy may not be the latest version, not that nothing was written.

Planning the Parts

Source: crates/r2dock-core/src/parts.rs, lines 39 to 50

/// Choose a part size: `max(16 MiB, ceil(size / 9,000))`,
/// rounded up to a whole MiB.
pub fn part_size_for(file_size: u64) -> Result<u64, PartError> {
    if file_size > MAX_OBJECT_SIZE {
        return Err(PartError::TooLarge);
    }
    let by_count = file_size.div_ceil(PART_COUNT_TARGET);
    let size = by_count.max(PREFERRED_PART_SIZE).div_ceil(MIB) * MIB;
    if size > MAX_PART_SIZE {
        return Err(PartError::TooLarge);
    }
    Ok(size)
}

Divide the size by 9,000 and round up, take the larger of that and 16 MiB, and round up to a whole mebibyte. PART_COUNT_TARGET is 9,000 rather than 10,000 to leave headroom, and rounding up can only shrink the count. PREFERRED_PART_SIZE is 16 MiB because, as the code comment says, it “keeps retries cheap and progress smooth.” Figure 9.1 shows the decision with worked examples.

A 100 MiB file gets six 16 MiB parts and a 4 MiB tail. The 16 MiB floor holds up to 144,000 MiB (about 140.6 GiB), exactly 9,000 parts; one byte more gives 17 MiB parts and 8,471 of them. A 200 GiB file gets 23 MiB parts, 8,905 in all (the test large_files_scale_part_size checks the 23 MiB). At 5 TiB the part size is 583 MiB with 8,993 parts, so the MAX_PART_SIZE check cannot fail for a valid size; it guards against future changes to the constants.

plan_parts turns the size into PartRange values (1-based number, offset, len), rejecting part sizes outside 5 MiB to 5 GiB and plans over 10,000 parts. The property test plans_are_contiguous_and_within_limits generates sizes up to 64 GiB and checks that numbers count from 1, parts are contiguous, every part but the last has the planned size of at least 5 MiB, and the lengths sum to the file size. Without it, a bad formula would surface only at completion. The chosen part size is stored with the upload and never recomputed, so a resumed upload keeps the size its existing parts were cut to.

Walking Through a Multipart Upload

Figure 9.2 shows a new upload under the Ask, Skip, or Keep both policy.

run in upload.rs opens the source and first looks for saved multipart state. It continues that upload only if the fingerprint and key still match; otherwise it aborts the old upload (ignoring errors, since R2 expires it anyway) and starts fresh. resolve_key then applies the conflict policy before any data moves: Replace skips the check; otherwise HeadObject decides, and Keep both tries name (1).ext and onward, up to 100 candidates. The test conflict_policies_for_uploads covers Skip, Keep both, Ask, and resolving Ask with Replace.

create_upload computes the part size, sends CreateMultipartUpload with content type and compression metadata, and saves a MultipartState (upload ID, key, part size, fingerprint, empty map of finished parts) through ctx.save_resume. A response without an upload ID is a retryable server error. If the app dies after R2 created the upload but before the journal reached disk, R2 holds an upload nothing will complete, which it removes after seven days; Chapter 15 (Crash Consistency and Recovery) classifies this as a harmless orphan.

Reading, Hashing, and Sending a Part

Every byte comes from a SourceFile (crates/r2dock-transfer/src/source.rs). SourceFile::open does not follow a final symbolic link (O_NOFOLLOW on Unix, FILE_FLAG_OPEN_REPARSE_POINT on Windows), refuses anything but a regular file, refuses a different device and inode than the scan recorded, and keeps a same_file::Handle plus a Fingerprint of size and nanosecond modification time. Each read (the part hash, the part body, and every retry of it) calls reopen, which compares the new handle with the stored identity. A file replaced by an editor’s save-and-rename fails with FileChanged (tests detects_replacement and refuses_symlink; Chapter 23, Filesystem Security, goes deeper).

upload_part first runs md5_range on a blocking thread, which reads the range with a 1 MiB buffer and fails with FileChanged if it gets fewer bytes than planned. It then sends UploadPart with the upload ID, part number, length, Content-MD5, and a body from range_body in body.rs. That body wraps a closure in SdkBody::retryable: each time the SDK needs the body, the closure reopens the file with the identity check, seeks to the offset, and streams the range in 64 KiB chunks. A request-level retry therefore resends from disk without holding the part in memory, and the closure subtracts the previous attempt’s bytes from the progress counter so progress never jumps past 100 percent. If the reopen fails, the body yields a “source file changed” error.

Each part is thus read twice. PLAN.md section 8.10 acknowledges the doubled reads; hashing while streaming cannot work because Content-MD5 must precede the body. In exchange, memory per active part is a 1 MiB hash buffer and a 64 KiB chunk plus HTTP buffers. PLAN.md section 8.4 mentions ByteStream::read_from(); the code’s own retryable body is what enables the per-attempt identity check and progress accounting.

The UploadPart reference says S3 checks the part against Content-MD5 and returns an error on mismatch. The R2 compatibility page lists the header as supported, but whether R2 rejects a mismatch is marked [Verify behavior] in PLAN.md section 8.10. Because the client uses checksum calculation WhenRequired (Chapter 8), the part MD5 does three jobs: it protects the part on the network, it is saved to predict the final ETag, and, computed just before sending, it detects an edit between hash and send. From<R2Error> for JobError in retry.rs maps BadDigest and InvalidDigest to JobError::file_changed(), a fatal error, because retrying cannot help; the file must be planned again.

Parallel Parts and Bounded Concurrency

parts_per_job (default 4 in EngineConfig::new) caps how many parts one job has queued, and the shared semaphore part_slots (default global_parts of 8) caps part requests across all jobs. Chapter 6 owns the semaphore design and Chapter 7 (Backpressure and Resource Management) explains what these numbers bound.

Source: crates/r2dock-transfer/src/upload.rs, lines 455 to 474

while failure.is_none()
    && ctx.control.stop() == Stop::None
    && in_flight.len() < ctx.parts_per_job
{
    let Some(part) = pending.next() else { break };
    let slots = ctx.part_slots.clone();
    let control = ctx.control.clone();
    let fut = upload_part(ctx, spec, &snapshot, source.clone(), part);
    in_flight.push(async move {
        let Ok(permit) = slots.acquire_owned().await else {
            return None;
        };
        if control.stop() != Stop::None {
            return None;
        }
        let r = fut.await;
        drop(permit);
        Some(r)
    });
}

Parts are queued into a FuturesUnordered set while nothing has failed, no pause or cancel is pending, and the job is below parts_per_job. The global permit is acquired inside each part’s future, not in the loop. As the code comment says, “waiting never stops this job from polling (and finishing) the parts it already started.” If the loop waited for a permit, a job could block while holding permits for parts it no longer polled, and jobs could starve each other. The regression test concurrent_multipart_jobs_do_not_deadlock runs three four-part jobs over two global slots.

The loop then waits with tokio::select! for a cancel, a pause, the pause grace, or a finished part, which goes into state.done and is saved at once. After a failure no new parts are queued, but parts in flight may finish.

A pause lets in-flight parts finish for PAUSE_GRACE, three seconds, then drops them; unrecorded parts are resent on resume. The test pause_and_resume_multipart pauses a 64 MiB upload, checks the journal holds an uploadId, resumes, and compares the object byte for byte. Cancel aborts the upload through abort_in_background, a separate task with a 60 second timeout, so the job reports “Cancelled” immediately; if the abort never succeeds, R2’s seven day cleanup applies. cancel_multipart_leaves_nothing checks that nothing exists at the key but not that the abort succeeded.

ETags, Completion, and the Final Check

Each finished part is a PartDone in crates/r2dock-transfer/src/ctx.rs with the returned etag, the hex md5 as sent, and the len, kept in a BTreeMap so part numbers stay sorted, as CompleteMultipartUpload requires. If R2 returns no part ETag, upload_part falls back to the quoted part MD5. That assumes part ETags equal part MD5s, as on Amazon S3 without server-side encryption with customer-provided keys (SSE-C); the R2 pages fetched for this book do not state the format, so the fallback is a best effort.

When all parts are done the job enters JobState::Verifying. ensure_unchanged compares the fingerprint with the one recorded at the start; a change aborts the upload, since parts from two versions must never be assembled. Then the key is checked again.

This is weaker than If-None-Match: *. Amazon S3 documents conditional headers on CompleteMultipartUpload, but R2’s compatibility page lists none, and PLAN.md section 8.4 marks them [Verify]. A file created by another client between this check and completion would be replaced; both the plan and the comment document the window. A conflict found this late also discards every uploaded part. A last check honors a cancel that arrived during verification, since a completed object cannot be taken back.

Completion sends each part number with its saved ETag. R2Dock then computes the expected object ETag.

Source: crates/r2dock-core/src/etag.rs, lines 33 to 40

/// Expected ETag for a multipart object from its part MD5 digests.
pub fn multipart_etag(part_md5s: &[[u8; 16]]) -> String {
    let mut hasher = Md5::new();
    for d in part_md5s {
        hasher.update(d);
    }
    format!("{}-{}", hex::encode(hasher.finalize()), part_md5s.len())
}

It hashes the concatenated binary digests and appends the part count, following Cloudflare’s documented rule; multipart_etag_matches_s3_rule checks it. A mismatch only logs “multipart ETag differs from the locally computed value” and the job still completes. The comparison is diagnostic, reasonable since R2 verified each part, but a mismatch is visible only in logs. The AWS reference warns that completion “could take several minutes” and that a 200 OK can carry an embedded error, which the SDK detects; the call has only stall protection, no attempt timeout.

Resuming an Interrupted Upload

MultipartState is part of the ResumeState the engine journals; the done map is serialized as a list (parts_as_list in ctx.rs) because JSON object keys are strings. After a restart, or after a retryable part failure that leaves the state in place, run re-enters multipart with the saved state when the fingerprint and key still match. Retry policy is Chapter 16 (Retries, Cancellation, and Idempotency).

Saved records can be wrong: a part may have been overwritten by a failed re-upload, or the upload may have expired. So reconcile pages through ListParts, following NextPartNumberMarker because, per the ListParts reference, a response “returns a maximum of 1,000 uploaded parts.” It keeps only saved parts that R2 still holds with the same normalized ETag and uploads the rest again, which the overwrite rule makes correct. If a marker repeats, the loop stops and unseen parts are simply resent. An unknown upload ID returns NoSuchUpload (404), which Chapter 8’s status fallback maps to NoSuchKey; that, or any other unrecognized Service error, is read as “this upload is gone” and the job starts fresh. An unrelated 400 therefore also restarts the upload, costing bandwidth but never a wrong object.

The app may also have stopped after R2 completed the upload but before the journal recorded it. Starting over would waste bandwidth and, under Ask or Skip, report a conflict with the app’s own object. finished_before_restart handles this: if every planned part was recorded, it computes the expected multipart ETag from the saved digests and accepts the job as completed only if HeadObject shows the same size and ETag. Otherwise the conflict policy applies again and a new upload begins. paused_multipart_resumes_after_restart covers resume across a restart.

One gap remains: an edit that preserves size and modification time (a deliberately reset timestamp) goes undetected for parts already sent. On Windows, FileIdentity::of returns no device and inode, so the scan-time check is skipped, though the handle comparison on every reopen still applies.

Working on This Code

Planning lives in crates/r2dock-core/src/parts.rs and ETag arithmetic in etag.rs, tested with cargo test -p r2dock-core. The flow is in crates/r2dock-transfer/src/upload.rs, with resume in reconcile and finished_before_restart. The body is in body.rs, source checks in source.rs, saved state in ctx.rs. Run cargo test -p r2dock-transfer --test engine for uploads, conflicts, pause, cancel, and restart against the in-process S3 server, and cargo test -p r2dock-transfer --release --test stress -- --include-ignored for load.

Never read a whole part into memory: bodies stay streaming through SdkBody::retryable, and every read goes through SourceFile::reopen. Keep hashing on spawn_blocking, and keep every part waiting for a part_slots permit inside its own future. Record a part only after its ETag arrives, keep numbers sorted, and keep the saved part size for the upload’s life. Remember that no conditional header protects multipart completion on R2, and that local tests do not prove R2 behavior such as rejecting a bad Content-MD5.

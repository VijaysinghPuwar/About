4 Rust Concepts Used in R2Dock

This chapter teaches the Rust features R2Dock depends on, using the project’s own code, and owns their definitions for the rest of the book. Asynchronous Rust belongs to Chapter 5 (Tokio and Asynchronous Execution). Each section states the problem, the concept, and where R2Dock relies on it.

Ownership: Every Value Has One Owner

Most languages free memory with a garbage collector or manual calls; Rust decides at compile time. The ownership chapter of The Rust Programming Language states three rules: each value has an owner, there is only one owner at a time, and the value is dropped when its owner goes out of scope. Assigning a heap-owning value such as a String, or passing it by value, moves it, and the old name can no longer be used.

Moves also express “this can happen only once”. The activity log’s builder Act (src-tauri/src/activity/mod.rs) has an end method that takes self by value, so after act.end(&result) the compiler rejects any further use of act, and a duplicate comma-separated values (CSV) row from ending an action twice cannot be written. A garbage-collected language would need a runtime flag.

Values are also moved into closures that run on other threads, as in blocking(move || hashing.md5_range(0, size)) in upload.rs, because the closure may outlive the current stack frame.

Borrowing: Using Data Without Taking It

A reference &T lets code read a value it does not own, and &mut T lets it modify one. The compiler enforces two rules: at any moment there are either any number of shared references or exactly one mutable reference, and no reference outlives its value. Helpers in r2dock-core use this to return views of their input instead of new strings.

Source: crates/r2dock-core/src/keys.rs, lines 86 to 93

/// The last segment of a key, without a trailing slash.
pub fn base_name(key: &str) -> &str {
    let trimmed = key.strip_suffix('/').unwrap_or(key);
    match trimmed.rfind('/') {
        Some(i) => &trimmed[i + 1..],
        None => trimmed,
    }
}

With one input reference and one output reference, lifetime elision tells the compiler the result borrows from key. base_name("Podcasts/Season 2/Episode 01.mp3") returns Episode 01.mp3 without copying, and keeping that result after freeing the key would not compile.

upload::run(ctx: &JobCtx, spec: &mut UploadSpec) reads the context but may change the specification, for example when “Keep both” renames the destination key. Because an upload can take an hour, run_job clones the specification out of the locked job map, runs on its own copy, and writes it back under a second short lock instead of holding a guard across the upload (Chapter 5 explains why).

Enums and Pattern Matching

A Rust enum is a type whose value is exactly one of several variants, each able to carry data. With match, which the compiler checks for exhaustiveness, enums replace flag combinations, magic strings, and null checks. The transfer job state is an enum with thirteen variants, classified by two methods.

Source: crates/r2dock-transfer/src/model.rs, lines 43 to 55

impl JobState {
    pub fn is_terminal(self) -> bool {
        matches!(self, Self::Completed | Self::Cancelled | Self::Skipped)
    }

    /// States that hold a scheduler slot.
    pub fn is_active(self) -> bool {
        matches!(
            self,
            Self::Preparing | Self::Running
                | Self::Retrying | Self::Verifying
        )
    }
}

matches! expands to a match that returns true for the listed patterns, and because JobState derives Copy, taking self by value costs nothing. Chapter 13 (Transfer State Machines) owns the meaning of each state; the point here is that adding a variant forces the author to revisit every exhaustive match, which is what a growing state machine needs.

Variants carry data too: ResumeState is None, Multipart(MultipartState), or Download(DownloadState), serialized with a kind tag so the journal is self-describing. Enums also serve as private vocabulary: Inner::control decides what a user action means inside a block that holds the jobs lock and evaluates to a local Then enum, then performs side effects after the guard is dropped, so “never emit while holding the jobs lock” is structural.

Two newer forms appear constantly. let ... else binds a pattern or leaves: let Some(e) = jobs.map.get_mut(&id) else { return; };. Let chains, available in the 2024 edition the workspace uses, combine if let with boolean conditions; the end of run_job uses one to clear a job’s control only if Arc::ptr_eq shows that no newer run replaced it.

Traits: Shared Behavior and Seams for Testing

A trait declares behavior several types can implement, like an interface. R2Dock uses traits mostly as seams: a lower crate calls into something it does not depend on, and tests substitute fakes.

Source: crates/r2dock-secrets/src/lib.rs, lines 62 to 68

pub trait SecretStore: Send + Sync {
    fn backend(&self) -> Backend;
    fn set(&self, reference: &str, secret: &SecretString)
        -> Result<(), SecretError>;
    fn get(&self, reference: &str) -> Result<SecretString, SecretError>;
    /// Deleting a missing entry is not an error.
    fn delete(&self, reference: &str) -> Result<(), SecretError>;
}

KeyringStore and MemoryStore (a locked HashMap for session-only mode) implement it, and the supertraits Send + Sync make the compiler check that every implementation can be shared between threads. ConnectionService holds Option<Arc<dyn SecretStore>>: a trait object whose concrete type is chosen at runtime by the startup keychain probe, called through a table of function pointers. The connection tests pass a MemoryStore and never touch a real keychain.

The engine needs R2 clients, but only the application crate can read secrets and the transfer crate must not depend on it. So the engine defines ClientProvider, whose one method returns a BoxFuture (a Pin<Box<dyn Future<Output = T> + Send + 'a>>, one concrete type as dyn requires), and EngineClients in src-tauri/src/state.rs implements it. Compression tests substitute a NoClient provider that always fails, and JobHooks in ctx.rs lets a running transfer report back without knowing engine internals.

Generics: One Implementation for Many Types

Generics let one definition serve many types with static checking and no runtime cost, because the compiler specializes a copy per type. Registry<T> in src-tauri/src/state.rs backs all four opaque identifier maps: insert takes ownership, drops expired entries, evicts the oldest at 256, and returns a random identifier, and take removes the value so a token works once. A separate impl<T: Clone> Registry<T> block adds a non-consuming get; T: Clone is a trait bound placed exactly where it is needed.

Closure parameters are the other common form: the blocking<T, F> helper in upload.rs and download.rs accepts any F: FnOnce() -> Result<T, JobError> + Send + 'static, the bounds spawn_blocking requires (Chapter 5).

Result, Option, and the Question Mark Operator

Rust has no exceptions and no null. A fallible function returns Result<T, E> (Ok(value) or Err(error)), and a possibly absent value is an Option<T> (Some(value) or None). The compiler warns when a Result is ignored, so failures cannot be dropped silently without an explicit let _ =.

The ? operator returns early with the error, converting it with From::from if needed, or returns None early on an Option. spawn_blocking(...).await yields a nested result (outer Err only if the task panicked), so ConnectionService::client ends with .await.map_err(|_| blocking_err())??: the first ? handles a panic, the second a credential store error.

Clippy warns on unwrap() and expect(), and continuous integration (CI) makes that an error, so even an infallible conversion states a fallback, such as u32::try_from(parts.len()).unwrap_or(u32::MAX).

Error Types with thiserror and the AppError Boundary

Each layer defines its own error enum because each knows different things. According to the thiserror documentation, deriving Error generates Display from #[error("...")] attributes, a source() method, and optional From implementations, and the crate “deliberately does not appear in your public API”. R2Dock writes its From implementations by hand, which keeps each conversion visible and lets it discard information on purpose.

R2Error in crates/r2dock-r2/src/error.rs has variants such as InvalidAccessKey, AccessDenied, NoSuchKey, rate limiting, timeout, an open Service variant, and cancellation, filled by from_sdk. Its detail strings keep only the code, status, and request identifier; the test maps_codes checks that a fake message reading “raw server text with secrets?” does not leak. is_retryable and is_auth_failure classify it, and impl From<R2Error> for AppError calls to_app_error, so commands can apply ?.

The engine needs more than an AppError: it must decide whether to retry, stop all jobs of a connection, or mark a job cancelled. crates/r2dock-transfer/src/retry.rs therefore defines JobError, an AppError plus retryable, auth, and cancelled flags.

Source: crates/r2dock-transfer/src/retry.rs, lines 86 to 104

impl From<R2Error> for JobError {
    fn from(err: R2Error) -> Self {
        if err == R2Error::Cancelled {
            return Self::cancelled();
        }
        // A bad digest means the bytes changed between hashing and sending.
        if let R2Error::Service { code, .. } = &err
            && (code == "BadDigest" || code == "InvalidDigest")
        {
            return Self::file_changed();
        }
        Self {
            app: err.to_app_error(),
            retryable: err.is_retryable(),
            auth: err.is_auth_failure(),
            cancelled: false,
        }
    }
}

A server digest mismatch becomes “the file changed while uploading”, because the code computed the MD5 digest just before sending; only the transfer layer knows that, and the test classification checks it. Figure 4.1 summarizes the conversions.

Every boundary loses information deliberately, because paths, raw server responses, and keychain messages can contain personal or secret data. SecretError carries no operating system text, StorageError and PathGuardError keep only an io::ErrorKind, and io_error produces pathless sentences, checked by the test io_errors_never_include_paths.

Sharing Data Between Threads with Arc

Many tasks must share one queue, journal, and client cache. The standard library documentation describes Arc<T> as “a thread-safe reference-counting pointer”: cloning it increments a counter and points at the same allocation, and the value is dropped with the last Arc. An Arc gives only shared access; changing the data needs interior mutability such as a lock or an atomic.

Engine is a single inner: Arc<Inner> field with #[derive(Clone)], so every cheap clone (in AppState, in the event closure, in cleanup tasks) controls the same engine. Inner holds further Arc fields such as part_slots: Arc<Semaphore> that are handed separately to jobs.

Arc::ptr_eq compares identity rather than value. Each job run gets a fresh Arc<RunControl>, and when it ends it clears the job’s control only if the stored one is still its own, so it cannot erase a newer run’s control. Two fresh controls look identical by value.

Locks: Mutex and RwLock from parking_lot, std, and Tokio

A mutex (mutual exclusion lock) lets one thread at a time access the data inside, and a read-write lock (RwLock) allows many readers or one writer. In Rust both wrap the data they protect and return a guard; as the standard library Mutex documentation says, “When the guard goes out of scope, the mutex will be unlocked.” R2Dock uses three lock families deliberately.

parking_lot’s Mutex and RwLock hold almost all production shared state. Its Mutex documentation lists “No poisoning, the lock is released normally on panic”. The standard mutex instead becomes poisoned after a panic, and later lock() calls return an error that would need unwrap(), which the lints forbid. The trade-off is that a panic mid-update can leave data inconsistent without a signal, so R2Dock keeps critical sections short and free of fallible work, and adds a repair guard in the compression path (see Drop Guards later in this chapter).

tokio::sync::Mutex appears only where a lock must be held across an .await (Chapter 5): the settings writer, the connection file writer (persist_lock), and per-bucket coalescing in public_links.rs. The settings update uses both kinds.

Source: src-tauri/src/state.rs, lines 172 to 192

async fn commit_json<T>(
    cell: &RwLock<T>,
    lock: &tokio::sync::Mutex<()>,
    path: PathBuf,
    change: impl FnOnce(&mut T),
) -> Result<T, AppError>
where
    T: Clone + serde::Serialize + Send + 'static,
{
    let _writing = lock.lock().await;
    let old = cell.read().clone();
    let mut candidate = old.clone();
    change(&mut candidate);
    let snapshot = candidate.clone();
    tokio::task::spawn_blocking(move || write_json_atomic(&path, &snapshot))
        .await
        .map_err(|_| AppError::internal(
            "A background task stopped unexpectedly."
        ))?
        .map_err(|_| AppError::new(
            r2dock_core::ErrorCode::Io,
            "Could not save settings."
        ))?;
    *cell.write() = candidate;
    Ok(old)
}

The async mutex _writing spans the whole function, including the disk write, so two changes cannot interleave. The parking_lot RwLock is touched for one statement at a time, and *cell.write() = candidate publishes only after the save succeeded, so readers never wait for disk I/O. The test settings_change_is_published_only_after_it_is_saved checks that a failed save changes nothing.

Guard scope deserves care. In PublicLinks::domains, self.inflight.lock().entry(key.clone()).or_default().clone() clones an Arc out of the map and releases the temporary guard at the semicolon, before awaiting the per-bucket Tokio mutex; binding the guard to a variable would keep the map locked while the task is suspended. The engine’s emit likewise clones the sink out of its read lock, then calls it inside a delivery mutex that keeps events in order, which is why its comment says the sink must never block.

Atomics: Lock-Free Counters and Flags

An atomic integer can be updated by many threads without a lock, using indivisible processor instructions. Each operation takes a memory ordering. The Ordering documentation defines Relaxed as “No ordering constraints, only atomic operations” and SeqCst as adding that “all threads see all sequentially consistent operations in the same order”. Relaxed suffices when only the number matters; stronger orderings are needed when one thread’s write must make other data visible.

The busiest atomic is the progress Counter in crates/r2dock-transfer/src/progress.rs, updated for every 64 KiB upload chunk and every chunk a download writes, always with Ordering::Relaxed because it is only displayed. sub_in_flight shows the compare-and-swap loop, the basic tool for an atomic update that is not a built-in operation: load the value, compute cur.saturating_sub(bytes), store it with compare_exchange_weak only if nobody changed the value meanwhile, and otherwise retry with the actual value. Saturating subtraction prevents wrap-around when a request body is rebuilt after an SDK retry, and a lock here would add contention on the hottest path in the program.

RunControl in ctx.rs encodes continue, pause, or cancel in an AtomicU8 with SeqCst: request_pause uses compare_exchange(0, 1, ...) so it can only replace “continue”, while request_cancel stores 2 unconditionally, so cancel always wins.

Drop Guards: Cleanup That Cannot Be Forgotten

The Drop trait runs code when a value goes out of scope, whether by normal flow, return, ?, or a panic’s unwinding. A guard exists only for that cleanup; lock guards and semaphore permits are guards, and R2Dock writes one to protect the compression task.

Source: crates/r2dock-transfer/src/engine/compress.rs, lines 343 to 378

/// Runs on every exit of [`compress_job`], including a panic: releases the
/// run's control (only if no newer run replaced it) and wakes the
/// scheduler, so the next job can take the encode slot. A job still shown
/// as compressing at that point ended abnormally and is marked failed.
struct Finalize {
    inner: Arc<Inner>,
    id: JobId,
    control: Arc<RunControl>,
}

impl Drop for Finalize {
    fn drop(&mut self) {
        let stuck = {
            let mut jobs = self.inner.jobs.lock();
            match jobs.map.get_mut(&self.id) {
                Some(e)
                    if e.control
                        .as_ref()
                        .is_some_and(|c| Arc::ptr_eq(c, &self.control)) =>
                {
                    e.control = None;
                    e.snap.state == JobState::Compressing
                }
                _ => false,
            }
        };
        if stuck {
            // ...
        }
        self.inner.wake.notify_one();
    }
}

compress_job creates it first with let _finalize = Finalize { ... }; (a bare _ would drop it immediately). Without it, an encode that ended unexpectedly would leave its job compressing forever and the scheduler asleep, blocking the encode slot; with it, every exit releases the slot, wakes the scheduler, and fails a stuck job. Because the engine’s locks come from parking_lot, the guard can lock the job table even while a panic unwinds. The FFmpeg runner similarly uses KillOnDrop from process-wrap (Chapter 17).

PLAN.md section 12.5 says multipart cleanup “uses an RAII guard that calls AbortMultipartUpload on drop”. The audited code has no such guard: the only non-test Drop implementations are Finalize and the test kit’s servers. Instead, upload.rs calls abort_in_background or abort_multipart explicitly on each cancel and failure path (Chapter 16, Retries, Cancellation, and Idempotency). That is easy to follow but relies on every new exit path remembering the call, a plan and code mismatch worth resolving.

Finally, unsafe_code = "forbid" means no R2Dock crate contains unsafe; platform needs such as opening a file without following symbolic links use safe wrappers like OpenOptionsExt::custom_flags and the same-file crate.

Working on This Code

Give a new layer a thiserror enum whose messages contain no paths, secrets, or raw server text, with an explicit conversion to AppError. Never unwrap. Keep parking_lot critical sections to a few statements and never across an .await (use tokio::sync::Mutex there), and use atomics only for counters and flags. Write a Drop guard when something must be released on every exit path, and avoid wildcard _ arms on enums you own.

Run cargo test -p r2dock-core, cargo test -p r2dock-r2 (maps_codes), cargo test -p r2dock-transfer (classification, progress counter tests), and cargo test -p r2dock (registry and settings tests), then cargo clippy --workspace --all-targets -- -D warnings, since the lints are errors in CI.

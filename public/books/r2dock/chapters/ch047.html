35 Source-Code Study Roadmap

R2Dock’s tracked source is a few hundred files, and reading them in directory order is a slow way to understand it. This chapter gives an ordered path instead: which files to open first, what single concept to look for in each, and which chapter of this book explains it. Each stage builds on the previous one, moving from rules without input or output, through the network and the engine, to the application shell and the interface. A reader who follows it with the book open should be able to change any subsystem with confidence after about ten sessions.

Stage 1: The Shape of the System

Start with the documents, not the code. Read README.md for what the app promises and the sections of PLAN.md on architecture and the threat model, keeping Chapter 32 (Engineering Trade-offs and Future Improvements) beside you, because PLAN.md predates parts of the code. Then read the five Architecture Decision Records (ADRs) in docs/adr/; each is short and explains one foundational choice (Tauri with a Rust core, the keyring crate, ts-rs for types, the frontend libraries, the local S3 test server). Finally open the workspace Cargo.toml and each crate’s Cargo.toml to see which crate depends on which. Chapters 1 to 3 cover this stage.

Stage 2: Rules Without Input or Output

Open crates/r2dock-core. Its modules contain decisions with no network or disk access, which makes them the easiest code to read and test. Read app_error.rs first: AppError is the one error shape that crosses into the webview, and every later layer maps into it (Chapter 4, Rust Concepts Used in R2Dock). Read keys.rs for how object keys are validated and displayed, then parts.rs for part_size_for, plan_parts, and use_multipart (Chapter 9, Multipart Uploads in Depth). Read path_guard.rs slowly; it turns untrusted keys into safe local paths and is the security core of downloads (Chapter 23, Filesystem Security). Finish with settings.rs and storage.rs, the latter for write_bytes_atomic (Chapter 14, Journals and Persistent Queues). The unit and property tests at the bottom of each file are the best specification.

Stage 3: Secrets and the R2 Client

Read crates/r2dock-secrets/src/lib.rs to see how secrets go to the operating system’s credential store or session memory and never to a file (Chapter 21, Credential Storage and Authentication). Then open crates/r2dock-r2: client.rs for how the AWS software development kit (SDK) is configured (path style, checksums, retries, stall protection), error.rs for how SDK failures become typed, classified errors, and list.rs for paged listing with its defensive guards (Chapter 8, The S3-Compatible Protocol). Read ops.rs and bulk.rs for copy, delete, and the copy, verify, delete move (Chapter 11, Object Management and Consistency), and cfapi.rs for the optional Cloudflare API (Chapter 12, Public URLs and Cloudflare REST API Integration).

Stage 4: The Transfer Engine

This is the heart of the application and deserves the most time. Read crates/r2dock-transfer/src/model.rs first for JobSpec, JobState, and TransferEvent, the vocabulary of everything that follows (Chapter 13, Transfer State Machines). Then ctx.rs for JobCtx, RunControl, ResumeState, and the JobHooks boundary.

Next read engine/mod.rs in this order: EngineConfig and Engine::start, then enqueue, Inner::schedule, run_job, finish, and progress_ticker (Chapter 6, The Transfer Scheduler), and finally restore and control. With that in mind, upload.rs (single and multipart paths, reconcile, finished_before_restart) and download.rs (range resume, verification, finalization) read naturally (Chapters 9 and 10). body.rs, source.rs, and progress.rs are short supporting files for streaming, file identity, and byte counting. Then read journal.rs and history.rs (Chapter 14), and retry.rs (Chapter 16, Retries, Cancellation, and Idempotency). Read engine/compress.rs last in this stage; it only makes sense once the scheduler is familiar (Chapters 7 and 20).

Chapter 33 (Complete End-to-End Execution Walkthrough) is the companion to this stage: it follows one upload through these files in execution order.

Stage 5: Media Processing

Open crates/r2dock-media only if you will work on compression. Start with ffmpeg/run.rs for how an external process is started, watched, and stopped (Chapter 17, How FFmpeg Integrates with Rust), then tools/manifest.rs and tools/install.rs for pinned, hashed tool downloads. The audio path is probe.rs, classify.rs, plan.rs, and verify.rs (Chapter 18, Audio Compression Internals); the video path is the video/ module (Chapter 19, Video Compression Internals); pipeline.rs ties a plan to an encode and its checks (Chapter 20).

Stage 6: The Application Shell

Now open src-tauri. Read src/lib.rs from top to bottom: it is the startup sequence, building services, starting the engine and activity log, registering commands, and flushing on exit (Chapter 2, Complete Software Architecture). Read state.rs for AppState and the opaque-identifier Registry. Then read build.rs and capabilities/main.json together with tauri.conf.json, which define the command allowlist and the Content Security Policy (Chapter 22, Tauri Security Architecture).

Read the commands next, starting with commands/mod.rs for the argument validators and with_client, then commands/transfers.rs with planning.rs, dialogs.rs, and dragdrop.rs. Read connections.rs for the client cache and credential lifecycle (Chapter 21), media.rs for the custom preview protocol (Chapter 24, The Custom Media Preview Protocol), and the activity/ folder for the comma-separated values (CSV) log and its bounded writer thread (Chapter 5, Tokio and Asynchronous Execution).

Stage 7: The Frontend

In src/, begin with src/ipc/commands.ts, the only module that calls invoke, and glance at src/ipc/bindings/, which is generated from Rust (Chapter 26, React and Tauri IPC). Read src/app/App.tsx and src/app/queries.ts for the query keys and the cache of Rust answers, then src/app/objectChanges.ts for invalidation (Chapter 27, Frontend State Management). Read src/features/transfers/subscription.ts and transferStore.ts for the event batching and the reducer, then src/features/browser/useExplorerData.ts and FileTable.tsx for ghost rows and virtualization (Chapter 28, UI Performance and Large Queues). Feature folders such as connections, manage, and preview can be read on demand.

Stage 8: Tests, Benchmarks, and Releases

Finish with the evidence. Read crates/r2dock-testkit/src/lib.rs for the in-process S3 server and network shaping, then crates/r2dock-transfer/tests/engine.rs and recovery.rs, and crates/r2dock-r2/tests/move_races.rs with its request-boundary mock (Chapter 29, Automated Testing Strategy). Read the three files in docs/benchmarks/ and the tests that produce them (Chapter 30, Performance Benchmarking). Last, read .github/workflows/ci.yml, release.yml, and tools.yml (Chapter 31, CI/CD and Desktop Releases).

Working on This Code

Read actively. At each stage, run that area’s tests before and after a small experiment: cargo test -p r2dock-core for stage 2, cargo test -p r2dock-r2 for stage 3, cargo test -p r2dock-transfer for stage 4, cargo test -p r2dock-media for stage 5 (media tests skip without FFmpeg), cargo test -p r2dock for stage 6, and npm test for stage 7. Changing one constant, such as the progress interval or the part size floor, and watching which tests fail is a fast way to learn what depends on it. Keep the invariants from earlier chapters in mind while exploring: secrets and local paths stay in Rust, every fan-out is bounded, large data is streamed, and blocking work runs off the async runtime. Revert experiments before starting real work, and follow Chapter 34 (Your First Contribution) for the checks before a pull request.

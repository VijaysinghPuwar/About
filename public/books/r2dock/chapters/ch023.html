16 Retries, Cancellation, and Idempotency

A request can fail before it leaves the machine, fail on the server, succeed and lose its response, or stop moving, and a user can press Cancel at any moment. This chapter covers when R2Dock tries again, how Cancel reaches an HTTP connection or an FFmpeg process, and idempotency: which operations can safely be repeated when the outcome is unknown. It builds on Tokio cancellation from Chapter 5 (Tokio and Asynchronous Execution), the job states of Chapter 13 (Transfer State Machines), and the error mapping of Chapter 8 (The S3-Compatible Protocol).

Two Layers of Retry

R2Dock retries at two levels. The lower level belongs to the AWS software development kit (SDK) for Rust, R2Dock’s S3 client. crates/r2dock-r2/src/client.rs builds every client with RetryConfig::standard().with_max_attempts(3), a connect timeout, and stalled stream protection. The AWS guide Configuring retries in the AWS SDK for Rust states that three attempts is the default (“By default, a call will be tried three times”), that “socket timeouts”, “service-side throttling”, and “transient service errors like HTTP 5XX responses” are retried while “authentication/security errors” are not, and that the capped exponential delay has “random jitter”. R2Dock keeps the documented backoff (one second initial, twenty maximum) but writes the attempt count down, following PLAN.md section 8.1 (“never rely on SDK defaults”).

SDK retries happen inside one send().await, invisible to the engine. To resend a body, range_body in crates/r2dock-transfer/src/body.rs uses SdkBody::retryable: each rebuild reopens the source with an identity check, seeks to the part offset, and subtracts the bytes the failed attempt counted from progress.

The upper level is the job. When a whole attempt fails with a retryable error, the job waits and runs again, using the policy in crates/r2dock-transfer/src/retry.rs.

Source: crates/r2dock-transfer/src/retry.rs, lines 9 to 21

/// Maximum attempts per job, including the first.
pub const MAX_ATTEMPTS: u32 = 3;

// ...
pub fn backoff(attempt: u32) -> Duration {
    let base = match attempt {
        0..=2 => 2.0,
        3 => 8.0,
        _ => 30.0,
    };
    let jitter: f64 = rand::random::<f64>() * 0.4 + 0.8;
    Duration::from_secs_f64(base * jitter)
}

Jitter multiplies the base by a factor between 0.8 and 1.2 (checked by backoff_ranges), so jobs that all failed when the network dropped do not retry in the same instant. run_job calls backoff(attempt + 1) with attempt starting at one and retries only while attempt < MAX_ATTEMPTS, so the waits are about two and eight seconds. The 30 second step that PLAN.md section 8.11 lists is never reached unless the limit is raised.

The layers multiply: a small upload can send up to nine HTTP attempts. PLAN.md section 8.11 says “total retry budget per part is capped”; the code bounds it only through the two constants. For multipart uploads a job retry is cheap, because it resumes from saved parts.

Deciding What Is Retryable

R2Error::from_sdk in crates/r2dock-r2/src/error.rs separates failures on the way (TimeoutError, DispatchFailure, ResponseError) from service errors with a status and S3 code. R2Error::is_retryable accepts five variants: rate limiting (SlowDown, TooManyRequests, or status 429), server errors (any 5xx), network failures, timeouts, and unreadable responses (Protocol). Access denied, missing bucket or object, failed preconditions, other 4xx errors (Service), unbuildable requests, and cancellation are final. A separate is_auth_failure marks InvalidAccessKey and SignatureMismatch. The test retry_classes checks a sample.

The engine’s JobError refines this in its From<R2Error> implementation: BadDigest or InvalidDigest means the file changed between hashing and sending, so it becomes a final “file changed” error. JobError::io retries only Interrupted, TimedOut, and WouldBlock, because “Disk full and permission problems do not fix themselves.” The engine also raises retryable errors itself, for example when a download stream breaks or ends short.

The code agrees with PLAN.md’s retry table except on one row. The plan says a TLS failure should not be retried, but from_sdk maps every non-timeout dispatch failure to the retryable R2Error::Network. Unless the SDK reports TLS failures elsewhere, a broken proxy certificate costs a few seconds of futile retries before the job fails.

What the Engine Does With a Failure

The retry loop at the end of run_job in crates/r2dock-transfer/src/engine/mod.rs does three things. A rate limit or server error starts a 60 second slowdown during which effective_concurrency halves the jobs the scheduler runs, with a minimum of one (Chapter 7, Backpressure and Resource Management). The plan says concurrency should “recover gradually”; the code restores it all at once. Because the check uses the user-facing ErrorCode, and to_app_error maps unrecognized service and protocol errors to ServerError, a non-retryable unknown 4xx also triggers the slowdown.

An authentication failure is never retried. fail_connection fails every queued job on that connection and an AuthFailed event asks for new credentials, preventing a retry storm against a revoked token. The test wrong_credentials_fail_without_retry_storm in crates/r2dock-transfer/tests/engine.rs checks this.

Otherwise, a retryable error with attempts left sets the job to Retrying and waits for backoff inside a tokio::select! that also watches the job’s cancellation token, so Pause or Cancel during “Retrying” does not wait for the timer.

Timeouts

A retry needs a detected failure. client.rs sets three limits. CONNECT_TIMEOUT is 10 seconds; the AWS guide Configuring timeouts lists 3.1 seconds as the default. METADATA_ATTEMPT_TIMEOUT is 30 seconds per attempt, applied by metadata_timeouts to HeadObject, listings, and the bucket list. STALL_GRACE is 60 seconds of stalled stream protection, which the same page describes as an error “when a stream is idle for longer than the acceptable period”; the SDK default is 20 seconds.

Transfers have no total time limit: a 50 GB download on a slow line may take a day, and a stall, not a clock, should end it. The AWS guide notes that “Operation and attempt timeouts do not apply to streaming data consumed after the SDK for Rust has returned a response,” so stall protection guards the download body. The multipart create, complete, and abort calls have only the connect timeout, though an abort after cancel is bounded at 60 seconds.

Cancellation: From a Click to a Closed Connection

A cancel crosses three boundaries, shown in Figure 16.1.

The first boundary is Inter-Process Communication (IPC; Chapter 26, React and Tauri IPC): transferControl in src/ipc/commands.ts invokes the transfer_control command in src-tauri/src/commands/transfers.rs, which calls Engine::control and returns without waiting for the job to stop.

Inside Engine::control, the state check and change happen under the jobs lock, so the scheduler cannot start the job in between. A job that is not running becomes Cancelled at once, and discard_partial aborts any saved multipart upload and deletes partial files (tested by cancel_queued_job_is_final). A running or compressing job is only asked to stop.

RunControl in crates/r2dock-transfer/src/ctx.rs, created for every run, holds an atomic stop flag and two CancellationTokens. request_cancel sets the flag and cancels both. request_pause cancels only stopping (stop starting new parts), plus cancel (drop work in flight) for downloads, Retrying jobs, and compression. The CancellationToken documentation guarantees that cancelled() “completes immediately if the token is already cancelled”, so a late check never misses an early cancel. R2Dock uses no child tokens.

At the third boundary, every long wait is a tokio::select! with the token as one branch. A single-request upload races the whole request.

Source: crates/r2dock-transfer/src/upload.rs, lines 206 to 212

let result = tokio::select! {
    () = ctx.control.cancel.cancelled() => {
        settle(&ctx.counter, &sent, None);
        return Err(JobError::cancelled());
    }
    r = req.send() => r.map_err(R2Error::from_sdk),
};

When the cancel branch wins, the send() future is dropped, and with it the body stream and the HTTP connection; in Rust, dropping a future is how async work is cancelled. The same pattern guards the download’s GetObject and every body chunk, the retry backoff, and the multipart loop, where drop(in_flight) drops every part request at once. The compressed copy check runs on a blocking thread, so it polls the stop flag between one mebibyte reads. For compression the token reaches the FFmpeg runner, which kills the process (Chapter 17, How FFmpeg Integrates with Rust).

Two places do not listen. CompleteMultipartUpload is awaited without a select, after a check commented “Last chance to honour a cancel before the object becomes visible”; a visible object cannot be un-cancelled. And a cancel that wins the race against a single PUT whose body already arrived may leave the object stored while the job reads Cancelled; the code does not check afterwards.

Aborting Multipart Uploads

A cancelled multipart upload leaves parts that cost storage. abort_in_background in upload.rs spawns the abort as its own task with a 60 second limit (ABORT_TIMEOUT) and logs failures at debug level. Its doc comment explains that a cancelled job “should read ‘Cancelled’ at once. An abort that never succeeds is cleaned up by R2”, which aborts incomplete uploads after seven days by default per Cloudflare’s multipart documentation. As recorded in docs/benchmarks/2026-10-18-compression-at-scale.md (not re-run for this book), with 100 jobs and a test server delaying aborts by five seconds, “Cancel all” fell from 5.0 seconds to 21 milliseconds. The test cancel_multipart_leaves_nothing checks that no object appears.

PLAN.md section 12.5 describes “an RAII guard that calls AbortMultipartUpload on drop” (Resource Acquisition Is Initialization, cleanup in a destructor). The code instead aborts explicitly: in the background on cancel, awaited when the source or destination changed underneath the upload, and spawned by discard_resume for dismissed jobs. A pause never aborts, since the parts are needed. Explicit calls suit this case: a destructor cannot run async code and would fire on pause too.

Did the Request Apply?

A timeout after a request was sent says nothing about whether the server acted, and an SDK retry may be the second execution of a successful operation. The table shows what a repeat does for each operation the transfer code sends.

Operation Repeat after success R2Dock handling
PutObject, Replace Same object written again Harmless
PutObject, If-None-Match 412 for its own object Reported as conflict or skip
UploadPart Same part replaced ETag recorded per success
CreateMultipartUpload Second upload ID First orphaned until R2 aborts
CompleteMultipartUpload Not verified Retry path detects completed object
AbortMultipartUpload Upload already gone Error ignored
GetObject, HeadObject, ListParts Read only Harmless

Two rows are subtle. Under “Ask” and “Skip”, single PUTs send If-None-Match: *. If the first attempt succeeds and its response is lost, the SDK retry gets 412 from the job’s own object, and single reports NeedsDecision or Skipped for a correctly uploaded file. Nothing is lost, but the outcome is confusing. This is an analysis of code and documented SDK behavior, not a tested case.

For CompleteMultipartUpload, the repository does not record how R2 answers a repeat, and this book did not verify it. If it is NoSuchUpload, from_service maps the 404 to the non-retryable R2Error::NoSuchKey, and the job fails with “File no longer exists” while the object is complete. The resume state survives because finish keeps it for failed jobs, so a manual Retry finds the upload gone, runs finished_before_restart, and completes without sending data (Chapter 15, Crash Consistency and Recovery).

Downloads are naturally repeatable: they write to a job-specific partial moved into place only at the end, and If-Match keeps two object versions from mixing. Parts are recorded with the ETag of the attempt that succeeded, so completion lists only ETags actually received.

Working on This Code

crates/r2dock-r2/src/error.rs maps SDK errors and decides is_retryable and is_auth_failure; crates/r2dock-transfer/src/retry.rs holds MAX_ATTEMPTS, backoff, and JobError; the retry loop is at the end of run_job in engine/mod.rs; timeouts are constants in client.rs; cancellation starts in RunControl in ctx.rs and is consumed by the selects in upload.rs, download.rs, the engine, and crates/r2dock-media/src/ffmpeg/run.rs.

Give every new error variant a deliberate retry class and add it to retry_classes and classification. Every new long wait must select on the job’s token, or poll the stop flag on a blocking thread, or Pause and Cancel will seem to hang. Never make a cancel wait on the network.

Run cargo test -p r2dock-r2 and cargo test -p r2dock-transfer, which include wrong_credentials_fail_without_retry_storm, cancel_multipart_leaves_nothing, and cancel_queued_job_is_final. Also test cancellation while a job is Retrying, waiting for a part slot, and compressing.

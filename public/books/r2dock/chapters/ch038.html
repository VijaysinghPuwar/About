28 UI Performance and Large Queues

A cloud file manager can overwhelm its own window in two ways. One is size: a folder can hold tens of thousands of objects, far more table rows than a webview can lay out smoothly. The other is rate: a folder upload enqueues thousands of jobs that each change state several times and report progress continuously, and if every change caused its own React render, the main thread would never get back to the user. R2Dock answers size with virtualization and rate with a pipeline of throttling and batching that starts in Rust and ends in a pure reducer. Chapter 26 (React and Tauri IPC) described the channel and Chapter 27 (Frontend State Management) the stores.

Targets Without Measurements

PLAN.md requirement N8 asks that the “UI stays responsive (no frame longer than about 100 ms from app logic) with 10,000 loaded rows and 500 queued transfers,” and section 14 targets “no long tasks over 50 ms” while scrolling 10,000 rows. Both are provisional, and section 14 opens with “No benchmark numbers exist yet.” That is still true for the frontend: the reports in docs/benchmarks/ cover the activity log, the transfer engine (2026-10-17-stress.md, up to 3,012 files against an in-process S3 server, Rust only), and compression, but none measures the webview. This chapter therefore describes mechanisms and the tests that pin their behavior, not frame times.

Two Throttles and a Debounce

Figure 28.1 shows the path from the engine to the screen, with each stage that reduces the rate of work.

On the engine side, owned by Chapter 6 (The Transfer Scheduler), workers only increment per-job counters. progress_ticker in crates/r2dock-transfer/src/engine/mod.rs wakes when a job becomes active and every progress_interval (250 milliseconds by default) emits one Progress event listing every active job whose bytes changed or whose speed is known. Eight running uploads mean four progress events per second, not thirty-two. PLAN.md section 12.4 says “at most every 250 ms per active job”; the code is stricter. State changes are not throttled: set_state emits Updated with a full JobSnapshot on every transition, and enqueue emits Added in chunks of at most 500 jobs “to keep IPC messages small.” A folder of small files can therefore produce thousands of Updated events back to back.

The frontend never applies events as they arrive.

Source: src/features/transfers/subscription.ts, lines 163 to 184

/** Subscribe to transfer events once for the app's lifetime. */
export function startTransferSubscription(client: QueryClient): void {
  if (started) return;
  started = true;
  // ...
  let pending: TransferEvent[] = [];
  const flush = () => {
    const events = pending;
    pending = [];
    const before = useTransferStore.getState().jobs;
    useTransferStore.getState().applyMany(events);
    for (const event of events) afterEvent(client, before, event);
  };
  transferSubscribe((event) => {
    if (pending.length === 0) setTimeout(flush, FLUSH_MS);
    pending.push(event);
  }).catch((e: unknown) => {
    started = false;
    toast.danger(`Transfer updates are not available. ${errorMessage(e)}`);
  });
}

FLUSH_MS is 50. The first event into an empty buffer schedules a flush and every event in the next 50 milliseconds joins it. The flush swaps the buffer out, so events arriving meanwhile start a new batch, updates the store once with applyMany, and only then runs side effects. Added latency is at most 50 milliseconds, invisible beside a 250 millisecond progress interval, while store updates, and thus renders, stay near twenty per second whatever Rust sends. Capturing before gives afterEvent a stable previous state, so it records one completion per job rather than one per duplicate Updated.

The code uses setTimeout, not requestAnimationFrame. Browsers pause animation frames in hidden windows, so with frames the buffer would grow without bound while a minimized app kept transferring; a timer keeps draining it. No comment states this, so treat it as the likely rationale rather than the documented one. The 0.4.1 CHANGELOG.md entry reports “Large queues stay responsive: transfer updates are applied in batches” with a before and after measurement, but that measurement is not in docs/benchmarks/ and states no machine or method, so this book does not repeat its numbers.

A Reducer That Copies Once per Batch

Batching helps only if applying a batch is cheap. Zustand re-renders when a selected value is a new object, so updates must be immutable. Copying the job map per event costs N copies of an N-entry map for a burst of N events, which grows with the square of the queue. The comment above reduceTransferBatch in src/features/transfers/transferStore.ts records that this really happened: “copying every job for each one froze the window”. The fix is copy on write, at most once per batch.

Source: src/features/transfers/transferStore.ts, lines 28 to 52

export function reduceTransferBatch(state: TransferState,
  events: TransferEvent[]): TransferState {
  let { jobs, order, authFailed } = state;
  let ownJobs = false;
  let ownOrder = false;
  let changed = false;
  const writableJobs = () => {
    if (!ownJobs) {
      jobs = { ...jobs };
      ownJobs = true;
    }
    return jobs;
  };
  const writableOrder = () => {
    if (!ownOrder) {
      order = [...order];
      ownOrder = true;
    }
    return order;
  };
  const put = (list: JobSnapshot[]) => {
    for (const job of list) {
      if (!(job.id in jobs)) writableOrder().push(job.id);
      writableJobs()[job.id] = job;
    }
  };

The first write in a batch copies the map or the order array; later writes reuse the private copy. order is copied only when a new id appears, so updates to known jobs leave it as the identical array and components selecting only order do not re-render. A snapshot replaces both structures. A progress event replaces only the affected job objects with new byte counts, speed, time remaining, and parts done, and ignores unknown ids, which covers progress that races a removed. If nothing changed, the original state object is returned and Zustand sees no difference.

The tests in transferStore.test.ts pin this down. “a batch gives the same result as applying events one by one” is the property that makes batching safe: an optimization, never a change in meaning. Others check that the input is not mutated, that an empty batch returns the identical object, and that “updating a known job keeps the same order array”.

Side Effects Without Per-Event Cost

afterEvent runs once per event, so it must be constant time. Its main job is noticing when a batch of work finishes, so that one summary toast (“Uploaded 200 files to books.”) replaces two hundred. It keeps batch, the job ids seen since the queue was last idle, and moving, the subset still working, “so the idle check is O(1) per event”; only when moving empties does it walk batch once. Cache invalidation is debounced instead: scheduleRefresh collects changed objects and restarts an 800 millisecond timer (REFRESH_MS) on every completion, then calls invalidateObjectChanges and, if needed, invalidates qk.history.

The refresh therefore fires 800 milliseconds after the last completion of a burst. Batching guarantees regular progress; debouncing waits for quiet, because invalidation triggers real ListObjectsV2 requests. The ghost rows of Chapter 27 cover the gap. A consequence worth knowing: with completions arriving less than 800 milliseconds apart, the open folder is not re-listed until the stream ends. The test “coalesces a burst of completions into one refresh per bucket” in subscription.test.ts uses Vitest fake timers to deliver 200 completions and asserts one listing invalidation and at most five invalidateQueries calls; “100 uploads that go up uncompressed over hours give one notice and one summary” checks the toast batching across a long queue.

Selecting Without Waste

TransfersPage selects jobs with useTransferStore(useShallow((s) => orderedJobs(s))). The Zustand README recommends useShallow “to prevent unnecessary rerenders when the selector output does not change according to shallow equal”, which matters because orderedJobs builds a new array each time. Be precise about the savings: a progress batch replaces every active job object, so during transfers the page still re-renders about every 250 milliseconds; useShallow avoids renders for changes that touch no job and keeps the array stable while the queue is quiet. Derived values (filterDirection, countTabs, and the linear-time grouping in buildItems) are chained through useMemo, so switching tabs recomputes items but not filtered.

React’s memo is not used anywhere at this commit, including on TransferRow. The React memo reference says it pays off only when a component “re-renders often with the same exact props”. Active rows get a new job object every batch, so memo could skip only queued and finished rows, and virtualization already limits rendering to visible rows. Whether it would help is a question for profiling, not a known problem.

Virtualization With TanStack Virtual

Virtualization renders only visible rows plus a margin, positioned inside a container as tall as the full list, so the document stays small regardless of length. R2Dock uses @tanstack/react-virtual, chosen in architecture decision record (ADR) 0004 over react-virtuoso. The Virtualizer API reference defines the options used: count, getScrollElement, estimateSize, overscan (default 1), initialRect (“The initial Rect of the scrollElement”), and getItemKey.

FileTable in src/features/browser/FileTable.tsx has fixed-height rows, so estimateSize is exact: Explorer.tsx passes 26 pixels for compact density and 32 for comfortable, and an Effect calls measure() when density changes. The same values exist as the --row-h token in src/styles/tokens.css, a harmless duplication today, but a token change alone would not change the virtualizer’s arithmetic. overscan is 12, hiding blank space during fast scrolling, and initialRect of 800 by 600 lets the first render contain rows before the container is measured. When another page exists, count is one more than the loaded rows; that extra item is the “Loading more…” footer, and when the last rendered index reaches the end of the loaded rows an Effect calls onLoadMore. Pagination is driven by scrolling, so an unscrolled folder costs one request, and the footer never states a total, following DESIGN.md section 7.3: “A count is never claimed until the full listing is loaded.”

Virtualization bounds the document, not the data. Every loaded page stays cached, and rowsFromPages, sortRows, and filterRows in src/features/browser/rows.ts run over all loaded rows, memoized in useExplorerData; the search term is debounced by 150 milliseconds through useDebounced, matching PLAN.md section 11. The code does not cap the number of loaded pages. FileGrid.tsx virtualizes lines of tiles, with columns computed from a ResizeObserver width.

TransferList.tsx is the one list whose rows change height, because a row can expand to show error details, so it measures rows instead of trusting the estimate.

Source: src/features/transfers/TransferList.tsx, lines 17 to 30

  const scrollRef = useRef<HTMLDivElement>(null);
  const rowH = compact ? 52 : 56;
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => scrollRef.current,
    estimateSize: () => rowH,
    overscan: 8,
    initialRect: { width: 800, height: 600 },
    getItemKey: (i) => {
      const it = items[i];
      if (!it) return i;
      return it.type === "group" ? `g:${it.group.id}` : `j:${it.job.id}`;
    },
  });

Each rendered row passes ref={virtualizer.measureElement} and a data-index. getItemKey matters because items move: a job leaves the Active tab when it completes, and expanding a group inserts children. With index keys, a measured height would stick to a position and the next row would inherit the wrong size; id-based keys keep measurements and component state with the right item.

Accessibility and Testing

Removing rows from the document can break assistive technology. DESIGN.md section 12 requires that “Virtualized lists must expose total row counts when known (aria-rowcount) or -1 when unknown.” FileTable uses role="grid" with aria-rowcount set to rows plus header when the listing is complete, or -1 while more pages exist, and each rendered row carries its absolute aria-rowindex; FileTable.test.tsx asserts both cases. Focus stays on the grid container and aria-activedescendant points at the active row, which suits virtualization because a focused row element would be destroyed when scrolled away. Toaster.tsx mirrors toasts into polite and assertive live regions. One divergence: DESIGN.md suggests a treegrid for expanded transfer groups, while TransferList renders role="list" with expand buttons carrying aria-expanded.

jsdom performs no layout, so every element measures zero and a virtualizer renders nothing. src/test/setup.ts patches clientHeight, clientWidth, offsetHeight, and offsetWidth on HTMLElement.prototype to 800 by 1,000 pixels “so virtualized lists render rows”, and stubs scrollTo and scrollIntoView.

What remains unmeasured is concrete: a scroll test with 10,000 rows against the 50 millisecond long-task target, a queue of 500 or more transfers against N8, and a transfer page profile to decide whether memo or per-row selectors would pay off. PLAN.md section 14 already describes the method (scripted scenarios, five repetitions, median and spread), and results belong in docs/benchmarks/.

Working on This Code

The event path is src/features/transfers/subscription.ts and transferStore.ts. A new TransferEvent variant in crates/r2dock-transfer/src/model.rs needs regenerated bindings (cargo test -p r2dock-transfer) and a new case in reduceTransferBatch; TypeScript narrowing points at every switch. Keep the reducer pure: copy jobs and order at most once per batch, never mutate input, and return the same state when nothing changed. Side effects go in afterEvent and must be constant time per event. Never add a per-event store update, an unthrottled Rust emit, an invalidation per completed job, or progress over Tauri global events instead of the channel.

For lists, copy FileTable.tsx for fixed heights and TransferList.tsx for measured rows with stable keys, and keep aria-rowcount and aria-rowindex correct. Changing row heights means changing both --row-h and Explorer.tsx. Run npm test (notably transferStore.test.ts, subscription.test.ts, TransferRow.test.tsx, FileTable.test.tsx), cargo test -p r2dock-transfer, and for the engine stress run cargo test -p r2dock-transfer --release --test stress -- --include-ignored.

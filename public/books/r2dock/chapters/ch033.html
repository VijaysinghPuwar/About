24 The Custom Media Preview Protocol

A file manager is expected to show a picture when the user clicks it and to play a sound file without downloading it first. For a cloud file manager this creates a hard security problem: the webview must display bytes from a private bucket without ever holding the credentials that unlock the bucket. R2Dock solves it with a custom URI scheme, r2dock-media, served entirely by Rust. The general mechanics of ranged downloads are taught in Chapter 10 (Downloads and HTTP Range Requests).

Why Not a Presigned URL or a Local Server

A presigned URL, whose query string carries a signature granting temporary read access, is itself a credential while valid, and would linger in page memory, caches, and error messages. PLAN.md section 9.5 rejects it explicitly: “No presigned URL or credential reaches the webview.” It would also force the Content Security Policy (CSP) to allow images from *.r2.cloudflarestorage.com, which injected content could use too.

A local HTTP proxy on 127.0.0.1 keeps credentials native, but its socket is reachable by every local process and, through Domain Name System (DNS) rebinding, sometimes by pages in the user’s browser.

A custom scheme avoids both. The webview routes requests for the scheme directly to a Rust callback inside the process: no socket, no signature in the URL. The Tauri Builder documentation describes register_asynchronous_uri_scheme_protocol as taking “an asynchronous responder that allows you to process the request in a separate thread”, and documents the URLs as <scheme_name>://localhost/<path> on macOS and Linux and http://<scheme_name>.localhost/<path> on Windows and Android.

R2Dock registers the scheme in src-tauri/src/lib.rs. The callback spawns a Tokio task that runs media::serve and hands the finished http::Response to the responder, then returns at once so the webview’s networking layer is never blocked. In src-tauri/tauri.conf.json, both spellings of the scheme appear in img-src and media-src and nowhere else; connect-src allows only the IPC transport, so page script cannot fetch the scheme. Tauri’s general file-serving asset protocol, which the convertFileSrc documentation treats as its default, is not enabled. Chapter 22 (Tauri Security Architecture) covers the policy as a whole.

Opaque Tokens as Capabilities

The URL contains nothing but a token. The media_token command in src-tauri/src/commands/browse.rs validates the bucket and key with the same validators as every other command, checks that the connection exists, and asks the registry to issue a token.

Source: src-tauri/src/media.rs, lines 36 to 64

#[derive(Default)]
pub struct MediaRegistry {
    map: Mutex<HashMap<String, (Instant, MediaTarget)>>,
}

impl MediaRegistry {
    pub fn issue(&self, target: MediaTarget) -> String {
        let token = Uuid::new_v4().simple().to_string();
        let mut map = self.map.lock();
        let now = Instant::now();
        map.retain(|_, (t, _)| now.duration_since(*t) < MEDIA_TTL);
        if map.len() >= MAX_TOKENS
            && let Some(k) = map
                .iter()
                .min_by_key(|(_, (t, _))| *t)
                .map(|(k, _)| k.clone())
        {
            map.remove(&k);
        }
        map.insert(token.clone(), (now, target));
        token
    }

    pub fn resolve(&self, token: &str) -> Option<MediaTarget> {
        let map = self.map.lock();
        let (t, target) = map.get(token)?;
        (t.elapsed() < MEDIA_TTL).then(|| target.clone())
    }
}

A token is a random version 4 UUID (122 random bits) written as 32 lowercase hexadecimal characters, mapping to a MediaTarget, either R2 { connection, bucket, key } or Local { path }. Tokens expire after one hour (MEDIA_TTL); the registry holds at most 2,000 (MAX_TOKENS) and evicts expired, then oldest, entries on each issue.

A token is a capability: possessing it is the permission. Only R2Dock’s own webview can request the scheme, and it could ask for the same token anyway; the safety comes from what a token is not. It is not a credential, so a leak exposes one object for at most an hour, through R2Dock only; it names no path, so the webview cannot forge a local target; and it reveals nothing about the key. Tokens are reusable until expiry, unlike the single-use plan tokens in src-tauri/src/state.rs, because an audio element issues many range requests for one source. Tokens are not revoked when a connection is removed, but serve builds the client through ConnectionService::client, which then fails, so such tokens stop working immediately; after an edit they use the new credentials because the client cache is invalidated (Chapter 21, Credential Storage and Authentication).

The Request Path in Rust

serve first extracts the token with token_from_path, which accepts only a path segment of exactly 32 hexadecimal characters; anything else, such as /../etc/passwd, yields 404. The test tokens_parse_strictly covers these cases. For an R2 target, serve then obtains a client, takes a fetch slot from a semaphore, and sends HEAD to learn the object’s size and entity tag (ETag). Every failure becomes a bare status code with an empty body (404 for an unknown token or a missing key, 502 Bad Gateway for most R2 failures, 503 in rare internal cases), so no error text naming a key or endpoint reaches the page.

HTTP Range Support

Audio elements request byte ranges with the Range header (for example bytes=1048576-) and ask for more as the user seeks; the server answers 206 Partial Content with a Content-Range header naming the bytes sent and the total size. Without ranges, seeking in a long audiobook would require downloading it first. R2Dock supports exactly one range per request, parsed by parse_range in media.rs. The three single-range forms are accepted: bytes=a-b, bytes=a-, and bytes=-n (the last n bytes). Multiple ranges, other units, reversed ranges, and malformed numbers return None, treated as “no range”. All arithmetic saturates, so a header such as bytes=18446744073709551615- cannot overflow. The key step is the clamp: whatever was asked, the reply covers at most RANGE_CHUNK (2 MiB) from the start. Players handle short replies by asking for the next range. The test ranges checks each form.

Without a Range header, fetch_object serves an object of at most MAX_WHOLE (64 MiB) whole with status 200, and serves the first 2 MiB of anything larger as a 206. A start at or beyond the end returns 416 Range Not Satisfiable with Content-Range: bytes */<size>.

Bounding Memory, Even Against a Misbehaving Server

The handler returns a complete http::Response<Vec<u8>>, because the responder takes a whole response rather than a stream. Every body therefore sits in memory, which makes bounds essential. The first bound is the per-response limit above. The second is a pair of process-wide Tokio semaphores: FETCHES with six permits (MAX_FETCHES) and BYTES with 128 (BUDGET_MIB), where budget_permits charges one permit per started MiB of expected body, clamped to between 1 and BUDGET_MIB. So at most six R2 previews are in flight, holding at most 128 MiB together. A 64 MiB image takes 64 permits, so two can load at once and a third waits. The upper clamp guarantees any single request can eventually acquire its permits, so the budget cannot deadlock. The test budget_permits_are_bounded checks the arithmetic and that the budget is at least MAX_WHOLE.

The third bound covers a reply that disagrees with HEAD: the object may have been replaced by a larger one, or a server may ignore Range and send everything.

Source: src-tauri/src/media.rs, lines 302 to 327

/// Read a body that must be exactly `want` bytes. Reading stops as soon as
/// it would go past `want`, so a response can never use more memory than
/// expected, whatever its headers say.
async fn read_exact_capped<S, B, E>(
    stream: S,
    want: u64
) -> Result<Vec<u8>, BodyError>
where
    S: futures_util::Stream<Item = Result<B, E>>,
    B: AsRef<[u8]>,
{
    use futures_util::StreamExt;
    let mut stream = std::pin::pin!(stream);
    let cap = usize::try_from(want).map_err(|_| BodyError::TooLong)?;
    let mut out = Vec::with_capacity(cap);
    while let Some(chunk) = stream.next().await {
        let chunk = chunk.map_err(|_| BodyError::Read)?;
        let chunk = chunk.as_ref();
        if chunk.len() > cap - out.len() {
            return Err(BodyError::TooLong);
        }
        out.extend_from_slice(chunk);
    }
    if out.len() == cap {
        Ok(out)
    } else {
        Err(BodyError::TooShort)
    }
}

The buffer is allocated once at the expected size; a chunk that would overflow it ends the read with TooLong before it is copied, and a short body fails with TooShort. Both become 502 with no body, so the webview never gets bytes mixed from two object versions. The test body_reads_stop_at_the_expected_length feeds an endless stream and checks that it is cut off. Before reading, fetch_object also rejects the reply if the HEAD and GET ETags differ, or if Content-Range does not name exactly the requested start, end, and total (range_matches). The test changed_objects_are_never_served_past_the_expected_size runs a stale size, a larger size, a mismatched range reply, and a changed ETag against the local S3 server in r2dock-testkit, each answered with 502.

PLAN.md section 9.5 notes that abandoned requests are not cancelled early; they finish within these bounds and are discarded. Section 9.8 adds that bytes handed to the webview stay in its memory until it releases them.

Content Types and Response Headers

content_type_for in media.rs picks the content type from the key’s extension using a fixed allowlist: PNG, JPEG, WebP, GIF, AVIF, BMP, ICO and SVG images, and MP3, M4A, AAC, Ogg/Opus, WAV and FLAC audio. Everything else, including .html, becomes application/octet-stream, and the object’s stored Content-Type, which an uploader could set to text/html, is ignored. The test content_types_are_allowlisted checks both directions.

Every successful reply also carries X-Content-Type-Options: nosniff, so an HTML file named photo.png is a broken image rather than a page; Cache-Control: no-store, keeping private objects out of the disk cache; Accept-Ranges: bytes; and a response CSP of default-src 'none'; style-src 'unsafe-inline'; sandbox, so a response loaded as a document could load nothing and run no script. The test responses_have_safe_headers checks them. SVG is the one allowlisted format that can contain script; R2Dock shows images only through <img> (MediaImage in src/features/preview/PreviewBodies.tsx), where engines do not run SVG scripts, with the response CSP as a second layer. PLAN.md section 9.4 marks this “[Verify per webview]”, and the code does not record that verification.

Local Targets: Compression Samples

The scheme also serves the 30 second samples of “Compare quality” (Chapter 18, Audio Compression Internals). compression_preview in src-tauri/src/commands/compression.rs writes them under the cache folder preview/<random id>/ and issues MediaTarget::Local tokens; the webview never supplies a path. serve_local reads the file on a blocking thread with the same range rules and headers (test local_samples_are_served_with_ranges). Unlike the R2 path, it takes no semaphore permits and opens files with std::fs::File::open, which follows symbolic links. That relies on the cache folder being private to the user, as the out-of-scope rules in SECURITY.md assume.

Tracing One Request

Figure 24.1 follows one audio preview.

On the page, the useMediaUrl hook calls media_token through TanStack Query, keyed by connection, bucket, and key, so reopening a preview reuses the token, and mediaUrl in src/lib/media.ts builds the URL with convertFileSrc(token, "r2dock-media"). For a 48,000,000 byte MP3, the first request is clamped to bytes 0 to 2,097,151 and takes two byte permits; seeking to the middle produces bytes=24000000-.

Each range costs two billable R2 requests. The fresh HEAD is what detects a changed object and caps the body; caching it per token is a possible future optimization with weaker change detection. PLAN.md section 9.5 also marks as “[Verify]” whether all three platform webviews handle ranges correctly through the asynchronous scheme; the tests exercise the Rust handler directly, so that remains a manual check.

Working on This Code

Everything lives in src-tauri/src/media.rs. Tokens come from media_token in src-tauri/src/commands/browse.rs and compression_preview in src-tauri/src/commands/compression.rs; the frontend side is src/lib/media.ts and src/features/preview/useMediaUrl.ts; the CSP entries are in src-tauri/tauri.conf.json. The unit tests and the local S3 integration test run with cargo test -p r2dock. When changing range handling, extend the ranges table and changed_objects_are_never_served_past_the_expected_size, then check audio seeking by hand on each platform.

The invariants: no presigned URL, credential, or local path reaches the webview; tokens are unguessable and map only to targets Rust created; content types come from the allowlist with nosniff on every reply; every R2 body is read with read_exact_capped under both semaphores. A new previewable type must be unable to execute script in its element; HTML or PDF would need a design review and probably an ADR. The classic pitfall is streaming the body through without the cap, or trusting Content-Length.

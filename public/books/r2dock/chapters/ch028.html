20 Compression Scheduling and Data Integrity

The previous chapters treated compression as a function: give it a file, get back a smaller copy or a reason to upload the original. In the running app, that function sits between a user’s file and an upload that may happen hours or a restart later. Meanwhile the user can edit the original, the copy can be altered, the app can be killed mid-encode, and the disk can fill. This chapter shows how R2Dock uploads only a verified encode of the file the user chose and leaves nothing behind. The code is mostly in crates/r2dock-transfer/src/engine/compress.rs, with source.rs and engine/mod.rs in the same crate. Job states belong to Chapter 13 (Transfer State Machines) and the journal to Chapter 14 (Journals and Persistent Queues).

Two Stages, One Job

A compressed upload is one job with two stages: Queued (needs compression), Compressing, Queued again, then the normal upload from Chapter 9 (Multipart Uploads in Depth). The job’s UploadSpec in model.rs holds the request (compression: settings and failure policy) and the outcome (compressed: a CompressionResult that is Compressed, Unchanged, or Failed). needs_compression is true exactly when a request exists without an outcome, and since the specification is journaled, the decision survives a restart.

A job waiting for or running an encode holds no upload slot. schedule_compression starts encodes up to encode_limit (1 by default, up to 4) and only while finished copies awaiting upload stay within a bound; Chapter 7 (Backpressure and Resource Management) owns that bound. A picked job becomes Compressing, gets a fresh RunControl (the pause and cancel handle from Chapter 16), and runs compress_job as its own task. Figure 20.1 shows the path and its integrity checks.

Where Temporary Files Live

The work folder is paths.cache.join("compress") in the app’s cache directory (set in src-tauri/src/lib.rs). Copies are named <job id>.<ext>, and sample files <job id>.sample.<ext> are deleted right after measuring, so jobs never collide and the user’s folders are never written.

Before a full encode, pipeline.rs requires free space of SPACE_FACTOR (1.2) times the estimate. A full disk is not a failure: the original is uploaded as Unchanged::NoDiskSpace. Because the check uses is_ok_and, unknown free space lets the encode proceed, and since it is a snapshot, another program filling the disk is only detected later as an FFmpeg error. The scale benchmark did not drive it to a full disk.

Proving the Original Did Not Change

A file still being recorded, synced, or edited could change mid-encode, giving a copy of a version that no longer exists. R2Dock opens the original through SourceFile::open in source.rs, as an upload does: no symbolic links, regular files only, identity (device and inode on Unix) compared with the scan, and a Fingerprint of length and modification time in nanoseconds (see Chapter 23, Filesystem Security). After an encode, the same SourceFile checks for changes before the copy is recorded.

ensure_unchanged compares fresh and saved fingerprints. A change deletes the copy and reruns the pipeline; CHANGED_RETRIES is 2, so after three encodes the job fails with “the file is still changing”, which the 0.4.1 CHANGELOG says replaced “being re-encoded forever.” The test a_file_that_keeps_changing_fails_after_retries appends a byte every 20 milliseconds. In the elided middle, a failed hash or mismatched size deletes the copy as a compression failure.

The original is not hashed. An edit that keeps the length and restores the modification time would go undetected; hashing every large original twice more is the cost the code declines. The copy, which R2Dock must later prove untouched, is hashed.

Recording and Rechecking the Copy

digest_written_until in source.rs computes the copy’s SHA-256 (Secure Hash Algorithm with a 256 bit digest) with a fixed 1 MiB buffer, opening without following links, asking a stop callback between blocks so pause or cancel can interrupt it, and rejecting the hash if the metadata changed during the read. Callers run it in spawn_blocking.

The resulting CopyDigest (length, modification time, identity, and hex digest) is stored in CompressedCopy with everything needed to undo compression: the copy’s path (temp), the original’s path, key, size, fingerprint, scan identity, and preset. compress then points the specification’s local, key (a .wav key may become .mp3), size, and identity at the copy, saves the job, and requeues it at the front.

The copy may wait on disk across a restart. Before every upload attempt, first or retry, gate_copy in engine/mod.rs calls check_copy on a blocking thread.

Source: crates/r2dock-transfer/src/engine/compress.rs, lines 301 to 325

pub(super) fn check_copy(c: &CompressedCopy, stop: &dyn Fn() -> bool)
    -> CopyCheck {
    // Size and time tell whether the original changed. Its scan identity
    // is checked when the original itself is uploaded (`restore_original`).
    let original_ok = SourceFile::open(&c.original_local, None)
        .is_ok_and(|s| s.fingerprint == c.original);
    if !original_ok {
        return CopyCheck::Unusable;
    }
    let Some(want) = &c.output else {
        return CopyCheck::Unusable;
    };
    let same_shape = |f: &WrittenFile| f.len == want.file.len
        && f.mtime_ns == want.file.mtime_ns;
    let quick = std::fs::symlink_metadata(&c.temp)
        .is_ok_and(|m| m.is_file() && same_shape(&WrittenFile::of(&m)));
    if !quick {
        return CopyCheck::Unusable;
    }
    match digest_written_until(&c.temp, stop) {
        Ok(Some((file, sha256)))
            if same_shape(&file) && sha256 == want.sha256 =>
        {
            CopyCheck::Usable(file.identity)
        }
        Ok(None) => CopyCheck::Stopped,
        _ => CopyCheck::Unusable,
    }
}

The original must still match its fingerprint, the copy must have a digest (older versions saved none), and the copy must match its recorded length and time (a cheap check) and then its SHA-256. Per the doc comment, the copy’s device and inode are not compared because some file systems report new values after a restart.

In gate_copy, a usable copy proceeds with its proven identity written into the specification, and Stopped becomes a pause or cancel. An unusable copy never fails the job: drop_compressed(id, true) deletes it and restores the original, and the job returns to Queued to compress afresh. Tests in crates/r2dock-transfer/tests/compress.rs cover altered copies, digest-less copies, and a_copy_changed_during_a_retry_wait_is_not_uploaded, a real bug before 0.5.0 per the scale benchmark. That benchmark measured one SHA-256 of a 353 MiB copy at 0.64 seconds on an Apple silicon Mac, with at most 3.1 milliseconds of delay on a 10 millisecond runtime timer (synthetic data, warm cache likely; recorded in docs/benchmarks/2026-10-18-compression-at-scale.md, not re-run for this book).

Uploads attach compression_metadata from upload.rs as x-amz-meta- headers (Chapter 8): r2dock-original-size, r2dock-compression (the preset), and a percent encoded r2dock-original-name, since header values must be ASCII.

Falling Back to the Original

Unchanged (already compressed, too small, no disk space, tools missing, tracks at risk) always continues with the original. Failed (an FFmpeg error, failed verification, the watchdog, an unhashable copy, an original that kept changing) follows the “If compression fails” setting: by default CompressionFailure::UploadOriginal uploads the original under its own key, while SkipFile ends the job Failed with a “Compression failed:” message. The test failure_policies covers both, and the activity log records compress_failed and the other compress_* events.

restore_original swaps the original’s path, key, size, and scan identity back; without the identity, the original would be checked against the copy’s identity or none (a 0.5.0 fix per the scale benchmark).

Pause, Cancel, and Crashes

Encodes are not resumable mid-file. Pausing a Compressing job cancels the token passed to FFmpeg; the runner from Chapter 17 kills the process, the partial output is deleted, and with no outcome recorded, resuming starts over. Cancel ends in Cancelled. The test cancel_and_pause_while_compressing checks both, and the scale benchmark confirmed with pgrep -P that no FFmpeg child or work file remained after cancelling 100 jobs mid-encode.

A task can also end unexpectedly, for example by a panic in a callback. compress_job therefore holds a Finalize guard whose Drop runs on every exit (Chapter 4 explains Drop). Without it, a panic would leave the job showing Compressing forever with its encoder slot counted busy, so no other encode could start. The guard releases the job’s control only if no newer run replaced it (an Arc::ptr_eq comparison), fails a job still in Compressing with “a background task stopped”, and always wakes the scheduler.

finish deletes the journal entry and the copy before announcing Completed, Cancelled, or Skipped, so nobody who sees “completed” finds the copy still there. A failed job keeps its copy for a retry until removed.

At startup, a restored copy that is missing or lacks a digest is forgotten (restore_original). A present copy is not read then (restoring 20 held copies took 0.39 milliseconds in the benchmark); gate_copy checks it before upload. Jobs return as Interrupted (Chapter 15). The tests restart_reuses_the_copy_and_edits_compress_again and an_unchanged_result_survives_a_restart cover this.

A crash mid-encode leaves no outcome, so the job compresses again, but partial output stays on disk. sweep_work_dir deletes every regular file in the work folder that no restored job refers to, once at startup on a blocking thread, with the comment “Copies left by a crash, before any encode can start.” That ordering relies on timing: encodes wait for the separately spawned CompressionService::refresh to check tools and test encoders, which normally takes far longer, but nothing guarantees the sweep finishes first. Until refresh completes, schedule_compression would mark a new compression job ToolsMissing and upload the original; whether the interface can enqueue in that window was not verified.

Working on This Code

engine/compress.rs holds scheduling, the per job task (compress_job, compress), check_copy, and cleanup (drop_compressed, sweep_work_dir, restore_original); gate_copy is in engine/mod.rs, the data model in model.rs, hashing in source.rs. New fields in journaled types need #[serde(default)] so older journals load.

cargo test -p r2dock-transfer --test compress runs the engine tests against the in-process local S3 server; they need R2DOCK_TEST_FFMPEG and skip with a message otherwise. cargo test -p r2dock-transfer --test compress_scale holds the scale scenarios, some ignored and run by name.

Never upload a copy that has not passed check_copy right before that attempt, never let a copy check fail a job, never hold an upload slot while compressing, hash only on blocking threads with fixed buffers and a stop callback, and clean up before announcing a final state. A common pitfall is an early return in compress that records no outcome, leaving needs_compression true forever.

7 Backpressure and Resource Management

Chapter 6 (The Transfer Scheduler) explained which job runs next and how many run at once. This chapter asks where the excess goes when one stage is faster than the next, which decides how much memory, disk, and CPU a large job consumes. Compression internals belong to Part V, and Chapter 20 (Compression Scheduling and Data Integrity) owns the integrity of the copies discussed here.

Fast Producers and Slow Consumers

When a producer outpaces its consumer, the surplus can be buffered, dropped (never acceptable for files), or the producer can be slowed. That third option is backpressure. A transfer tool has several such pipelines: disk to socket, socket to disk, encoder to uploader, and user to engine. R2Dock’s rule, visible throughout the code, is that every buffer is bounded by configuration, never by input size.

Memory: Streaming Instead of Buffering

Upload bodies are built by range_body in crates/r2dock-transfer/src/body.rs, which reopens the source, seeks to the byte range, and wraps it in a tokio_util::io::ReaderStream with a fixed CHUNK of 64 KiB. A stream yields a chunk only when the client asks, which happens only when the socket can take more, so a slow network means fewer reads, not more memory. PLAN.md section 12.3 states the bound as “roughly in-flight requests x SDK buffer size, independent of file size”. That is a design intent: this book did not measure peak memory, and docs/benchmarks/ does not report it.

In-flight requests are bounded by Chapter 6’s job slots and part permits. Each part is hashed with MD5 by SourceFile::md5_range in source.rs through a single 1 MiB buffer on a blocking thread, inside the part’s future after the permit is acquired, so hash buffers are bounded by the same permits.

Downloads apply the same idea in the other direction:

Source: crates/r2dock-transfer/src/download.rs, lines 298 to 317

let mut body = out.body;
let mut written = offset;
loop {
    let chunk = tokio::select! {
        () = ctx.control.cancel.cancelled() => {
            let _ = file.flush().await;
            drop(file);
            return stopped(ctx, &temp);
        }
        c = body.next() => c,
    };
    match chunk {
        None => break,
        Some(Ok(bytes)) => {
            file.write_all(&bytes)
                .await
                .map_err(|e| JobError::io(&e, "save the download"))?;
            written += bytes.len() as u64;
            ctx.counter.set_committed(written);
        }

Because write_all is awaited before body.next() is called again, a slow disk stops the loop from reading the socket, and TCP flow control slows the server. The select! lets a cancel interrupt a stalled read at once.

The Job Queue as a Buffer

The queue of accepted jobs is the one buffer allowed to grow large, and it stays safe because it holds descriptions of work, not data. The folder scanner in crates/r2dock-transfer/src/scan.rs stops at MAX_FILES (200,000) and reports too_many, Added events go out in chunks of at most 500, and the queue file is a snapshot plus an append-only log so a draining queue is not rewritten over and over (Chapter 14, Journals and Persistent Queues).

Compression as a Separate Stage

With compression enabled (off by default, see CompressionPrefs in crates/r2dock-core/src/compression.rs), an audio or video upload becomes two steps: encode a smaller copy into R2Dock’s work folder, then upload it. If both shared one slot, a two hour encode would hold an upload slot idle for two hours. The module comment of crates/r2dock-transfer/src/engine/compress.rs states the design: “a job that waits for or runs an encode holds no upload slot, so file 2 compresses while file 1 uploads.” A job needing compression stays Queued, the upload pick loop skips it, schedule_compression moves it to Compressing when an encoder is free, and when the encode ends the job returns to the upload queue with the copy in its spec. Figure 7.1 shows the pipeline and its bounds.

MediaRuntime::encode_limit comes from CompressionPrefs::encode_limit (default 1, clamped to 1 to 4). The disk budget ready_bytes is always DEFAULT_READY_BYTES, 4 GiB; no setting changes it in the audited version. When FFmpeg is not installed, waiting jobs are marked Unchanged with reason ToolsMissing and upload the original instead of waiting forever. FFmpeg runs below normal priority (see crates/r2dock-media/src/ffmpeg/run.rs) with its threads unlimited. As recorded in docs/benchmarks/2026-10-18-compression-at-scale.md (not re-run for this book), one MP3 audiobook encode used about 141% CPU on a 10-core Apple silicon Mac, sampled with ps; software video encoders can use every core and were not measured at scale.

Bounding the lead of the encoder

An encode limit alone does not prevent a pile-up when uploads are slower than encodes. Before 0.5.0 the benchmark document reports “Encodes ran ahead of uploads without limit”, peaking at 9 copies for 12 short books, and estimates that with 100 long books “the peak grows toward 100 copies (about 35 GB at 353 MB each)”. The fix is a gate in schedule_compression:

Source: crates/r2dock-transfer/src/engine/compress.rs, lines 112 to 154

// Finished copies waiting for (or in) upload. Encodes stop
// while these fill the upload slots plus one per encoder, so a
// big queue never piles up copies on disk faster than they
// upload. Paused or stopped jobs do not hold back the rest.
let (ready, ready_bytes) = map
    .values()
    .filter(|e| e.snap.state == JobState::Queued
        || e.snap.state.is_active())
    .filter_map(|e| match &e.spec {
        JobSpec::Upload(u) if u.compressed_copy().is_some() => Some(u.size),
        _ => None,
    })
    .fold((0usize, 0u64), |(n, b), size| (n + 1, b + size));
let uploads = self.concurrency.load(std::sync::atomic::Ordering::Relaxed);
// ...
    let encoders = media.encode_limit.max(1);
    if running >= encoders
        || ready + running >= uploads + encoders
        || (ready > 0 && ready_bytes >= media.ready_bytes)
    {
        break;
    }

Any of three conditions stops new encodes. The first is the plain encode limit. The second is the backpressure rule: ready counts queued or uploading jobs holding a finished copy, running counts encodes, and a new encode starts only while their sum is below upload slots plus encoders (3 plus 1 by default), so the encoder runs at most one step ahead. The third is the disk budget: once ready copies reach 4 GiB no encode starts, but ready > 0 guarantees progress, so a single copy larger than 4 GiB is still allowed.

Copies held by Paused, Failed, or NeedsDecision jobs are not counted (“Paused or stopped jobs do not hold back the rest”), so one paused file cannot freeze compression, at the cost that the disk can hold more copies than the formula suggests when many jobs are paused. The gate reads the configured concurrency, not the halved overload value, and the loop uses break, so encodes start in queue order and a closed gate is rechecked when the next upload finishes. The test copies_waiting_for_upload_stay_bounded in tests/compress_scale.rs queues 12 short synthetic books with one encoder and a 600,000 bytes per second simulated uplink, and asserts “peak_files <= 4” (“3 upload slots + 1 encoder”) and that every copy is deleted after upload; the benchmark records 9 copies before the fix and 4 after.

Just before running FFmpeg, pipeline::prepare in crates/r2dock-media/src/pipeline.rs checks free space in the work folder for 1.2 times (SPACE_FACTOR) the estimated output. If space is short, the result is Unchanged with reason NoDiskSpace and the original is uploaded. A failure to query free space is treated as enough (is_ok_and), so a real disk-full error then surfaces as an encode failure handled by the user’s “If compression fails” policy. The benchmark document notes that this check was not driven to a full disk.

Head of Line Blocking

Head of line blocking happens when the front of a queue cannot proceed and everything behind it waits. R2Dock 0.5.0 fixed three instances, each recorded with before and after numbers in the compression-at-scale benchmark (single runs, Apple silicon Mac, release builds, in-process local S3 server with a simulated link limit, not re-run for this book).

The first was in the upload pick loop: jobs waiting for the encoder filled the 256-job window and hid everything behind them. Chapter 6 describes the fix; 50 small files behind 300 waiting books went from not starting within 30 seconds to finishing in 0.11 seconds. The reverse direction is handled by requeue_front in compress.rs, which returns a job with a finished copy to the front of the upload queue. At the back, the copy would sit on disk behind thousands of uploads, keeping the gate closed.

The second was pausing a multipart upload. A pause lets in-flight parts finish, but on a slow link a 16 MiB part can take minutes; a pause of three uploads on a 2 MB/s link took 66.6 seconds. The multipart loop in upload.rs now sets a deadline of PAUSE_GRACE (3 seconds) when a pause arrives; when it fires, the loop drops the remaining part futures, releasing their permits, and those parts are sent again on resume. The same pause then took 3.0 seconds, and “Pause all” over 100 jobs went from 14.7 to 3.0 seconds. The test pause_on_a_slow_link_is_prompt_and_resume_completes checks promptness and that resume completes with correct bytes.

The third was cancellation, which must send AbortMultipartUpload. Each cancelled job used to wait for it. abort_in_background in upload.rs now spawns the abort with a 60 second ABORT_TIMEOUT and lets the job finish at once; an abort that never succeeds is left to R2’s default seven day cleanup of incomplete multipart uploads, which the function’s comment cites from PLAN.md section 8.4. Cancelling 100 jobs whose aborts each took 5 seconds went from 5.0 seconds to 21 milliseconds. Each such task lives at most about 60 seconds, one per cancelled multipart upload. Chapter 16 (Retries, Cancellation, and Idempotency) covers the uncertainty this trade introduces.

Releasing Resources on Every Exit Path

Semaphore permits are released by Drop when their part future ends or is dropped. Job slots are derived from state, and every exit from run_job sets a non-active state and wakes the scheduler. Encode slots are also derived (the count of Compressing jobs), so a compression task that panicked without changing state would leak the encoder forever. compress_job prevents that with a drop guard, Finalize (lines 353 to 378), which runs on every exit including an unwinding panic. Under the jobs lock it clears the job’s control handle only if it still belongs to this run (a pause and resume may have replaced it, checked with Arc::ptr_eq), marks a job still shown as Compressing as Failed with “a background task stopped”, and always calls wake.notify_one(). The test early_compression_failure_starts_the_next_job in tests/recovery.rs checks that an early failure frees the slot at once, so the next job starts without any other activity.

Blocking work (hashing, checking a copy’s SHA-256, appending history) goes to Tokio’s blocking pool with spawn_blocking (Chapter 5). The Tokio runtime builder documentation states that the default max_blocking_threads is 512 and that excess tasks “will remain in the queue until one of the busy threads pick it up”; that queue is unbounded. Most callers are bounded by slots or permits, but Inner::finish spawns one history append per finished job, so cancelling 100,000 queued jobs queues 100,000 small writes: short, and they drain, but bounded by queue size rather than configuration. By contrast, gate_copy in engine/mod.rs runs inside a job holding an upload slot and checks for pause or cancel between 1 MiB reads. The benchmark records one SHA-256 check of a 353 MiB copy at 0.64 seconds and a worst 3.1 ms delay of a 10 ms async timer during 20 checks (the copies were hard links, so reads probably hit the page cache).

What the Realistic Runs Show

With six 24.5-hour synthetic books, one encoder, and a 2,000,000 bytes per second uplink, the benchmark document records encodes of 193.3 to 213.0 seconds, a peak of 2 copies (678 MB), and one FFmpeg process at a time. With three 1-hour books on a 600,000 bytes per second uplink, uploads were the bottleneck and the peak was 3 copies. The document notes that the long run’s total time is approximate and that real R2 latency, loss, and throttling are not modeled. At default settings, then, 100 long books hold about four copies on disk (the document says “about 1.4 GB at 353 MB”), one encode, three uploads, and eight part requests, however many files are queued.

Working on This Code

The gate is Inner::schedule_compression in crates/r2dock-transfer/src/engine/compress.rs, with budgets in MediaRuntime set by src-tauri/src/compression.rs. The free space rule is SPACE_FACTOR in crates/r2dock-media/src/pipeline.rs. Streaming bodies are in body.rs and download.rs; pause grace and background aborts are constants in upload.rs.

Most tests in tests/compress_scale.rs and tests/compress.rs need a real FFmpeg: set R2DOCK_TEST_FFMPEG and run cargo test -p r2dock-transfer --release --test compress_scale -- --nocapture --test-threads=1. Without the variable those tests return early and pass trivially; pause_on_a_slow_link_is_prompt_and_resume_completes uses no FFmpeg and always runs. The realistic tests need --ignored and take hours.

Keep the encoder out of upload slots, so compression waiting states stay out of JobState::is_active. Give every new buffer a limit independent of file size, never read a body or file whole, and protect any state-counted resource with a drop guard like Finalize. Do not change requeue_front to push_back; copies would wait on disk behind the whole queue and starve the encoder.

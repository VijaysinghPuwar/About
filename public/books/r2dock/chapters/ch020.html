13 Transfer State Machines

Every transfer row in R2Dock shows a state word such as Queued or Failed, backed by a small finite state machine. Much of the engine’s reliability comes from keeping it honest: a running job must hold a slot, a cancelled job must never upload another byte, and a completed job must leave nothing behind. This chapter is the reference for JobState, its transitions, and the controls that pause or cancel a job another task is running. Chapter 6 (The Transfer Scheduler) covers picking jobs, Chapter 14 (Journals and Persistent Queues) restarts, and Chapter 16 (Retries, Cancellation, and Idempotency) error classification.

Why Model Transfers as a State Machine

A transfer is touched by the scheduler, a job task, the user’s clicks, a compression task, and restarts. If each kept its own idea of the job, they would disagree, which is how “cancelled but still uploading” bugs happen. A state machine gives the job one current state and allows only certain transitions. In R2Dock it is the state field of the job’s JobSnapshot, held behind the jobs mutex; the frontend renders the same snapshot, so screen and engine cannot disagree for longer than one event.

The Thirteen States

The states are a plain enum in crates/r2dock-transfer/src/model.rs, exported to TypeScript through ts-rs:

Source: crates/r2dock-transfer/src/model.rs, lines 21 to 55

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, TS)]
#[serde(rename_all = "camelCase")]
#[ts(export)]
pub enum JobState {
    Queued,
    // ...
    Compressing,
    Preparing,
    Running,
    Paused,
    Retrying,
    Verifying,
    /// A conflict needs the user's choice (policy "Ask").
    NeedsDecision,
    Completed,
    Failed,
    Cancelled,
    Skipped,
    /// Stopped by an app quit or crash; can be resumed or discarded.
    Interrupted,
}

impl JobState {
    pub fn is_terminal(self) -> bool {
        matches!(self, Self::Completed | Self::Cancelled | Self::Skipped)
    }

    /// States that hold a scheduler slot.
    pub fn is_active(self) -> bool {
        matches!(
            self,
            Self::Preparing
                | Self::Running
                | Self::Retrying
                | Self::Verifying
        )
    }
}

The enum carries no data; the error, attempt, and progress live in the snapshot. The elided doc comment on Compressing describes audio and says the state “Does not hold an upload slot”; since 0.4.0 it also covers video. The table below gives each state’s meaning and the predicates that include it: “Active” is is_active, “Terminal” is is_terminal, and “Finished” is the engine’s private is_finished.

State Meaning Predicates
Queued Waiting for an encoder or upload slot none
Compressing Encoding, holds no upload slot none
Preparing Open file, check conflicts, plan Active
Running Bytes moving Active
Retrying Waiting out a backoff Active
Verifying Final checks after the last byte Active
Paused Stopped by the user, work kept none
NeedsDecision Conflict under policy Ask none
Interrupted Restored after a restart none
Completed Done Terminal, Finished
Skipped Not transferred by conflict policy Terminal, Finished
Cancelled Stopped by the user, work discarded Terminal, Finished
Failed Stopped by an error Finished

is_active marks the states that occupy a scheduler slot; the scheduler counts them and the progress ticker samples only them. Retrying is active, so a job in backoff keeps its slot and a burst of failures is not replaced by more jobs that will hit the same outage. Compressing is not, which lets encoding overlap uploading (Chapter 7, Backpressure and Resource Management). is_terminal marks states a job never leaves on its own and that “Clear finished” (Engine::clear_finished) removes. Failed is not terminal, so the user sees the error and can retry, and Cancel still applies to discard partial state.

is_finished in engine/mod.rs adds Failed to the terminal states. Entering a finished state removes the job from the persistent queue file, and save_intent checks the same predicate so a late save cannot resurrect it.

The code shows a subtlety no document states. Inner::finish removes the resume journal entry (a separate file from the queue file, Chapter 14) only for Completed, Cancelled, and Skipped, keeping a failed multipart upload’s parts for Retry, and Engine::restore brings back every job found in either file as Interrupted. So, as far as the code shows, a job that failed while holding resumable state reappears as Interrupted after a restart. The test finished_jobs_are_not_restored covers only a failed download without saved state. Whether this is intended is undocumented; it is harmless because resuming re-checks everything.

How Transitions Are Performed

Inner::set_state is the general path: under the jobs lock it writes the state, error, and timing and pushes a Queued job to the back of the queue; after the lock it drops finished jobs from the queue file and emits TransferEvent::Updated.

Inner::finish handles final states and cleans up first: “Clean up before announcing the final state, so anyone who sees ‘completed’ never finds the job’s copy or journal entry still there.” It then calls set_state and appends a history entry.

The scheduler, schedule_compression, requeue_front, and Inner::control write the state directly under the jobs lock, because the change must be atomic with a decision made under that lock. A running transfer reports Preparing, Running, and Verifying itself through the JobHooks::state callback, which forwards to set_state.

The Main Path

Figure 13.1 shows the transitions of a transfer that happen without user action; compression, which happens before it, is described after the figure.

Compression sits before this path. An upload that asked for it moves from Queued to Compressing when the encoder gate allows (without FFmpeg it uploads the original, reason ToolsMissing). A run that produces a copy, decides “unchanged”, or fails under the default “upload the original” policy returns the job to the front of the queue through requeue_front. A failure under the “skip file” policy finishes it as Failed. A pause or cancel stops FFmpeg, and the stop flag picks Paused or Cancelled; a paused encode keeps no partial output and starts again on resume. If the task ends without settling the state, the Finalize guard from Chapter 7 marks it Failed.

Before every attempt, run_job calls gate_copy, which re-checks a compressed copy (original unchanged, SHA-256 still matching). If the copy is unusable (lines 1125 to 1137 of engine/mod.rs), drop_compressed deletes it and restores the original in the spec, the job’s control is cleared, and the job returns to Queued, so it goes back through the compressor. This never fails the job (test a_copy_changed_during_a_retry_wait_is_not_uploaded); Chapter 20 (Compression Scheduling and Data Integrity) covers the checks.

Inside the transfer, upload::run or download::run reports Preparing while it opens the source, applies the conflict policy, and plans, Running while bytes move, and Verifying while it checks the source did not change or the received length matches. It returns a JobError or an Outcome (Completed, Skipped, NeedsDecision, or Paused, in ctx.rs), which run_job maps to the state of the same name, using finish for the final ones. A cancelled error becomes Paused if the stop flag says pause, otherwise discard_partial runs and the job finishes Cancelled. Completed can come straight from Preparing when a restarted job proves its work was already done (an edge Figure 13.1 omits).

Other errors go through the retry branch (lines 1233 to 1257). If the error is retryable, fewer than MAX_ATTEMPTS (3, including the first) have run, and no stop was requested, the job enters Retrying and waits backoff(attempt + 1) in a select! against control.cancel. backoff in retry.rs gives about 2 then 8 seconds, with 80% to 120% jitter. After the wait, continue restarts the loop, so gate_copy runs again and the transfer reports Preparing: the real path is Retrying to Preparing, not to Running. A pause or cancel ends the wait at once, because pausing a Retrying job also fires the cancellation token.

When the error is not retryable or attempts are used up, the job finishes Failed. A RateLimited or ServerError code also opens the 60 second slowdown of Chapter 6. An authentication error additionally calls fail_connection, which fails every Queued job of that connection and emits TransferEvent::AuthFailed. The test wrong_credentials_fail_without_retry_storm checks that this causes no retry storm.

The Control Path

The user’s click arrives through transfer_control in src-tauri/src/commands/transfers.rs while a Tokio task runs the job. Overwriting the state would not stop that task, so each run gets a RunControl:

Source: crates/r2dock-transfer/src/ctx.rs, lines 26 to 56

/// Pause and cancel requests for one run of a job.
#[derive(Debug, Default)]
pub struct RunControl {
    pub cancel: CancellationToken,
    /// Fires on any pause or cancel request, so a job waiting for parts in
    /// flight notices a pause without polling.
    pub stopping: CancellationToken,
    stop: AtomicU8,
}

impl RunControl {
    pub fn new() -> Self {
        Self::default()
    }

    /// Multipart uploads finish in-flight parts; downloads stop at once.
    pub fn request_pause(&self, interrupt_streams: bool) {
        let _ = self
            .stop
            .compare_exchange(0, 1, Ordering::SeqCst, Ordering::SeqCst);
        self.stopping.cancel();
        if interrupt_streams {
            self.cancel.cancel();
        }
    }

    pub fn request_cancel(&self) {
        self.stop.store(2, Ordering::SeqCst);
        self.stopping.cancel();
        self.cancel.cancel();
    }

The atomic stop records the reason (0 none, 1 pause, 2 cancel); pause’s compare_exchange never downgrades a cancel. Of the two tokio-util tokens, stopping fires on any request and stops new work, while cancel fires on a cancel or interrupting pause and stops in-flight requests. The CancellationToken documentation says cancelled() “will complete immediately if the token is already cancelled”, so an early request is never missed. Each run gets a new RunControl in the job’s Entry, and when it ends it clears the entry’s control only if it is the same object (Arc::ptr_eq), because after a quick pause and resume a newer run may already own it.

In the Pause branch of Inner::control (lines 715 to 738), the current state decides what happens. A Compressing job gets request_pause(true). Otherwise a job that is not pausable refuses: downloads are always pausable, uploads only if they need compression or use multipart, since a single PUT cannot resume halfway (test single_put_cannot_pause). An active job gets request_pause, interrupting streams only for downloads and Retrying jobs; for active and compressing jobs the state is left for the task to settle, and the interface shows “Pausing…” meanwhile. A Queued job is set Paused and removed from the queue under the lock, so the scheduler cannot start it in between.

set_result recomputes pausable from the file to be uploaded, which causes a minor inconsistency no test covers: a paused compression calls set_result(id, |_| {}) while compression is still pending, so a file below the multipart threshold becomes not pausable. After Resume it waits for the encoder refusing Pause, and “pause all” skips it, until schedule_compression sets pausable back to true.

The remaining actions are summarized in the following table, which lists each action, the states it accepts, and the result.

Action Accepted states Result
Resume Paused, Interrupted Queued at the back
Retry Failed, Interrupted, Cancelled Queued, attempt reset to 1
Resolve NeedsDecision Policy stored, then Queued
Cancel Any non-terminal state Cancelled, partial work discarded

Retry also clears a failed compression result so compression is tried again. Retry and Resolve save the updated spec to the queue file under the lock, since a finished job was removed from it; the unit test a_retried_job_finished_while_it_is_saved_is_not_kept forces that save to race with the job finishing again. Cancel on an active or compressing job calls request_cancel and lets the task settle; any other non-terminal job is set Cancelled under the lock, and discard_partial aborts a saved multipart upload in the background or deletes a partial download, and deletes a compressed copy.

Dismiss is a removal, refused while a job is active or compressing; otherwise it cleans up the job’s records and partial work and emits TransferEvent::Removed. On restart, Engine::restore creates every saved job as Interrupted with its committed byte count, outside the run queue; Chapter 15 (Crash Consistency and Recovery) covers what is proven before its work is trusted.

Where the Documentation Differs

PLAN.md section 12.2 has an older diagram of the job machine. It includes a Cancelling state that exists only as a UI label, shows Retrying returning to Running (the code goes through Preparing), shows Running moving to Interrupted on a crash (the code assigns it in restore on the next start), maps “discard” to Cancelled (the code’s Dismiss removes the job), and lacks Compressing and NeedsDecision. Trust the enum over the plan.

Working on This Code

The enum is in crates/r2dock-transfer/src/model.rs, and its TypeScript copy is generated by ts-rs, so update the frontend when a variant changes. Transitions live in engine/mod.rs and engine/compress.rs; RunControl is in ctx.rs. Run cargo test -p r2dock-transfer (with R2DOCK_TEST_FFMPEG set for the compression tests).

When adding a state, decide whether it holds a slot (is_active), can be cleared (is_terminal), and ends the job’s life for a restart (is_finished), and update pause_all, active_count, and the compression gate’s filter, which list states by hand. Check and change state under one lock acquisition, signal running jobs through RunControl instead of overwriting their state, clean up before announcing a final state, and never clear a control without the Arc::ptr_eq check.

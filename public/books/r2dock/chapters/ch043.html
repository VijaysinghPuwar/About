32 Engineering Trade-offs and Future Improvements

Every chapter so far described what R2Dock does. This one collects what it deliberately does not do, why, and what the evidence in the repository suggests changing. The chapter keeps two kinds of statement strictly apart. Sections about compromises describe current behavior at the audited commit, verified in the source. The final section lists proposals; none of them is implemented or committed to in the repository unless the text says so. Between the two sits one consolidated list of places where the project’s documents and its code disagree, since those are the first thing a new contributor trips over.

Intentional Compromises in the Current Code

The project’s stated priority order, in CONTRIBUTING.md and PLAN.md, is “secure, then stable, then easy for beginners, then fast”. Most compromises below follow from it: they trade some speed, generality, or theoretical durability for code that is small, auditable, and hard to misuse.

Job slots are counts, not a semaphore

The engine limits concurrent jobs without a semaphore. Inner::schedule in crates/r2dock-transfer/src/engine/mod.rs recounts the active jobs (Preparing, Running, Retrying, Verifying) under the jobs lock on every pass and starts queued jobs until the count reaches the limit. Chapter 6 (The Transfer Scheduler) explains why: a semaphore only answers whether someone may proceed, while the scheduler must choose who, skipping jobs waiting for the encoder, keys already being written, and groups that already have running jobs, and must change the limit at runtime or halve it for 60 seconds after overload. A count derived from job states cannot drift out of sync with them.

The cost is a pass whose time grows linearly with the number of jobs, and approximate fairness: only the first 256 eligible jobs are considered, and all ungrouped jobs share one bucket. No benchmark measures the pass. The only semaphore, part_slots with 8 permits, covers multipart parts; single uploads and downloads are bounded by job slots alone, which are clamped to at most 8.

A JSON snapshot and log instead of a database

Transfer state lives in journal.json (a resume journal rewritten atomically on each save) and in queue.json plus an append-only queue.log (Chapter 14, Journals and Persistent Queues). An embedded database would give transactions, checksums, and indexed updates. The project chose plain files: no new dependency, human-readable state, and one small module, journal.rs, that a reviewer can read in full. The benchmark docs/benchmarks/2026-10-18-compression-at-scale.md records that this design cut the bytes written while draining 50,000 jobs from a 100,000-job queue from about 636 MB to about 45 MB (single run, release build, an Apple silicon Mac, bytes estimated by polling file sizes; not re-run for this book).

The price is paid in edge cases: log lines carry no checksum, so replay stops at the first unreadable line; JOURNAL_VERSION is written but never checked; tagged enums cannot hold 128-bit integers or numeric map keys; and a corrupt snapshot is backed up while its log is discarded.

Batched durability and no directory sync

Journal changes reach the disk in batches, within 200 milliseconds for the resume journal and one second for the queue. Only persist_now, just before a finished download is moved, writes synchronously. A new upload ID, or the record of a multipart upload’s last part, can therefore be lost to a crash, and recovery then repeats work under the conflict policy (Chapter 15, Crash Consistency and Recovery). The alternative is an fsync per part; the project accepts a short window because recovery re-checks every hint against R2 and the file system.

No code syncs a directory after a rename, and the queue log is truncated after the snapshot rename without a sync. After a process crash this is harmless; after a power loss, a file system that kept the truncation but not the rename would bring back the old snapshot with an empty log. This is analysis, not an observed failure.

A 1 MiB margin instead of verified resume

A resumed download drops the last mebibyte of its partial file (RESUME_BACKOFF in download.rs), because after a power loss a file can be longer than the data that reached the disk. The margin is a heuristic, not a bound. Single-part objects get a final MD5 check against the entity tag (ETag); multipart objects get only a length check, so a hole earlier in the file would pass. Partials are synced only at the end, not while streaming.

Moves are copy, verify, then delete

R2 has no rename, atomic move, or conditional delete. move_one in crates/r2dock-r2/src/bulk.rs copies the inspected source version, confirms the copy’s ETag at the destination and that the source is unchanged, and only then deletes, four objects at a time (Chapter 11, Object Management and Consistency). A source change in the one request before the delete can still be lost, as the code comment and the README’s Limitations admit, and moves are not journaled, so an interrupted move is not resumed.

Simple overload handling and bounded retries

On a RateLimited or ServerError result, run_job halves effective concurrency for a fixed 60 seconds. The AWS software development kit (SDK) makes up to 3 attempts per request, and the engine runs a job at most MAX_ATTEMPTS (3) times, the first attempt included; since run_job calls backoff(attempt + 1) for attempts 1 and 2, the waits are about 2 and 8 seconds and the 30 second step is unreachable. The scheme cannot oscillate, but it treats one stray 503 like sustained throttling, and ServerError also covers non-overload errors such as unrecognized 4xx responses.

Logs that may lose rows

History and activity records are deliberately weaker than the journals. history.jsonl is appended without a sync. The activity log’s writer thread in src-tauri/src/activity/writer.rs holds at most 200,000 rows or 64 MiB, drops and counts rows beyond that rather than making a transfer wait, and gets at most two seconds at exit. Both describe the past, so the project trades completeness for never blocking a transfer.

Unsigned builds without an updater

Release builds are not signed or notarized: release.yml publishes an “Unsigned preview build” with SHA256SUMS.txt, and there is no updater. Signing would need paid certificates and an Apple Developer account (Chapter 31, CI/CD and Desktop Releases). As a result the operating system cannot identify the publisher, checksums help only users who check them, and fixes arrive only when users download them.

Other compromises worth knowing

Restored jobs never restart on their own, costing a click after every crash. Originals are identified by size, modification time, and file identity, not hashed, while compressed copies are verified by SHA-256 lazily before each attempt so startup reads nothing. A failed job with resume state returns as Interrupted after a restart, so “failed” is not final across restarts.

A few smaller mismatches sit in comments rather than documents. The JobState::Compressing doc comment in model.rs says “Audio” though video is compressed too. The load doc in journal.rs says a corrupt file is backed up, which is true only for the snapshot. The comment in the test finished_jobs_are_not_restored says a failed job is not restored, which holds only without resume state. The queue_scale.rs header still mentions only queue.json. In src/lib/errors.ts, isCredentialError and isOfflineError are exported but never imported. The Jurisdiction enum supports default, EU, and FedRAMP, while Cloudflare’s documentation also lists a US jurisdiction. Finally, CI tests only stable Rust, never the declared rust-version of 1.94, and the release workflow runs no tests of its own.

Two rows deserve emphasis because they are security relevant. The delete flow is stricter than SECURITY.md says, which is good, but PLAN.md’s threat model understates what a compromised webview can do: delete_preview returns both the token and the typed phrase, so such a page could confirm a folder delete by itself (Chapter 25, Threat Modeling and Remaining Risks). And ConnectionInput holds the secret as a plain Option<String> in a type that derives Debug; nothing logs it today, but a future debug statement would.

Improvements the Evidence Supports

Everything in this section is a proposal by the book’s authors, derived from the analysis above. None is implemented at the audited commit, and none is a plan the project has recorded unless stated.

For durability, the cheapest fix is to sync the parent directory after each snapshot rename and before truncating queue.log, closing the power-loss gap in compaction. Calling persist_now after CreateMultipartUpload and before CompleteMultipartUpload would close the two upload windows at the cost of two small synchronous writes per large upload. A startup sweep of .r2dock-*.tmp files and the ListMultipartUploads cleanup that PLAN.md section 13 already proposes would remove the remaining orphans. Checking JOURNAL_VERSION on load, and backing up queue.log with a corrupt snapshot, would make future format changes and manual repair safer.

For data integrity, downloads of multipart objects could be verified fully by recomputing per-part MD5s when the part size can be inferred, covering what the 1 MiB margin cannot. A move journal would make interrupted folder moves resumable, as PLAN.md 8.7 describes.

For security, a native confirmation dialog shown by Rust for prefix deletes would make the delete token meaningful against a compromised page. A redacting Debug implementation, or a secret wrapper type, for ConnectionInput would enforce PLAN.md 9.2 in the type system. Removing the unused core permissions (core:app:allow-version, core:window:allow-is-focused, core:path:default) would shrink the page’s reach. Adding deny.toml and a cargo deny step would match the plan. Signing and notarizing releases, then adding an updater with signed manifests, are already listed as Phase 7 deliverables in PLAN.md.

For performance, measure first: no benchmark records a scheduling pass or interface responsiveness (the CHANGELOG’s 0.4.1 numbers have no benchmark file). A gradual recovery restricted to genuine 429 and 503 responses would match PLAN.md 8.11. For testing, a CI job on Rust 1.94, R2DOCK_TEST_FFMPEG on Linux and macOS, and a test that kills a real process mid-upload would turn analysis into evidence.

For documentation, updating PLAN.md’s status line, the benchmark statement, the state diagram, and the text about a Resource Acquisition Is Initialization (RAII) abort guard would remove most of the table above in one change.

Working on This Code

Most items here are good first or second contributions because they are small and well bounded. Documentation fixes touch only PLAN.md, SECURITY.md, and comments in engine/mod.rs, model.rs, and journal.rs; keep the project rule that documents never describe planned features as done. Durability changes belong in crates/r2dock-transfer/src/journal.rs and crates/r2dock-core/src/storage.rs, whose helper is shared with settings and connection files, so test with cargo test -p r2dock-core and cargo test -p r2dock-transfer, and add a reload test next to the existing ones. Security changes in src-tauri need cargo test -p r2dock and must keep build.rs, capabilities/main.json, and src/ipc/commands.ts in agreement. A change that contradicts an Architecture Decision Record (ADR) needs a new ADR in docs/adr/.

The invariants to protect while improving any of this: recovery may only finish work it can prove; no change may block the async runtime or the event sink; and nothing may weaken the path guard, the rule that no secret crosses Inter-Process Communication (IPC), or the bounded concurrency described in earlier chapters.

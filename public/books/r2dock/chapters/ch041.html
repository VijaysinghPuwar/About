30 Performance Benchmarking

A performance number without its conditions is a rumor. This chapter explains how R2Dock measures, how to read each kind of metric, and what the three recorded benchmark documents show, with environment, workload, method, and limitations. Chapter 7 (Backpressure and Resource Management) explains the mechanisms these numbers validate.

Unless stated otherwise, every number below is as recorded in docs/benchmarks/ at the audited commit and was not re-run for this book. Numbers produced for this book are labeled as such.

Where Benchmarks Live

R2Dock has no separate benchmark harness. Measurements are integration tests that print timings with eprintln!, usually marked #[ignore] and run with --release and --nocapture. Results are copied by hand into three dated files in docs/benchmarks/. Because the measuring code also asserts correctness, a benchmark cannot pass with wrong bytes; but there is no stored baseline and no continuous integration (CI) job that runs the measurements, so regressions are found only by hand.

PLAN.md section 14 asks for each scenario “scripted and repeated 5 times; report median and spread” on named reference hardware, with provisional targets such as cold start under 1.5 seconds and idle memory under 200 MB. The recorded documents say their numbers “are from single runs” on one machine, and none of those targets has a measurement. The section’s line “No benchmark numbers exist yet” is now out of date, while section 17.1 still lists Phase 6 (benchmarks) as not started. R2Dock has targeted measurements of specific risks, not a general performance profile.

Instruments in the Test Code

Besides wall-clock timers (std::time::Instant), three instruments recur. Sampling threads watch resources from outside the engine: WorkWatch in crates/r2dock-transfer/tests/compress_scale.rs polls the compression work folder every 5 milliseconds on a plain operating system thread, so the work it observes cannot delay it, and keeps peaks with fetch_max. A sampler can miss a peak shorter than its interval, so its result is a lower bound. DiskWatch in queue_scale.rs estimates logical bytes written to the queue files, not physical device writes. Process inspection, the Unix-only ffmpeg_load, sums the ps CPU percentages of FFmpeg children of the test process and counts their threads.

A runtime responsiveness probe completes the set. While 20 compressed copies are checked with SHA-256 after a restart, the test sleeps for 10 milliseconds in a loop and records how late it wakes.

Source: crates/r2dock-transfer/tests/compress_scale.rs, lines 808 to 818

    while count_final(&engine, &ids) < copies_n {
        let before = Instant::now();
        tokio::time::sleep(Duration::from_millis(10)).await;
        // How late the runtime wakes us: hashing must not block it.
        late = late.max(
            before.elapsed().saturating_sub(Duration::from_millis(10))
        );
        ticks += 1;
        if first_done.is_none()
            && count_where(&engine, &ids, JobState::Completed) > 0
        {
            first_done = Some(t.elapsed());
        }
        assert!(t.elapsed() < Duration::from_secs(1800), "timed out");
    }

If hashing ran on runtime worker threads, timers would fire late by as much as one hash takes; this probe is the experimental check of the spawn_blocking rule from Chapter 5 (Tokio and Asynchronous Execution). The Tokio documentation for sleep says the timer “operates at millisecond granularity” and may be coarser on some platforms, so a wake delay of a few milliseconds is near the probe’s resolution floor.

How to Read Each Kind of Metric

CPU figures from ps are smoothed percentages of one core, so “about 141 percent” means roughly 1.4 cores busy. Memory has no recorded measurement: the activity export’s “memory bounded to one day” is a design statement, and the PLAN.md memory targets are unmeasured, so bounded memory is an architectural argument (Chapters 6 and 7), not a benchmarked fact. Disk metrics are either space (peak copies awaiting upload) or write volume (which matters for drive wear). Throughput is meaningful only when the clock measures the transfer alone, and every transfer benchmark uses the in-process local S3 server, so it never measures an internet path or R2. For latency and queues, the interesting question is usually a bound, not an average.

Benchmark: Transfer and Activity Log Stress

docs/benchmarks/2026-10-17-stress.md records stress runs at version 0.2.0 on an Apple silicon MacBook with release builds. It states that “All transfers go to the in-process local S3 server, so network time is not included” and that “Numbers are from single runs.”

The stress function in crates/r2dock-transfer/tests/stress.rs runs eight concurrent transfers over small files with awkward names and large files whose sizes are not a multiple of the part size. The default test uses 400 small and 4 large files of about 20 MiB; the heavy test uses 3,000 small and 12 of about 96 MiB.

Source: crates/r2dock-transfer/tests/stress.rs, lines 137 to 151

    let started = Instant::now();
    let ids = engine.enqueue(specs, None);

    // Pause everything while work is in flight, then resume it all.
    tokio::time::sleep(Duration::from_millis(300)).await;
    engine.pause_all();
    tokio::time::sleep(Duration::from_millis(300)).await;
    let paused: Vec<JobId> = engine
        .snapshot()
        .into_iter()
        .filter(|j| j.state == JobState::Paused)
        .map(|j| j.id)
        .collect();
    engine.control_many(&paused, JobAction::Resume);

The upload clock starts before enqueueing and includes two deliberate 300 millisecond sleeps. The recorded results are 404 files (96.9 MB) uploaded in 0.75 seconds and downloaded in 1.89 seconds, and 3,012 files (1,306.5 MB) uploaded in 3.21 seconds and downloaded in 15.28 seconds, with “all bytes match” in both. For the default size, 0.6 of the 0.75 seconds is deliberate waiting, so that figure must not be quoted as throughput. The download phase has no pauses; simple division of the recorded figures gives about 51 MB per second and 86 MB per second of local engine throughput. The document does not explain why downloads were slower; extra temporary file and move work per download (Chapter 10) is plausible but unmeasured here. The stronger result is correctness: thousands of jobs paused mid-multipart, resumed in bulk, and compared byte for byte.

The activity log section records 160,000 rows from 32 threads written in 3.8 seconds with “every row written once” and “no formula cells, no secret”, asserted by concurrent_writers in src-tauri/tests/activity_stress.rs, and an export of 1,830,000 rows in 0.44 seconds.

Benchmark: Video Encoders

docs/benchmarks/2026-10-17-video-encoders.md chose the default video encoder (Chapter 19, Video Compression Internals). It used an Apple silicon MacBook with a package manager FFmpeg 9.0.1 “for measurement only”, not the pinned build, and one source: “a 31 minute 1080p30 H.264 web video (3.6 Mbps video, 186 kbps AAC)”, itself hardware encoded. Quality was measured with Video Multi-Method Assessment Fusion (VMAF) through FFmpeg’s libvmaf filter, which the FFmpeg filter documentation describes as scoring a distorted video against a reference; n_subsample=10 scored every tenth frame. The document treats 95 and above as “indistinguishable for most viewers” and below 90 as “visible loss”.

On a 60 second video-only slice, the chosen default, SVT-AV1 at -crf 35 -preset 8, produced 29.6 percent of the source size at VMAF 96.7 in 8.9 seconds. Hardware High Efficiency Video Coding (HEVC) at -q:v 50 matched that size (29.4 percent) but scored only 88.2. Two x264 rows are “GPL, reference only”: x264 is under the GNU General Public License (GPL), so it cannot ship in R2Dock’s builds under the GNU Lesser General Public License (LGPL). On the full file with R2Dock’s pipeline, 936 MB became 285 MB in 355 seconds, VMAF 97.1 on the first 30 seconds. Limitations: one already-compressed source and one machine, plus a recorded pitfall: seeking both files by time “can compare frames one apart”, which produced misleading scores of 75 to 78.

Benchmark: Compression and Uploads at Scale

docs/benchmarks/2026-10-18-compression-at-scale.md is the most instructive because it records measurements, fixes, and re-measurements. Its question: “what happens when a user queues about 100 long audiobooks (and also 1,000 small files) with compression on?” It ran on an Apple silicon MacBook with 10 cores and 24 GB of memory, FFmpeg 9.0.1 from a package manager, and release builds, uploading to the local S3 server through the test kit’s Network shaping (Chapter 29, Automated Testing Strategy). All audio was synthetic tone plus noise from FFmpeg’s lavfi source, and numbers are from single runs.

The findings span every metric type. Disk space: 12 short books on a slow link peaked at 9 copies in the work folder, projected to about 35 GB for 100 books; after the fix, an encode starts only while copies plus running encodes stay below upload slots plus encoders (3 plus 1) and under 4 GiB, and the peak was 4. Queue behavior: 50 small files behind 300 waiting books did not start within 30 seconds because the scheduler examined only the first 256 queued jobs; after the fix they finished in 0.11 seconds. Control latency: Pause all on 100 jobs on an 8 MB/s link went from 14.7 to 3.0 seconds, pausing 3 multipart uploads on 2 MB/s from 66.6 to 3.0 seconds, and Cancel all with a 5 second abort delay from 5.0 seconds to 21 milliseconds, with aborts still sent in the background. Write volume: draining 50,000 of 100,000 jobs used to rewrite queue.json at 59.4 MB per save, about 636 MB in total; the compact snapshot plus append log wrote a 50.1 MB first save and about 45 MB while draining (Chapter 14, Journals and Persistent Queues).

The “Realistic sizes” run used six 24.5 hour books on a 2,000,000 bytes per second link: encodes took 193.3 to 213.0 seconds each, the total was 1,359 seconds, the folder peaked at 2 copies (678 MB), and one FFmpeg ran at about 141 percent CPU. The document flags its weaknesses: with an earlier link limiter “the total time is approximate”, and the machine “also ran builds part of the time, so treat 193 s as an upper figure”. A longer run also uncovered a deadlock in the new queue log, now fixed and covered by two tests.

The restart run held 20 copies of 353 MiB: restoring the engine took 0.39 milliseconds because copies are not read at startup, one SHA-256 check took 0.64 seconds, all 20 were checked and uploaded in 14.4 seconds, and the worst wake delay was 3.1 milliseconds. The copies were hard links to the same content, so “later reads likely came from the page cache”, which measures memory, not disk. A real network, real R2, a cold-cache reread, and a full disk are listed as not covered.

Re-running a Benchmark for This Book

The four default tests in compress_scale.rs were run once for this book at the audited commit, with R2DOCK_TEST_FFMPEG set and cargo test -p r2dock-transfer --test compress_scale -- --nocapture --test-threads=1, on an Apple silicon Mac laptop with FFmpeg 9.0.1 from a package manager. This was an unoptimized debug build. All four passed and printed: 50 small files finished 528 milliseconds after being queued behind 300 waiting encodes; Pause all on 100 jobs settled in 3.003 seconds; Cancel all on 100 jobs took 15.3 milliseconds; 12 books completed in 16.6 seconds with a peak of 4 copies (3,202,200 bytes); and pausing 3 multipart uploads on a 2 MB/s link took 3.003 seconds.

These match the design bounds: pause sits just above the 3 second grace period for parts in flight, cancel takes milliseconds, and the copy peak equals 4. The small-files figure is several times the recorded 0.11 seconds, unsurprising for one debug run. Debug builds can check bounds; comparable timings need repeated release runs.

What Has Not Been Measured

No recorded benchmark covers cold start, idle memory or CPU, memory over a long transfer, interface responsiveness with large folders, throughput against real R2, or a comparison with rclone. The CHANGELOG entry for 0.4.1 describes a responsiveness improvement with 2,000 queued downloads, but no benchmark file records the method, so this book does not repeat its figures. bulk_controls_timing computes medians of five runs on 5,000 jobs, the one place the PLAN.md repeated-run method is implemented, but no result is recorded.

Working on This Code

Benchmarks are tests, so follow Chapter 29: a fast default test that asserts a bound, and a realistic #[ignore = "..."] variant whose reason says how to run it. Keep correctness assertions next to timings. The files are stress.rs, compress_scale.rs, queue_scale.rs, and bulk_controls.rs in crates/r2dock-transfer/tests/, and src-tauri/tests/activity_stress.rs. Reuse WorkWatch, DiskWatch, ffmpeg_load, and the wake probe, and shape links with LocalS3::network.

Measure in release mode, for example cargo test -p r2dock-transfer --release --test stress -- --include-ignored --nocapture. Media tests need R2DOCK_TEST_FFMPEG and synthetic lavfi audio only; never benchmark or name personal recordings. Record results in a new dated file in docs/benchmarks/ with a generic machine description, build profile, exact commands, workload, repetitions, and gaps. Watch for sleeps in timed regions, the page cache, and a busy machine.

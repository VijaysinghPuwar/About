5 Tokio and Asynchronous Execution

R2Dock spends most of its time waiting for R2, FFmpeg, or the user. This chapter owns the definitions of futures, tasks, the Tokio runtime, spawn and spawn_blocking, tokio::select!, cancellation tokens, channels, Notify, and timeouts. Semaphores in the scheduler belong to Chapter 6 (The Transfer Scheduler).

The Problem: Many Slow Things at Once

With one thread per activity, a few uploads, a download, and an encode would need about twenty threads, most blocked on a socket, and a queue of 10,000 files would invite 10,000. Asynchronous programming inverts the model: a task that would block returns control to a scheduler (“wake me when the socket is readable”), so a small thread pool drives many tasks. The price is that code must never block a thread for long, because a blocked thread cannot run the other tasks assigned to it.

Futures: Computations That Run When Polled

An async fn or async block does not run when called. It returns a future, a value that makes progress only when polled. Each .await is a point where it may pause until the runtime polls it again. Creating a future is therefore cheap; the multipart loop creates each part’s future early and polls it later. And dropping a future cancels it: its locals are dropped at the last .await, running their Drop code. This is the foundation of cancellation in async Rust.

The Runtime and Its Threads

R2Dock’s executor is Tokio. The Tokio runtime documentation says the multi-thread scheduler runs futures “on a thread pool, using a work-stealing strategy”, by default with “a worker thread for each CPU core”, plus extra threads for spawn_blocking, and that its fairness holds only when “no task is blocking the thread”.

Tauri creates the runtime (tauri::async_runtime), and the Calling Rust guide says async commands are “executed on a separate async task using async_runtime::spawn”, while synchronous commands run on the main thread. Engine::start spawns tasks (“Must be called inside a Tokio runtime”), so the synchronous setup hook enters the runtime explicitly.

Source: src-tauri/src/lib.rs, lines 95 to 99

let engine = {
    let runtime = tauri::async_runtime::handle();
    let _guard = runtime.inner().enter();
    Engine::start(Arc::new(EngineClients(connections.clone())), config)
};

Per the Tokio Handle documentation, entering the context lets tokio::spawn work without panicking; the guard lives to the end of the block.

Tasks: spawn and the ’static and Send Bounds

A task is a future the runtime polls independently, “an asynchronous green thread” in the words of the Tokio spawning tutorial, which explains two bounds. A spawned future must be 'static: it “must not contain any references to data owned outside the task”, because nobody knows how long it will run. And it must be Send, which “allows the Tokio runtime to move the tasks between threads while they are suspended at an .await”.

So Engine::start spawns the scheduler and progress_ticker tasks with engine.inner.clone(), each owning its own Arc<Inner>. Inner::schedule spawns one run_job task per started job, the compression path one compress_job per encode, and Journal::spawn_writer one writer per journal.

Spawning is cheap, but the count stays bounded. The scheduler starts at most the configured concurrency (3 by default, clamped to 1 to 8), encodes are limited by the encode limit, and part uploads are not tasks at all. Dropping a JoinHandle does not stop a task, and the engine never awaits its job handles; each task reports through shared state and events. This keeps the scheduler simple, but a panic in a job task is visible only through its effects, which the compression path covers with its Finalize guard (Chapter 4, Rust Concepts Used in R2Dock).

spawn_blocking: Where Blocking Work Goes

Keychain access, hashing, directory walks, and fsync cannot be asynchronous, and inside a task they would block a worker. spawn_blocking runs a closure on a separate pool and returns a future for its result. The spawn_blocking documentation adds three facts: the thread limit “is very large by default”, blocking tasks “cannot be aborted once they start running”, and “runtime shutdown will wait indefinitely for all started spawn_blocking to finish running”.

R2Dock uses spawn_blocking in about thirty places: credential store calls, file opening and hashing, journal and settings writes, folder scans, and audio probing. ConnectionService::client shows the shape: it clones an Arc of itself and the configuration into a 'static closure, runs read_secret on the pool (where a keychain that waits for user approval harms nothing else), and compares a generation counter before caching, so a client built from credentials that changed during the read is never stored. A cancellation-aware blocking closure looks like gate_copy, which passes &|| stop.stop() != Stop::None into compress::check_copy, checked between 1 MiB reads, so a pause stops hashing a multi-gigabyte copy within one read.

tokio::fs looks asynchronous, but its documentation says “Tokio will use ordinary blocking file operations behind the scenes” on the spawn_blocking pool and recommends batching. Downloads write and upload bodies read each chunk through tokio::fs::File, so each chunk costs a trip to the pool, while whole-file hashing runs in one blocking closure, as advised. One exception: the retryable body in body.rs calls source.reopen(), a short synchronous open and identity check, inside the body builder of the AWS software development kit (SDK), which may run on a runtime worker; the code does not move it to the blocking pool.

Folder scanning shows a trade-off. scan in crates/r2dock-transfer/src/scan.rs runs in one spawn_blocking call from upload_prepare and collects the whole selection into a Vec, refusing more than MAX_FILES (200,000); Engine::enqueue then sends Added events in chunks of 500. PLAN.md section 12.3 describes a lazy walk that adds child jobs in batches instead. The code is simpler and bounded by the file limit, but its memory grows with the selection, so the plan describes intent, not behavior.

Conversely, compression_estimate in src-tauri/src/planning.rs runs inside spawn_blocking and calls rt.block_on(decide_video(...)) to run ffprobe. Tokio documents that Handle::block_on panics “from within an asynchronous context”, so the function’s comment requires a blocking thread inside the runtime; the Tokio page does not discuss blocking pool threads explicitly.

A Dedicated Thread for the Activity Log

Writer::with_limits in src-tauri/src/activity/writer.rs starts an operating system thread, r2dock-activity, fed over a standard library channel, because a session-long consumer of blocking writes would occupy a pool thread forever and delay shutdown. send never blocks: the channel is unbounded, and two atomic counters cap the queue at 200,000 rows and 64 MiB by default. A row that does not fit is dropped and counted in Settings, so a slow disk loses log rows rather than blocking a command. At exit, shutdown flushes with a two second deadline.

Notify: Waking a Sleeping Task

The scheduler must sleep until something changes without polling (requirement N9). With tokio::sync::Notify, one side calls notify_one and the other awaits notified(). The Notify documentation says that if no task is waiting, “a permit is stored”, and “many sequential calls to notify_one will result in a single permit being stored”. A wake-up sent while the scheduler is busy is not lost, and a burst costs one extra pass.

Source: crates/r2dock-transfer/src/engine/mod.rs, lines 1009 to 1028

async fn scheduler(inner: Arc<Inner>) {
    loop {
        inner.schedule();
        // Re-check after a slowdown window ends even without other events.
        let wait = inner
            .slow_until
            .lock()
            .map(|t| t.saturating_duration_since(Instant::now()))
            .filter(|d| !d.is_zero());
        match wait {
            Some(d) => {
                tokio::select! {
                    () = inner.wake.notified() => {}
                    () = tokio::time::sleep(d) => {}
                }
            }
            None => inner.wake.notified().await,
        }
    }
}

The loop runs one scheduling pass, then waits for a notification. After a rate limit or server error the engine halves its concurrency for 60 seconds (slow_until), so the scheduler also wakes when that window ends. schedule is synchronous and recomputes from the whole job table under one lock, so it does not matter which event woke it. The same pattern drives progress_ticker and the journal writer, which awaits a dirty notification, sleeps one batch interval to absorb bursts, and flushes on the blocking pool at most every 200 milliseconds for the resume journal and every second for the queue (Chapter 14, Journals and Persistent Queues).

select!: Waiting for the First of Several Events

tokio::select! waits on several futures and runs the branch of whichever completes first. Per its documentation, it then returns, “cancelling the remaining branches” by dropping their futures. Branches are checked in random order unless biased; is given, and a branch with a false if precondition is disabled. Because losers are dropped, every select! raises the question of cancellation safety. The documentation lists mpsc::Receiver::recv as safe, and Mutex::lock, Semaphore::acquire, and Notify::notified as losing their queue position when dropped; the scheduler tolerates that because its next pass reads all state afresh.

R2Dock uses select! in thirteen places, most racing work against cancellation: run_job selects over control.cancel.cancelled() and inner.provider.client(connection), and the same shape guards uploads, downloads, listing, bulk operations, and backoff sleeps. Dropping an in-flight HTTP future abandons its connection, which is what a cancel should do.

The multipart upload loop is the most demanding use, with four event sources, two of which depend on state.

Source: crates/r2dock-transfer/src/upload.rs, lines 455 to 488

while failure.is_none()
    && ctx.control.stop() == Stop::None
    && in_flight.len() < ctx.parts_per_job
{
    let Some(part) = pending.next() else { break };
    let slots = ctx.part_slots.clone();
    let control = ctx.control.clone();
    let fut =
        upload_part(ctx, spec, &snapshot, source.clone(), part);
    in_flight.push(async move {
        let Ok(permit) = slots.acquire_owned().await else {
            return None;
        };
        if control.stop() != Stop::None {
            return None;
        }
        let r = fut.await;
        drop(permit);
        Some(r)
    });
}
// ...
let next = tokio::select! {
    () = ctx.control.cancel.cancelled(),
        if ctx.control.stop() == Stop::Cancel => None,
    () = ctx.control.stopping.cancelled(),
        if ctx.control.stop() == Stop::None => Some(None),
    () = sleep_until_opt(pause_deadline) => None,
    r = in_flight.next() => r,
};

The parts in flight are futures in a FuturesUnordered (from futures-util), which yields results in completion order, all inside the single run_job task, so the loop owns its bookkeeping without locks. Each first takes a permit from the engine-wide part-slot semaphore (8 by default; Chapter 6).

The select! waits for the first of four events. A cancel ends the loop, enabled only when the stop state really is “cancel”. A pause, signaled by the stopping token, wakes the loop so it stops queuing parts; enabled only while the state reads “continue”, it fires once and then lets in-flight parts finish. A pause deadline three seconds later (PAUSE_GRACE) ends the wait for slow parts; without a deadline, sleep_until_opt returns std::future::pending(), which never completes. The normal event is the next finished part. When the loop breaks, drop(in_flight) cancels unfinished part requests and releases their permits, while completed parts are already in the resume state.

The FFmpeg runner in crates/r2dock-media/src/ffmpeg/run.rs uses biased; so its cancel branch is checked before reading the next progress line, and a continuous stream of output can never delay a cancel; rx.recv() is cancellation safe, so nothing is lost.

CancellationToken: One Signal, Many Listeners

A cancel must reach the job loop, a part future, a body stream, and a backoff sleep. CancellationToken from tokio-util provides this. Its documentation says cancel() “will wake up all tasks which are waiting for cancellation”, cancelled() completes when cancellation is requested (immediately if it already was) and “is cancel safe”, and clones share state. R2Dock wraps two tokens and an atomic state in RunControl, created fresh for every run.

Source: crates/r2dock-transfer/src/ctx.rs, lines 26 to 56

/// Pause and cancel requests for one run of a job.
#[derive(Debug, Default)]
pub struct RunControl {
    pub cancel: CancellationToken,
    /// Fires on any pause or cancel request, so a job waiting for parts in
    /// flight notices a pause without polling.
    pub stopping: CancellationToken,
    stop: AtomicU8,
}

impl RunControl {
    // ...
    /// Multipart uploads finish in-flight parts; downloads stop at once.
    pub fn request_pause(&self, interrupt_streams: bool) {
        let _ = self
            .stop
            .compare_exchange(0, 1, Ordering::SeqCst, Ordering::SeqCst);
        self.stopping.cancel();
        if interrupt_streams {
            self.cancel.cancel();
        }
    }

    pub fn request_cancel(&self) {
        self.stop.store(2, Ordering::SeqCst);
        self.stopping.cancel();
        self.cancel.cancel();
    }

A cancel fires both tokens. A multipart pause fires only stopping, so in-flight parts finish and are kept, while a download pause also fires cancel because the partial file is kept for resume anyway. Code that must know why it woke reads stop. A resumed job gets a new RunControl; reused cancelled tokens would stop it immediately. Elsewhere, tokens are passed by reference into the FFmpeg runner, installer, and bulk operations, and commands without a cancel button pass &CancellationToken::new().

Channels: Passing Values Between Tasks and Threads

A channel moves values from senders to a receiver, and R2Dock uses four kinds. A Tokio oneshot carries one value: pick_files in src-tauri/src/dialogs.rs turns the native dialog’s callback into an awaitable result, so no thread blocks while the user browses. A bounded Tokio mpsc (multi-producer, single-consumer) channel of capacity 256 carries FFmpeg’s output lines, so if the runner falls behind, the reader tasks and then FFmpeg wait instead of memory growing. Standard mpsc channels feed the activity thread, and Tauri’s Channel<T> (Chapter 2) carries events to the webview through a sink that never awaits, because emit holds the delivery lock.

Async Locks Versus Blocking Locks

The async question about Chapter 4’s locks is when one may be held across an .await. The Tokio Mutex documentation says the ordinary blocking mutex is “often preferred” in async code, that the async mutex’s advantage is “the ability to keep it locked across an .await point”, and that holding a blocking guard across an .await “virtually never leads to correct concurrent code”. R2Dock follows this: engine state uses short parking_lot sections, and the three tokio::sync::Mutex instances serialize operations that await, such as the per-bucket Cloudflare lookup in public_links.rs, where a burst of requests shares one lookup.

Timeouts

A peer can stop responding without failing; tokio::time::timeout returns an error if a future does not finish in time, dropping it. crates/r2dock-r2/src/client.rs configures a 10 second connect timeout, a 30 second per-attempt timeout for metadata and listing calls, and stalled stream protection that fails a transfer stream moving no bytes for 60 seconds. abort_in_background in upload.rs lets a cancelled multipart upload show “Cancelled” at once by spawning the abort with owned strings and a 60 second timeout; if it fails, R2 removes the incomplete upload after its default retention, as the comment notes. The FFmpeg watchdog (120 seconds by default) kills a silent process, and video probing and encoder detection use 60 and 20 second limits.

Working on This Code

Decide first whether work belongs in a task, on the blocking pool, or on a dedicated thread. Keychain calls, file reads and hashes, and folder walks must use spawn_blocking, with a stop callback for long closures, as check_copy does. Spawn with owned values or Arc clones and a bounded task count, check each select! branch for cancellation safety, never hold a parking_lot guard across an .await, bound every network call and child process with a timeout, and wake loops with Notify or a channel, never a polling timer.

Run cargo test -p r2dock-transfer (engine, recovery, pause and cancel against the local S3 server) and cargo test -p r2dock-media (needs FFmpeg). The stress suites are cargo test -p r2dock-transfer --release --test stress -- --include-ignored and cargo test -p r2dock --release --test activity_stress -- --include-ignored. A common pitfall is calling a blocking helper such as a keychain read from an async command “just this once”; it passes a quick test and stalls the runtime under load.

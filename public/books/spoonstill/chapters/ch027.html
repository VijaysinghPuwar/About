22 The Security Model

This chapter is an educational review, not an audit. Each item is labelled Verified protection, Likely protection, Design intention or Potential risk.

22.1 Command execution and shell injection

  • Verified protection. No shell is ever used. All programs start from an absolute path with an argument vector (command.rs); no_shell_strings.rs fails the build if any other file in the media crate constructs a process or contains shell fragments. Hostile filenames are exercised end to end in segment_integrity.rs.
  • Verified protection. A filename starting with - cannot become an option: inputs always follow -i.
  • Verified protection. No file path enters an FFmpeg filter graph string, where : and \ are syntax.
  • Verified protection. The concat list refuses any segment name it did not generate rather than trying to escape it.

22.2 Which binaries run

  • Verified protection. Binaries are resolved to absolute paths from PATH and a fixed list of package-manager folders (D-103).
  • Potential risk. That search trusts whatever executable is first found. A malicious ffmpeg earlier on PATH, or planted in ~/.local/bin, would be run. This is the normal trust model for command-line tools; still doctor and the diagnostics bundle print the exact paths used, which helps detection.
  • Design intention. spoonstill never downloads FFmpeg itself (D-012); installs go through Homebrew or winget, which verify their own packages.

22.3 Paths and directory traversal

  • Verified protection. Every path from a manifest or project.yaml is canonicalised (following symlinks) and checked to stay inside the project, component by component. Error messages do not reveal whether a file outside exists (path_safety.rs, tests path_safety_rejects_dotdot_traversal, ..._leaks_no_existence_through_a_symlink).
  • Verified protection. The output: destination is contained the same way (D-112). --out on the command line goes wherever the operator says, by design.
  • Verified protection. SceneId refuses separators and ...

22.4 Overwriting and data loss

  • Verified protection. Originals are copied, never moved. Ingest never overwrites: it claims each name with create_new.
  • Verified protection. still remove and picture replacement move files to removed/; nothing is deleted. Renumbering parks files under journal names and recovers after a crash (D-121).
  • Verified protection. project.yaml is never written by the renderer (gate 7g checks its mtime and content after a render).
  • Verified protection. The film and every cache file are written beside and renamed, so a crash cannot leave a half-written file under the final name.
  • Likely protection. The cache sweep deletes only names matching spoonstill's own patterns; a stranger's file in .spoonstill/segments survives (tested).

22.5 Untrusted media and text

  • Verified protection. A .txt is size-checked before reading (256 KiB); project.yaml is limited to 1 MiB; chapters to 4 MiB (D-126).
  • Verified protection. Caption bands are clamped to the frame so a huge caption cannot allocate gigabytes (D-139); output geometry has a ceiling so arithmetic cannot overflow (D-114).
  • Potential risk. Decoding a malicious image or audio file is FFmpeg's job; spoonstill inherits FFmpeg's parser security. Running FFmpeg as a separate process does isolate a crash from the spoonstill process, but not from the user's files.

22.6 The desktop window

  • Verified protection. A strict Content Security Policy (script-src 'self', no remote content), and the asset protocol scope grants only the displayed stills, one file at a time (D-127).
  • Verified protection. Writing commands compare the page's root with the project the window has open; opening and revealing files take no path from the page.
  • Design intention. The webview is treated as less trusted than the Rust process.

22.7 Logs and secrets

  • Verified protection. Credentials are redacted when an event is created, so no sink sees them; narration text is kept out of logged command lines by passing it in a file (--file).
  • Verified protection. CSV formula injection through folder names is defused (D-122).
  • Note. There are no API keys in the product today: the only TTS provider needs none. Planned keyring storage for a future paid provider (D-014) does not exist yet.

22.8 Network

  • Verified from source. spoonstill's own Rust code opens no network connections. Speech traffic is made by the edge-tts child process to Microsoft's service; the text of every spoken line leaves the machine. Installers (install.sh, install.ps1) and package managers also use the network.

22.9 Install scripts and releases

  • Verified protection. Both installers download SHA256SUMS.txt from the release and refuse to install an asset whose checksum line is missing or wrong. The release workflow verifies every checksum before publishing, and pins all GitHub Actions to full commit SHAs (D-125).
  • Potential risk. The installer is fetched from the mutable master branch and piped into a shell; checksums come from the same release they verify, so they protect against corruption and partial downloads, not against a compromised release page.
  • Potential risk. Builds are not code-signed or notarized; install.sh removes macOS's quarantine attribute so the app opens (D-099). That is convenient but bypasses Gatekeeper's check for this app.
  • Verified protection. cargo audit --deny warnings runs in CI; 18 advisories are explicitly reviewed and recorded in .cargo/audit.toml with the platform each one reaches.

22.10 unsafe_code = "forbid"

What it protects against: writing unsafe blocks anywhere in spoonstill's own crates, which means no raw pointer dereferences, no FFI calls written by hand, and no manual memory management in this code. forbid (unlike deny) cannot be overridden by an inner #[allow]. This is why the CLI uses the ctrlc crate for signals and sysinfo for RAM: both would otherwise need unsafe.

What it does not protect against: unsafe code inside dependencies (Tauri, the webview bindings, sysinfo, the standard library); bugs in FFmpeg or edge-tts, which run as separate programs; logic errors, path mistakes, or resource exhaustion; and panics. It is a strong guarantee about this repository's own Rust, not about the whole program.

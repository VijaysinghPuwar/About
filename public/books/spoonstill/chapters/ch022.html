18 Captions: Drawing Text Into the Picture

18.1 Why spoonstill draws its own text

FFmpeg can burn subtitles with its subtitles or drawtext filters, but both need the libass and libfreetype libraries, and the Homebrew ffmpeg that the README tells people to install has neither (measured: No such filter: 'drawtext'). So spoonstill_media::caption draws the text into an RGBA image itself, and FFmpeg only composites it with overlay, which every build has (D-106).

18.2 Fonts and shaping

Six fonts are compiled into the binary with include_bytes!: Inter Regular, SemiBold and Bold, and Noto Sans Devanagari in the same three weights (all SIL Open Font License). fontdue rasterises glyphs; harfrust (a Rust port of HarfBuzz) shapes Devanagari, where letters combine into conjuncts and a vowel sign can be drawn to the left of the consonant it follows. Latin text is deliberately not shaped, so every existing Latin caption stays byte-identical (D-157). Characters no bundled font covers (Bengali, Tamil, Arabic, Chinese, emoji) would draw as boxes, so validation warns and names them.

18.3 Layout

For one cue, render_cue:

  1. computes the font size and maximum width as fractions of the frame (so a theme looks the same at every resolution);
  2. wraps words greedily, never breaking a word;
  3. shrinks the text 6% at a time (down to 62%) while it needs more than the theme's maximum lines;
  4. balances the lines by bisection so two lines are nearly equal in width;
  5. clamps the band so it can never be taller than the frame (a 256 KiB caption once produced a 1920x39 839 band, 291.8 MB, 49 s for one cue, D-139);
  6. draws shadow, plate, outline and fill, in that order, into a canvas the full width of the frame.

Two optimisations made this fast enough for 4K (D-130): the outline's disc-shaped dilation became a per-row sliding-window maximum, and the blur became a running sum. At 4K the punch theme went from 604 ms to about 62 ms per cue, with byte-identical output (the old implementations are kept in the tests as the definition of correct).

18.4 How a cue reaches FFmpeg

Each cue's image is written as raw RGBA bytes beside the segment's temporary file and added as an input. From the analysis run's captioned scene:

-f rawvideo -pixel_format rgba -video_size 1920x95 -framerate 30
-i <run>/spoken/.spoonstill/segments/.seg-4629796d93191411.mp4.partial-16618-3.cap00.rgba
-filter_complex '[0:v]...,setsar=1,format=yuv420p[vbase];
   [vbase][2:v]overlay=x=0:y=909:enable='gte(t,0.000)*lt(t,2.836)'[v];
   [1:a]aresample=48000,apad,atrim=end_sample=137600,asetpts=N/SR/TB[a]'
  • Inputs 0 and 1 are the still and the audio, so caption images start at input 2.
  • The overlay comes after the motion chain's format=yuv420p, so the colour and SAR rules are untouched, and the profile check proves it.
  • The window gte(t,S)*lt(t,E) is half-open: a cue is shown from S up to but not including E, so two cues never overlap on the frame they share (between() would include both ends).
  • A one-frame raw input persists because overlay repeats the last frame.
  • The band files are deleted by a Drop guard on every exit path.

18.5 When a scene is captioned

Captions are off by default, because burning text into pixels cannot be undone. When on (subtitles.enabled: true, or --subtitles THEME), a scene is captioned if it has words: an explicit caption column, else the text it speaks, else the .txt beside its recording. The cue text and timing are part of the segment key, so changing a caption re-renders only that scene.

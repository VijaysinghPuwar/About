21 Error Handling

21.1 The philosophy

The project's documents repeat two rules. First, an error is a sentence the operator can act on: it names the scene, the file, the program, and what to do (D-089, D-105). Second, report everything at once: an operator with 500 scenes should not fix one problem, re-render, and discover the next (D-020 and validation's design).

21.2 The layers of error types

Crate Type Example variants
core GeometryError, PathError, SceneIdError, ProblemKind UnusableShortEdge, Outside, NoAudioSource
media MediaError BinaryMissing, Exit, Timeout, Cancelled, ProfileMismatch, JoinStopped
tts TtsError Unavailable, BadRequest, NoAudio, Cancelled, Process(Box<MediaError>)
app ImportError, AudioError, FilmError, IngestError, ArrangeError Import, HasProblems, Locked, VoiceService, Render { failures, not_started }
surfaces String printed after still: or shown in the window

Errors are converted upward with From implementations and ?, and only at the surface are they flattened to text with Display.

21.3 Problems versus errors

Validation does not use Err for project problems. It collects a list of Problem values with a severity. Errors stop a render; warnings are shown and the render continues. ImportError is reserved for "cannot even read the project" (unparseable YAML, missing folder, cancellation).

21.5 Logging every failure

Every scene failure is recorded as an event at the boundary where it happens (render_scene records "scene failed" itself, so no caller can forget), with the full stderr, into both the project log and runs.csv. still diagnostics export packages the logs with an environment description (D-016).

21.6 Rendering is never failed by bookkeeping

A full disk while writing the log, a locked runs.csv, an unwritable recent-projects list: all are swallowed silently by design. A render must not fail because a spreadsheet could not be updated.

5 spoonstill-core: The Pure Domain Model

5.1 Why it exists

spoonstill-core is the vocabulary every other crate speaks. It defines what a scene is, how big a frame is, how long a scene lasts, how a still moves, which problems a project can have, and the exact text of the FFmpeg filter graph. It does no I/O: no files, no processes, no clock, no network. Things that need the outside world are expressed as traits that a higher crate implements (for example RealPath for canonicalising paths and Diagnostics for recording events).

What it deliberately does not own: processes (media), fonts and pixel drawing (media), the H.264 level table (media), cache keys themselves (app), file formats like YAML and CSV (app).

Docs and code disagree. crates/spoonstill-core/Cargo.toml and src/lib.rs describe the crate as holding "cache keys". The keys are actually assembled in spoonstill-app (film.rs:1800-1857 for segments, audio.rs for narrations). Core holds the hash functions and SubtitleSpec::key_fields.

5.3 motion: how a still is told to move

// crates/spoonstill-core/src/motion.rs (types, abridged)
pub enum MotionKind { ZoomIn, ZoomOut, PanLeft, PanRight, PanUp, PanDown }
pub enum Anchor { Center, North, NorthEast, East, SouthEast, South,
                  SouthWest, West, NorthWest }
pub struct MotionSpec { pub kind: MotionKind, pub amount: f64,
                        pub anchor: Anchor, pub seed: u64 }
pub enum MotionSeed { #[default] V1, V2 }

amount is how far to zoom: clamped to 0.02 to 0.50, default 0.10. A NaN becomes the default.

Seeding. If the operator did not pick a move, one is chosen deterministically from a hash, so re-rendering produces the identical film (D-035):

  • MotionSeed::V1 hashes (project folder name, scene index, image content hash). Moving a scene changes its index, so its move changes and its cached segment is no longer valid.
  • MotionSeed::V2 hashes ("motion-seed-v2", project folder name, occurrence, image content hash). "Occurrence" counts how many earlier scenes use the same photo, so one photo shown twice still gets two different moves, but reordering changes nothing (D-153).
// crates/spoonstill-core/src/motion.rs:376-379 (from_seed)
let kind = MotionKind::ALL[(seed % MotionKind::ALL.len() as u64) as usize];
let anchor = Anchor::ALL[((seed >> 20) % Anchor::ALL.len() as u64) as usize];
let amount = 0.08 + ((seed >> 40) % 5) as f64 * 0.01;

So a seeded move has one of 6 kinds, one of 9 anchors, and an amount between 0.08 and 0.12. Projects without a motion_seed: key use V1 forever, so films made before V2 existed do not change; still new writes motion_seed: v2 into every new project.

build_filter(source, output, motion, frames) -> String returns the filter chain. Chapter 15 dissects it completely.

5.4 geometry: legal frame sizes

OutputSpec has private fields, so the only way to get one is OutputSpec::new(aspect, short_edge, fps), which validates:

  1. short edge not zero and even (yuv420p needs even sizes);
  2. for 16:9 and 9:16, short edge divisible by 9, long edge = short / 9 x 16 computed with checked_mul so it cannot overflow;
  3. fps from 1 to 120;
  4. at most 36 864 macroblocks (16x16 blocks) per frame.

That last number is "derived, not chosen": it is MaxFS, the largest frame H.264 level 5.2 allows, the top row of the level table in spoonstill-media. 4K (3840x2160) is 32 400 macroblocks and passes; 8K is 129 600 and is refused. A test in media asserts that the core constant equals the table's last row, because the two crates cannot see each other's constants (D-114). Before this ceiling existed, a huge short_edge in project.yaml could overflow arithmetic and produce nonsense like a 3340530176x32 canvas.

PRESCALE_FACTOR = 3: the motion canvas is three times the output. SourceGeometry records a probed image's width, height and SAR; native_short_edge suggests the largest output a photo can fill without enlarging (a 1376x768 photo: 756 landscape, 432 portrait).

5.5 timing: the frame arithmetic

// crates/spoonstill-core/src/timing.rs:25-38
pub fn frames_for_duration(seconds: f64, fps: u32) -> u32 {
    if !seconds.is_finite() || seconds <= 0.0 || fps == 0 {
        return 1;
    }
    let exact = seconds * f64::from(fps);
    let frames = (exact - 1e-9).ceil();
    // Saturating rather than `as u32`, which would wrap a nonsense duration
    // into a small frame count and render a plausible-looking wrong segment.
    if frames >= f64::from(u32::MAX) {
        u32::MAX
    } else {
        (frames as u32).max(1)
    }
}

In plain English: round up to whole frames, but first subtract a tiny epsilon so that a duration that is exactly on the frame grid (4.0 s at 30 fps is 120.0, which floating point might compute as 120.00000000000001) does not gain a 121st frame. samples_for_frames(frames, fps) returns (frames x 48000 + fps/2) / fps with integers, exact at 24, 25, 30, 50 and 60 fps.

5.6 project: scenes and problems

The central types:

pub enum AudioSource {
    Tts { text: String, provider: ProviderId, voice: VoiceId, settings: TtsSettings },
    File { original_path: PathBuf },
    Silent { seconds: f64 },
}
pub struct SceneDraft { /* every field Option: id, image, text, audio, duration,
                          voice, zoom_direction, zoom_anchor, caption */ }
pub struct SceneSpec { pub id: SceneId, pub image: PathBuf, pub source: AudioSource,
                       pub motion: MotionRequest, pub caption: Option<String> }
pub struct Problem { pub scene: Option<SceneId>, pub kind: ProblemKind }

A draft is a raw row (from a CSV line or a group of files); a spec is a validated scene. validate_drafts turns all drafts into specs plus a list of every problem, not just the first. The key rule (D-020) is "exactly one of text, audio, duration":

// crates/spoonstill-core/src/project.rs:918-937
let declared: Vec<&'static str> = SOURCE_COLUMNS
    .into_iter()
    .zip([text.is_some(), audio.is_some(), duration.is_some()])
    .filter_map(|(name, present)| present.then_some(name))
    .collect();

match declared.len() {
    0 => {
        problems.push(Problem::in_scene(id.clone(), ProblemKind::NoAudioSource));
        return None;
    }
    1 => {}
    _ => {
        problems.push(Problem::in_scene(
            id.clone(),
            ProblemKind::ConflictingAudioSources { declared },
        ));
        return None;
    }
}

ProblemKind has 22 variants. Severity is a property of the kind, not of the caller. Five are warnings (UnpairedFile, UnlistedImage, UndersizedSources, UndrawableCaption, and NeedsPicture when at least one scene has a picture); the rest are errors, and any error stops a render. Examples of errors: MissingImage, NoAudioSource, ConflictingAudioSources, DurationAbsurd (over 3 600 s), Path (a path escaping the project), NotUsableMedia, AmbiguousScene (001.jpg beside 001.png), ToolingMissing, InterruptedRename.

SceneId is a newtype around String with a validating constructor: it rejects blank ids, / or \, . and .., and control characters.

MAX_SCRIPT_BYTES = 256 KiB is derived: one hour of speech at the fastest measured rate of 17.3 characters per second, times 4 bytes per UTF-8 character, rounded up. A .txt larger than that is refused before it is read into memory (D-126).

5.7 captions: subtitle themes and timing

Six themes: classic (default), boxed, band, card, punch, minimal. Every length is a fraction of the frame, so a theme looks the same at 720p and 4K. cues(text, seconds, budget) splits a line into on-screen pieces:

  1. collapse whitespace; allow at most floor(seconds / 0.9) cues (and at most 60);
  2. greedily pack words up to the character budget, ending early at a sentence end;
  3. carry_weak_endings: if a piece ends on a dangling word like "the" or "and", move that word to the next piece;
  4. merge any piece whose share of time would be under MIN_CUE_SECONDS = 0.9 into a neighbour, so no caption flickers;
  5. assign times in proportion to character counts so the last cue ends exactly at the end of the narration.

Timing is proportional to characters because true word timing would need word boundaries from the speech provider, which is the one decision still Open (D-072).

5.8 chapter: cutting a chapter into scenes

still import-chapter takes a pasted chapter and cuts it into pieces of roughly 3 to 5 seconds of speech "where the story allows". The cutter is a classic shortest-path dynamic program over word gaps: every possible cut point has a cost (0 after a sentence or paragraph end, 1 after a clause, 2 after a comma, 25 in the middle of a clause, plus 20 after a dangling word such as "the" or "his"), every piece has a length cost if it is shorter than 3 s or longer than 5 s at the measured 16.3 characters per second, and pieces that cross a sentence boundary in the middle are effectively forbidden. cut_words finds the cheapest sequence of cuts in time proportional to the number of words times the longest allowed piece. A property test generates 1 500 random chapters on every cargo test and checks that no word is lost and every rule holds.

5.9 path_safety: keeping paths inside the project

A manifest cell is untrusted input. It might say ../../../etc/passwd, or name a symlink that points out of the project. resolve_within(root, requested, fs) canonicalises both paths (following every symlink) and checks containment component by component, so /proj-evil is not mistaken for something inside /proj. Two subtle rules:

  • One answer for out of bounds. Whether or not the outside file exists, the answer is Outside, never Missing; otherwise the error messages could be used to probe the disk.
  • Missing paths are resolved from the deepest real ancestor, so a symlinked folder is resolved before deciding.

The filesystem is reached through a trait, which keeps core pure and makes the tests easy:

// crates/spoonstill-core/src/path_safety.rs:59-66
pub trait RealPath {
    fn real_path(&self, path: &Path) -> Option<PathBuf>;
}

resolve_destination_within uses the same core function for the film's output path, where "does not exist yet" is normal (D-112). without_verbatim_prefix strips Windows' \\?\ prefix that canonicalize adds, because FFmpeg's concat demuxer mis-resolved relative entries against such paths (D-142).

5.10 hash: stable hashing

Rust's built-in DefaultHasher is not guaranteed stable across releases, and its default RandomState reseeds every process. A cache key must be the same forever, so core implements 64-bit FNV-1a, a tiny well-known non-cryptographic hash, verified against published reference vectors in a test.

There are two ways to hash several fields:

  • fnv1a_fields puts a separator byte 0x1f between fields. This is only safe if no field can contain 0x1f.
  • fnv1a_prefixed writes each field's length (8 bytes) before the field. No precondition.

The difference matters. Subtitle text is operator text and can contain 0x1f, so ["alpha beta", "gamma"] and ["alpha beta\x1f...gamma"] could join to the same bytes and the same segment key: one film would show another film's subtitles from cache. Decision D-118 moved the segment key to the length-prefixed form.

5.11 language, remedy, diagnostics

  • language::of(text) counts characters per script (Devanagari, Bengali, Cyrillic, Arabic, Han, kana, and more) and returns a language code for the dominant non-Latin script, or None for Latin text. Han with any kana is Japanese, Han alone is Chinese. It is used only when no voice was chosen (D-158).
  • Remedy { need, install, detail } describes a missing tool as data: one plain sentence, an optional tool id the window turns into an Install button, and technical detail.
  • diagnostics defines Event (severity, scope, message, fields), the Diagnostics trait (Send + Sync, object-safe), and redaction: messages and field values are scrubbed when an event is built, so no sink ever sees a secret. A line containing api_key=, token:, password=, Bearer and similar loses everything after the marker, and any 32+ character token-like word is replaced with [redacted].

17 Audio and Text-to-Speech

17.1 Three sources, one result

Every scene's audio is one of three AudioSource variants, and every variant resolves to the same thing: a normalized WAV file plus its measured duration. Nothing after that point needs to know where the audio came from (D-020).

Source Work done Cache file
Tts { text, provider, voice } speak (if the raw speech is not cached), then normalize with trimming spoken-<key>.spoken then tts-<key>.wav
File { recording } normalize, never trimmed file-<key>.wav
Silent { seconds } generate exact-length silence silent-<key>.wav

17.2 Supported recordings

Recordings with extensions mp3 m4a wav aac flac ogg opus wma are accepted in convention mode (anything FFmpeg can decode works in a manifest). Each is probed during validation: no audio stream or no duration is a NotUsableMedia problem with a plain sentence first and the evidence after.

17.3 Normalization: two FFmpeg passes

Pass 1, analyse (real command from the analysis log):

ffmpeg -hide_banner -nostats -loglevel info -i <run>/renderable/audio/002.mp3
       -map 0:a:0 -vn -af loudnorm=I=-16:TP=-1.5:LRA=11:print_format=json -f null -

loudnorm here is used only to measure loudness and true peak; for speech, silencedetect=n=-45dB:d=0.05 is appended to find leading and trailing silence. -map 0:a:0 -vn takes only the first audio stream and ignores an MP3's embedded cover art. -f null - throws the output away.

Pass 2, write:

ffmpeg -hide_banner -nostats -loglevel warning -y -i <run>/renderable/audio/002.mp3
       -map 0:a:0 -vn -af volume=5.84dB -ar 48000 -ac 2 -c:a pcm_s16le -f wav
       <run>/renderable/.spoonstill/cache/audio/.file-64bbaa4704c542e8.wav.partial-16446-0.wav

The gain is computed in Rust:

// crates/spoonstill-media/src/audio.rs:284-296
fn gain_db(analysis: &Analysis) -> Option<f64> {
    let loudness = analysis.loudness?;
    let wanted = LOUDNESS_TARGET_LUFS - loudness;
    let allowed = analysis
        .peak
        .map_or(f64::INFINITY, |peak| TRUE_PEAK_CEILING_DBTP - peak);
    let gain = wanted.min(allowed).clamp(-MAX_GAIN_DB, MAX_GAIN_DB);
    (gain.abs() >= 0.05).then_some(gain)
}

Read it as: aim for -16 LUFS, but never push the peak above -1.5 dBTP, never change by more than 24 dB, and skip a change too small to matter. A single constant volume gain is used instead of loudnorm's own correction mode, because that mode compresses dynamics and can change between FFmpeg versions; a constant gain is byte-identical run to run (D-084). The trade-off: a very peaky recording stops short of -16 LUFS rather than clipping.

For speech only, atrim cuts the provider's leading and trailing silence down to tts.trim_head (0.10 s) and tts.trim_tail (0.25 s). Your own recordings are never trimmed: their pauses are a choice; a provider's are an artifact.

17.4 Silence

ffmpeg -hide_banner -nostats -loglevel warning -y -f lavfi -i anullsrc=r=48000:cl=stereo
       -af atrim=end_sample=96000 -c:a pcm_s16le -f wav <...>/.silent-2cc0b07ecacda096.wav.partial-16446-2.wav

A 2.0 s silent scene is exactly 96 000 samples. Silence is a real audio track so a silent scene follows exactly the same path as a narrated one.

17.5 Measuring

measure first checks the WAV's own header: the RIFF size plus 8 must equal the file length, and a data chunk must fit inside the file. Only then does it run ffprobe and check pcm_s16le, 48 000 Hz, 2 channels, and a positive duration. The header check exists because a cached WAV truncated to 200 bytes still probes as valid audio of 0.0006 s, which once turned an 18.055 s fixture film into a 12.788 s film with exit code 0 (D-190).

17.6 How narration controls scene length

duration (measured from the WAV)  ->  frames = ceil(duration x fps)
                                  ->  samples = frames x 48000 / fps
segment: video exactly `frames` long; audio = WAV + silence, cut at `samples`

The narration is padded, never trimmed (D-022). A narration longer than expected simply makes a longer scene; spoonstill never squeezes speech to fit a picture. The only upper limit is MAX_SCENE_SECONDS = 3 600.

17.7 The text-to-speech path

text in 001.txt (UTF-8, <= 256 KiB, BOM stripped, trimmed)
  -> AudioSource::Tts { text, provider: "edge", voice }
  -> speech key = hash("tts", text, provider, voice, settings)
  -> cached spoken-<key>.spoken ?  yes: skip the network entirely
  -> no: Edge::speak
        pace gate (2 in flight, 1.2 s apart, cool-down on refusal)
        edge-tts --voice V --rate --volume --pitch --file script.txt --write-media out
        retry transient failures (3 attempts)
        check bytes look like audio; join pieces; rename into the cache
  -> normalize (trim provider padding, -16 LUFS) -> tts-<key>.wav
  -> measure -> duration -> frames

In the analysis run, the line "The harbour wakes slowly, one light at a time." produced 21 312 bytes of MP3 from en-GB-RyanNeural, normalized and trimmed to 2.836 s, which became 86 frames (2.867 s) at 30 fps.

Ownership is clear: spoonstill's Rust decides what to say, in which voice, how to retry and how to check the result; the edge-tts tool (Python, third party) talks to Microsoft's service over a websocket; FFmpeg normalizes and measures what came back.

Limits worth knowing: the Edge service returns 24 kHz mono MP3 at 48 kb/s, so a TTS line can never be better than that (README); the service throttles heavy use, which is why the pace gate exists; and it is an unofficial endpoint, which is why the plan calls for an official provider with your own key in a commercial build (D-023, not built).

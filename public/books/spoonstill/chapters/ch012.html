9 spoonstill-app: The Orchestration Layer

9.1 Why it exists

This is where the product lives. Everything either control surface can do is a public function here: make a project, add media, import a chapter, place pictures, validate, render, list voices, check tools. The CLI and the window are forbidden from reaching past it, which is why lib.rs re-exports the few lower-level types they need (Cancel, VideoEncoder, Journal, the TTS facade).

9.4 Import: folder to project

import::load(root, media, cancel) turns a folder into a Project and one list of problems:

  1. canonicalise the root; it must be a directory;
  2. settings::load: read project.yaml (at most 1 MiB) into a raw struct with #[serde(deny_unknown_fields)], so a typo like apsect: is a parse error, then validate each value;
  3. rows::collect: an explicit manifest:, else scenes.csv if present, else convention mode (numbered files in the folder);
  4. ask the probe tool once whether it can run at all (MediaCheck::ready); if FFmpeg is missing, record one ToolingMissing problem instead of one error per photo;
  5. validate_drafts in core;
  6. resolve and probe every file in parallel with pool::run, each path checked for containment first;
  7. warnings: images not listed in a manifest, undersized stills, characters no bundled font can draw, scenes waiting for a picture;
  8. sort problems: project-level first, then by scene.

MediaCheck is a trait so tests and --no-probe can skip FFmpeg:

// crates/spoonstill-app/src/import/mod.rs:90-121 (abridged)
pub trait MediaCheck: Sync {
    fn check(&self, path: &Path, role: Role) -> Result<Option<SourceGeometry>, String>;
    fn ready(&self) -> Result<(), Remedy> { Ok(()) }
}

Convention mode groups files by natural sort of their stem (scene2 before scene10), folding case so Shot.jpg pairs with shot.wav. The folder is sorted before pairing because read_dir order differs between filesystems. Two stills for one slot (001.jpg and 001.png) is an AmbiguousScene error naming both, rather than a silent guess (D-111).

9.5 Ingest: getting files in

still new and still add copy photos in as 001, 002, ... in natural order and pair recordings and scripts by stem first, then by position. Three rules: copy, never move; never overwrite (numbering continues past the highest existing number); unusable files are skipped and reported. A .md file is paired only if its stem matches a photo, never by position, after a README.md was once read aloud (D-152).

Copying is crash-safe (D-120): copy to a hidden partial file beside the destination, claim the final name with create_new (which fails if it exists), then rename over the claim. On a FAT32 volume an interrupted copy used to leave 232 MB of a 400 MB photo at 001.jpg.

create_project also writes a starter project.yaml containing motion_seed: v2 and, if the machine has a fallback voice, a tts: voice: line. This is the one time spoonstill writes project.yaml, and only if the file does not exist.

9.6 The audio cache

Narrations live in .spoonstill/cache/audio/ in two layers:

File What Key includes
spoken-<key>.spoken raw MP3 from the provider text, provider, voice, settings
tts-<key>.wav normalized speech the speech key, trim settings, the normalized profile
file-<key>.wav normalized recording the recording's bytes, the profile
silent-<key>.wav generated silence sample count, the profile

Two layers mean that changing the loudness target or trim re-normalizes every line but re-speaks none. The post-render sweep removes old derived WAVs and never touches spoken- files (D-147), because speech cost a network call.

Single-flight. If eight workers need the same narration (common: one recording reused, many silent stills of the same length), only one does the work: resolve first looks without a lock, then takes a per-key mutex from a global map and looks again before working (D-108). The same pattern memoizes image hashes and audio measurements, so a fully cached 500-scene render no longer probes one silence file 500 times (D-184).

9.7 Pools: bounded parallelism

pool::run(items, jobs, cancel, work) runs work on every item with at most jobs threads and returns results in input order. pool::pipeline runs two dependent stages that overlap: as soon as a scene's narration is ready, its segment can start, while other narrations are still being fetched. Before this (D-146), the CPU sat idle while waiting for the network and the network sat idle while encoding; overlapping them made a cold render about 35% faster in a measurement with simulated network delay.

Two details matter for correctness:

  • results are stored at their index, so the order of finishing never affects the film (D-077: --jobs 1 and --jobs 4 produce byte-identical films, asserted by gate 3);
  • a stage-one failure stops admitting new work, and the report says "N more scenes were not started, because a narration failed before them", not "cancelled" (D-174).

9.8 Capacity: how many at once

The default worker count is half the CPU cores, at most 4 (pool::default_jobs): the measured speed-up curve flattens after 3 to 4 workers. Since D-144 it is also capped by memory. Each worker is modelled as 192 MiB + 36 bytes per prescale pixel (about 0.8 GB at 1080p, 2.7 GB at 4K), against a budget of 70% of total RAM. On an 8 GB machine at 4K that allows 2 workers; on 24 GB the core count decides. An explicit --jobs is always obeyed, with a warning if it does not fit. This was added after a 4K render with four workers froze a Windows machine hard enough to need the power button.

9.9 Arrange and picture: moving files safely

Under the folder convention, the order is the numbers, so moving scene 5 to position 1 means renaming files. arrange::renumber does it in two passes (park every file under a temporary name, then rename to its final name), because renaming 002 onto a live 001 would destroy a file. The temporary name is the journal: .arranging-<from>-to-<wanted>.<ext>. If the process is killed midway, recover runs before the next read and finishes or rolls back each file from its name alone (D-121). Removed scenes go to removed/; nothing is deleted. picture.rs builds put, replace, move, swap and undo on the same machinery.

9.10 Voice: who chose it

voice::resolve(chosen, project_voice, fallback, provider_default) applies one precedence rule and returns both what to show and what to send:

Origin Meaning
Run chosen for this render (--voice, or picked in the window)
Project tts.voice in project.yaml
Fallback the machine's fallback voice (still voices --use NAME)
Unchosen none of the above: each line is read by the script-based default

The window and the CLI both call this function, so "what is shown is what is sent" (D-166). An unchosen voice is a one-line warning in the CLI and a blocked Render button in the window until a voice is chosen once (D-167).

9.11 Machine settings

<config dir>/spoonstill/settings.yaml holds the fallback voice and the chapter-cut preference. machine::read distinguishes "no file" (silent defaults) from "damaged file" (defaults plus a visible problem). Saving uses replace_file: write beside, then rename, so a crash cannot leave a half-written settings file (D-171).

9.12 Tests

265 unit tests, the most of any crate. Examples: eight_workers_wanting_one_photograph_read_it_once (proves single-flight with a barrier), pool ordering and stop-reason tests, renumber crash-recovery tests, and the capacity model's headroom test (the model must stay above every measurement).

Docs and code disagree (all verified by reading): film.rs's module comment says the two pools "run as separate phases" (they overlap since D-146) and that moves are seeded "before the pool starts" (they are seeded inside stage two); pool::SEGMENT_MEMORY_BYTES is public but used nowhere; import/rows.rs lists seven manifest columns but the code accepts eight (caption was added); the default TTS trims are defined twice, in import/settings.rs and audio.rs, with equal values that could drift.

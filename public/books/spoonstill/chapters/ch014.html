11 The Desktop Application

11.1 What it is

apps/desktop is a Tauri 2 application. Tauri runs a native Rust process that hosts the operating system's own web view (WKWebView on macOS, WebView2 on Windows). The user interface is plain HTML, CSS and JavaScript in apps/desktop/ui/ (index.html, styles.css, app.js): no bundler and no npm. JavaScript reaches Rust only through window.__TAURI__.core.invoke("command_name", args). The Rust side is apps/desktop/src/main.rs, and its header repeats the rule: "This window owns no business logic. Every command below is a translation: arguments in, a call into spoonstill-app, a serializable view out."

11.2 Configuration and permissions

Setting (tauri.conf.json) Value Why
window 1180x820, minimum 900x600
titleBarStyle Overlay macOS draws the page's own header under the title bar; ignored on Windows
title empty, set to spoonstill at runtime on Windows only otherwise Windows shows a blank title bar (D-160)
CSP default-src 'self'; script-src 'self'; img-src 'self' asset: ... no inline scripts, no remote content
assetProtocol.scope empty at start each displayed still is allowed individually when a project opens
bundle targets dmg, app, nsis no .msi (D-133)

capabilities/default.json grants only core:default, window dragging (needed for the custom title strip, D-088), and the open-file dialog. There is no general filesystem permission: opening the film or revealing the folder is done by Rust commands that take no path from the page, so the web page cannot name a file to open.

11.3 State held in Rust

// apps/desktop/src/main.rs:716, 800-811 (abridged)
struct Active(Mutex<Option<Cancel>>);          // the running render, if any
struct Session {
    root: Mutex<Option<PathBuf>>,              // the project this window has open
    film: Mutex<Option<PathBuf>>,              // the last film it rendered
    probes: Mutex<ProbeMemo>,                  // remembered probe results
    undo: Mutex<(Option<PathBuf>, Vec<Change>)>, // picture undo, 50 deep
}

Every command that writes checks the page's root against Session.root (project_root), so a page cannot ask Rust to change a project other than the one open (D-127).

11.4 The commands

There are 38 #[tauri::command] functions. The main ones: validate_project (open a project and build its view), create_project, add_media, set_narration, remove_scene, move_scene, set_picture, fill_pictures, move_picture, remove_picture, undo_picture, import_chapter, chapter_cut, voices, preview_voice, voice_choice, subtitle_themes, subtitle_preview, output_formats, resolve_output, render_project, cancel_render, open_film, reveal_project, app_settings, set_default_voice, install_tool, ffmpeg_status, provider_status, recent_projects.

Asynchronous commands follow one pattern: an outer function calls an _inner function that does blocking work inside tauri::async_runtime::spawn_blocking, and passes the outcome to journalled(scope, root, outcome), which writes a row to the logs. A test (every_fallible_window_command_is_written_down) fails if any command returning Result neither journals nor appears on a four-item exempt list.

11.5 The screens

app.js toggles four screens: start (Home: recent projects, New, Open, Settings), settings (voice service, FFmpeg, fallback voice, chapter-cut default, activity log, theme), fill ("Choose photos..." for an empty project), and app (the project). Inside a project, a left rail switches panes: Scenes, Voice, Subtitles, Output, Render, plus an Import chapter pane.

Notable pieces:

  • drawFix is the one component that draws a missing-tool report from a Remedy, with an Install it for me button that calls install_tool.
  • renderBlocker() returns the reason Render is disabled (no project, FFmpeg missing, errors in the project, a bad output path, or an unchosen voice), and the reason is written next to the button (D-089).
  • Picture drag and drop: OS file drops arrive as Tauri events with a position; on macOS that position is in window points but on Windows it is in physical pixels, so only Windows divides by the device pixel ratio (D-194).
  • onFrame coalesces bursts of keystrokes into at most one redraw per animation frame, and tokens stop a slow earlier answer painting over a later one (D-185).

11.6 A Render click, end to end

  1. The Render button's click handler calls render() in app.js (only enabled when renderBlocker() is empty).
  2. render() re-asks Rust which voice will be used (voice_choice) and resolves the output path (resolve_output), then draws one live row per scene in film order.
  3. It creates a Channel for progress and calls invoke("render_project", { request, onProgress }).
  4. Rust's render_project command receives the JSON as a typed RenderRequest (serde, camelCase), parses the overrides, and claims the window's render slot with an ActiveRender guard (a second Render is refused).
  5. Inside spawn_blocking, it builds RenderProjectOptions and calls the same spoonstill_app::render_project the CLI calls.
  6. Each FilmEvent is converted to a ProgressView and sent through the Channel as JSON tagged by kind (planned, audio, segment, failed, joining). The page updates its rows and progress bar.
  7. When the render returns, the result becomes a FilmView, the film path is remembered for Play, the guard drops (freeing the slot even if the render panicked), and one journal row is written.
  8. Stop calls cancel_render, which sets the same Cancel flag; closing the window also requests cancellation.

Things the window does not send that the CLI can: --encoder, --keep-cache, --fps. Jobs are left to Rust's automatic sizing.

11.7 Tests

37 test functions: 13 unit tests and 24 in tests/ui_contract.rs, which reads app.js, index.html, styles.css and main.rs as text and enforces contracts that a browser would otherwise fail silently: every el("id") exists in the markup, every invoke("name") is a registered command, every writing command sends root, the voice shown is the voice sent, every colour combination meets a WCAG contrast ratio, and no input handler calls Rust on every keystroke. scripts/ui-smoke.mjs loads app.js in Node with a fake DOM and fails if its top level throws.

There is no GUI automation: the window's behaviour is tested at its seams, not by clicking (D-131).

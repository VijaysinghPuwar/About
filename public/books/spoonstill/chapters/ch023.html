19 What Happens When I Press Render?

This chapter answers one question in order, without skipping layers: what exactly happens inside my computer after I press Render? It follows the desktop app, and notes where the CLI differs. The example is a three-scene project: 001.jpg with 001.txt, 002.jpg with 002.m4a, and 003.jpg alone.

1. You click Render. The button was clickable only because renderBlocker() in app.js found nothing wrong: a project is open, FFmpeg was found, the project has no errors, the output path is valid, and a voice has been chosen. (In the CLI, you type still render ~/film and clap parses it.)

2. The page asks two last questions. render() asks Rust which voice will actually be used (voice_choice) and where the film will go (resolve_output). Path joining happens in Rust, never in JavaScript.

3. The page prepares to listen. It draws one row per scene in film order, creates a progress Channel, and calls invoke("render_project", { request, onProgress }). The request is JSON: the project path, voice, output folder and name, subtitle choices, aspect and size.

4. Rust receives the request. Tauri deserializes the JSON into a RenderRequest struct. The command parses each override and refuses a bad one immediately. It claims the window's single render slot (a second Render is refused) and creates a fresh Cancel flag.

5. Work moves off the UI thread. spawn_blocking starts a worker thread that calls spoonstill_app::render_project, the same function the CLI calls. From here on, the GUI and the CLI share every line of code.

6. The project is read. import::load reads project.yaml (here, the starter file with motion_seed: v2), lists the folder, and groups files by stem: scene 001 is spoken, 002 is a recording, 003 is silent. Every path is checked to stay inside the project.

7. Every file is inspected. In parallel, ffprobe opens each photo (width, height, pixel shape) and the recording (has audio, has a duration). Problems are collected, not thrown one at a time.

8. Settings are applied in memory. Your chosen voice replaces the scene's voice for this run; the chosen size builds a new OutputSpec (say 1920x1080 at 30 fps). project.yaml is never written.

9. A last check. Any error means stop now, with every problem listed. Warnings (for example "your photos are smaller than the frame") are sent to the page before work starts.

10. The machine is sized up. capacity::plan divides 70% of your RAM by about 0.8 GB per 1080p worker and takes the smaller of that and half your cores, at most 4.

11. The project is locked. .spoonstill/render.lock is locked by the operating system so a second render of this project (from another window or terminal) is refused.

12. Tools are found. Absolute paths for ffmpeg and ffprobe are fixed for the whole run, and the FFmpeg version is logged.

13. The voice service is checked once. Scene 001's speech is not cached yet, so Edge must be available. If edge-tts were missing, the render would stop here, before any work, naming the tool and the Install fix.

14. Audio starts. Up to audio_jobs workers resolve narrations:

  • scene 001: the text's cache key is computed; no cached speech, so the pace gate lets the request through; edge-tts writes an MP3 into the cache; FFmpeg measures its loudness and silence, then writes a trimmed, -16 LUFS, 48 kHz stereo WAV; the WAV is measured: say 2.836 s;
  • scene 002: FFmpeg measures and normalizes the recording (not trimmed);
  • scene 003: FFmpeg generates exactly 4.0 s of silence (192 000 samples).

Each finished narration sends an audio event; the page updates that row.

15. Video starts as soon as each scene's audio is ready. Segment workers do not wait for all narrations. For scene 001:

  • frames = ceil(2.836 x 30) = 86; samples = 86 x 48000 / 30 = 137 600;
  • the photo's bytes are hashed (once, even if several scenes use it);
  • the motion is chosen from the hash of (folder name, occurrence, photo hash), for example pan-up@east:0.1000;
  • the segment key is computed from all of the above plus size, encoder and captions;
  • if seg-<key>.mp4 already exists and passes the profile and frame-count check, it is reused instantly.

16. FFmpeg makes the segment. Otherwise a child process starts with an argument vector like the one in Chapter 15. FFmpeg decodes the JPEG, scales it to 5760x3240 (cover-fit), crops, and zoompan emits 86 frames of 1920x1080, each a slightly different window; it pins the colour, converts to yuv420p, encodes H.264 with libx264, pads and trims the WAV to 137 600 samples, encodes AAC, and writes an MP4 to a hidden temporary file. Progress lines flow back through a pipe.

17. The segment is checked. ffprobe -count_frames decodes it: exactly 86 frames, High profile, level 4.0, yuv420p, tv, bt709, SAR 1:1, 1/90000, AAC 48 kHz stereo. Only then is it renamed to seg-<key>.mp4. A segment event goes to the page.

18. All segments are joined. concat.rs writes a list of the three segment names and runs ffmpeg -f concat -safe 0 -i list -c copy into a hidden temporary beside your output. No re-encoding: the compressed bytes are copied.

19. The film is checked. A header probe confirms the profile, a frame count equal to the sum of segments, and durations within one frame (plus the one AAC frame the container adds). If the film stopped early, the guilty segment is named and deleted so the next render rebuilds only it.

20. Last chance to stop. If you pressed Stop during the join, the film is not published.

21. The film appears. The temporary is renamed to film.mp4 in one atomic step: anything watching the folder sees either the old file or the new one, never a half-written one.

22. Housekeeping. Old cache generations beyond two spares are swept; a film complete row is written to the project log and runs.csv; the lock is released when the function returns.

23. The page is told. The worker thread returns a FilmView; the render slot is freed; the promise in app.js resolves; the page shows "Done", the duration, and how many scenes were reused, with Play and Reveal buttons. (The CLI prints the path and statistics and exits 0.)

If you press Stop at any point: the shared flag is set; no new scene is started; each running FFmpeg receives q, then is killed after 2 s if it has not stopped; finished segments stay in the cache; nothing is published; the page shows "Stopped. The film file was not written." The next Render picks up where this one left off.

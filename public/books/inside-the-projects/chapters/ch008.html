8 Productivity Apps and Developer Tools

This chapter covers the tools Vijaysingh built to save himself time: a translator, an exam simulator, a job finder, text splitters, a web novel saver, a security vault, a video renderer, and several smaller experiments. Most are web apps built on Next.js, some are desktop or local tools in Python and C#, and a few are early front-end exercises. Together they show the same habits again and again. He splits big inputs into safe chunks, keeps secrets on the server, and adds guard rails such as rate limits, clamps, and validation before letting anything expensive run.

TOC Extractor

At a Glance

TOC Extractor is a desktop app for Mac and Windows that saves chapters of a web novel as one clean TXT or PDF file. You paste the novel's main page, the app scans it to find the chapter list and the story text, you pick a range such as chapters 350 to 400, and it saves just the story in reading order. It is for readers who want to read offline without ads and menus. It is also the largest project in this chapter: 91 commits, a Python reference implementation of about 4,000 lines, and a C# port plus desktop app of about 27,000 lines including tests.

How It Works (Simple Version)

Think of a librarian sent to copy a book that is only available as a thousand separate loose pages, scattered across a noisy building full of adverts. First the librarian walks to the table of contents and writes down where each chapter lives. Then, for each chapter, the librarian goes to that page, copies only the story paragraphs, and skips the posters on the wall. If a guard at the door asks "are you a person?", the librarian does not try to sneak past. The librarian waits for you to answer the guard, and from then on walks slowly in that building. At the end, the copied pages are bound into one book, named only for the chapters actually inside.

Deep Dive

Two implementations on purpose. dotnet/README.md explains that the two codebases exist to be compared. A shared "golden" corpus in tests/golden/ (for example v1_golden.json and robots_conformance.json) is read by both test suites, so text cleaning, file naming and robots.txt decisions must agree. A golden corpus is a fixed set of inputs with known correct outputs. The README lists every deliberate difference. One example: Python gave the same 25 second timeout to navigation, to each selector wait and to the outer fetch wrapper, so the outer timer always fired first. The C# port turns one PageBudget into a single cancellation token that every layer must honour.

Politeness and URL safety. politeness.py holds three pieces: a robots.txt policy, a per-host rate limiter, and a URL guard. robots.txt is the file where a website says which paths crawlers may visit. The project implements RFC 9309 (the robots.txt standard) itself, with longest-match rules, * and $ wildcards and Allow winning ties, because Python's urllib.robotparser answered differently across Python versions. The URL guard refuses anything that resolves to a private address, which prevents SSRF. SSRF (server-side request forgery) is when a tool is tricked into fetching internal addresses such as a cloud metadata endpoint.

def _is_private(address: str) -> bool:
    try:
        ip = ipaddress.ip_address(address)
    except ValueError:
        return False

    if (isinstance(ip, ipaddress.IPv6Address)
            and ip.ipv4_mapped is not None):
        ip = ip.ipv4_mapped

    return (
        ip.is_private
        or ip.is_loopback
        or ip.is_link_local
        or ip.is_reserved
        or ip.is_multicast
        or ip.is_unspecified
    )

The interesting line is the IPv4-mapped unwrap: without it, ::ffff:127.0.0.1 would look like a public IPv6 address while actually pointing at localhost. Every rejected link is recorded with a RejectionReason enum value such as PRIVATE_ADDRESS or ROBOTS_DISALLOWED, so nothing is dropped silently. The browser layer applies the same guard again at the request layer, because an allowed host can redirect to a forbidden one.

Scanning without per-site setup. NovelScanner.cs (835 lines) runs scripts inside the page to find the chapter list, the story box and the next and previous links. It infers address patterns such as "id = 3,254,000 + chapter number" and checks them on the live site before using them. RangePlanner.cs then plans the cheapest way to reach a chosen range. Chapters with known addresses are fetched directly. A stretch with no known address is "walked" from whichever neighbour costs fewer pages outside the range. Chapters saved earlier are used as cheap starting points: the comment notes that fetching 101 to 150 after 1 to 100 were saved costs no extra pages, while starting from chapter 1 would cost a hundred.

Adapting to the machine. MachineBudget.cs decides how many Chromium tabs the app may open.

public static int MostTabsFor(long memoryBytes, int cores)
{
    if (memoryBytes <= 0)
    {
        return Math.Clamp(cores * TabsPerCore,
            FewestTabs, MostTabsAnywhere);
    }

    var gigabytes = memoryBytes / (1024.0 * 1024 * 1024);
    var byMemory = (int)((gigabytes - ReservedGigabytes)
        * TabsPerGigabyte);
    var byCores = Math.Max(1, cores) * TabsPerCore;
    return Math.Clamp(Math.Min(byMemory, byCores),
        FewestTabs, MostTabsAnywhere);
}

It reserves 4 GB for the system, allows 2 tabs per remaining gigabyte (a measured working tab is 150 to 400 MB), at most 4 per core, and clamps between 4 and 48. On top of the ceiling it reads free memory at runtime: below 20% free no new tab opens, below 8% work shares the tabs already open. An environment variable TOC_SIMULATE_MEMORY_GB lets tests pretend a large Mac is a small one.

Checking that nothing was skipped. TextAudit.cs compares the saved chapter with the whole story box as the page showed it. Removing ads is the one step that could silently drop a paragraph. Measured across 91 chapters on five sites, the longest legitimate removed line was 10 words, while story paragraphs run 20 to 60 words. So any removed line of 20 or more words flags the chapter, and any 40+ character line that appears more often in the saved text than on the page counts as doubled.

Site pace. SitePaces.cs remembers, per site, whether a "verify you are human" check has appeared. After a check, that site is read at one page every 12 seconds, shared by every book on that site, and the person clicks the check themselves. The README is explicit that the app never solves or bypasses a check.

Resume and checkpoints. checkpoint.py and Checkpoint.cs record each completed chapter with its output file name and a SHA-256 hash, keyed by a fingerprint of the table-of-contents URL and selectors. On restart the app verifies files against their recorded hash and skips what it already has. Two ranges of the same book can save at once because they share one progress record behind a lock.

Packaging. packaging/macos/make-app.sh builds an .app and .dmg; packaging/windows/installer.iss is an Inno Setup script for a per-user installer. .github/workflows/release.yml builds and self-tests both packages when a version is tagged. On first launch the app downloads its own private Chromium (about 150 MB) into its data folder.

Key Design Decisions and Trade-offs

  • A real browser instead of HTTP requests. Many novel sites render chapter lists with JavaScript and sit behind bot checks, so Playwright driving Chromium is slower but far more reliable than a plain HTTP client.
  • Keeping Python as a reference. Maintaining two implementations costs time, but the port found bugs: commit 6775a4e is titled "a second implementation in C#, and the 12 bugs it found".
  • Avalonia over a web UI. A native cross-platform window avoids shipping a server and gives direct file system access on both operating systems.
  • Politeness over speed. Shared per-site rate limiters mean ten books from one site never ask more of it than one book.

Challenges and How They Were Solved

The commit history reads like a field log. Stress tests of 12, 20 and then 40 books at once drove most fixes: "two chapter-losing bugs under load" (031058d), "a busy site no longer costs chapters" (921aa2d), and "one tab no longer serves forty books" (eb5b22c). A 40-book run showed a site occasionally serving a chapter page without its story box, so C# now retries such a page once if the selectors have already worked elsewhere in the run. A concurrency difference also surfaced: Python's single-threaded event loop made some shared counters safe by accident, while .NET continuations really run in parallel, so the tally became a concurrent dictionary and sink writes go through a gate. The README reports that against version 2.2.1 on the same 40 books, average CPU dropped from 272% to 142% and peak memory from 8.2 GB to 7.1 GB.

Security and Performance Notes

  • The URL guard blocks private, loopback, link-local and metadata addresses, including on redirects mid-chain, and tests pin this.
  • Idle tabs close after 30 seconds and images, video and web fonts are blocked while the app reads unattended.
  • One CSV log records every page load, retry, check and unhandled exception for later diagnosis.

txttranslation (Google API Translation)

At a Glance

txttranslation is a Next.js web app for translating and narrating very large texts. Users sign in with Google, upload their own Google Cloud service-account credential, and translate up to a million characters through backend-only routes. It then turns text into speech with Google Cloud Text-to-Speech or Microsoft Edge voices. It solves a common problem with translation APIs: they reject large inputs, so the app splits text intelligently and stitches the results back together. During the current deployment phase, full access is limited to an admin allowlist.

How It Works (Simple Version)

Imagine a translator who can only read one page at a time. You hand over a 300-page manuscript. A helper cuts it at paragraph breaks into page-sized stacks, never in the middle of a sentence if it can help it. The translator works through the stacks in order, and the helper tapes the translated pages back together, keeping the original blank lines between paragraphs. The app does exactly that, and the "key to the translator's office" is your own Google credential, kept in a locked safe that only the server can open.

Deep Dive

Credential storage. A service-account JSON is Google's machine credential: a project id, a client email and a private key. lib/google-credentials.ts validates that the pasted JSON has "type": "service_account" and the three required fields, then runs a tiny live translation as a test. lib/crypto.ts encrypts the whole JSON with AES-256-GCM before it reaches the database. AES-GCM is a cipher mode that both hides the data and adds an authentication tag, so any tampering makes decryption fail.

export function encryptString(value: string) {
  const iv = randomBytes(IV_BYTES);
  const cipher = createCipheriv(
    CIPHER_ALGORITHM, getEncryptionKey(), iv);
  const encrypted = Buffer.concat([
    cipher.update(value, "utf8"), cipher.final()]);
  const tag = cipher.getAuthTag();

  return JSON.stringify({
    version: 1,
    iv: iv.toString("base64"),
    tag: tag.toString("base64"),
    ciphertext: encrypted.toString("base64"),
  } satisfies EncryptedPayload);
}

A fresh 12-byte IV (initialisation vector, a random starter value) is used each time, and the payload carries a version field so the format can change later. The Prisma model UserCredential stores only encryptedJson plus safe metadata (projectId, clientEmail, isValid).

Recursive chunking. lib/translate.ts keeps each request under GOOGLE_SAFE_CHUNK_SIZE = 4500 characters. It tries progressively finer split strategies.

const splitStrategies = [
  (segment: string) =>
    splitByCapturedDelimiter(segment, /((?:\r?\n){2,})/),
  (segment: string) =>
    splitByCapturedDelimiter(segment, /(\r?\n)/),
  splitBySentenceBoundary,
];

splitSegmentRecursively first splits by blank lines (paragraphs), then single newlines, then sentence ends (., !, ? followed by closing quotes or brackets). Pieces are greedily packed back into chunks up to the limit. Only if no strategy works does hardSplitSegment cut, and even then it prefers the last whitespace after 60% of the window. Because delimiters are captured in the regex, they are kept with the text, so joining translated chunks restores the original layout. translateChunk also strips leading and trailing whitespace before calling the API and puts it back afterwards, since the API tends to trim it.

Text-to-speech. lib/tts/ has a provider interface. The Google provider uses Neural2 voices with the same service account. The Edge provider (edge-synthesize.ts) uses the msedge-tts package, which speaks the WebSocket protocol behind Microsoft Edge's read-aloud feature. It splits text into 1,000-character sentence groups, drains each audio stream with a 20 second timeout, and caps the whole call at 50 seconds to stay under Vercel's 60 second function limit.

Background jobs. The Job model stores progress, stage text and chunk counts. A comment in schema.prisma notes that processing is "client-orchestrated": lib/jobs/context.tsx loops over chunks in the browser, calls the synthesis route per chunk, and updates the job record. Progress only advances after a chunk finishes, which fixed a "stuck at 2%" bug.

Access control and rate limiting. /api/translate checks the session, then calls assertRateLimit with key translate:<userId>, 12 requests per 60 seconds. The limiter in lib/rate-limit.ts is a fixed-window counter in a Map. Errors map to precise HTTP codes: 401 not signed in, 402 subscription needed, 403 admin-only, 412 credential missing, 429 too many requests.

Key Design Decisions and Trade-offs

  • Bring your own key. Users pay Google directly, so the app carries no translation cost, at the price of a harder setup.
  • Fixed-window in-memory limiter. Simple and dependency-free, but each serverless instance has its own map, so limits are per instance.
  • Client-orchestrated jobs. Splitting long work into many short requests avoids serverless timeouts, but the browser tab must stay open.
  • Kokoro dropped. History shows several days spent on Kokoro, a browser-side TTS model, with WASM loading and bundle size problems, before it was replaced by server-side Google TTS (be51a58).

Challenges and How They Were Solved

The log shows a run of deployment fixes: Prisma enum imports breaking Vercel builds, bufferutil and utf-8-validate needing to be webpack externals for Edge TTS, and "speech job creation failure" fixed by running prisma db push during build. The 200k character limit was raised to 1M once chunking proved stable. The most recent commit (2e6bf21) stops leaking internal error text to clients and drops IP addresses from rate-limit keys.

Security and Performance Notes

  • proxy.ts (Next.js 16's renamed middleware) sets HSTS, X-Frame-Options: DENY, nosniff, a Permissions-Policy and a CSP, and redirects stray *.vercel.app hosts to the canonical domain.
  • .gitignore excludes credentials/*.json and client_secret*.json; the local copies of these files are not tracked by git.
  • Stripe webhooks are signature-verified and PayPal approvals are re-checked server-side.

JEE Test Simulator (JEE CBT)

At a Glance

JEE Test Simulator recreates the computer-based test (CBT) interface of India's JEE Main engineering entrance exam. A student uploads a question paper PDF and its answer key, a vision-capable AI model turns them into structured questions, and the student takes a timed three-hour, 75-question test with the real marking scheme of +4 for correct and -1 for wrong. It solves the gap between static PDF papers and the actual on-screen exam experience. Users bring their own OpenAI, Anthropic or Gemini key.

How It Works (Simple Version)

Picture three examiners, one for Mathematics, one for Physics, one for Chemistry, each given a photocopy of the paper and the answer key. Each reads only their own section and writes out 25 clean question cards with the right answer on the back. They work at the same time, and each hands in their stack as soon as they finish. The student then sits at a mock exam desk with a timer, a question palette and the same buttons as the real test. When time is up, a grader flips each card and adds up the marks.

Deep Dive

PDF extraction in the browser. lib/pdf-extract.ts uses pdf.js to pull text and also renders compressed page images. Uploads are checked for MIME type, a 10 MB cap and the %PDF- magic bytes (the fixed first bytes every PDF file starts with). Text is capped at 180 KB.

Prompting. lib/providers/prompt.ts defines a strict system prompt: return only a JSON array, ids like M1 to M25, 20 single-correct MCQs and 5 numerical answers per subject, LaTeX inside $...$ for formulas, and use page images as the source of truth when PDF text is garbled. It even tells the model to ignore Symbol-font private-use glyphs that commonly corrupt math in extracted text.

Per-subject fan-out with streaming. Parsing all 75 questions in one call blew past the 60 second serverless limit (commit ff35a0d, "Fix /api/parse 504"). The fix runs one model call per subject in parallel and streams results back as newline-delimited JSON (NDJSON, one JSON object per line).

const tasks = subjects.map(async (subject) => {
  try {
    const qImgs = pickSubjectPageImages(qpImages, subject);
    const aImgs = pickSubjectPageImages(akImages, subject);
    const questions = await parseSubject(
      provider, apiKey, qp, ak, subject, qImgs, aImgs);
    send({ type: "chunk", subject,
           count: questions.length, questions });
  } catch (e) {
    send({ type: "error", subject,
           error: providerErrorMessage(e, subject) });
  }
});

await Promise.allSettled(tasks);
send({ type: "done" });

Promise.allSettled waits for every subject even if one fails, so a Chemistry error does not throw away a good Physics result. pickSubjectPageImages in image-input.ts finds the page with the subject heading and stops before the next subject's heading, sending at most 12 pages per call.

Validation. Model output is parsed inside try/catch and checked against a Zod schema (Zod is a TypeScript library that validates data shapes at runtime). If a subject returns fewer than 25 usable questions, the route reports it as incomplete rather than starting a broken exam.

Grading. lib/grading.ts normalises answers (trim, lowercase, remove spaces) and compares numerical answers as numbers within 1e-6.

const marks = attempted
  ? correct
    ? config.positiveMark
    : -config.negativeMark
  : 0;

Per subject it computes attempted, correct, wrong, unattempted, score and accuracy, which feed the Recharts charts on the results page.

BYOK key storage. lib/key-store.ts encrypts the API key with AES-256-GCM and stores it in an httpOnly, sameSite=strict cookie named jee_byok. The clever part is in lib/crypto.ts: the signed-in user's id is passed as AAD (additional authenticated data, extra input that must match at decryption time). A cookie copied to another account fails to decrypt.

Key Design Decisions and Trade-offs

  • Stateless key storage in a cookie needs no database and suits serverless, but keys live per browser.
  • Saved papers in localStorage, keyed by email, avoid re-parsing (which costs API money) but stay on one device.
  • Three providers give students a choice; each adapter (openai.ts, anthropic.ts, gemini.ts) maps the same prompt and images to its SDK.
  • The parse route is not an open proxy. It accepts only a fixed payload, so a stolen session cannot use someone's key for arbitrary prompts.

Challenges and How They Were Solved

The June 2026 history is a sequence of timeout fixes: first per-subject parallelism, then a "6-way fan-out" to fit OpenAI inside 60 seconds, then per-subject requests from the client. Math PDFs produced corrupt glyphs, which led to the vision fallback (199aaf9) and KaTeX rendering. A missing NEXTAUTH_SECRET caused opaque sign-in failures, so /api/health and lib/env-check.ts now list missing variables.

Security and Performance Notes

  • Every API route requires a NextAuth session; middleware redirects protected pages to /signin.
  • /api/parse is limited to 10 requests per 60 seconds per user (in-memory, per instance; the README suggests Upstash Redis for production).
  • CSP, HSTS and frame-blocking headers are set in next.config.ts.

ResGhost JobRadar

At a Glance

ResGhost JobRadar (repo resghost, folder JobHunt/jobradar) is a private AI job finder built for a focused cybersecurity internship and job hunt. You upload a resume, it searches several legal job sources plus live web search, removes duplicates, ranks the results against your profile, and lets you save jobs, create tailored resume variants and track applications. It replaces a messy routine of many tabs and spreadsheets with one pipeline. Access is restricted to an allowlist plus email/password sign-up.

How It Works (Simple Version)

Think of a recruiter's assistant with a stack of newspapers from different cities. The assistant reads your resume, circles every ad that fits, and notices when the same job appears in three papers so it only clips one copy (keeping a note of the other two). Deep Dive

Sources. lib/search-sources.ts (850 lines) calls the Adzuna API, The Muse public API, the Arbeitnow job board API, Google Jobs through SerpAPI, and an OpenAI Responses call with the web_search_preview tool for sites without APIs. Every fetch goes through fetchJson with a 12 second timeout so one slow source cannot stall the search. Each source's raw fields are normalised into one Job type.

Duplicate detection. lib/dedupe.ts normalises company names (removing "inc", "llc" and aliasing "amazon web services" to "aws"), titles ("cyber security" becomes "cybersecurity") and locations. Similarity uses Jaccard overlap: the number of shared words divided by the number of distinct words in both.

if (companyScore < 0.6 || titleScore < 0.58) {
  return 0;
}

let score =
  companyScore * 0.32 +
  titleScore * 0.28 +
  locationScore * 0.12 +
  urlScore * 0.12 +
  descriptionScore * 0.1 +
  postedScore * 0.03 +
  payScore * 0.03;

Company and title act as a gate; only after passing it do the other signals count. Penalties apply when the same role appears in clearly different non-remote locations, because that is often two real openings. A group's canonical job is chosen by source priority (company site first), then richest description, then newest date. Its id is a SHA-1 hash of normalised company, title and location, so the same job keeps the same id across searches.

Ranking. lib/ranking.ts combines eight scores into one number:

job.matchScore * 0.50 +
  freshnessScore * 0.12 +
  sourceQualityScore * 0.10 +
  domainRelevanceScore * 0.10 +
  locationFitScore * 0.08 +
  typeFitScore * 0.04 +
  workModeFitScore * 0.02 +
  salaryFitScore * 0.02 +
  duplicateConfidenceScore * 0.02

Freshness steps down from 100 (posted today) to 28 (older than 30 days). Source quality ranks "Company Site" at 100 and "OpenAI Web Search" at 68. A long list of irrelevant title patterns (marketing, sales, recruiter, barista) sinks off-domain roles.

Storage. lib/kv.ts wraps Vercel KV (a hosted Redis) but falls back to an in-memory object with values, hashes and lists so local development needs no setup. Keys are namespaced per user email. Key Design Decisions and Trade-offs

  • Legal sources only. The README stresses public APIs and web search over scraping job boards, trading coverage for safety.
  • Base resume never overwritten. Tailored variants are separate records, and each application stores the exact variant used.

Deep Dive

Authentication flow. After Google OAuth completes, the NextAuth signIn callback in frontend/lib/auth.ts posts the user's Google subject id, email and name to /api/auth/sync. The backend creates or updates the user, logs a login event and returns a JWT signed with JWT_SECRET_KEY. A JWT (JSON Web Token) is a signed, self-contained token listing who you are and when it expires. core/security.py decodes it on every request via FastAPI dependencies, and require_admin returns 403 for non-admins.

Vault encryption. core/encryption.py uses Fernet, which combines AES-128-CBC encryption with an HMAC-SHA256 integrity check. The key comes only from VAULT_ENCRYPTION_KEY; a decryption failure returns a generic 500 rather than details.

Threat rules. core/threat.py runs after every audited event:

Rule Trigger Severity
repeated_unauthorized_access 3+ unauthorized hits in 5 min high
rapid_vault_operations 10+ vault ops in 5 min medium
admin_escalation_attempt 5+ admin-path denials in 30 min critical

An alert is only created if no unresolved alert of the same type exists in the window, which stops alert floods.

Risk score. The score sums audit events from the last 24 hours with weights by severity.

weights = {"info": 0, "warning": 2, "critical": 5}
score = sum(weights.get(row.severity, 0) * row.cnt
            for row in rows)

if score <= 10:
    label = "Low"
elif score <= 25:
    label = "Medium"
elif score <= 50:
    label = "High"
else:
    label = "Critical"

The query groups by severity in SQL, so only three rows come back regardless of how many events exist.

Key Design Decisions and Trade-offs

  • Separate Python backend keeps the security logic in a language and framework (FastAPI with Pydantic) suited to validation, at the cost of running two services.
  • Fernet over raw AES removes the chance of misusing IVs or forgetting integrity checks.
  • Rules over machine learning. Threshold rules are explainable and testable, which matters for a course project.
  • Docs only in development. /docs and /redoc are disabled unless APP_ENV is development.

Security and Performance Notes

  • The /api/auth/sync endpoint accepts google_sub and email from the request body without verifying a Google ID token. The google-auth package is in requirements.txt but is not imported anywhere in backend/app. Anyone who can reach the backend could therefore request a JWT for any email. Verifying the Google ID token server-side (or requiring a shared secret between frontend and backend) would close this gap.

Deep Dive

Unicode-safe counting. JavaScript strings are UTF-16, so an emoji or many CJK extension characters count as two units with .length. splitter.ts uses [...text], which iterates by Unicode code point, so a split never lands between the two halves of a character.

Smart split. The search window starts at 60% of the limit, so a chunk is never shorter than 60% unless the text ends.

let breakAt = pos + limit;
const windowStart = pos + Math.floor(limit * 0.6);

let found = false;
for (let i = breakAt - 1; i >= windowStart; i--) {
  if (chars[i] === "\n" && i > 0 && chars[i - 1] === "\n") {
    breakAt = i + 1;
    found = true;
    break;
  }
}
// then single "\n", then " ", else hard cut at limit
chunks.push(chars.slice(pos, breakAt).join(""));
pos = breakAt;

Worker and progress. splitter.worker.ts re-implements the split so the worker bundle has no imports. It posts a progress message about 20 times per job (reportEvery = approxTotal / 20) and one final result with the chunks, total characters and duration. The main thread only computes the first three chunks for the live preview, on a slice of limit * 3 characters.

Export. exporter.ts uses window.showDirectoryPicker (File System Access API, available in Chrome and Edge) to write each file directly, optionally into a timestamped subfolder, and records per-file success or failure. Other browsers get downloadAsZip, which uses fflate's zipSync at compression level 1 (fast). fileNaming.ts pads numbers to the width of the total, so 120 files are named 001.txt to 120.txt and sort correctly.

Key Design Decisions and Trade-offs

  • Browser-first rebuild. The repo started as a monorepo with a Tauri (Rust) desktop app, a web landing page and a shared core package. Commit 141127e deleted all of it in favour of one Next.js app, because the browser's File System Access API made the desktop shell unnecessary.
  • Duplicated split logic in the worker and lib/splitter.ts keeps the worker self-contained, at the cost of two copies to keep in sync. Jest tests cover the library copy.
  • localStorage with try/catch autosaves drafts up to 512 KB and survives private-mode failures.

Challenges and How They Were Solved

A TypeScript 5.7 change made Uint8Array generic, which broke passing fflate's output to Blob (2359fed); the fix casts to Uint8Array<ArrayBuffer>. Tests in __tests__/ pin Unicode safety, file naming and splitting edge cases. An empty TTSGUI/ folder suggests a planned text-to-speech companion that was never started.

Security and Performance Notes

Text never leaves the machine. Splitting is O(n) over code points; the worker prevents UI freezes on multi-megabyte inputs.

How It Works (Simple Version)

Imagine exploring a building floor by floor versus room by room. Breadth-first (BFS) lists every room on floor 1, then every room on floor 2, which makes a confusing list. Depth-first (DFS) walks into a room, lists everything inside it, including rooms within rooms, and only then comes back out to the next door.                         v

Deep Dive

doGet() serves Index.html. buildTopologyFast clamps options server-side (maxDepth 1 to 50, maxItems 100 to 50,000) because client values cannot be trusted. listChildrenV3_ queries '<id>' in parents and trashed=false, adds a MIME filter for folders unless files are requested, pages through results 1,000 at a time, stops early once a per-folder budget is reached, and sorts names with localeCompare.

The tree drawing happens in walkFolderDFS_:

const child = children[i];
const isLast = i === children.length - 1;
const branch = isLast ? "└── " : "├── ";

if (child.type === "folder") {
  lines.push(prefix + branch + child.name + "/");
  state.itemsRendered++;

  const nextPrefix = prefix + (isLast ? "    " : "│   ");
  walkFolderDFS_(child.id, nextPrefix, depth + 1,
    maxDepth, maxItems, includeFiles, lines, state);
  if (state.stopped) return;
}

The prefix string carries the vertical bars of all ancestors. If a folder is the last child, its descendants get blank space instead of a bar, which is what makes the tree's lines join up correctly. A shared state object lets any level stop the whole walk once maxItems is reached.

On the client, google.script.run is Apps Script's asynchronous bridge from page to server. Because an Apps Script call cannot be cancelled, the Stop button sets ignoreResult = true and simply discards the eventual reply. The failure handler maps common errors to hints: quota, a v2 versus v3 field mismatch, or missing access.

Key Design Decisions and Trade-offs

  • "Execute as user accessing the app" is recommended in the README so each person sees only folders they can access, rather than exposing the deployer's Drive.
  • Advanced Drive service over DriveApp iterators allows field selection and large pages, which is much faster.
  • Hard caps protect against Apps Script's 6 minute execution limit and quotas.

Challenges and How They Were Solved

The header comment of Code.gs lists the fixes: switching from BFS to DFS for correct order, and staying on Drive API v3 (files, name, pageSize) after v2 field names produced "Invalid field selection items" errors.

Deep Dive

Validation by allowlist. _prepare_job accepts only known values: resolutions 1280x720 or 1920x1080, FPS 24, 30 or 60, presets fast, medium or slow, AAC bitrates 128k to 256k, and CRF 0 to 51. CRF (Constant Rate Factor) is x264's quality dial, where lower means better quality and bigger files. Output names go through werkzeug's secure_filename plus a regex, so a user cannot write outside outputs/.

Command building. The image mode uses -loop 1 on the image, a scale-and-pad filter to letterbox any aspect ratio, -tune stillimage, and -shortest so the video ends with the audio. The loop mode uses -stream_loop -1 to repeat the video forever, again cut by -shortest. The command is a Python list passed to Popen, never a shell string, so file names with spaces or quotes cannot inject commands. A "sample" option uses FFmpeg's lavfi test sources (color, testsrc2, sine) to render a 12 second test clip without any input files.

Progress parsing. -progress pipe:1 makes FFmpeg print key=value lines to stdout.

key, value = line.split("=", maxsplit=1)
if key == "out_time_ms":
    current_seconds = max(float(value) / 1_000_000.0, 0.0)
    progress_percent = 0.0
    if total_duration and total_duration > 0:
        progress_percent = min(
            (current_seconds / total_duration) * 100.0, 99.0)
    with self._lock:
        self._state["current_time"] = (
            format_seconds_for_ui(current_seconds))
        self._state["progress_percent"] = progress_percent
elif key == "progress" and value == "end":
    with self._lock:
        self._state["progress_percent"] = 100.0

Despite its name, out_time_ms is in microseconds, hence the division by a million. Progress is capped at 99% until FFmpeg says progress=end. The total duration comes from ffprobe -show_entries format=duration on the audio file.

Log streaming. Logs live in a list; the browser polls /api/status?cursor=N and receives only lines after N plus the new cursor. This is a cheap way to stream without WebSockets.

Cancellation. cancel sends terminate() (SIGTERM) and starts a helper thread that calls kill() if the process has not exited after 3 seconds.

Key Design Decisions and Trade-offs

One render at a time keeps the state model simple. Polling over WebSockets avoids extra dependencies. Flask's threaded dev server is fine for a single local user.

Challenges and How They Were Solved

Reading stdout and stderr on separate threads avoids a classic deadlock where FFmpeg blocks because one pipe's buffer is full while the parent waits on the other. detect_ffmpeg also checks /opt/homebrew/bin/ffmpeg, since apps launched outside a shell on Apple silicon Macs often lack Homebrew on PATH.

Security and Performance Notes

The server binds to 127.0.0.1 by default (overridable with FFMPEG_WEB_GUI_HOST). Uploaded inputs are deleted after each job. libx264 with -preset controls the speed versus compression trade-off.

At a Glance

ResumeAI is an ATS resume analyzer built during a GDG On Campus workshop. ATS (applicant tracking system) software is what companies use to filter resumes before a human reads them. How It Works (Simple Version)

A careful reader sits with your resume on the left and a job ad on the right. They tick off every skill the ad asks for that your resume mentions, note the ones that are missing, check whether your layout would confuse a scanning machine, and grade you in five categories. The app asks Gemini to be that reader and to fill in a fixed form, so the answer is always in the same shape and easy to chart.

Architecture

UploadZone -> pdfParser.js (pdf.js, rebuild lines)
App.jsx -> geminiService.analyzeResume
   direct mode: fetch generativelanguage API (dev)
   cloud mode: POST Cloud Function analyzeResume
       verifyIdToken -> rateLimits/{uid} -> Gemini
   <- JSON matching analysisResponseSchema.json
ScoreDashboard, KeywordHeatmap, SectionCard
historyService.js -> Firestore (userId, createdAt)

Deep Dive

Rebuilding lines from a PDF. pdf.js returns text fragments with coordinates, not lines. pdfParser.js groups fragments by rounded Y position and sorts them.

for (const item of content.items) {
  const y = Math.round(item.transform[5] / 2) * 2;
  if (!lines[y]) lines[y] = [];
  lines[y].push({ text: item.str, x: item.transform[4] });
}

const sortedYs = Object.keys(lines)
  .map(Number)
  .sort((a, b) => b - a);

transform[5] is the Y coordinate and transform[4] the X. Rounding to 2-point buckets merges fragments on the same visual line; PDF Y grows upward, hence the descending sort. Under 30 extracted characters means the PDF is probably a scanned image.

Structured output. atsPrompt.js defines the rubric (keywords 30%, formatting 20%, experience 20%, completeness 15%, readability 15%) and caps list lengths to avoid truncation. geminiService.js also sends responseMimeType: "application/json" with a responseSchema, Gemini's structured output feature, and falls back to the default model if a configured model is unavailable.

Cloud Function. functions/analyzeResume.js keeps the Gemini key in Secret Manager via defineSecret, verifies the Firebase ID token with admin.auth().verifyIdToken, and enforces 20 requests per user per hour with a Firestore document holding windowStart and count.

Key Design Decisions and Trade-offs

Two modes let workshop attendees start with a direct API call and graduate to a secure proxy. The direct mode puts VITE_GEMINI_API_KEY into the browser bundle, which is acceptable only for local development.

Challenges and How They Were Solved

Long JSON answers were being cut off, which led to the list caps in the prompt, a configurable maxOutputTokens (default 8,192), and the response schema.

Security and Performance Notes

firestore.rules and storage.rules are still the Firebase "test mode" defaults that allow anyone to read and write everything until 19 April 2026, after which all client access is denied. Per-user rules such as request.auth.uid == resource.data.userId are needed for real use. The rate-limit read-then-write is not in a transaction, so concurrent requests can slip past the limit.

cp .env.example .env.local  # VITE_GEMINI_API_KEY, ...
npm run dev
npm run build && firebase deploy

5 Text-to-Speech Projects

This chapter covers the projects that turn written text into spoken audio. They range from a set of quick experiments (Gradio, Tkinter and Next.js front ends wrapped around the Kokoro model) to SetupTTS, a shipped desktop app with installers, a CI pipeline and more than 700 automated tests, built to finish twelve-hour audiobooks without losing a sentence. A short primer on how neural speech synthesis works comes first, because every project in the chapter builds on the same ideas: text normalization, phonemization with espeak-ng, an acoustic model run through ONNX Runtime, and careful handling of chunks of audio.

Primer: How Neural Text-to-Speech Works

The pipeline in five stages

A modern text-to-speech (TTS) system is a chain of transformations. Each stage turns one representation into a slightly more "sound-like" one.

 raw text
    |  1. normalization  ("Dr. 5 km" -> "Doctor five kilometres")
    v
 clean text
    |  2. phonemization  (espeak-ng / misaki: letters -> IPA)
    v
 phonemes  "h@l'oU w'3:ld"
    |  3. tokenization   (phoneme -> integer id via a lookup map)
    v
 int64 ids [0, 50, 83, 54, ...]
    |  4. acoustic model (VITS / StyleTTS2 in ONNX Runtime)
    v
 float32 waveform, 22 050 or 24 000 samples per second
    |  5. encoding       (PCM -> WAV, MP3 via LAME, AAC via FFmpeg)
    v
 audio file
  1. Normalization rewrites text into something speakable. Curly quotes become straight quotes, soft hyphens disappear, bullet characters are dropped, and numbers are expanded.
  2. Phonemization converts spelling into pronunciation. English spelling is irregular ("though", "through", "tough"), so a model that reads letters directly has to learn pronunciation rules from scratch. Instead, a grapheme-to-phoneme (G2P) tool produces symbols from the International Phonetic Alphabet (IPA), a notation where each symbol is one sound. espeak-ng is an open source speech synthesizer whose rule tables and dictionaries cover over 100 languages; Piper and Kokoro both use it (Kokoro through its misaki G2P library, which falls back to espeak-ng for words it does not know).
  3. Tokenization maps each phoneme symbol to an integer using a fixed table that was frozen when the model was trained. Piper ships this table in the voice's .onnx.json file as phoneme_id_map. Kokoro's config.json (present in the kokoro_CPU Only or AMD/model folder) has a vocab with n_token: 178.
  4. The acoustic model is a neural network that takes the ids and outputs audio samples. Piper voices are VITS models: an encoder reads phonemes, a duration predictor decides how long each phoneme lasts, and a decoder generates the waveform directly. Kokoro (82 million parameters) is based on StyleTTS 2: a phoneme encoder, a prosody predictor conditioned on a style vector (a list of numbers that captures a speaker's timbre and delivery), and an ISTFTNet vocoder. A vocoder turns an intermediate representation into a waveform; ISTFTNet predicts short spectra and runs an inverse short-time Fourier transform to produce samples cheaply. The Kokoro config in the workspace confirms this: an istftnet block with gen_istft_n_fft: 20, a plbert block (a small BERT that reads phonemes for context), and style_dim: 128.
  5. Encoding packs the floating-point samples into a file. A WAV file stores raw 16-bit integers; MP3 compresses them with a psychoacoustic model.

Why ONNX Runtime shows up everywhere

ONNX (Open Neural Network Exchange) is a file format that stores a trained network as a graph of standard operators plus its weights. ONNX Runtime is Microsoft's engine that executes that graph. It is the reason a model trained in PyTorch can run in a 30 MB desktop app with no PyTorch installed. Its key concept is the execution provider: a backend that runs operators on specific hardware. CPUExecutionProvider is always present; CoreMLExecutionProvider targets Apple's Neural Engine and GPU, CUDAExecutionProvider targets NVIDIA cards, and DmlExecutionProvider (DirectML) targets any DirectX 12 GPU on Windows. You pass an ordered list of providers when you create an InferenceSession, and ONNX Runtime assigns each operator to the first provider that supports it. That list, and checking what was actually used, is a recurring theme in this chapter.

Speed, rate and length scale

Both model families expose speed as a scaling factor on predicted phoneme durations. In Piper this is length_scale (bigger means slower); Kokoro takes a speed input (bigger means faster). SetupTTS converts a "+24%" rate into length_scale = default / 1.24, and LocalTTSVideoStudio passes --length_scale 1/speed to the Piper command line.

Why everything is chunked

Every project splits long text into pieces before synthesis. Neural models have a maximum input length (Kokoro's BERT has 512 positions), memory grows with input length, and the online Microsoft service limits each request to a few thousand bytes. The interesting engineering is in how each project splits, how it stitches the pieces back together, and how it proves nothing was lost.

SetupTTS

At a Glance

SetupTTS is a desktop application for macOS and Windows that converts pasted text or .txt files into MP3 audio. It offers three voice sources in one picker: more than 300 Microsoft neural voices streamed over a websocket, about 170 offline Piper neural voices that run on the CPU (or an NVIDIA GPU on Windows), and the operating system's built-in voices. It is aimed at people producing long-form audio, such as audiobooks from web novels, where a job can run for many hours. The core problem it solves is not "call a speech API" but "finish a 12-hour job over an unreliable connection and refuse to hand over a file that is missing even one sentence."

How It Works (Simple Version)

Think of a book printer who has to photocopy a 900-page manuscript on a copier that sometimes jams silently and spits out half a page.

  1. The printer splits the manuscript into sections that end at a paragraph or sentence break, and writes on a tracking sheet exactly which pages each section covers.
  2. Each section is sent to the copier. When the copy comes back, the printer checks it against the original: does the last line match? Is the page the right length?
  3. A good copy goes into a numbered folder and its line goes on the tracking sheet. A bad copy is thrown away and the section is tried again, later in smaller pieces if it keeps failing.
  4. If the power goes out, the printer reopens the folder the next day, trusts only the unbroken run of good copies from page one, and carries on from there.
  5. Only when the tracking sheet shows every page covered exactly once, with no gaps and no overlaps, does the printer bind the book.

SetupTTS does the same with text ranges, audio chunk files and a JSON manifest.

The UI thread never does network or model work. Each job runs in a QThread; online jobs create their own asyncio event loop inside the thread because edge-tts is an async library. Deep Dive

Entry point and process modes

main.py is three lines that call app.main.main(). That function does several things before Qt even starts:

  • Sets SSL_CERT_FILE to certifi's bundle, because a PyInstaller bundle cannot find it otherwise.
  • Handles two hidden command-line modes. --selftest <out.json> [--network] (in app/selftest.py) is used by CI to test the packaged app; --gpu-check (in app/gpu_check.py) runs a GPU speed test in a separate process.
  • Acquires a single-instance lock (app/utils/single_instance.py). The first copy holds a QLockFile and listens on a QLocalServer; a second launch sends the word activate over a local socket and exits. The docstring explains why: a real log showed two copies started nine seconds apart, and a second copy could resume a job the first was still writing.
  • On Windows, calls gpu_accel.startup() before anything imports onnxruntime, so the GPU build can be swapped in (covered below).

Online voices: edge-tts over a websocket

app/services/tts_service.py is the only module that imports edge_tts, a community library that speaks the same protocol as the Microsoft Edge browser's Read Aloud feature. The client opens a websocket (a long-lived, two-way TCP connection upgraded from HTTP), sends an SSML document (Speech Synthesis Markup Language, an XML format that names the voice, rate and text), and receives a stream of binary MP3 frames (24 kHz, 48 kbit/s, mono) interleaved with JSON metadata events. The metadata includes SentenceBoundary or WordBoundary events, each with an offset and duration measured in ticks of 100 nanoseconds and the text that was spoken.

The module patches edge-tts in three places:

  • Endpoint failover. On 12 October 2026 the legacy host began answering every synthesis request with HTTP 403. The module keeps a tuple SYNTHESIS_ENDPOINTS with api.msedgeservices.com first and the legacy host second; synthesis_refused(host) rotates to the next one under a lock, and ignores late refusals from a host already abandoned so that two failing jobs cannot flip it back and forth.
  • Certificates. build_ssl_context() trusts certifi plus the operating system store (ctx.load_default_certs()). Antivirus "web shields" and corporate proxies re-sign HTTPS with their own root certificate installed in the Windows store, which certifi alone does not trust; this one change fixed "Could not load voices" for those users.
  • Proxies. aiohttp only reads proxy environment variables, while Windows stores the proxy in the registry. system_proxy() reads it via urllib.request.getproxies() and caches the bypass check for five minutes, because on Windows that check performs DNS lookups and it ran once per chunk.

It also replaces edge-tts's HTTP date parser with email.utils.parsedate_to_datetime, because strptime follows the process locale and failed to parse "Mon, 12 Oct 2026" under German or Portuguese locales, which broke clock-skew correction.

Detecting silent truncation

The hardest bug the project solved: when the websocket closes before the service's turn.end message, edge-tts ends the stream quietly and returns the partial audio as if it were complete. A chunk that should hold four minutes of speech might hold three, and nothing raises. _stream_incomplete_reason() in app/workers/tts_worker.py catches this with two independent checks:

_MP3_BYTES_PER_SECOND = 48_000 // 8
_TICKS_PER_SECOND = 10_000_000
_AUDIO_END_TOLERANCE_S = 0.35
_UNSPOKEN_TAIL_LETTERS = 4

audio_s = audio_bytes / _MP3_BYTES_PER_SECOND
speech_end_s = max(off + dur for off, dur, _ in boundaries) \
    / _TICKS_PER_SECOND
if audio_s + _AUDIO_END_TOLERANCE_S < speech_end_s:
    return (f"received {audio_s:.1f} s of audio but the "
            f"speech runs to {speech_end_s:.1f} s")

source = _speakable(text)          # letters+digits, casefolded
position = 0
for _, _, boundary_text in boundaries:
    spoken = _speakable(boundary_text)
    idx = source.find(spoken, position)
    ...
    position = idx + len(spoken)
unspoken = len(source) - position
if unspoken > _UNSPOKEN_TAIL_LETTERS:
    return f"the audio stopped with about {unspoken} letters unspoken"

Because the stream is constant bit rate (CBR: every second of audio uses the same number of bytes), the byte count converts exactly to seconds: 48 000 bits per second is 6000 bytes per second. The first check catches a cut inside a sentence: the audio stops before the last announced sentence ends. The second check catches a cut between sentences: the announced sentences, matched in order against the source text (letters and digits only, so punctuation and case differences do not matter), stop short of the end. If the service rewrote part of a sentence (numbers, symbols), the matcher anchors on the last 12 letters instead. The comments record the validation: complete streams from 36 voices in 9 languages produced zero false alarms, and every possible cut point of real streams was detected. A detected truncation raises _AttemptFailure("timeout_after_audio"), which the retry logic treats exactly like a stall.

Chunk planning and adaptive recovery

The worker cuts text with _take_chunk_at(), which prefers paragraph breaks, then sentence boundaries (a regex that also understands CJK punctuation such as ，、；：), then word gaps, and only hard-splits as a last resort. Limits depend on job size: 10 500 characters and 3 750 payload bytes for short jobs, shrinking to 9 200 and 3 600 for jobs over 90 000 characters. The payload is measured by _edge_payload_size(), which XML-escapes the text the same way edge-tts does, because & becomes &amp; and inflates the request. Complex scripts get tighter limits from _COMPLEX_SCRIPT_LIMITS, and multilingual voices get about 15 % less on long jobs.

The first chunk is a small "probe" (1 200 characters), followed by "ramp" chunks of 3 200, so the user hears progress quickly and a broken voice fails fast. Per-chunk timeouts scale with the expected audio length (measured at 15.8 source characters per audio second, with a worst-case streaming speed of 0.45x realtime). After a slow chunk the size shrinks by a factor of 0.82; after healthy chunks it grows by 1.18.

Failures follow a ladder. Up to five attempts per chunk with exponential backoff (base 2 s), each with a fresh edge_tts.Communicate object so no half-dead socket is reused. If a chunk keeps failing, _subdivide_range_for_recovery() splits its [start, end) range into smaller sub-ranges (down to 180 characters, at most three levels deep) whose union must equal the parent range exactly. Before counting a failure, _wait_out_outage() probes the service; if it is unreachable, the job shows "Waiting for internet connection" and polls at 3, 5, 10, 15, then every 30 seconds for up to 30 minutes, without spending retries.

The chunk store: a crash-safe manifest

app/workers/chunk_store.py is 1 135 lines devoted to making progress durable. Each job gets a staging folder containing source.txt (the cleaned text), manifest.json (schema version 2) and one chunk_NNNNNN.mp3 per finished section. Each ChunkRecord stores index, start_char, end_char, a 16-hex-digit SHA-256 prefix of the chunk text, the file name, audio_bytes, retries, and any recovery sub_ranges.

Every write goes through this helper:

def _atomic_write_bytes(path: Path, payload: bytes) -> None:
    tmp = path.with_name(
        f"{path.name}.{uuid.uuid4().hex[:8]}.tmp")
    try:
        with open(tmp, "wb") as fh:
            fh.write(payload)
            fh.flush()
            os.fsync(fh.fileno())
        _replace_with_retry(tmp, path)
    finally:
        try:
            tmp.unlink(missing_ok=True)
        except Exception:
            pass

This is the classic write-then-rename pattern: the new content goes to a temporary file, fsync forces it from the OS cache onto the disk, and os.replace swaps it in atomically, so readers see either the old file or the new one, never half of each. The docstring explains two subtleties. The temp name is unique per call because the UI thread (listing resume candidates) and a worker could both rewrite a manifest, and a shared .tmp name let one rename the other's half-written file. The fsync matters because a power cut could otherwise leave a chunk with the right size but zeroed contents, which a size-based check would accept. replace_with_retry() in app/utils/file_ops.py retries the rename up to five times on Windows, where antivirus scanners and search indexers briefly lock new files.

On resume, only the unbroken prefix is trusted:

def _trusted_cursor_from_records(records) -> int:
    cursor = 0
    expected_index = 0
    for record in sorted(records, key=lambda c: c.index):
        if record.index != expected_index:
            break
        if record.start_char != cursor:
            break
        if record.end_char <= record.start_char:
            break
        cursor = record.end_char
        expected_index += 1
    return cursor

The function walks records in index order and stops at the first gap, out-of-order index, or empty range. Everything after that point is regenerated. Combined with hash checks of each record's text against source.txt, a damaged manifest can never cause audio to be stitched in the wrong place.

finalize() then fails closed. coverage_report() must show no gaps, no overlaps, no missing or invalid files, no hash mismatches, and covered_chars == total_chars. The chunks are concatenated into book.mp3.part (MP3 frames are self-contained, so byte concatenation produces a valid file), the written size must equal the sum of recorded sizes, and an optional verify callback checks that the audio length is plausible for the text. Only then is the .part file renamed over the destination. If verification fails, the existing file is untouched and the suspect audio is kept as name (incomplete).mp3. Staging folders are kept for 60 days so the Resume button keeps working.

Offline voices: Piper on ONNX Runtime

app/services/piper_tts.py (837 lines) wraps the piper-tts package. Voice keys look like en_US-lessac-medium (language, speaker, quality) and are exposed in the picker as piper:en_US-lessac-medium. One voice is bundled; the rest come from the rhasspy/piper-voices catalog on Hugging Face. download_voice() streams the config and model in 256 KB blocks to .part files, verifies both size and MD5 against the catalog, and renames the model last so the rename is the commit point. Chinese, Japanese, Hebrew and Thai voices are hidden because their phonemizers need packages that are not bundled.

_open_voice() builds the ONNX Runtime session itself rather than letting PiperVoice.load build a default one and then replacing it (which loaded the model twice). It sets intra_op_num_threads, and disables thread spinning (session.intra_op.allow_spinning = 0), because idle worker threads otherwise busy-wait, costing about 30 % more CPU for no speed gain.

PiperSynthesizer.synthesize() is where phonemization and inference meet. It holds a global _PHONEMIZE_LOCK while calling voice.phonemize(text), because espeak-ng keeps global C state and is not thread-safe; inference itself runs unlocked. Each sentence's phoneme list is then shaped by two splitters:

_CLAUSE_SPLIT_PHONEMES = 60
_MIN_CLAUSE_PHONEMES = 12
_CLAUSE_MARKS = frozenset(",;:")

def _split_clauses(phonemes, limit=_CLAUSE_SPLIT_PHONEMES):
    if len(phonemes) <= limit:
        return [phonemes]
    pieces, start = [], 0
    for i, ph in enumerate(phonemes):
        end = i + 1
        if (ph in _CLAUSE_MARKS
                and end - start >= _MIN_CLAUSE_PHONEMES
                and len(phonemes) - end >= _MIN_CLAUSE_PHONEMES):
            pieces.append(phonemes[start:end])
            start = end
            while start < len(phonemes) and phonemes[start] == " ":
                start += 1
    pieces.append(phonemes[start:])
    return [p for p in pieces if p]

The comment above it records the evidence: the Ryan (high) voice garbled one long sentence 8 times in 8 and another 6 in 8, but split at commas both came out right 8 in 8, and on 120 other sentences the split changed nothing measurable when checked with speech recognition. A second splitter, _cap_phonemes(), hard-limits any run to 250 phonemes at word gaps, because VITS memory grows steeply with input length and ONNX Runtime keeps its peak arena: one long unpunctuated table pushed the app past 3 GB.

Each piece is rendered by voice.phonemes_to_ids() then voice.phoneme_ids_to_audio(), peak-normalized to 16-bit PCM, and joined with silence: 120 ms after a sentence, 70 ms after a clause, none after a memory-only cut, because Piper trims each output and pieces would otherwise run together.

Version 1.8.1 added _known_phonemes(). espeak-ng marks syllabic consonants (the "n" in "button") with the combining character U+0329, which some voices have no id for. Piper silently skipped it but logged a warning each time, 290 in one book. SetupTTS now drops unknown phonemes itself and logs each once per voice; the release notes record that model input was byte-identical across 150 000 characters.

Concurrency is bounded at several levels. _plan_parallel_runs() returns two runs per voice with the cores split between them on machines with 4+ cores and 8+ GB of RAM (measured 133 to 171 characters per second for Ryan high on an M-series Mac), and one run otherwise. Each loaded voice carries a BoundedSemaphore(_PARALLEL_RUNS) shared across all jobs and previews, and only one voice stays cached (_MAX_LOADED = 1) because each holds about 400 MB once run.

On Windows, espeak-ng opens files with ANSI APIs, so a data folder under a profile like C:\Users\José cannot be read. _espeak_data_dir() falls back to the 8.3 short path via GetShortPathNameW, or copies the data once to an ASCII-named folder under ProgramData.

Built-in voices and MP3 encoding

app/services/system_tts.py lists and drives OS voices. On Windows a long-lived PowerShell helper drives SAPI (including OneCore voices such as David and Zira), so a misbehaving third-party voice can crash only the helper. On macOS it calls say. Both write WAV, which is read back and resampled to 22 050 Hz.

app/services/local_tts.py defines the LocalSynthesizer protocol (synthesize, cancel, close) and Mp3Writer, which streams PCM into lameenc (Python bindings for the LAME encoder) at 64 kbit/s mono into name.mp3.part, fsyncs it, then renames. If the destination is open in a media player, it saves under the next free name instead of discarding the work. LocalTTSWorker cuts text into 1 200-character chunks, retries each, and reports characters per second and an ETA.

NVIDIA GPU acceleration (Windows, beta)

app/services/gpu_accel.py (761 lines) adds GPU support without bloating the installer. The CUDA build of ONNX Runtime plus NVIDIA's CUDA 13 and cuDNN 9 libraries total about 1.3 GB, so they are an optional download. Each wheel in WHEELS is pinned by URL, size and SHA-256, and downloads are resumable. Requirements are checked against nvidia-smi output: driver R580 or newer and compute capability 7.5 or higher (CUDA 13 dropped Maxwell, Pascal and Volta).

The clever part is how the GPU build replaces the bundled CPU build at runtime. activate() inserts a custom import finder at the front of sys.meta_path:

class _RedirectFinder(importlib.abc.MetaPathFinder):
    def __init__(self, package, directory):
        self.package = package
        self.directory = directory

    def find_spec(self, fullname, path=None, target=None):
        if fullname == self.package:
            return importlib.machinery.PathFinder.find_spec(
                fullname, [str(self.directory)])
        if fullname.startswith(self.package + "."):
            parent = sys.modules.get(fullname.rpartition(".")[0])
            search = getattr(parent, "__path__", None)
            if search is None:
                return None
            return importlib.machinery.PathFinder.find_spec(
                fullname, list(search))
        return None

Python asks each finder on sys.meta_path in order where a module lives. This one answers only for onnxruntime and its submodules, pointing them at the downloaded folder, so import onnxruntime anywhere in the app loads the GPU build. The NVIDIA DLL folders are added with os.add_dll_directory and also prepended to PATH, because cuDNN loads its engine libraries with plain LoadLibrary, which ignores the former.

decide(mode, installed, check) chooses the device. "Processor" never uses the card; "Graphics card" always does when installed; "Automatic" uses the card only if a speed check found it at least 1.25x faster. That check runs SetupTTS --gpu-check in a separate process so a driver crash cannot take down the app, and times piper_tts.benchmark() (best characters per second over two runs of a fixed narrative passage) on both devices.

Two defensive details in _open_voice(): ONNX Runtime quietly drops a provider that fails to start, so the code checks session.get_providers()[0] and raises GpuUnavailable if CUDA is not first; and it calls session.disable_fallback(), because otherwise a CUDA failure inside run() makes ONNX Runtime silently rebuild the session on the CPU and the voice would still be reported as "on the card". If the card fails mid-job, PiperSynthesizer retries that piece on the CPU, and only if the CPU succeeds does it blame the card, mark it failed, and switch the rest of the job to the processor.

Power management

app/utils/power.py keeps long jobs alive. On macOS it runs caffeinate -i -w <pid>, reference-counted across jobs; -w makes caffeinate exit when SetupTTS does, so a crash never leaves the Mac unable to sleep. It also calls NSProcessInfo beginActivityWithOptions: through ctypes and the Objective-C runtime, because macOS App Nap lowered a hidden window's priority within a minute and made offline jobs 3 to 4 times slower (the NSAppSleepDisabled Info.plist key no longer works on macOS 26). On Windows it calls SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED) per worker thread and opts the process out of EcoQoS power throttling with SetProcessInformation. Every failure is logged and ignored: a job must never fail because the computer could not be kept awake.

Text cleanup and language checks

app/services/tts_quality.py (1 102 lines) normalizes text before any engine sees it. It strips zero-width characters but deliberately keeps ZWNJ and ZWJ (U+200C/D), which change how Persian and Indic words are shaped. It removes soft hyphens so "inter-national" reads as one word, maps curly quotes and full-width brackets to ASCII, collapses runs of decorative symbols, and keeps meaningful symbols such as degree and trademark signs. It also classifies the script of the text across 24 Unicode ranges so the app can warn when, say, Devanagari text is sent to an English voice; a 1.6.2 fix stopped reading one to three accented Latin letters as Cyrillic.

History, packaging and CI

Finished jobs go into a SQLite table jobs (id, text_preview, voice, rate, output_path, created_at, duration_secs, status, error_message) with an index on created_at DESC, managed by app/services/history_service.py with versioned migrations.

Packaging uses PyInstaller with two spec files. setuptts.spec builds a macOS .app or a Windows onedir folder (an executable plus an _internal folder of libraries). It reads the version from app/__init__.py so nothing else needs editing, writes a Windows VERSIONINFO resource so Explorer shows the version, and uses collect_all for aiohttp and its C-extension dependencies (multidict, yarl, frozenlist, aiosignal), which PyInstaller's static analysis sometimes misses. setuptts_portable.spec builds a onefile EXE for the portable zip; its docstring explains that users ran the onedir EXE from inside a zip without extracting _internal, causing "Failed to load Python DLL" errors. An early commit records the opposite trade-off for the installer: onefile was replaced by onedir there to fix slow Windows startup, since onefile unpacks itself to %TEMP% on every launch.

installers/windows.iss is an Inno Setup script: per-user install (PrivilegesRequired=lowest), LZMA2 compression, x64 only, and MinVersion=10.0.17763 because Qt 6.8+ needs Windows 10 1809. build_macos.sh reads the version, runs scripts/fetch_bundled_voice.py, builds, verifies assets, and zips with ditto -c -k --keepParent because plain zip can break the symlinks inside an app bundle.

.github/workflows/build.yml runs the test suite on both operating systems, checks that the git tag matches APP_VERSION and that release notes exist, verifies that the declared minimum macOS covers every bundled binary, and then self-tests the packaged app in every form it ships: the bundle, the app inside the DMG, the app extracted from the zip, the onedir build, the app installed silently by the real installer, and the portable EXE. The Windows job also downloads the GPU pack and confirms that with "Graphics card" chosen on a runner with no card, offline synthesis still succeeds on the processor.

Tests and benchmarks

The tests/ folder has 21 files and 458 test functions (749 test cases once parametrized), run headless with QT_QPA_PLATFORM=offscreen. Names show the focus: test_long_form_scale.py (12-hour-scale simulations), test_long_session_stability.py, test_chunk_store.py, test_reliability_regressions.py, test_piper_phonemes.py, and test_network_setup.py, which checks that the private edge-tts names the app patches (_SSL_CTX, WSS_URL) still exist in the pinned version.

scripts/stress_voices.py runs hostile text through every voice source, and scripts/local_benchmark.py times a real 715 000-character book with the worker's own chunking at the +24 % rate real jobs use, appending results to benchmark_results.jsonl. The one recorded run (app 1.7.4, Apple M5, Ryan high, CPU) shows 5 994 characters in 50 seconds: 120 characters per second, 5.5x realtime. The 1.8.1 notes report about 209 characters per second for the same voice after the parallel-run optimization.

Key Design Decisions and Trade-offs

  • Fail closed rather than best effort. The app would rather stop with a resumable job than produce an MP3 with a silent hole. This costs complexity (a 1 100-line chunk store) but matches the user's real problem: nobody notices a missing paragraph until hour nine of listening.
  • Character ranges, not chunk counts, as the unit of truth. Recording [start, end) ranges lets recovery split chunks arbitrarily and still prove exact coverage, and lets resume validate against the source text.
  • edge-tts without an official agreement. It gives 300+ high-quality voices for free, but the README states plainly that availability can change, and the 403 incident proved it. The two-endpoint failover and the offline Piper path both hedge against that risk.
  • Piper over Kokoro for offline voices. Piper has a catalog of about 170 voices in about 50 languages with per-file checksums and runs fast on CPU. Kokoro sounds richer but covers fewer languages and needs more compute.
  • Patching library internals. Replacing edge_tts.communicate._SSL_CTX and WSS_URL is fragile, so versions are pinned exactly in requirements.txt and a test fails if the names disappear.
  • GPU as an optional, measured download. Shipping CUDA in every installer would add over a gigabyte for a minority of users, and a weak card can lose to a strong CPU, so "Automatic" only enables the card after measuring it.

Security and Performance Notes

  • Every downloaded artifact is verified: Piper voices by size and MD5 from the catalog, GPU wheels by SHA-256 pinned in source.
  • The SSL context adds the OS store but never disables verification, so it trusts nothing the machine does not already trust.
  • The apps are not code-signed; the README tells users how to get past Gatekeeper and SmartScreen.
  • Performance levers that the code measures rather than guesses: thread spinning off (about 30 % less CPU), two parallel runs per voice (about 30 % faster), cached proxy bypass checks (avoids per-chunk DNS on Windows), payload sizes computed once per chunk rather than per stream event.

Deep Dive

kokoro_tts: talking to the ONNX graph directly

This is the most substantial original code in the folder. main.py starts a Tkinter AppRoot and, on any startup exception, shows the full traceback in a dialog. A comment notes that on macOS the error box "flashes then disappears" if the process exits immediately, so it runs a tiny Tk main loop just for the dialog.

app/tts/engine.py wraps an ONNX Runtime session without assuming input names, because different Kokoro exports name their tensors differently. KokoroEngine searches candidate lists (tokens, input_ids, ids; style, speaker_embedding; speed, rate; audio, wav, output) first exactly, then case-insensitively, and raises a clear error listing what it found if anything is missing. pick_default_providers() prefers CoreML, then CUDA, then DirectML, always ending with CPU. Output is sanitized with np.nan_to_num and clipped to the range -1 to 1.

The most instructive piece is how a voice style is chosen. In voices-v1.0.bin, each Kokoro voice is not one vector but a stack of 510 vectors of 256 numbers, one per possible input length; the model was trained so that the style for a given utterance is the row matching its token count. app/tts/synth.py reproduces that indexing:

def _style_for_tokens(style_raw, tokens):
    style = np.asarray(style_raw, dtype=np.float32)
    t = np.asarray(tokens).reshape(-1)
    token_len = int(t.shape[0])
    if token_len >= 2 and int(t[0]) == 0 and int(t[-1]) == 0:
        token_len -= 2                 # ignore BOS/EOS padding
    if style.ndim == 3 and style.shape[1] == 1:
        style = style[:, 0, :]         # (510,1,256) -> (510,256)
    if style.shape == (STYLE_DIM,):
        return style.reshape(1, STYLE_DIM)
    if style.ndim == 2 and style.shape[1] == STYLE_DIM:
        idx = min(token_len, style.shape[0] - 1)
        return style[idx : idx + 1, :]
    ...

The 256 numbers are two 128-dimensional halves (the config's style_dim: 128): one conditions the decoder's timbre, the other the prosody predictor.

Tokenization is the weak point, and the code is honest about it. The primary tokenizer uses ttstokenizer.IPATokenizer (which needs NLTK's part-of-speech tagger, downloaded on first use) and frames the ids with 0 at each end. Nothing in the code maps those ids onto Kokoro's own 178-symbol vocabulary, so quality depends on whether the two tables happen to agree. The fallback ByteFallbackTokenizer feeds raw UTF-8 bytes as ids, and its docstring says it is "NOT ideal quality" and exists only to avoid a crash. This is a good lesson: the official kokoro and kokoro-onnx packages exist largely to get stage 2 and 3 of the pipeline right.

Stitching is handled carefully. Chunks are packed to 240 characters at sentence boundaries; each chunk is synthesized with the last 18 characters of the previous chunk prepended so the model has context for intonation, and then 120 ms is trimmed from the head of its audio to remove the repeated words. Leading silence below an amplitude of 0.008 is trimmed, and the non-streaming path joins pieces with an equal-power crossfade:

x = np.linspace(0.0, 1.0, n, dtype=np.float32)
fade_out = np.cos(x * (np.pi / 2.0)).astype(np.float32)
fade_in = np.sin(x * (np.pi / 2.0)).astype(np.float32)
head = a[:-n]
mid = a[-n:] * fade_out + b[:n] * fade_in
tail = b[n:]
return np.concatenate([head, mid, tail], axis=0)

Because cos squared plus sin squared equals one, the combined power stays constant through the 50 ms overlap, avoiding the volume dip a linear crossfade produces.

app/services/stream_session.py and wav_stream_writer.py add "save while generating": chunks go to an optional sounddevice realtime player and to a background thread writing a 16-bit PCM WAV through a bounded queue (256 chunks) with a configurable backpressure policy (what to do when the producer outruns the consumer): drop_oldest, drop_newest or block. Dropping is a questionable default for a file writer, since it would lose audio, and it suggests the code was designed with realtime playback in mind first.

KOKORO_GUI: packaging

KokoroTTS.spec is a PyInstaller spec that bundles all four model variants (kokoro-v1.0.onnx full precision, fp16, fp16-gpu, int8) and the voices file into a windowed macOS .app, using collect_all('kokoro_onnx') for the library's data files. Bundling every variant makes the app several hundred megabytes; later projects instead pick one file at runtime. .voicecache.json lists 50-odd validated voice ids (af_alloy to zm_yunyang), the same cache format used by the KokoroTTS v5 app described below.

kokoro_CPU Only or AMD: a portable Windows bundle

This folder is a downloaded community package, not original code: the Gradio UI's header promotes another creator's YouTube channel, and kokoro-tts/ is a vendored copy of nazdridoy's CLI. Run KOKORO.bat launches python\python.exe scripts\gradio_v5\gradio_inf.py with an embedded interpreter, and setting HF_HOME to the current folder keeps all downloaded voices (.cache/huggingface/.../voices/*.pt) inside the bundle, making it relocatable.

scripts/gradio_v5/tts_core.py uses the official kokoro package's KPipeline. The first letter of a voice id selects the language pipeline (a American English, b British, j Japanese, z Mandarin, e Spanish, f French, h Hindi, i Italian, p Portuguese), which decides which G2P misaki uses. smart_chunk_text() packs sentences up to 50 words, counts characters instead of words when CJK text is detected, and splits overlong sentences at commas including ，、；. The five gradio_v* folders show the evolution from single-shot generation to chunked progress.

coqui_tts_gui.py and the Coqui downloader

Despite its file name, GENERAL SOFTWARE/coqui_tts_gui.py is a "Kokoro TTS - Chapter Narrator" for macOS using kokoro_onnx. It loads the model lazily on first use, splits text into chunks to drive a progress bar, generates on a background thread, and previews with afplay. Two issues are visible in the code: it calls Kokoro() with no paths and kokoro.generate(chunk, speaker=...), while the kokoro-onnx API used elsewhere in the workspace is Kokoro(model, voices).create(text, voice=..., speed=..., lang=...); and its voice list includes ids such as am_david and cf_jenny that do not appear in Kokoro's validated list. The neighbouring voice/download_voices.py is genuinely Coqui: it sets TTS_HOME and downloads Tacotron2-DDC, Glow-TTS and XTTS v2, synthesizing a test sentence with each. Together they show the moment the author switched from Coqui (heavy PyTorch models) to Kokoro.

LocalSpeech (third party)

This is a copy of JEMcats-Software's GPL-3.0 Electron app, kept as a reference for packaging Kokoro on Apple Silicon. Its index.js starts an Express server on a random port (server.listen(0)), downloads the kokoro-multi-lang-v1_0 model and a compiled sherpa-onnx binary (a C++ speech toolkit from the k2-fsa project) on first run, and for each request creates a websocket path named by a UUID. Synthesis shells out using a command template in backend/run_cmd.txt:

USERDATAPATH/ApplicationResources/mac_exec \
  --kokoro-model=.../kokoro-multi-lang-v1_0/model.onnx \
  --kokoro-voices=.../voices.bin \
  --kokoro-tokens=.../tokens.txt \
  --kokoro-data-dir=.../espeak-ng-data \
  --kokoro-lexicon=.../lexicon-us-en.txt,.../lexicon-zh.txt \
  --num-threads=providerThreads --sid=voiceId \
  --provider="providerMethod" \
  --output-filename=USERDATAPATH/OutputFiles/outputfiletitle.wav \
  ''text''

The flags make the pipeline explicit: a tokens table (stage 3), espeak-ng data plus English and Chinese lexicons (stage 2), and a speaker id selecting a style. Progress is scraped from lines matching progress= on stdout and forwarded over the websocket. The text is escaped with a single-quote shell escaper before substitution, but the command still runs with spawn(..., { shell: true }) and other values (threads, voice, provider) come from a user config file unescaped, which is a pattern worth avoiding.

qwen/kokoro-next-ui: an HTTP client and an LLM rewriter

This Next.js 14 App Router project calls a Kokoro server rather than running a model. app/lib/kokoro.ts posts an OpenAI-compatible payload (model: "kokoro-v1", input, voice, format, speed) to KOKORO_BASE_URL (default http://127.0.0.1:8880/v1/audio/speech), the API exposed by the Kokoro-FastAPI Docker image; the Docker/out.wav file is a leftover output from that server. app/api/tts/route.ts streams the upstream body with getReader() and estimates progress by comparing bytes received with an expected size (14 characters per second of speech, 48 000 bytes per second for 24 kHz 16-bit WAV, 6 000 for MP3), storing it in an in-memory Map that clients poll with GET /api/tts?jobId=. A comment notes the map only works for a single server instance.

app/api/qwen/route.ts adds a pre-processing step: it sends the text to a local Ollama server (qwen2.5:7b by default, temperature 0.2) with the instruction "Rewrite the text to be clear, natural, and ready for TTS", truncating input to 12 000 characters. api/qwen/model/route.ts lists installed Ollama models and filters those containing "qwen". The folder also holds a downloaded Qwen3-TTS-12Hz-0.6B-CustomVoice checkpoint (a 600 million parameter TTS model controllable by natural-language instructions), but no code in the workspace loads it, and qwen/app/api is empty.

Key Design Decisions and Trade-offs

  • Raw ONNX versus a wrapper library. kokoro_tts shows full control over sessions, providers and style selection, but has to solve phonemization itself and does so imperfectly. kokoro-onnx and KPipeline handle G2P correctly at the cost of control.
  • In-process versus server. The Next.js UI and LocalSpeech keep the model in another process (a Docker server, a sherpa-onnx binary), which isolates crashes and allows any front end, at the cost of an extra service to run.
  • Overlap-and-trim versus clean sentence cuts. The overlap trick gives the model context but trims a fixed 120 ms regardless of how long the repeated words take, which can cut real speech or leave fragments. SetupTTS later chose clean cuts at clause marks plus inserted pauses instead.

Challenges and How They Were Solved

  • Model export differences. Solved in engine.py by searching for tensor names instead of hard-coding them.
  • Silent failures at startup on macOS. Solved with the mini main loop for the error dialog.
  • Large first-run downloads. The portable bundle pins HF_HOME inside its folder so voices download once and travel with it.
  • Unresolved: missing source for KOKORO_GUI, empty README and requirements in kokoro_tts, and the API mismatch in coqui_tts_gui.py show this folder was a scratchpad rather than a maintained project.

Security and Performance Notes

  • .env.local files exist in TTS/ and qwen/; they were not read for this chapter and should stay out of any published copy.
  • LocalSpeech's shell: true command assembly is the main risk; argument arrays (as LocalTTSVideoStudio uses) avoid shell parsing entirely.
  • The int8 and fp16 model variants trade a little quality for smaller size and faster inference; fp16 tends to suit CoreML, and int8 suits CPUs.

KokoroTTS (Hybrid GUI)

At a Glance

KokoroTTS is a single-file Tkinter desktop app that runs the Kokoro ONNX model locally on macOS (CoreML or CPU) and Windows (CUDA, DirectML or CPU). It is for anyone who wants private, offline narration with a simple interface: paste text, pick a validated voice, set speed and loudness, preview, and save a WAV. The repository keeps every version side by side (v1.0 to v5.0), which makes it a readable history of learning how ONNX Runtime providers behave on real hardware.

How It Works (Simple Version)

  1. On launch the app finds kokoro-v1.0.onnx (or the fp16 variant) and voices-v1.0.bin next to the script, optionally downloading them from Hugging Face.
  2. It asks ONNX Runtime which accelerators exist and picks the best one, like a driver choosing the fastest open lane.
  3. It builds a list of candidate voice names and tests each one by saying "Hi". Only voices that actually speak appear in the menu.
  4. When you press Speak, the text is split into sentence groups of up to 480 characters, each group is spoken, and the pieces are joined.
  5. Preview plays through the sound card; Save writes the WAV in one-second blocks so the progress bar moves smoothly.

Provider selection and verification

v5.0/kokoro_tts_gui.py (1 407 lines) maps the Compute menu to a provider list:

def resolve_providers(choice: str) -> list[str]:
    avail = available_providers()
    if choice == "CPU":
        return ["CPUExecutionProvider"]
    if choice == "CoreML":
        return ["CoreMLExecutionProvider", "CPUExecutionProvider"]
    if choice == "CUDA":
        return ["CUDAExecutionProvider", "CPUExecutionProvider"]
    if choice == "DirectML":
        return ["DmlExecutionProvider", "CPUExecutionProvider"]
    # AUTO
    if _is_apple_silicon() and "CoreMLExecutionProvider" in avail:
        return ["CoreMLExecutionProvider", "CPUExecutionProvider"]
    if "CUDAExecutionProvider" in avail:
        return ["CUDAExecutionProvider", "CPUExecutionProvider"]
    if "DmlExecutionProvider" in avail:
        return ["DmlExecutionProvider", "CPUExecutionProvider"]
    return ["CPUExecutionProvider"]

CPU is always appended as a fallback so that operators the accelerator cannot run still execute. Requesting a provider does not guarantee it is used, so _assert_primary_provider() reads the session's actual get_providers() and raises "Requested CUDA but active providers: [...]" if the first entry differs; the UI shows this in a banner. The Compute dropdown also hides options that ort.get_available_providers() does not report, because the CPU, GPU and DirectML ONNX Runtime packages are separate pip packages that cannot be installed together. The README walks users through swapping them (pip uninstall onnxruntime then pip install onnxruntime-directml==1.20.1).

init_kokoro() creates Kokoro(model, voices, providers=...) and runs a warm-up create("Hi", ...). The first inference is slow because ONNX Runtime allocates its memory arena and CoreML compiles the graph for the Neural Engine; paying that cost at startup makes the first real request feel fast.

Voice discovery by probing

validate_voices_async() runs on a daemon thread. It fetches candidate ids from online sources (Kokoro's VOICES.md and the ONNX model card, parsed with regexes), falls back to the cached list in .voicecache.json, then to a hard-coded FALLBACK_VOICES. It then calls k.create("Hi", voice=vid, ...) for every candidate and keeps the ones that do not throw. This is an empirical approach: rather than parsing the binary voices file, it asks the library. Results are cached, and the callback is marshalled back to the Tk thread with app.after(0, finish), since Tkinter widgets must only be touched from the main thread.

Synthesis, loudness and saving

chunk_text() splits with the regex ([.!?]+[\s\n]+) (keeping punctuation with its sentence) and packs sentences up to 480 characters. synthesize_chunked() calls kokoro.create() per chunk and reports progress by characters done, capped at 99 until the end so the bar never claims completion early. Pieces are joined with np.concatenate, with no crossfade or inserted pause.

apply_volume_boost() converts decibels to a linear factor with 10 ** (dB / 20) (so +6 dB roughly doubles amplitude) and clips to the range -1 to 1 in place. save_wav_chunked() writes 48 000 frames at a time through soundfile.SoundFile, which is about two seconds at Kokoro's 24 kHz.

Playback prefers sounddevice (PortAudio bindings) and falls back to winsound on Windows, which can only play files, so the app writes a temporary WAV and retries deleting it because Windows keeps it locked while playing.

The Diagnostics dialog collects the ONNX Runtime and kokoro-onnx versions, available versus active providers, model paths, the CUDA GPU name (from nvidia-smi) and Metal information on macOS (from system_profiler).

Key Design Decisions and Trade-offs

  • One script per version. Easy to download and run, and keeps old versions working, but bug fixes must be repeated and the repo carries 4 900 lines of mostly duplicated code.
  • kokoro-onnx instead of raw ONNX. After the tokenization difficulties in the experiments folder, delegating G2P and style selection to the library made quality reliable.
  • Probe-based validation. Accurate and simple, but it costs one inference per candidate at startup, which is why v5 added the cache.
  • WAV only. No MP3 encoder dependency; files are larger (about 2.9 MB per minute at 24 kHz 16-bit mono).

Challenges and How They Were Solved

  • Silent CPU fallback. Users chose CUDA and got CPU speed without knowing; v2.1 added the primary-provider assertion and banner.
  • Voices in the menu that failed at runtime. Solved with probe validation.
  • NameError: VOICE_CANDIDATES in edge paths. Caused by duplicate legacy worker blocks; v5 removed them.
  • Documentation drift. The READMEs tell users to run kokoro_tts_hybrid_cross.py, but the v5 file is kokoro_tts_gui.py; v1.0's install_deps.bat installs from a requirements.txt that is not in the folder. The git log also contains a stray commit, "Update print statement from 'Hello' to 'Goodbye'".

Security and Performance Notes

  • Fully offline after the model files exist; text never leaves the machine.
  • Auto-download is off by default in v5 (AUTO_DOWNLOAD = False), so the app makes no network calls unless the online voice catalog is reachable.
  • For speed, the README recommends the fp16 model with CoreML on Apple Silicon and AUTO elsewhere.

LocalTTSVideoStudio

At a Glance

LocalTTSVideoStudio is a Flask web app that runs on localhost and turns pasted story text into a narrated MP4 video: text in, cleaned and spoken by a local TTS engine, timed into subtitles, and rendered over a still image or a looping background video with FFmpeg. It targets creators making narrated story videos who want the whole pipeline on their own machine. Its central idea is an engine adapter layer: Piper, Kokoro and Coqui run offline, and edge-tts is available as a clearly labelled online fallback.

How It Works (Simple Version)

Picture a small film studio with four rooms:

  1. The editor's desk cleans the script: removes "Read more at..." scraping junk, fixes quotes, applies a pronunciation dictionary.
  2. The recording booth has several narrators (Piper, Kokoro, Coqui, Edge). A receptionist checks who is in today and lets you pick one.
  3. The captioner listens to how long the narration is and divides that time across the sentences, giving longer sentences more seconds.
  4. The projection room (FFmpeg) puts the narration under a picture or a looping clip, burns in the captions, and exports an MP4.

You watch it all from a web page that polls for progress and shows a live log.

Deep Dive

Engine adapters

services/tts_engines/base_engine.py defines an abstract class BaseTTSEngine with three required methods: diagnose(), list_voices() and synthesize(text, voice, settings, output_path, log_callback, cancel_event). metadata() fills in a uniform status dictionary (installed, usable, executable_found, python_package_found, models_found, voice counts, a status_label of Ready, Partial or Missing, and a fix_suggestion) so the UI can show one consistent System Check panel regardless of engine. This is the adapter pattern: different libraries with different APIs are wrapped behind one interface.

  • PiperEngine runs the piper executable with an argument list and pipes the text on stdin. Speed becomes --length_scale equal to 1 divided by speed, and the optional --noise_scale (randomness in the audio) and --noise_w (randomness in phoneme durations) expose VITS's sampling controls.
  • KokoroEngine supports two runtimes. With the official kokoro package it iterates KPipeline(lang_code)(text, voice, speed) and concatenates segments; with kokoro-onnx it calls Kokoro(model, voices).create(...) directly. _infer_lang_code() derives the language from the voice prefix unless one is configured. The README explains the choice: on newer Python versions kokoro-onnx is the practical path.
  • CoquiEngine scans models/coqui/ recursively for folders with config.json and weights; the workspace has Tacotron2-DDC with a HiFi-GAN v2 vocoder downloaded.
  • EdgeTTSEngine is marked is_local = False and only selectable when allow_online_tts is true.

Volume adjustments go through FFmpegRunner.apply_audio_volume(), writing a _raw file first and filtering it.

Subtitle timing without alignment

The app has no forced aligner (a model that finds exactly when each word is spoken), so services/subtitle_service.py estimates timing. build_segments() splits text into sentences or chunks, gives each a weight of words * 1.7 + chars / 18 (a blend of word count and length), assigns each segment a share of the measured audio duration proportional to its weight with a minimum of 0.24 s per word, then rescales so the last segment ends exactly at the audio's end. Word-level timings for highlight and karaoke modes divide each segment by word length:

def _word_timings(self, words, start, duration):
    if not words:
        return []
    weights = [max(1.0, len(word.strip(".,!?;:'\"")))
               for word in words]
    total = max(sum(weights), 1.0)
    current = start
    timings = []
    for index, word in enumerate(words):
        word_duration = duration * (weights[index] / total)
        end = current + word_duration
        timings.append({"text": word,
                        "start": round(current, 3),
                        "end": round(end, 3)})
        current = end
    if timings:
        timings[-1]["end"] = round(start + duration, 3)
    return timings

Forcing the last word to end exactly at the segment end prevents rounding drift from accumulating across a long video. The service writes both SRT (a simple numbered list of time ranges and lines) and ASS (Advanced SubStation Alpha, a richer format with styles, positions, colours in &HAABBGGRR order, and override tags such as \k for karaoke timing). Settings cover placement, wrapping width, highlight colours and simple animations. shift_segments_for_insertion() pushes subtitle times later when a promotional clip is inserted.

Rendering with FFmpeg

VideoService.build_render_command() produces an argument list, never a shell string. For an image it uses -loop 1 -i image; for a video, -stream_loop -1 (loop forever) with optional -ss and -t trimming. The audio is the second input. The filter chain scales with force_original_aspect_ratio=decrease, pads to the target size with a dark colour, sets fps, and appends a subtitles= or ass= filter when burning is requested and the FFmpeg build has libass. The output uses AAC audio, yuv420p pixel format (needed for wide player compatibility), +faststart (moves the index to the front so playback can begin before download completes) and -shortest (stop when the narration ends, since the background loops forever).

RenderCapabilitiesService probes ffmpeg -encoders and chooses between libx264 (software), h264_nvenc/hevc_nvenc (NVIDIA) and h264_videotoolbox/hevc_videotoolbox (Apple). A smoke-test render verifies that a hardware encoder actually works before recommending it, the same "check what really ran" lesson as the ONNX provider assertions in KokoroTTS.

TimelineService.resolve_insert_seconds() places a promo clip at a number of minutes or a percentage of the main video and refuses positions outside it; separate commands normalize the promo and concatenate the three parts.

Jobs, state and the API

JobManager allows one active job at a time, runs it on a background thread, keeps an in-memory log and progress, registers the FFmpeg Popen so /api/job/<id>/cancel can terminate it, and appends finished jobs to config/history.json. Configuration lives in four JSON files (app defaults, last-used form values, an engine detection snapshot, history). The Flask app exposes about 30 routes, including /api/system/check, /api/tts/engines, /api/generate/audio, /api/generate/subtitles, /api/preview/command (shows the exact FFmpeg command before running it) and /api/generate/video, plus self-test endpoints that render small samples for each engine; their outputs (kokoro_local_render_check.srt, piper_local_render_check.srt, coqui_local_render_check.srt) are in outputs/.

Key Design Decisions and Trade-offs

  • Web UI on localhost instead of a desktop toolkit. HTML and CSS make rich controls (subtitle styling, live logs) easier than Tkinter, at the cost of running a server and opening a browser.
  • Estimated rather than aligned subtitles. No extra model or download, but timing drifts within long segments; aligning with word boundaries (as edge-tts provides) or a forced aligner would be more accurate.
  • Pinned heavy dependencies. Coqui requires torch, torchaudio and torchcodec at matching versions and transformers below 5, so requirements.txt pins them; this makes the install large but reproducible.
  • One job at a time. Simple and safe for FFmpeg's CPU use; the README lists a queue as a future extension.

Challenges and How They Were Solved

  • Matplotlib and fontconfig cache warnings from Coqui were redirected into temp/ (visible as temp/mplconfig and temp/.cache/fontconfig).
  • FFmpeg builds without libass cannot burn subtitles; the render falls back to a sidecar file and adds a warning instead of failing.
  • Engines partly installed (package present but no model) are reported as Partial with a specific fix suggestion rather than crashing the UI.
  • Upstream kokoro on new Python versions was impractical, so the ONNX path was added as an alternative runtime.

Security and Performance Notes

  • All subprocesses use argument arrays, so file names with spaces or quotes cannot inject shell commands.
  • /files/<path> and the open-folder endpoints resolve paths and check them with is_within_allowed_roots() before serving or revealing anything, which blocks ../ traversal to arbitrary files.
  • The server binds to 127.0.0.1 by default, so it is not exposed to the local network.
  • Hardware video encoders (NVENC, VideoToolbox) are much faster than libx264 for long videos, at slightly larger file sizes for the same quality.

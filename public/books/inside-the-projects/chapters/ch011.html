Dual-ISP Network Assessment and Subnet Remediation

At a Glance

A home network had two routers, each on its own internet service provider (ISP), and a network storage box (a NAS) plugged into both. Device lists taken from different computers kept contradicting each other. This project traces the cause to both routers using the same factory-default subnet and gateway address, which made two physically separate networks look identical at the IP layer. It then documents the fix (renumbering the second network) and proves it with live evidence. It is written for network and security engineers and for anyone who wants a repeatable, evidence-first way to troubleshoot "why can't I see that device".

How It Works (Simple Version)

Imagine two apartment buildings on different streets that were both built with the same floor plan, so both have a "Unit 1" for the building manager. A tenant in building A asks for "Unit 1" and gets their manager. A tenant in building B asks for "Unit 1" and gets a different manager. Nobody notices anything wrong, because each tenant gets an answer. Now imagine a storage company that rents a room in both buildings. When someone in building A sends it a letter, the reply may go out of the wrong building's door and never arrive.

That is what happened here:

  1. Both routers shipped with LAN address 192.168.0.1 and subnet 192.168.0.0/24. Nobody changed either one.
  2. Every computer saw "gateway 192.168.0.1", so the IP layer looked fine.
  3. At the hardware layer, the gateway answered with a different MAC address (the burned-in hardware ID of a network card) depending on which router you were plugged into. That was the clue.
  4. The fix moved the second router to 192.168.20.0/24 and gave the NAS's second port a fixed address in that new range with no gateway.
  5. A re-assessment two months later checked, from the first network, that only one device now owns the gateway address, only one DHCP server answers, there are no duplicate addresses, and the new range is not reachable from the first network.

Deep Dive

The original scanners. 01_Scanner_Scripts/Home_Network_Inventory_v1.5.ps1 (about 1,300 lines) and its macOS port Mac_Network_Inventory_v1.1.sh (about 1,470 lines, written for the old Bash 3.2 that ships with macOS) do the same job. They find the private IPv4 subnets the machine is on, do an ICMP ping sweep (ICMP is the protocol behind ping), merge in the ARP cache, test a fixed list of 22 TCP ports, guess a device type, and write HTML, CSV, JSON and PDF reports. ARP (Address Resolution Protocol) is how a computer asks "who has this IP address?" on the local network; the ARP cache is its memory of the answers. Merging the ARP cache matters because some devices drop ping but must still answer ARP to use the network at all.

The Windows ping sweep is deliberately synchronous, and a comment explains why:

# Windows PowerShell 5.1 can throw "Argument types do not match" when
# async Task objects and Generic.List[object] are returned through an
# array subexpression. A synchronous Ping.Send call is more compatible
# ...
foreach ($address in $Addresses) {
    $pinger = New-Object System.Net.NetworkInformation.Ping
    try {
        $reply = $pinger.Send($address, $TimeoutMs)
        $alive = $reply.Status -eq `
            [System.Net.NetworkInformation.IPStatus]::Success
        ...
    }
    finally { $pinger.Dispose() }
}

The port check, by contrast, is concurrent. Get-OpenTcpPorts starts a TcpClient.ConnectAsync for every port at once, then waits on each task with a timeout. That turns 22 sequential timeouts into roughly one. The device guesser Get-LikelyDeviceType is a chain of port rules: 5000/5001/6690 means "Synology NAS (likely)", 445/3389/5985 means "Windows PC", 9100/515/631 means "printer". The project's own write-up notes that this rule misfired: a Mac had TCP 5000 open (most likely the macOS AirPlay Receiver) and was labelled a NAS. The macOS script also counted multicast addresses as devices in its July run, which inflated its totals. Both quirks are documented rather than hidden.

The baseline collector. tools/windows/Get-NetworkBaseline.ps1 is a read-only snapshot of one Windows host's view of the network, built on NetTCPIP cmdlets such as Get-NetIPConfiguration, Get-NetRoute, Get-NetNeighbor (the ARP cache) and Get-NetTCPConnection. For each active interface it records the address, prefix, gateway, the gateway's MAC, DNS servers, the Windows network profile (Public or Private), and adapter error counters. It counts default routes, because two 0.0.0.0/0 routes would mean the host can leave by two paths. It also searches its own neighbor cache for one IP mapped to more than one MAC.

The subnet arithmetic is written out by hand so it can be unit tested:

$bytes = $ip.GetAddressBytes()
[Array]::Reverse($bytes)                 # network to host order
$value = [BitConverter]::ToUInt32($bytes, 0)
$mask = if ($PrefixLength -eq 0) { [uint32]0 } else {
    [uint32](([uint64]4294967295 -shl (32 - $PrefixLength)) `
        -band [uint64]4294967295) }
$net = [BitConverter]::GetBytes([uint32]($value -band $mask))
[Array]::Reverse($net)

A /24 "prefix length" means the first 24 bits name the network and the last 8 name the host. The code builds a mask of 24 one-bits by shifting a 32-bit all-ones value left, then ANDs it with the address to get the network address. Two Pester tests use this directly: one shows the two original LANs reduce to the same network, and one shows the remediated LANs are disjoint.

The script writes two copies. private/baseline.json holds raw values and is git-ignored. public/baseline.json and public/baseline.md go through Protect-Text and ConvertTo-PublicBaseline, which mask MACs to the vendor prefix, replace public IPs with <public-ip>, replace home folder paths with <HOME>, strip the computer and user name, and reduce the list of listening ports to a count.

MAC masking and the U/L bit. Every tool in the repo shares one rule for MAC addresses, shown here from the Python parser:

def is_locally_administered(mac: str) -> bool:
    """True when the U/L bit is set, i.e. a randomized MAC."""
    first = int(re.sub(r"[^0-9A-Fa-f]", "", mac)[:2], 16)
    return bool(first & 0x02)


def mask_mac(mac: str | None) -> str:
    if not mac:
        return ""
    if not MAC_RE.match(mac):
        raise ValueError(f"not a MAC address: {mac!r}")
    if is_locally_administered(mac):
        return "XX:XX:XX:XX:XX:XX (randomized)"
    octets = re.split(r"[:-]", mac.upper())
    return ":".join([*octets[:3], "XX", "XX", "XX"])

A MAC has two halves. The first three bytes, the OUI (Organizationally Unique Identifier), name the manufacturer. The last three identify the individual device. The second-lowest bit of the first byte (the "U/L" bit) is set when the address was made up by software, which is what phones and laptops do for privacy ("randomized MAC"). The finding depends on showing "same IP, two different vendors", so the OUI is kept. The device half is hidden, and a randomized MAC is hidden entirely because it carries no vendor meaning, only a tracking value.

The packet summarizer. tools/windows/Invoke-PacketSummary.ps1 runs a fixed list of tshark display filters against a capture and records only counts and metadata. tshark is the command-line version of Wireshark. The filters include arp.opcode==1 and ==2 (ARP requests and replies), arp.src.proto_ipv4==0.0.0.0 (RFC 5227 probes, where a host checks whether an address is free before using it), arp.duplicate-address-detected, dhcp, ssdp, tcp.analysis.retransmission and broadcast and multicast frames. The core of the analysis is the ARP binding report:

$pairs | Group-Object IP | ForEach-Object {
    $macs = @($_.Group.Mac | Select-Object -Unique)
    [pscustomobject]@{
        IP           = $_.Name
        Frames       = $_.Count
        DistinctMacs = $macs.Count
        MacOui       = ($macs | ForEach-Object {
                           ConvertTo-OuiMac $_ }) -join ', '
        Conflict     = $macs.Count -gt 1
    }
} | Sort-Object { [version]($_.IP) }

It groups every (sender IP, sender MAC) pair from ARP frames by IP and flags any IP claimed by more than one MAC. That is the exact signature of the original fault. Sorting with [version] is a small trick: it makes PowerShell compare IP addresses as four numbers, so .20 sorts before .118, instead of comparing them as text.

The Nmap parser. tools/parsers/nmap_inventory.py uses only the Python standard library. It reads one or more Nmap XML files, keeps hosts whose status is up, merges ARP discovery and service scans by IP into an Asset dataclass, keeps the most accurate OS guess, and drops open|filtered UDP results because they are "ambiguous, not evidence of a service". Before writing any row, require_private() raises an error if the IP is not private. Hosts are labelled from a private assets.json map; anything unmapped becomes UNKNOWN-01, UNKNOWN-02, and so on.

The privacy gate. tools/privacy/Test-PublicArtifacts.ps1 scans every tracked text file, and the text inside .pptx and .docx files, for full MACs, public IPv4 addresses, email addresses, Windows SIDs, home paths, credential-like strings, packet capture files, and terms from a local, git-ignored denylist of real hostnames. Its public-IP test skips private ranges, CGNAT (100.64.0.0/10), the RFC 5737 documentation ranges, a short list of well-known public DNS resolvers, and strings with leading zeros such as version numbers.

The assessment method. docs/methodology.md sets a strict order: scope and authorization, local baseline, passive capture before any active scan (so scan traffic does not pollute the baseline), Nmap ARP sweep, full TCP and top-50 UDP service scans, broadcast discovery (a DHCPDISCOVER that counts DHCP servers, plus SSDP, mDNS and WS-Discovery listeners), and a negative test against the new subnet. The NSE scripts are limited to (default or discovery) and safe and not external and not broadcast; NSE is Nmap's scripting engine, and external would send data to third-party services. Each conclusion in the root-cause document is tagged Observed, Inferred or Not tested.

Key Design Decisions and Trade-offs

  • Renumber rather than bridge or merge. The two ISP networks were meant to stay separate. Giving the second router a new /24 removes the duplicate identity without connecting the domains. The alternative (one router, one subnet, dual-WAN failover) would change the household's ISP design rather than fix a misconfiguration.
  • NAS second port gets no gateway. With two interfaces in one /24, the NAS had two equal routes to the same network and could answer on the wrong port, which is called asymmetric routing. One default route (through the first network) and a gateway-less second port removes the ambiguity.
  • Multiple vantage points as evidence. Instead of trusting one scan, inventories were taken from four machines on two LANs and compared. Different answers from different places were treated as data, not as tool error.
  • ARP over ICMP for discovery. A Windows host on the Public network profile drops ping by default but still answers ARP. ICMP silence is treated as "unknown", not "absent".
  • Publish summaries, never raw data. Raw captures and Nmap XML contain full MACs and banners. The repo only holds derived, sanitized files, and the CI blocks any .pcap, .pcapng, .cap or .etl file.
  • Keep private RFC 1918 addresses. Vendor-default ranges such as 192.168.0.0/24 are shared by millions of networks, and the finding cannot be shown without them, so they stay. Public IPs, SIDs, serials and SSIDs are removed.

Challenges and How They Were Solved

  • The symptom pointed nowhere. Each LAN worked on its own; internet, DHCP and DNS were fine everywhere. The playbook in docs/troubleshooting-playbook.md captures the lesson as step 4, "Who actually owns the gateway address?": compare the gateway's MAC with the router you think you are using. Layer 3 alone cannot see the overlap; Layer 2 can.
  • Proving a negative. A failed probe to the new subnet cannot tell "isolated" apart from "does not exist". docs/validation.md solves this by pairing two checks. The NAS's own SSDP advertisement on the first network listed a URL on its second-port address, which proves that address exists. The failed ICMP and SYN probes then prove it is unreachable. Together they confirm the design.
  • Misleading labels. The port-based device guess called a Mac a NAS. The fix was to document the quirk and rely on OUI and ARP correlation instead of port fingerprints alone.
  • PowerShell 5.1 async quirks. The ping sweep was rewritten to synchronous Ping.Send to avoid an "Argument types do not match" error in Windows PowerShell 5.1.
  • What remains open. Two checks need a host on the second network or shell access to the NAS (router answering on the new gateway, NAS default route). They are listed as Not tested rather than assumed.

Security and Performance Notes

  • The September re-assessment produced four findings beyond the fixed overlap: UPnP Internet Gateway Device enabled on the first router (any LAN program can open inbound port forwards), NAS services such as SSH, SMB, iSCSI and HTTP admin exposed to every LAN host, the NAS advertising its second-network address into the first, and one unidentified device.
  • All tools are read-only. No credentials were tried, no configuration was changed, and no intrusive, brute, DoS or exploit NSE categories were run.
  • CI (.github/workflows/quality.yml) runs PSScriptAnalyzer, Pester, ShellCheck, ruff, pytest, markdownlint, the privacy gate, a "no packet captures tracked" check, and gitleaks. Its header comment says it never contacts any network.
  • Retransmissions seen in the baseline capture (467) were 88% concentrated in one internet download, and the post-scan capture had 4, so the analysis concluded there was no LAN fault. Get-StreamConcentration computes that "share of the worst stream" figure.

Hardening Linux Servers with iptables

At a Glance

This is a group term project for a graduate network security course (CYB623, Spring 2026), built by a three-person team. It shows how a deliberately exposed Ubuntu server can be defended against SSH password guessing, ICMP ping floods and TCP SYN floods using only the kernel's built-in firewall, and how an internal web service can be published on a different port through destination NAT. Attacks are launched from a Kali Linux VM, and the defenses are measured by reading the firewall's own packet counters. It is aimed at students and junior defenders who want a reproducible, scripted firewall lab.

Item Value
Language(s) Bash

How It Works (Simple Version)

Think of the server as a building with a security guard at the door. Without the guard, anyone can try the door handle as many times as they like (password guessing) or crowd the lobby so real visitors cannot get in (floods). The guard follows a short rule book:

  1. SSH door: write down the face of everyone who knocks. If the same face knocks twice within two minutes, turn them away.
  2. Ping and new-connection doors: let people in at a steady pace (one ping per second, three new connections per second) with a small allowance for a sudden burst. Turn away the overflow.
  3. Front desk redirect: visitors who ask for room 80 are quietly walked to room 8080, where the real web server lives.

The lab runs in three steps: set up both VMs, apply the rules, fire the attacks, then run a checker that reads how many visitors each rule turned away.

Deep Dive

netfilter basics. netfilter is the packet-filtering framework inside the Linux kernel; iptables is the command-line tool that writes its rules. Rules live in tables (filter for allow and deny, nat for address rewriting) and inside each table in chains (INPUT for packets addressed to this machine, PREROUTING for packets just arrived, before a routing decision, POSTROUTING for packets about to leave). Rules are checked top to bottom, and the first rule with a terminating target (ACCEPT, DROP, DNAT) wins.

setup-defender.sh installs apache2, openssh-server, iptables-persistent, hping3 and curl with DEBIAN_FRONTEND=noninteractive, so the iptables-persistent installer does not pop up a text menu. It then moves Apache from port 80 to 8080 by editing ports.conf and the default virtual host, but only if Listen 8080 is not already present. setup-attacker.sh installs Hydra, hping3 and nmap and generates a small lab wordlist.

apply-rules.sh is the heart of the project. It has subcommands ssh, icmp, syn, nat, all, status and reset. Each prints the chain before and after the change and a one-line "why". The key engineering idea is idempotence (running it twice gives the same result as running it once):

ipt() { sudo iptables "$@"; }

ensure_input() {
  if ! ipt -C INPUT "$@" 2>/dev/null; then
    ipt -I INPUT "$@"; ok "added: iptables -I INPUT $*"
  else
    warn "skip (exists): INPUT $*"
  fi
}

iptables -C ("check") exits with success only if an identical rule already exists. The helper adds the rule only when the check fails, so re-running the script never stacks duplicate rules. There are four variants: ensure_input inserts at the top (-I), ensure_input_a appends (-A), and ensure_pre and ensure_post append to the NAT chains.

SSH brute-force defense with recent. The recent match keeps a small in-kernel list of source IPs and timestamps, named here SSHBF, visible under /proc/net/xt_recent/SSHBF.

cmd_ssh() {
  ensure_input -p tcp --dport 22 -m conntrack --ctstate NEW \
    -m recent --set --name "$RECENT_LIST"
  ensure_input -p tcp --dport 22 -m conntrack --ctstate NEW \
    -m recent --update --seconds "$SSH_WINDOW" \
    --hitcount "$SSH_HITCOUNT" --name "$RECENT_LIST" -j DROP
}

conntrack --ctstate NEW limits the rule to the first packet of each new connection, so an established, working SSH session is never counted. The first call records the source (--set). The second updates its timestamp and drops the packet if the source has hit 2 new connections within 120 seconds. The order is subtle. Because ensure_input inserts at the top, the second call lands above the first, so the DROP check runs before the recording rule. The troubleshooting guide spells this out: "Line 1 should be the --update ... -j DROP." If the order were reversed, every attempt would be recorded and then checked in the wrong sequence.

Flood defense with limit. The limit match is a token bucket. Picture a bucket that holds 5 tokens (the burst) and refills at 1 token per second (the rate). Each matching packet takes a token. If there is a token, the rule matches and the packet is accepted; if the bucket is empty, the rule does not match and the packet falls through to the next rule, an unconditional DROP. ICMP echo requests are limited to 1/s burst 5. New TCP connections, matched with --syn (the SYN flag opens a TCP handshake), are limited to 3/s burst 5. A SYN flood works by sending many SYNs and never finishing the handshake, filling the server's table of half-open connections (SYN_RECV). Capping the rate of SYNs that reach the TCP stack keeps that table small.

DNAT port forwarding. DNAT (destination NAT) rewrites the destination address or port of a packet as it arrives.

sudo sysctl -w net.ipv4.ip_forward=1 >/dev/null
ensure_pre -p tcp --dport "$PUBLIC_PORT" \
  -j DNAT --to-destination "$DEFENDER_IP:$INTERNAL_PORT"
ensure_post -j MASQUERADE

A request to port 80 is rewritten in PREROUTING to 192.168.56.6:8080, where Apache really listens. MASQUERADE rewrites the source of outgoing packets to the machine's own address. In this lab the forwarding target is the defender itself, so the rewritten packet goes to INPUT rather than FORWARD. Enabling ip_forward is what a real gateway forwarding to a separate internal host would need; here it mainly mirrors that production pattern.

run-attack.sh on Kali fires each attack: hydra -l <user> -P <wordlist> -t 4 -f -V ssh://... (4 parallel tasks, stop at first success, verbose so the rate limit is visible), hping3 --icmp --flood and hping3 -S --flood -p 80, each wrapped in timeout for 10 seconds, and a curl test of the DNAT path.

verify-mitigation.sh generates no traffic. It reads the firewall's own counters and prints PASS or FAIL:

INPUT_RULES=$(sudo iptables -L INPUT -v -n --line-numbers || true)

count_pkts() {
  local table="$1" pattern="$2"
  printf '%s\n' "$table" |
    awk -v p="$pattern" '$0 ~ p { print $2; exit }'
}

ssh_drop_pkts=$(count_pkts "$INPUT_RULES" \
  "dpt:22.*recent: UPDATE.*DROP")

iptables -L -v prints a pkts column for each rule; with --line-numbers it is the second field. The checker finds the right rule with a regular expression and pulls that number. A rule that exists but has a zero counter is a FAIL with a hint to run the attack first, so the script tests that a defense fired, not only that it was typed in. The ICMP check requires more than 100 drops. The SYN check also reads the live half-open table size with ss -ant state syn-recv. The script exits 0 only when every check passes, so it can gate automation.

teardown.sh and apply-rules.sh reset flush every chain in both tables and set default policies back to ACCEPT.

Key Design Decisions and Trade-offs

  • recent over fail2ban. fail2ban reads log files and adds bans afterward. recent acts in the kernel on the packet itself, with no log parsing, at the cost of having no allowlist: the troubleshooting guide notes that you can lock yourself out and shows how to clear one IP from the list.
  • Global limit versus per-source hashlimit. The limit match is one shared bucket for everyone. That is simple and absorbs a single-source flood, but during a real flood it also throttles legitimate users, and the SYN rule applies to every TCP port, SSH included. The hashlimit match keeps a bucket per source IP and would be the production choice.
  • Scripts, not a single rules file. One subcommand per defense lets the class demo each attack before and after its specific rule, with chains printed both times.
  • Counters as evidence. Reading kernel counters, rather than timing the attacker's output, gives a number the defender controls.
  • Host-only network. Floods and brute force never leave the VirtualBox host-only network, so the lab cannot harm anything outside it.

Challenges and How They Were Solved

  • Rule order. The commit history and troubleshooting guide both stress that the --update ... DROP rule must sit above --set, and that the limit ... ACCEPT rule must come before its DROP. The idempotent helpers use -I and -A deliberately to get this ordering.
  • Kernel table limits. xt_recent defaults to tracking 100 sources and 20 packets each; the guide shows how to reload the module with ip_list_tot and ip_pkt_list_tot.
  • Lint warnings. The last commit fixes ShellCheck warnings SC1007, SC2155 and SC2034. SC2155 is why run-attack.sh declares WORDLIST_DEFAULT on one line and marks it readonly on the next: combining readonly with a command substitution hides the command's exit status.
  • Reported results. The README reports the SSH attack rate falling from 6.00 to 1.00 attempts per minute with about 61 packets dropped, 94,671 ICMP flood packets absorbed, half-open connections capped at 3, and DNAT reaching Apache on 8080. These numbers come from the team's report; the repo contains the PDF, not the raw captures.

Security and Performance Notes

  • The rules are a demonstration set, not a complete server policy. The default policy stays ACCEPT, and there is no ESTABLISHED,RELATED accept rule or default-drop. A production firewall would start from default DROP and allow only the needed services.
  • iptables is now a compatibility front end on many distributions; new work usually targets nftables, which has its own rate-limit and set features.
  • Rate limiting in the kernel is cheap, which is why the ICMP flood stopped elevating ksoftirqd (the kernel thread that handles network interrupts).

hardened-static-page

At a Glance

This is a single static web page whose content is deliberately trivial: one screen, a shield logo, three cards. The real product is the engineering around it: a deny-by-default Content Security Policy, a strict page-weight budget, and a CI pipeline that fails the build if either one regresses. It began as a fan page carrying a 19.5 MB PNG and three third-party hosts, and the git history walks it down, one commit at a time, to a 34 KB cold load with no JavaScript and no external requests. It is a template and teaching example for anyone shipping a static site who wants security headers and performance that are tested, not assumed.

How It Works (Simple Version)

Think of a bank vault that only holds one envelope. The envelope is not interesting. The vault is: a door that refuses everything not on a short guest list, a scale at the entrance that sounds an alarm if anything heavy is carried in, and an inspector who, every night, tries to sneak a fake visitor through to prove the door really holds.

  1. The web host sends extra instructions (HTTP response headers) with the page, including a Content Security Policy that tells the browser "load only styles, images and fonts from this same site, and nothing else at all".
  2. A budget script weighs every file on every push. Too heavy, and the build fails.
  3. A CI job injects a hostile inline script into a copy of the page, loads it in headless Chrome under those headers, and fails if the script runs.
  4. Lighthouse, Google's page auditing tool, scores the page and fails the build if performance, accessibility or byte weight slip.

Deep Dive

The page. index.html is 52 lines. It preloads the self-hosted font, links one stylesheet, and shows an <img> of the SVG mark with explicit width and height. Those dimensions let the browser reserve space before the image loads, which keeps Cumulative Layout Shift (CLS, how much the page jumps around while loading) at 0. style.css (279 lines) declares the font with a Latin unicode-range subset and font-display: swap, defines colour tokens as CSS custom properties, and paints the background with three radial gradients. A comment records why: the previous background was a 120 KB image hotlinked from a wallpaper site, and an A/B render showed it changed only 237 of 1.15 million pixels.

The _headers file. Cloudflare Pages and Netlify both read this file from the site root: a path pattern, then indented Name: value lines.

/*
  Content-Security-Policy: default-src 'none'; style-src 'self';
    img-src 'self'; font-src 'self'; base-uri 'none';
    form-action 'none'; frame-ancestors 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Resource-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Strict-Transport-Security: max-age=63072000;
    includeSubDomains; preload

(The CSP and HSTS values are single lines in the real file; they are wrapped here to fit the page.) A Content Security Policy (CSP) is a header that tells the browser which sources each kind of content may come from. default-src 'none' blocks everything, then only styles, images and fonts from the same origin are allowed back. There is no script-src at all, so any script, inline or external, is blocked. base-uri 'none' stops an injected <base> tag from redirecting relative links, form-action 'none' stops forms from posting anywhere, and frame-ancestors 'none' stops other sites from framing the page (clickjacking). HSTS (HTTP Strict Transport Security) tells browsers to use HTTPS only, here for two years. COOP, COEP and CORP isolate the page from other origins. A Permissions-Policy turns off 18 browser features such as camera, microphone and geolocation. Later rules override earlier ones: /assets/img/og.jpg gets Cross-Origin-Resource-Policy: cross-origin so social media scrapers can fetch the preview image.

Caching is a deliberate trade-off recorded in a comment: assets get one week, not a year with immutable, because filenames are not content-hashed, and an immutable stale file would strand visitors until it expired. The HTML entry point always revalidates so deploys show up immediately.

tools/serve.py solves the problem that _headers is only read by the host. It parses the file and applies the same rules to Python's built-in HTTP server, so the policy can be tested locally and in CI:

def end_headers(self):
    url_path = posixpath.normpath(self.path.split("?", 1)[0])
    if url_path.endswith("/index.html"):
        url_path = url_path[: -len("index.html")]
    # Later matches win, so a specific path can override /*.
    applied = {}
    for pattern, headers in self.rules:
        if matches(pattern, url_path):
            for name, value in headers:
                applied[name] = value
    for name, value in applied.items():
        self.send_header(name, value)
    super().end_headers()

It overrides end_headers, the hook Python's SimpleHTTPRequestHandler calls just before finishing the response headers. It also registers MIME types Python's table lacks (font/woff2, image/avif, image/webp) and binds only to 127.0.0.1.

tools/check-headers.sh fetches a URL with curl -D - (dump headers) and checks 11 assertions, each a header name plus an extended regex the value must match. HSTS is checked only on https:// URLs, since hosts do not send it over plain HTTP; when checked, the regex max-age=(6[0-9]{7}|[1-9][0-9]{8,}) requires roughly two years or more. It also fails if X-Powered-By or X-AspNet-Version leaks server details.

Testing the CSP for effect. The most interesting CI step injects an inline script and proves it is blocked:

printf '%s\n<script>document.title="EXECUTED";</script>\n' \
  "$(cat index.html)" > /tmp/probe.html
cp /tmp/probe.html ./probe.html
title=$(google-chrome --headless --disable-gpu --no-sandbox \
          --virtual-time-budget=4000 --dump-dom \
          http://127.0.0.1:8000/probe.html 2>/dev/null \
        | grep -oP '(?<=<title>).*?(?=</title>)')
rm -f ./probe.html
if [ "$title" = "EXECUTED" ]; then
  echo "CSP did not block inline script"; exit 1
fi

If the script runs, it changes the page title. Headless Chrome dumps the final DOM, and grep -oP with lookbehind and lookahead pulls out the title. As the README puts it, a header string being present "proves very little"; this checks the policy for effect rather than for spelling.

The budget. tools/check-budget.sh sets three limits in bytes: the critical path (what a 2x screen downloads for a cold load: HTML, CSS, font, SVG mark, favicon) at 150 KB, any single tracked file at 200 KB, and all files tracked by git at 1 MB. It uses git ls-files so only committed content counts, and prints the three largest files even when everything passes. Lighthouse CI enforces a second, independent weight limit (total-byte-weight at most 153,600 bytes) plus minimum scores: 0.95 for performance and best practices, 1.0 for accessibility, and 1.0 for SEO on index.html. 404.html is exempt from SEO because it is noindex on purpose.

Image tooling. tools/build-images.sh rasterizes only what cannot be vector: a 32x32 favicon, a 180x180 Apple touch icon (flattened onto the page background because iOS fills transparency with black), and a 1200x630 Open Graph card. It uses rsvg-convert for SVG rendering because, per its comment, ImageMagick's own renderer handles gradients incorrectly.

Key Design Decisions and Trade-offs

  • Self-hosting the font is a security decision. The Google Fonts stylesheet is generated per browser, so it can never be pinned with Subresource Integrity (a hash that proves a file was not changed) or covered by style-src 'self'. Self-hosting a 26 KB Latin subset removed a render-blocking third-party request and made the strict CSP possible. Since the family only ships weight 400, the display face is used for headings and the system font stack for body text to avoid "synthetic bold".
  • One SVG instead of a responsive raster pipeline. An earlier commit built 240/480/720 px AVIF and WebP variants of the hero art. A later commit removed it in favour of a 1,020-byte hand-drawn SVG, with the note that "seven avif/webp/png derivatives of flat vector art would be worse engineering than one svg, even though the pipeline was more impressive to look at."
  • Host choice is part of security. GitHub Pages does not read _headers, so on it the whole policy would be dead config. The README names Cloudflare Pages and Netlify instead.
  • Actions pinned to commit SHAs. A git tag like v7 can be moved by whoever controls the action's repository; a commit SHA cannot. Dependabot bumps the pins weekly so the project still receives fixes.
  • Downloaded binaries verified. gitleaks is installed from a pinned release and checked with sha256sum --check --strict, because "pinning a version without checking the bytes is half a control".

Challenges and How They Were Solved

The commit messages read like a performance and security journal:

Step Before After
Hero artwork 19,523,366 B PNG 1,020 B SVG

  • The 19 MB PNG. The original hero was a 2124x2297 PNG scaled to 240 px by CSS. The budget job exists "because nothing stopped that 19 MB file the first time".
  • Mobile and Safari fixes. 100vh on mobile is taller than the visible area, so 100svh was added after the fallback. -webkit-backdrop-filter was restored after stylelint --fix stripped it, which broke the glass effect on Safari before version 18; the stylelint rule property-no-vendor-prefix was then turned off.
  • Reduced motion. Hover transforms are disabled under prefers-reduced-motion.
  • Secret scanning after a history rewrite. The official gitleaks action derives its scan range from the push event. After the history was rewritten (to drop the large PNG), the range became <root>^..<head>, and the root commit has no parent, so the job failed having scanned nothing. The fix runs a pinned gitleaks binary over the full history, which behaves the same on any push.
  • 404 page paths. A 404 page is served at whatever wrong URL the visitor typed, so its asset paths are root-absolute; relative paths would resolve against the bad URL and break.
  • Local vs deployed. serve.py proves the file is correct but not that the host applies it. A live CI job runs the same checker against the real deployment once the SITE_URL repository variable is set, and skips until then.

Security and Performance Notes

  • With no server, database, login or user input, the realistic attack surface is the supply chain and the headers, and the CI targets exactly those.
  • SECURITY.md notes that if JavaScript is ever added, script-src must be added deliberately; today it falls under default-src 'none' and any script is blocked rather than silently allowed.
  • Lighthouse reports performance, accessibility, best practices and SEO at 100, Largest Contentful Paint (LCP, when the biggest visible element finishes drawing) of 0.3 s, and CLS of 0.
  • Text contrast is above 9:1, and the only interactive element (the link back on the 404 page) has a :focus-visible ring.

Each solution below is explained with its time and space complexity. Big-O notation describes how running time or memory grows with input size n: O(1) is constant, O(n) grows in step with the input, O(n^2) grows with its square.

1. Contains Duplicate (hash set).

class Solution:
    def hasDuplicate(self, nums: List[int]) -> bool:
        hashset = set()
        for n in nums:
            if n in hashset:
                return True
            hashset.add(n)
        return False

A Python set is a hash table: it turns each value into a bucket index, so checking membership takes constant time on average. The loop remembers every number it has seen and stops the moment it meets one again. Time O(n), space O(n). The alternative of comparing every pair would be O(n^2); sorting first and checking neighbours would be O(n log n) time with less extra memory.

2. Valid Anagram (sort and compare).

class Solution:
    def isAnagram(self, s: str, t: str) -> bool:
        sort_s = "".join(sorted(s))
        sort_t = "".join(sorted(t))
        if sort_s == sort_t:
            return True
        return False

Two strings are anagrams if they contain the same letters in any order, so sorting both and comparing gives the answer. Time O(n log n) because of the sort, space O(n) for the sorted copies. The final if could simply be return sort_s == sort_t. The hash-map approach (count each character with a dictionary or collections.Counter) reaches O(n) time, with O(1) extra space for a fixed alphabet.

3. Two Sum (brute force).

class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        for i in range(len(nums) - 1):
            for j in range(i+1, len(nums)):
                if nums[i] + nums[j] == target:
                    return [i, j]

This tries every pair once (j always starts after i), so it is O(n^2) time and O(1) space. Both synced submissions use this approach. The standard improvement is a single pass with a dictionary from value to index: for each number, check whether target - number is already in the dictionary. That is O(n) time and O(n) space, and it is the solution most interviewers expect.

4. Remove Element (two pointers, in place).

class Solution:
    def removeElement(self, nums: List[int], val: int) -> int:
        k = 0
        for i in range(len(nums)):
            if nums[i] != val:
                nums[k] = nums[i]
                k = k + 1
        return k

This is the read/write pointer pattern. i reads every element; k marks where the next kept element should be written. Each element that is not val is copied forward, so after one pass the first k positions hold the answer. Time O(n), space O(1), and the relative order of kept elements is preserved.

5. Max Consecutive Ones (running counter).

The solution counts the current run of 1s in r, appends it to a list seen whenever a 0 breaks the run, appends the final run after the loop, and returns max(seen). Time O(n). Space is O(n) in the worst case because of the seen list. Keeping a single best = max(best, r) variable instead would bring space down to O(1).

6. Replace Elements with Greatest Element on Right Side (slicing).

class Solution:
    def replaceElements(self, arr: List[int]) -> List[int]:
        for i in range(len(arr)-1):
            arr[i] = max(arr[i+1:])
        arr[len(arr)-1] = -1
        return arr

For each position it takes the maximum of everything to its right. This is correct, but arr[i+1:] copies the rest of the list every time and max scans it, so the total work is O(n^2) time with O(n) temporary space per step. The intended solution walks from the right end with a running maximum: save the current value, write the running max into this slot, then update the running max. That is O(n) time and O(1) space. This problem is a good example of the "scan from the other end" idea.

Key Design Decisions and Trade-offs

  • Automatic sync over a hand-curated repo. No effort is needed to keep the repo current, at the cost of no README per problem and no notes on why a solution works.
  • Every attempt kept. Storing each submission as its own file preserves the history of re-solves. It also means the repo shows first, simple solutions (brute-force Two Sum, slice-based maximum) next to optimal ones, which honestly reflects where the practice is.
  • Python only. The platform supports many languages; using one keeps attention on patterns rather than syntax.

How It Works

The notable engineering is how the vault is maintained. A CLAUDE.md and AGENTS.md at the root describe the vault as an "LLM wiki": a knowledge base that an AI agent keeps compiled and current, rather than one re-derived on every question. A SessionStart hook (configured for both Claude Code and Codex) runs .claude/vault-check.sh before the agent's first reply and puts its output into the agent's context.

That script is a mechanical staleness detector. Its header states the principle: "Everything here is a thing that has actually gone stale at least once. Adding a check is cheaper than remembering." The checks include: a daily note exists for today, the dashboard note is dated today, checklists have been reset, embedded media are actually downloaded, there are no empty stray notes or blank canvas files, no two notes share a filename (which would break [[wikilinks]]), and no wikilink contains # (which Obsidian reads as a heading anchor). The # check is written in Python so it can skip fenced code blocks, because, as its comment says, "a checker with false positives is a checker that gets ignored."

The CLAUDE.md names the root cause these checks address: the same fact written in several places with nothing comparing them. Its two rules are to prefer deleting a duplicate over maintaining it, and to add a check in the same change whenever a duplicate must exist. The .gitignore keeps per-machine Obsidian UI state, caches and node_modules out of the repo.

This pattern of a small, cheap consistency checker that runs before any work starts carries over well to codebases, and it reflects the same approach as the CI gates in the other projects in this chapter.

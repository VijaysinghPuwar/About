3 Web Audio TV, an Audiobook Streaming Platform

Web Audio TV is the largest system in this book and the only one that runs in production for real users who pay for it. It combines a React single page application, a Postgres database with row level security, twenty five serverless functions, private object storage on Cloudflare R2, and a small Cloudflare Worker that delivers audio bytes. This chapter walks through how a listener presses Play and hears a chapter of a novel, and how the system makes sure only the right people hear it, that listening time is counted honestly, and that the hosting bill stays small.

Web Audio TV

At a Glance

Web Audio TV (webaudiotv.com) is a streaming site for audiobooks and audio novels. Listeners browse a catalogue of more than 400 novels and about 1,671 tracks (roughly 180 GB of audio), play chapters in a player that keeps going while they navigate, and earn XP, levels and streaks for listening. A PRO subscription, paid through PayPal or Stripe, unlocks PRO tier tracks, Early Access releases and downloads. Publishers apply for an account and manage only their own novels, while admins run user management, manual PRO grants and an XP forensics console. The README reports about 1,000 registered users and 200 daily actives.

How It Works (Simple Version)

Think of Web Audio TV as a library with a ticket booth and a separate listening room.

  1. You walk into the lobby. The React app loads in your browser. It reads the catalogue (novels, sections, tracks, covers, reviews) straight from the database, which only shows each visitor the rows they are allowed to see.
  2. You pick a chapter and press Play. The app does not know where the audio file lives. That location is hidden from every browser. Instead the app goes to the ticket booth: a server function called issue_stream_token.
  3. The booth checks your membership. It asks a few questions. Is this chapter published? Is the novel public? Is it a PRO chapter, and if so do you have PRO? Is the novel in an Early Access window? If everything passes, the booth prints a ticket that names you, names the chapter, and expires soon.
  4. You hand the ticket to the door of the listening room. The browser's audio element fetches the audio from either the Cloudflare Worker or a fallback function called stream_media. The door checks only one thing: is this ticket genuine, unexpired, and for this chapter? If yes, it streams the bytes from private storage.
  5. A clerk keeps your listening log. Every 60 seconds the player sends "I listened for N more seconds" to add_listen_time. The clerk checks the wall clock, refuses anything that does not add up, and awards XP. Because XP can be converted into free PRO time, this clerk is strict.

The two key ideas are that the booth decides and the door only checks, and that the server never trusts the client about time or money.

The components and how they talk:

  • React SPA (src/). Reads catalogue data directly from Postgres through PostgREST (Supabase's automatic REST layer over the database). Calls edge functions with the user's JWT (a signed JSON Web Token that proves who is logged in) in the Authorization header.
  • Supabase Postgres (supabase/migrations/, 100 SQL files). Holds 41 tables. Row Level Security (RLS, rules in the database that filter rows per user) and column privileges decide what a browser may read or write.
  • Edge functions (supabase/functions/, 25 functions plus a _shared folder). Deno programs that run with the service role key, which bypasses RLS. They handle streaming authorization, listen credit, payments, email, cron jobs and admin actions.
  • Cloudflare R2. S3 compatible object storage holding audio and covers. R2 does not charge for egress (data leaving the bucket), which is the key to the cost design.
  • Cloudflare Worker (workers/media-gate/). About 140 lines. Verifies a media ticket and streams the R2 object with HTTP Range support. It has no database access and no business logic.
  • Payment providers. PayPal subscriptions and orders, Stripe checkout, both confirmed through signed webhooks.

Deployment flows from GitHub main to Lovable (a hosted app builder that syncs with the repo), then Lovable publishes the build behind Cloudflare DNS.

Deep Dive

The content model and the database

Content is a three level tree:

novel  ->  section  ->  track
(book)     (volume)     (chapter: the actual audio or video file)

The important columns are on tracks: drive_file_url (where the audio lives), access_tier (free or pro), published, media_kind (audio or video) and file_type. On novels: visibility (public or private), publisher_id, and the Early Access fields early_access_enabled and early_access_until.

The schema is grouped into content (novels, sections, tracks, tags), identity (profiles, user_roles, publisher_profiles), engagement (listening_progress, listening_events, user_novel_stats, novel_reviews, review_reactions), gamification (user_xp_logs, user_xp_daily_totals, xp_abuse_flags, xp_flag_policy, pro_rewards, shop_items), commerce (subscriptions, payments, paypal_webhook_events, admin_pro_grants), email, and an admin_audit_log.

Three database layers enforce security before any edge function runs:

  1. RLS policies. A user reads and writes only their own progress, bookmarks and reviews. Drafts and private novels are visible only to the owning approved publisher and admins. Every ownership policy checks publisher_profiles.status = 'approved', so revoking a publisher instantly removes write access without touching their content.
  2. Column privileges. tracks.drive_file_url is revoked from the anon and authenticated roles at the column level. A browser can read a track's title but can never learn where its file is stored. This is what makes the ticket design necessary.
  3. A profile trigger. Columns such as plan, xp_total, level, streaks, listening totals and PRO dates cannot be changed from the client, even on the user's own row. Cosmetics must be owned before they can be equipped.

SECURITY DEFINER functions (SQL functions that run with the owner's rights rather than the caller's) pin their search_path so a malicious schema cannot shadow a table name, and admin functions check is_admin() at the top.

The frontend shell

src/main.tsx is eleven lines long, and its first import is deliberate: import "./startupGuard", followed by react-dom, App and the stylesheet. startupGuard.ts checks that VITE_SUPABASE_URL, VITE_SUPABASE_PUBLISHABLE_KEY and VITE_SUPABASE_PROJECT_ID exist. If any is missing, it writes a plain "App configuration error" screen into #root and throws.

This fixes a real outage. ES modules evaluate their imports before the importing file's body. When the environment check lived in the body of main.tsx, import App had already built the Supabase client and crashed, so a misconfigured build still showed a black page. Moving the check into its own module and importing it first means a thrown error stops every later import. A test, src/test/mainBootstrap.guard.test.ts, pins this import order.

App.tsx composes the provider tree in dependency order: ErrorBoundary, QueryClientProvider (TanStack Query, a cache for server data), ThemeProvider, TooltipProvider, BrowserRouter, AuthProvider, PlayerProvider, then the routes. The player sits inside auth because it needs the signed in user to flush listening time and show XP toasts. Auth sits inside the router because sign in callbacks read the URL.

Almost every page under src/pages/ (34 route pages) is loaded with React.lazy, each behind its own Suspense boundary. A slow admin chunk therefore cannot blank out the header and player, which matters because audio may be playing.

The QueryClient defaults were tuned after a cloud cost audit. It used to be new QueryClient(), which means staleTime: 0 (refetch on every mount and focus) and three retries for every failure. Now staleTime is 60 seconds and retries go through shouldRetryQuery in src/lib/queryRetry.ts. That function classifies errors: Postgres SQLSTATE classes 22, 23, 28 and 42 (bad data, constraint, auth, syntax or privilege) and PostgREST codes PGRST1xx to PGRST3xx are permanent and never retried; connection errors get exactly one retry. One dead request no longer becomes four.

A structural rule runs through the frontend: any logic worth testing is moved into a pure module in src/lib/ that does not import React. Examples include streamAuth.ts, listenCredit.ts, playerClock.ts, listenIdle.ts, progressSave.ts, playerInterruption.ts, mediaSession.ts and xpUtils.ts. The hook or component becomes a thin caller, and Vitest can test the rules without a browser media stack (jsdom, the fake browser used in tests, has no real audio pipeline).

The audio player engine

Despite the product name, playback does not use the Web Audio API (the browser's graph based audio processing API). It uses plain HTMLMediaElement: one <audio> and one <video> element, created once inside PlayerProvider in src/hooks/usePlayer.tsx and kept alive for the whole session. Route changes never touch them, which is how audio keeps playing while you browse. The only microphone code is in ReviewVoiceRecorder.tsx, which uses MediaRecorder to capture voice notes of up to 30 seconds for reviews, choosing audio/webm where supported and audio/mp4 on Safari.

usePlayer.tsx is about 2,450 lines, the largest hand written file in the repo. Its size comes from browser reality. The player has seven states:

idle -> resolving -> loading -> playing <-> paused
                        |          |
                        v          |
                     retrying -----+
                        |
                        v
                      error

resolving is the round trip to issue_stream_token; loading is the media element buffering. Separating them lets the UI say "checking access" versus "downloading", which need different error messages.

Some important constants and what they guard against:

Constant Value Purpose
R2_LOAD_TIMEOUT_MS 60,000 Slow first bytes from large files
DIRECT_LOAD_TIMEOUT_MS 12,000 A direct URL that has not loaded in 12 s is broken
TRACK_START_STEP_TIMEOUT_MS 15,000 Bounds session and saved position reads
LISTEN_FLUSH_INTERVAL_MS 60,000 Listen time reporting cadence
MAX_RETRY_ATTEMPTS 2 With delays of 2 s and 4 s
MAX_CONSECUTIVE_RECOVERY_RELOADS 3 Stop reload loops
MAX_CONSECUTIVE_SPURIOUS_ENDED 2 Stop autoplay racing through broken files

The hook holds many useRef values. The reason is the stale closure problem: native event listeners (error, stalled, ended) are attached once and capture the variables from the render in which they were attached. If they called saveProgress directly they would use an old currentTrack. Routing calls through a ref like saveProgressRef.current() means the listener always runs the newest version.

Playback position (currentTime) changes about four times per second. It lives in a separate PlayerTimeContext, read with usePlayerTime(). When it lived in the main context, every component using usePlayer(), including a novel page with a long chapter list, re-rendered four times a second.

Several pure helpers handle specific browser problems:

  • playerClock.ts. resolveDuration() picks the first trustworthy duration from three sources: the element's duration, the end of its seekable range, and the duration stored in the database. iOS Safari reports Infinity for streamed responses and every element reports NaN before metadata arrives, either of which would show "0:00" and a dead scrubber. readSeekableEnd() wraps seekable.end() in a try block because reading it on an empty range throws, which would kill the clock timer. pickClockSource() reads the clock from whichever element is actually playing in case a track was routed to the wrong one.
  • playerInterruption.ts. Every deliberate pause is tagged with a reason (user, track-change, ended, seeking, source-refresh, teardown). An untagged pause while playing must have come from the operating system, such as a phone call. Only those show a notice, at most once per 20 seconds.
  • mediaSession.ts. A feature detected wrapper around the Media Session API (the browser API that drives lock screen and headphone controls). It sets title and artwork, binds play, pause, next, previous, seek forward and back (10 s default) and seek to, and clamps position state to values the spec accepts. Every call is a no-op instead of a throw on browsers that lack an action.
  • listenIdle.ts. After three hours with no tap, click, key or lock screen action, playback pauses ("Still listening?"). isAudible() returns false when the element is muted or at zero volume, and no listening seconds are counted then.
  • progressSave.ts. Position is autosaved every 15 seconds and on pause, track change, route change, tab hide and unload. isRedundantProgressWrite() skips a write when the position has not moved (a stalled truncated file can pin the clock) but always writes after a deliberate scrub so seeking backwards is never lost.

Saved position restore is careful. safeSeekToProgress() bails out if a newer play request has replaced the current one, and resolveSavedPosition() throws away corrupt or out of range saved values and starts from the beginning instead of parking the UI hours ahead of the audio.

Page unload is the hardest moment to report listening time. The original code used navigator.sendBeacon, which cannot carry an Authorization header, so every unload report was rejected. The fix uses fetch with keepalive: true, which survives page unload and still sends headers, without ever putting the JWT in the URL. It listens to both beforeunload and pagehide (iOS often skips the first) with a flag so only one request goes out, and it subtracts any seconds already in flight so they are not reported twice.

Streaming authorization: the booth

Streaming started with a mistake that shaped everything after it. The first version streamed from stream_media?track_id=...&token=<Supabase JWT>. A token in a URL leaks into browser history, Referer headers, server logs and proxy logs, and a Supabase JWT is valid for every endpoint, not just one track. The replacement is a two step flow.

First, the browser POSTs { track_id } to issue_stream_token with the JWT in the header. The function loads the track, its section and novel in one embedded query (_shared/stream_context.ts), runs the access decision, and returns a short lived credential.

The access decision lives in exactly one place, supabase/functions/_shared/stream_access.ts. Before this module existed, issue_stream_token and stream_media each had their own copy of the rules; they agreed, but nothing forced them to. The module also makes the check lazy:

export function requiresProEntitlement(opts: {
  accessTier?: string | null;
  novel: NovelAccessContext | null;
  publiclyListed: boolean;
  downloadMode?: boolean;
  nowMs?: number;
}): boolean {
  return (
    !opts.publiclyListed ||
    isEarlyAccessActive(opts.novel, opts.nowMs ?? Date.now()) ||
    opts.accessTier === "pro" ||
    opts.downloadMode === true
  );
}

There are four gates that could deny: not publicly listed, Early Access active, PRO tier track, and download mode. Each one needs the user's entitlement (roles, publisher ownership, profile grants, subscriptions), which costs four database reads. requiresProEntitlement() is exactly the OR of those four conditions. When it is false (the common case: a published free track in a public novel, being streamed), no gate can deny, so the reads are skipped. This saves work without loosening any rule, and src/test/streamAccess.test.ts asserts exactly which reads each scenario performs, so adding a fifth gate without updating this function fails the tests.

When the reads are needed, resolveProAccess() issues them in two parallel batches. Roles and publisher ownership come first; an admin, or the approved publisher of this specific novel, short circuits to allowed. Otherwise profile and subscriptions are read, and proAccessEndsAt() (in _shared/pro_entitlement.ts) computes whether any grant is active and when the latest one ends. The gates then run in a fixed order:

  1. Not listed. A draft or private track returns 404 not_available, not a paywall. PRO buys tier access, not access to unreleased work, and this ordering avoids leaking an Early Access date for a hidden track.
  2. Early Access. Active window and no PRO returns 403 early_access_locked with unlocks_at.
  3. Track tier. A PRO track without PRO returns 403 pro_required.
  4. Download. Free users get 403 download_forbidden.

If a parent row read fails, stream_context.ts throws TrackContextUnavailableError and the function answers 503 context_unavailable. A failed read is never treated as "no parent", which would otherwise let the not listed gate see null and behave unpredictably.

On the client, src/lib/streamDenial.ts turns these reasons into helpful messages and the right button: "Early Access until ..." with an Upgrade button, rather than a Retry that can never succeed.

Two kinds of credential

issue_stream_token always returns a v1 stream token for the fallback path and, when the Worker is enabled for that user, a v2 media ticket.

The v1 token (_shared/stream_token.ts) is base64url(payload).base64url(HMAC-SHA256(payload)), where the payload holds user_id, track_id and exp. HMAC (a hash keyed with a secret, so only the holder of the secret can produce a valid signature) means the browser cannot forge or edit it. It lives six hours. The comment in issue_stream_token explains why: a shorter token would expire mid chapter, the next Range request (a seek) would get 401, and the audio element would reset to zero. Since the token is bound to one user and one track, six hours was judged an acceptable exposure. The signing secret comes from a shared helper getStreamSigningSecret() so signer and verifier cannot disagree, and it refuses any secret shorter than 32 characters.

The v2 media ticket (_shared/media_ticket.ts) is built for the Worker and is stricter:

const aad = (p: { sub: string; tid: string; exp: number; dl: boolean }) =>
  buf(enc.encode(`${p.sub}|${p.tid}|${p.exp}|${p.dl ? 1 : 0}`));

// inside signMediaTicket():
const { mac, aes } = await deriveKeys(opts.secret);
const exp = (opts.nowSeconds ?? Math.floor(Date.now() / 1000))
  + opts.ttlSeconds;
const iv = crypto.getRandomValues(new Uint8Array(12));
const ciphertext = new Uint8Array(await crypto.subtle.encrypt(
  { name: "AES-GCM", iv: buf(iv),
    additionalData: aad({ sub: opts.userId, tid: opts.trackId,
                          exp, dl }) },
  aes,
  buf(enc.encode(opts.objectKey)),
));
// payload = { v:2, aud, sub, tid, exp, ct, dl, iv, k: ciphertext }
const head = `v2.${opts.kid}.${b64u(enc.encode(JSON.stringify(payload)))}`;
const sig = new Uint8Array(
  await crypto.subtle.sign("HMAC", mac, buf(enc.encode(head))));
return { ticket: `${head}.${b64u(sig)}`, exp };

The format is v2.<kid>.<payload>.<hmac>. Several ideas are packed in:

  • The R2 object key is encrypted with AES-GCM (an authenticated cipher that both hides data and detects tampering). The file path never reaches the browser, so the column revoke on drive_file_url still means something.
  • AAD binds the ciphertext to the ticket. AAD (additional authenticated data) is extra text that is checked but not encrypted. Using user|track|exp|download as AAD means an encrypted key lifted from one ticket fails to decrypt inside another.
  • HKDF derives two keys from one secret. HKDF (a standard way to stretch one secret into several independent keys) produces a MAC key and an AES key with different info labels, so there is one secret to manage per key id.
  • Key ids allow rotation. The Worker holds a JSON map of kid to secret. To rotate, add a new kid, sign with it, keep verifying the old one for one ticket lifetime, then remove it.
  • Short life. mediaTicketTtlSeconds() in _shared/media_worker.ts caps tickets at 15 minutes and also at the end of the entitlement that granted access. A three month grant ending in five minutes gets a five minute ticket.

The verifier checks, in order: format, known kid, HMAC signature, audience (webaudiotv-media), expiry, that the track id in the URL path equals the ticket's, then decrypts the key and rejects any key starting with / or containing ...

The secret for tickets must be dedicated. The design documents are explicit that the Supabase service role key must never be copied to Cloudflare.

The Worker: the door

workers/media-gate/src/handler.ts handles GET and HEAD on /a/<track-uuid>?t=<ticket>. After the ticket checks, it looks up the object size with env.MEDIA.head(key) through an R2 binding (a direct connection from the Worker to the bucket, with no credentials in code), then serves bytes.

Range requests are how seeking works. The browser asks for Range: bytes=START-END and the server answers 206 Partial Content with a Content-Range header. The Worker implements the single range case of RFC 9110:

export function parseRange(header: string | null, size: number) {
  if (!header) return { kind: "none" };
  const m = /^bytes=(\d*)-(\d*)$/.exec(header.trim());
  if (!m) return { kind: "none" }; // multi-range: serve whole object
  const [, a, b] = m;
  if (a === "" && b === "") return { kind: "none" };
  if (a === "") {                   // suffix: last N bytes
    const n = Number(b);
    if (!Number.isSafeInteger(n) || n === 0)
      return { kind: "unsatisfiable" };
    return { kind: "range",
      range: { start: Math.max(0, size - n), end: size - 1 } };
  }
  const start = Number(a);
  if (!Number.isSafeInteger(start)) return { kind: "none" };
  if (start >= size) return { kind: "unsatisfiable" };
  let end = b === "" ? size - 1 : Number(b);
  if (!Number.isSafeInteger(end) || end < start)
    return { kind: "none" };
  end = Math.min(end, size - 1);
  return { kind: "range", range: { start, end } };
}

An unsatisfiable range returns 416 with Content-Range: bytes */SIZE, which Safari can use to learn a file's length. A malformed or multi range header falls back to a full 200, matching what stream_media did. The R2 body stream is returned as is: nothing is buffered, and a client disconnect cancels the R2 read. Responses carry Cache-Control: private, no-store (no shared cache may store PRO audio), X-Content-Type-Options: nosniff, and CORS headers only for the two allowed site origins. Downloads add Content-Disposition: attachment with a sanitised filename.

The wrangler.toml.example sets workers_dev = false so no public *.workers.dev copy exists, and turns observability off because the ticket sits in the query string and must not be logged.

The Worker is behind a server side flag, MEDIA_WORKER_ENABLED, which accepts exactly admins (a canary rollout to admin accounts) or all. Anything else, including a missing secret or a malformed base URL, means off, logged as media_worker_config_error. Turning the flag on therefore cannot break playback by itself. The repo's own status notes (dated 2 October 2026) record that the Worker was deployed and bound to R2 on the Cloudflare side while the matching Lovable secrets were still missing, so the flag was effectively off at that moment; the README, written the same day, reports first bytes of 0.35 s through the Worker against 0.6 s through the edge function.

Fallback and recovery on the client

src/lib/streamAuth.ts is the client side of streaming. It caches credentials per track in a Map, and each entry records the user id it was issued to. If user B signs in on the same browser, A's cached PRO ticket is never reused. clearStreamTokenCache() runs on sign out.

Failures are never cached, so every retry really calls the function again. The whole lookup has a 15 second deadline (STREAM_TOKEN_TIMEOUT_MS), added after a backend outage left the player spinning in resolving forever.

The Worker fallback logic is a small state machine:

export function noteStreamSourceError(trackId: string)
    : "proxy" | "worker-renew" | "fallback-to-proxy" {
  if (lastDelivery.get(trackId) !== "worker") return "proxy";
  const entry = tokenCache.get(trackId);
  const ticketLive = !!entry?.mediaExpiresAt &&
    entry.mediaExpiresAt - Date.now() > TICKET_EXPIRY_SLACK_MS;
  if (!ticketLive) {
    // Renew at most once a minute per track
    const last = lastRenewAt.get(trackId) ?? 0;
    if (Date.now() - last > RENEW_LOOP_WINDOW_MS) {
      lastRenewAt.set(trackId, Date.now());
      return "worker-renew";
    }
  }
  workerFailedTracks.add(trackId);
  workerSessionFailures += 1;
  return "fallback-to-proxy";
}

When the audio element reports an error, the player asks this function what to do next. If the last URL was the proxy, normal recovery applies. If it was the Worker and the ticket had expired, the player mints a new ticket and stays on the Worker. If the ticket was still valid, the Worker itself failed, so this track moves to stream_media for the rest of the session. After two such failures (WORKER_SESSION_FAILURE_LIMIT), every track does. A Worker outage can therefore cost at most one failed load per track and can never loop.

streamTokenExpiresAt() tells the player when the credential baked into the element's src will die, so a long chapter reloads its source with a fresh ticket before a seek would hit 401.

The fallback proxy: stream_media

stream_media verifies the v1 token, reruns evaluateStreamAccess as defence in depth, and then fetches the bytes. The original source may be one of three shapes, detected by src/lib/mediaResolver.ts and mirrored on the server:

Type Detected by Handling
r2 media.webaudiotv.com, *.r2.dev, *.cloudflarestorage.com SigV4 signed GET to private R2
gdrive drive.google.com, docs.google.com Rewritten to a direct download URL with confirm=t
direct anything else Fetched behind SSRF checks

For R2, _shared/r2_sign.ts implements AWS Signature Version 4 (the request signing scheme S3 compatible stores use) with only WebCrypto and no SDK. It builds a canonical request, hashes it, and derives the signing key through the chain AWS4+secret -> date -> region ("auto") -> "s3" -> "aws4_request". Two details matter: each path segment is percent encoded per RFC 3986 (so an apostrophe in a filename does not break the signature), and the Range header is included in the signed headers, or every seek would be rejected. extractR2ObjectKey() strips the bucket prefix only for the raw S3 endpoint form, and returns null for unknown hosts, so a publisher cannot point a track at an arbitrary host and get a signed request sent there.

For non R2 sources, _shared/media_security.ts defends against SSRF (server side request forgery, tricking a server into fetching internal addresses). isBlockedHost() rejects localhost, metadata.google.internal, *.internal, private IPv4 ranges, 169.254.* (the cloud metadata address) and private IPv6 ranges, after stripping a trailing dot and IPv6 brackets. Redirects are followed manually with redirect: "manual", and every hop is revalidated, with a cap of five hops. Automatic redirects would only validate the first URL. R2 requests use redirect: "error" since a signed request should never redirect.

stream_media also offers mode=metadata, which requests only the first 256 KB (bytes=0-262143) and reads the MP3 duration with _shared/mp3_metadata.ts. That parser skips an ID3 tag, finds the first MPEG frame (confirming it with the following frame), then trusts, in order, a Xing or Info header's frame count, a VBRI header's frame count, or a constant bitrate estimate only after five or more consecutive frames share the same bitrate. A zero frame count is refused rather than guessed. If an origin ignores the Range header and starts sending a multi hour file, the function reads only the prefix and cancels the stream.

Measuring how browsers actually fetch audio

docs/STREAMING_CLOUD_EFFICIENCY_AUDIT.md measured the real request pattern against a local origin that reproduced the exact response contract, using a 2.5 hour, 72 MB MP3. Key findings:

  • Continuous playback and pause or resume cost zero extra requests. One connection carried five minutes of audio.
  • One seek costs about one request. A saved position restore costs about four in Chrome and five in Safari.
  • Chrome sends only open ended ranges (bytes=N-) and aborts 19 of 21 connections once it has buffered enough. Safari sends bounded ranges and starts every source with a two byte probe (bytes=0-1) just to learn the length.
  • Proxied egress is a multiple of the file size: 109.7 MB in Chrome and 662.3 MB in Safari for the same 72 MB file, because aborted connections and fresh source loads re-fetch data.

That last finding is the economic case for the Worker. The design document records audio delivery as about 55 percent of the hosting platform's usage, and R2 storage at about a dollar a month, because R2 egress is free. Moving the bytes to Cloudflare turns every Range request from a billed function invocation plus database reads into a free Worker read.

The measurement also explained a cost that looked like a bug: the Safari two byte probe used to run the full entitlement chain to return two bytes. The lazy requiresProEntitlement() check and the embedded context read cut that work for free public tracks.

Listening credit: the clerk

supabase/functions/add_listen_time/index.ts is about 1,100 lines. It accepts { seconds, track_id, novel_id, session_id, request_id } and returns a receipt: accepted_seconds, rejected_seconds, deferred_seconds, retry_after_seconds.

Idempotency comes first. An idempotent operation gives the same result if repeated. Each flush carries a UUID request_id. If a listening_events row with that id already exists, the function returns the original receipt with duplicate: true before running any rate or pace checks, which would otherwise flag a legitimate retry as abuse. Two concurrent requests with the same id are resolved by a partial unique index on (user_id, request_id): the loser gets Postgres error 23505 and is answered as a duplicate.

Then the bounds apply in order:

Rule Value Meaning
REQUEST_CAP_PER_HOUR 120 Anti hammering only; deferred, not rejected
MAX_SECONDS_PER_REQUEST 3,600 An hour holds at most 3,600 seconds
Pace check elapsed + 15 s Cannot exceed wall clock since last event
MAX_SECONDS_NO_ANCHOR 900 No recent event to pace against
HOUR_SECONDS_CAP 3,900 65 minutes of credit per rolling hour
DAILY_LISTEN_SECONDS_CAP 57,600 16 hours per UTC day

The pace check is the core rule:

if (seconds > 0) {
  const lastCreatedAt = recentRows[0]?.created_at ?? null;
  if (lastCreatedAt) {
    const elapsed = Math.floor(
      (Date.now() - new Date(lastCreatedAt).getTime()) / 1000);
    const allowed = Math.max(0, elapsed + PACE_TOLERANCE_SECONDS);
    if (seconds > allowed) {
      await insertFlag("pace_violation", {
        requested: seconds, allowed, elapsed_since_last: elapsed,
      });
      // exceeded real elapsed time: never creditable
      rejectedSeconds += seconds - allowed;
      seconds = allowed;
    }
  } else if (seconds > MAX_SECONDS_NO_ANCHOR) {
    await insertFlag("no_pace_anchor", { requested: seconds,
      clamped_to: MAX_SECONDS_NO_ANCHOR });
    rejectedSeconds += seconds - MAX_SECONDS_NO_ANCHOR;
    seconds = MAX_SECONDS_NO_ANCHOR;
  }
}

You cannot be credited more seconds than have passed since your last credited event, plus 15 seconds of jitter. Two tabs playing at once, or a replayed request, hit this wall. The hourly cap is 3,900 rather than 3,600 so a client that was offline for a few minutes and flushes its backlog still lands in full.

The client side of this protocol is src/lib/listenCredit.ts. consumedSeconds() reads the receipt: accepted and rejected seconds are removed from the local accumulator, deferred seconds are kept for the next flush, and a failed request (no receipt) consumes nothing. reconcileAccumulator() subtracts rather than assigns, because the accumulator kept ticking while the request was in flight, and caps the pending buffer at one hour (MAX_PENDING_LISTEN_SECONDS = 3600). The same module contains simulateServerCredit(), a faithful copy of the server rules that exists only so 34 unit tests can check the arithmetic; a guard test pins its constants to the edge function's.

Every read before the claim is fail closed. If any query errors, the function throws ReadFailedError and answers 500 db_read_failed with nothing written, and the client keeps its seconds. Before this rule, a failed profile read was treated as "no profile", so the function rebuilt XP, level and streaks from zero and wrote them back over the real values. After the claim, a failed read may only withhold XP or a reward, and a failed write is logged as partial_commit.

XP, levels and anti abuse

XP is not decorative here. A 30 day streak grants 7 days of PRO, reaching level 50 grants 30 days, and the monthly leaderboard top three earn PRO through the award_monthly_badges cron function. The technical overview sums this up as "XP is money".

The level curve is superlinear: the XP needed for level N is the sum of floor(100 * n^1.5) for n from 1 to N minus 1. Level 2 needs 100, level 3 needs 382, level 4 needs 901. It is implemented in both src/lib/xpUtils.ts (for the progress bar) and the edge function (authoritative), because Deno functions cannot import from src/.

XP has three nested daily caps: 60 listening XP per track, 480 listening XP in total (eight hours), and 1,000 from all sources. Hitting a cap writes an abuse flag. There are 19 flag types, grouped as rate and pace, caps, behavioural (same_track_farm, rapid_track_switch, impossible_daily_listen above 20 hours) and review related. Flags are deduplicated by a dedupe_key with an occurrences counter, and severity thresholds live in a data table, xp_flag_policy, so they can be retuned with an UPDATE instead of a deploy.

For multi account detection, the function stores a SHA-256 hash of the IP address salted with the current UTC date. Accounts sharing a machine on the same day can be correlated, but yesterday's hash cannot be linked to today's, and raw IPs are never stored.

Review XP (+50) passes five gates: ownership, one award per user per novel ever, at least 600 seconds of listening on that novel, at most three review awards per day, and at most three in ten minutes. Corrections for historical abuse are append only: admin_correct_review_xp() writes a negative ledger entry, defaults to a dry run, requires the typed word CORRECT and a reason, and can be undone by admin_revert_xp_correction(). admin_freeze_xp suspends accrual on a suspicious account without banning it.

Payments

Eleven functions handle PayPal and three handle Stripe. Money logic is kept in pure, tested helpers:

  • _shared/paypal_security.ts compares captured amounts in integer cents, never as floats, and requires status COMPLETED and a matching currency. resolveSubscriptionOwnership() denies when the PayPal custom_id, the stored subscription owner or the payment owner disagrees with the caller, and also denies when none of them exists: absence of evidence is denial.
  • PAYPAL_ENV must be exactly live or sandbox. There is no default, because a wrong default would either take real money into a test account or grant PRO for test payments.
  • Stripe webhooks are verified by hand with WebCrypto (the SDK's synchronous verifier does not fit Deno), checking both the HMAC signature and a five minute timestamp window to stop replays.
  • isSandboxBlocked() rejects all sandbox Stripe traffic once PAYMENTS_MODE=live, because production and sandbox share one database.
  • sanitizeReturnUrl() rejects scheme relative URLs like //evil.com, allows only http and https, requires the site origin in live mode, and returns the original string so Stripe's {CHECKOUT_SESSION_ID} placeholder is not percent encoded.
  • Cron endpoints (award_monthly_badges, reconcile_subscriptions) require an x-cron-secret header.

Covers and images

Covers are served from media.webaudiotv.com through Cloudflare Image Transformations. coverImageUrl(url, width) in src/lib/utils.ts rewrites a cover URL to /cdn-cgi/image/width=W,quality=75,format=auto,fit=scale-down/<path>, clamping width between 32 and 1600 pixels, when VITE_IMAGE_RESIZE is on. The median cover went from 3.0 MB to about 80 KB (AVIF at 480 pixels), and repeat requests hit the edge cache in under 0.1 s. A Cloudflare WAF (web application firewall) rule blocks audio and video file types on that public domain, so it serves images only.

Publishers, reviews and the MCP endpoint

Publishers apply through publisher_applications. An admin calls approve_publisher_application(), an RPC (a remote procedure call into a SQL function) that atomically creates the profile, grants the role and writes the audit log, so there is never an approved application with no role. The publisher workspace in src/components/publisher/ provides novel, section, track and tag management and Early Access controls.

Reviews support star ratings, replies, reactions and short voice notes. src/lib/reviewRanking.ts sorts and aggregates reactions; reviewReplies.ts batches reply loading after an audit found one request per review (an N+1 query pattern).

supabase/functions/mcp/ is generated by @lovable.dev/mcp-js from src/lib/mcp/. It exposes seven tools (search novels, get novel, list tracks, rankings, continue listening, get and save progress) over the Model Context Protocol, a standard for letting AI assistants call application functions.

Testing

There are three kinds of tests.

  • Pure logic tests for src/lib/ and _shared/ modules: listen credit arithmetic, stream access read sets, ticket signing, PRO entitlement, payment security, SSRF filters, player clock and interruption rules.
  • Handler tests run real edge function code against a fake service client (src/test/fakeServiceClient.ts). addListenTime.handler.test.ts fails each database read in turn and checks that nothing is written.
  • Guard tests (*.guard.test.ts) read source files and assert that a forbidden pattern has not returned, for example that stream_media never accepts a ?token= JWT, that startupGuard stays the first import, or that ranking SQL keeps its LIMIT inside the subquery. These exist because a streaming outage was once nearly "fixed" by restoring the insecure pattern.

Outside Vitest, tests/db/rig.sh up starts a throwaway local Postgres, loads stubs for Supabase's auth schema and extensions, and applies all 100 migrations in order. tests/db/access_matrix.sql then runs 48 checks as real PostgREST roles with JWT claims: signed out, two free users, a PRO user, two publishers and an admin. For example, it checks that publisher 2 cannot see publisher 1's private draft and that no role can read drive_file_url. tests/db/seed_scale.sql seeds production sized row counts, and tests/db/load/*.sql are pgbench (Postgres's benchmarking tool) workloads. tests/worker-e2e/ drives the real production build in a browser against the real Worker running locally in Cloudflare's workerd runtime, with a mock Supabase that can compress ticket lifetime to 60 seconds and simulate a dead Worker or a bad ticket.

Key Design Decisions and Trade-offs

  • Booth and door instead of presigned URLs. The design documents considered giving the browser a direct presigned R2 URL (a URL with a time limited signature from the storage provider). That would expose the object key, could not be capped at the entitlement's end, and would put access logic in two places. The Worker keeps one decision point (evaluateStreamAccess) and makes the Worker a dumb, auditable gate.
  • 15 minute tickets versus revocation. A ticket cannot be revoked once issued. The trade-off accepted is that an unscheduled revocation, such as a refund, takes up to 15 minutes to bite, and bytes already buffered or downloaded are never revoked. Scheduled ends are exact because the ticket is capped at them.
  • Six hour v1 tokens. Longer than ideal for security, but a short token resets the audio element on seek. The binding to one user and one track limits the damage.
  • Fallback by default. Any Worker misconfiguration means off, and any Worker failure moves the session back to the proxy. Cost savings never come at the price of playback.
  • .env is tracked in Git. Normally wrong, but it holds only three publishable Supabase values that are compiled into the bundle anyway, and Lovable's build reads .env from the repo. All real secrets live only in Lovable Cloud Secrets and are read with Deno.env.get().
  • Fail closed everywhere. A failed read is never "no row". That costs an occasional 500 but has prevented data corruption and accidental access.
  • Bound seconds, not requests. The old limiter allowed 12 requests per hour; a continuous listener was throttled after 12 minutes and every rejected flush destroyed real seconds. Bounding credited seconds against the wall clock is both fairer and harder to cheat.
  • Pure modules plus guard tests. Deno functions cannot run in Vitest, so logic is extracted into plain TypeScript and the deployed code is pinned to the model by source asserting tests.
  • Append only XP corrections. Rebuilding totals from the ledger was rejected because historical totals had been written directly and would silently move legitimate scores. Negative compensating entries keep the evidence and can be reverted.
  • UA sniffing in the player. Usually poor practice, but iOS Safari, iOS Chrome and desktop browsers really do behave differently around autoplay, playback rate and backgrounding.

Challenges and How They Were Solved

  • Black screen on deploy. A build without VITE_SUPABASE_URL crashed before React mounted. The startup guard became the first import and shows a clear configuration error.
  • JWT in the URL. Replaced with the two function flow and guarded by tests. When issue_stream_token was later committed but never deployed (Lovable does not reliably deploy new functions), the player showed "Couldn't authorize this track". The runbook in CLAUDE.md now requires calling every new or changed function and checking for a 404 before declaring a deploy done. A later audit found eight functions still running six week old code and redeployed them.
  • The public audio bucket. An audit found every audio file downloadable without signing in, through the custom media domain and an r2.dev development URL. Covers were moved to the firewalled domain, the dev URL was disabled, a WAF rule blocks audio on the media domain, and the ticket checking Worker became the only intended public path to audio.
  • Truncated uploads. Users reported chapters that stopped halfway and showed --:-- for duration. docs/incidents/2026-09-20-truncated-audio-uploads.md found three tells: object sizes that are exact multiples of 64 KB, a final MP3 frame cut in half, and a Xing header with zero frames (ffmpeg writes a placeholder and patches it at the end, which never happened). The size test alone identified 65 broken files out of 1,671 without downloading the library.
  • Leaderboard farming. Forensic queries showed the top account credited 16 to 21 hours a day by a looping player. The fix added the 16 hour daily cap, the three hour idle pause, and no credit while muted.
  • Review XP farming. Deleting and rewriting a review produced a new row id, so the old dedup check never matched and +50 XP could be earned repeatedly. Dedup now matches on novel_id and on any review the user holds for that novel, with listening and burst gates.
  • invoke never throws. supabase.functions.invoke returns errors in { data, error }, so a try/catch treated failures as success and discarded listened seconds. The receipt protocol fixed this.
  • Exposed email queue. Queue functions were callable with the public key because a migration revoked access only from PUBLIC, not from Supabase's anon and authenticated roles. That would have allowed reading password reset links. Fixed by 20261002010000_lock_email_queue_rpcs.sql.
  • Slow admin audit page. A per user aggregate ran over every profile before LIMIT, timing out at 8 seconds. Ranking first and aggregating after, with two new indexes, took it to 0.49 s in production and from 806 ms to 18 ms locally, with byte for byte identical output.
  • Domain outages that were not code. A lapsed hosting plan at the registrar rewrote the nameservers, and Lovable's domain check stuck on that bad reading and served 421 Project not found. Another morning showed grey skeleton cards that looked like a storage failure but were a backend restart. CLAUDE.md now documents diagnostic curl and dig commands for each signature so nobody "fixes" code during an infrastructure incident.

Security and Performance Notes

Security layers:

Layer What it enforces
RLS and column privileges Own rows only; drafts hidden; drive_file_url unreadable by browsers
Profile trigger Plan, XP, levels, streaks, PRO dates not client writable
SECURITY DEFINER functions Pinned search_path; admin checks; internal functions revoked from anon and authenticated
Edge functions JWT in header only; fail closed reads; idempotent listen claims; signed webhooks; cron secret
Media Private bucket; WAF blocks audio on the public domain; tickets bound to user, track, mode and expiry
Downloads fetch plus Blob with an Authorization header, never a token in the URL

Performance numbers reported in the README:

Metric Before After
Points Audit top 50 8.05 s timeout 0.49 s
Median cover image 3.0 MB about 80 KB
Audio first bytes (Range) 0.6 s via edge function 0.35 s via Worker
XP audit query, 50 rows (local) 806 ms 18 ms

A pgbench mix of progress saves, credit transactions and home page reads on the local rig sustained 11,300 to 12,800 transactions per second from 10 to 100 clients with zero errors; credit transaction p95 latency rose from 1.3 ms to 88 ms. A lock contention test of 50 clients updating the same 20 users ran 364,000 transactions with no lost seconds. The notes are honest that the laptop is not production hardware and that add_listen_time reads then writes, so truly concurrent flushes for one user could under count. Real peak demand is about 8 writes per second.

CS601C Computational Statistics Project

At a Glance

This is a reproducible regression study written in R. It asks three questions of three classic teaching datasets (College, Auto and Boston from An Introduction to Statistical Learning) and answers them with linear regression, lasso and regression trees. It began as a midterm project for CS601C at Pace University in Spring 2025 and was later reworked with a held-out test set, a mean-only baseline, residual diagnostics, unit tests and continuous integration. It is aimed at anyone learning how to evaluate a statistical model honestly, rather than reporting how well it fits the data it was trained on.

How It Works (Simple Version)

Imagine a student who wants to prove they can predict exam scores. If they write the questions and also see the answers before predicting, any score they get means nothing. So a fair teacher hides 20% of the questions in a locked drawer. The student practises on the other 80%, and even while practising they quiz themselves in rounds (cross-validation). Only at the very end does the teacher open the drawer and grade once.

This project does exactly that for each dataset:

  1. Load the CSV and check it (no missing values, numbers really are numbers, percentages are within 0 to 100).
  2. Split the rows 80/20 with a fixed random seed.
  3. Fit several models on the 80% part, comparing them with 10-fold cross-validation.
  4. Score every model once on the hidden 20%, next to a "dumb" model that always predicts the average.
  5. Write everything into an HTML report, and refuse to finish if any sentence in the report is no longer true.

Deep Dive

Data validation (R/helpers.R). validate_dataset() stops with a clear message if a required column is missing, contains NA (R's marker for a missing value) or is not numeric. The Auto loader treats "?" as missing because the raw ISLR file uses that symbol for unknown horsepower. The College loader checks the six percentage columns and found two impossible rows: one college reports a graduation rate of 118 and another reports 103% of faculty with PhDs. These rows are excluded in code; the raw CSV stays untouched, so the cleaning step is visible and reversible.

Reproducible randomness. Random splits are a classic source of "my numbers changed" bugs. The helper below runs an expression with a fixed seed and then restores whatever random state the caller had, so calling it never disturbs other code.

with_seed <- function(seed, expr) {
  had_seed <- exists(".Random.seed", envir = globalenv(),
                     inherits = FALSE)
  if (had_seed) old_seed <- get(".Random.seed", envir = globalenv())
  on.exit({
    if (had_seed) {
      assign(".Random.seed", old_seed, envir = globalenv())
    } else if (exists(".Random.seed", envir = globalenv(),
                      inherits = FALSE)) {
      rm(".Random.seed", envir = globalenv())
    }
  })
  set.seed(seed)
  expr
}

R stores its random number generator state in a hidden global variable called .Random.seed. Because R evaluates function arguments lazily (only when first used), expr is evaluated after set.seed(), inside the protected window. on.exit() registers cleanup code that runs even if expr throws an error.

The fitter pattern. Every model is written as a "fitter": a function that takes training data and returns a prediction function. This is a closure, which means a function that remembers the variables that existed when it was created.

fit_linear <- function(formula, inverse = identity) {
  function(train) {
    model <- stats::lm(formula, data = train)
    function(newdata) {
      inverse(unname(stats::predict(model, newdata)))
    }
  }
}

Because every model has the same shape, one function (cv_rmse) can cross-validate any of them, and one function (compare_models) can build the results table. The inverse argument handles transformed responses: the Auto model predicts log(mpg), so inverse = exp maps predictions back to miles per gallon before they are scored.

Statistics from first principles.

  • Ordinary least squares (OLS) fits a straight-line relationship y = b0 + b1*x1 + ... + bp*xp by choosing the coefficients that minimise the sum of squared residuals (a residual is actual minus predicted). In matrix form the solution is b = (X'X)^-1 X'y, which lm() computes with a QR decomposition for numerical stability.
  • Multicollinearity happens when predictors are strongly correlated with each other. In the Auto data, displacement, cylinders, horsepower and weight all measure "how big is the engine and car". The model can still predict well, but it cannot tell which of them deserves credit, so individual coefficients swing wildly. The project measures this with the variance inflation factor: regress predictor j on all the others, take that R squared, and compute VIF = 1 / (1 - R2). A VIF of 19.3 means the variance of that coefficient is 19 times larger than it would be with uncorrelated predictors. The code comment rightly notes that VIF is not a measure of importance.
  • Lasso adds a penalty lambda * sum(|b_j|) to the least-squares objective. The absolute value has a sharp corner at zero, so as lambda grows some coefficients become exactly zero, which performs variable selection. fit_lasso picks lambda with cv.glmnet using lambda.1se: the largest penalty whose cross-validated error is within one standard error of the best. That is the "one standard error rule", a deliberate preference for a simpler model when the evidence cannot separate two choices.
  • Regression trees (rpart) split the data repeatedly on the predictor and threshold that most reduce squared error, producing a flowchart whose leaves predict the mean of their rows. A tree grown with a tiny complexity parameter (cp = 0.001) overfits, so fit_tree reads rpart's built-in cross-validation table and prunes back to the cp with the lowest cross-validated error. Trees capture nonlinearity and interactions that a linear model misses, which is why the tree won on Boston housing values.
  • Metrics. RMSE (root mean squared error) punishes large errors heavily; MAE (mean absolute error) treats all errors linearly. Out-of-sample R squared is 1 - SSE/SST on the test set. It can be negative, which simply means the model did worse than predicting the mean.

Nested cross-validation. The lasso and the tree tune themselves with their own inner folds (tune_seed = 7). When cv_rmse evaluates them with the outer folds (cv_seed = 2025), each outer fold re-runs that tuning on only its training rows. That is nested cross-validation, and it prevents the tuning step from secretly seeing the fold it is scored on. All models share the same outer folds, so their CV scores are directly comparable.

cv_rmse <- function(fitter, train, response, folds) {
  stopifnot(length(folds) == nrow(train))
  sq_err <- numeric(nrow(train))
  for (k in sort(unique(folds))) {
    hold <- folds == k
    predict_fn <- fitter(train[!hold, , drop = FALSE])
    sq_err[hold] <- (train[[response]][hold] -
                       predict_fn(train[hold, , drop = FALSE]))^2
  }
  sqrt(mean(sq_err))
}

Note that the squared errors from all folds are pooled before the square root, rather than averaging ten per-fold RMSE values. Pooling weights every row equally even when folds differ in size by one row.

Response transformations and diagnostics. Boston per capita crime is extremely right skewed (most suburbs near zero, a few very high). A linear model on raw crim produces residuals that are far from normal, which breaks the assumptions behind p-values. Modelling log1p(crim), which is log(1 + crim) and safe at zero, raised the Shapiro-Wilk W statistic of the residuals from 0.51 to 0.91 (W is 1 for perfectly normal data). The diagnostic_data() helper draws the standard three panels: residuals versus fitted (curvature means a missed nonlinearity), a normal Q-Q plot (points off the diagonal mean non-normal residuals) and scale-location (a funnel shape means variance changes with the fitted value).

Key Design Decisions and Trade-offs

  • A small model search. Only linear, lasso and a single tree are compared. Random forests or boosting would likely score better, but the goal was interpretable comparisons on teaching data, not a leaderboard.
  • One train/test split. With 79 to 155 test rows, small differences are noise. The README says so explicitly and points readers to the CV column as the more stable comparison. Repeated splits would be more robust, at the cost of a less simple story.
  • Back-transforming with exp. Predicting log(mpg) and applying exp() gives an estimate of the median, not the mean, of mpg (because the log is not linear). A smearing correction would remove that small bias. The simpler choice still won clearly here.
  • Fixed seeds in one settings list. All seeds live in analysis_settings, so a reader can change one value to test how sensitive the results are to the split.
  • Crime model fitted on all rows. The crime question is about association, not prediction, so it uses all 506 rows and reports p-values instead of test error.

Challenges and How They Were Solved

  • Impossible values. The percentage range check surfaced the 118 and 103 values. Excluding them in code (not by editing the CSV) keeps the data provenance clean.
  • Stale numbers. Early README edits ("Update README.md" appears four times in the history) risked text drifting from results. The claims check and README test made drift a build failure.
  • CI on Linux. The workflow comment notes that the fs package used by rmarkdown links against libuv on Linux, so the job installs libuv1-dev first. The workflow also fails if the rendered HTML contains any ## Warning lines, so silent R warnings cannot reach the published report.

Security and Performance Notes

GitHub Actions steps are pinned to full commit SHAs (for example actions/checkout@3d3c42e...), which protects against a moved or compromised tag. The workflow runs with contents: read by default and grants pages: write and id-token: write only to the deploy job. renv.lock pins every package version so the report renders identically on a clean runner.

CS601C Final Project

At a Glance

This is the capstone for the same course: a single 1,638-line R Markdown document answering three exam questions on three datasets. How It Works (Simple Version)

Think of it as three separate detective cases. In each case the detective first looks at the evidence (summaries, histograms, correlation heatmaps), then forms a hypothesis ("small companies pay more per user", "spam messages are longer"), then runs a formal test that says how surprising the evidence would be if the hypothesis were false. The cybersecurity case adds a twist: because all 1,217 organisations are available, the detective can pretend to see only a sample of 100 and then check whether the sample-based estimate actually caught the true answer.

Deep Dive

Question 1: regression and variable selection. The cost data has five predictors (security staff, attacks, databases, privileged users, users) and the response Cost P/M. janitor::clean_names() turns awkward headers like Cost P/M into cost_p_m. The analysis fits lm(cost_p_m ~ ., data), where the dot means "all other columns", checks VIF with car::vif, and then runs step(full_model, direction = "both"). Stepwise selection adds or drops one predictor at a time, keeping the change that lowers AIC (the Akaike Information Criterion, a score that rewards fit but charges a penalty of 2 per parameter). It is quick but greedy, and p-values from the final model are optimistic because the same data chose the variables.

Question 1: confidence intervals three ways. This is the statistical heart of the project.

set.seed(99)
iterations <- 1000
z <- qnorm(0.975)
coverage_rate <- replicate(iterations, {
  samp <- dplyr::sample_n(cyber_data_clean, sample_size)
  mean_val <- mean(samp$cost_p_m)
  se_val <- sd(samp$cost_p_m) / sqrt(sample_size)
  ci <- c(mean_val - z * se_val, mean_val + z * se_val)
  true_mean >= ci[1] && true_mean <= ci[2]
})
mean(coverage_rate)  # Expected about 0.95

A 95% confidence interval is a recipe that, if repeated on many samples, captures the true value 95% of the time. It does not mean "95% chance the truth is in this one interval". The standard error s / sqrt(n) measures how much a sample mean would wobble from sample to sample, and the Central Limit Theorem says that wobble is roughly normal for large n, which justifies mean +/- 1.96 * SE (1.96 is qnorm(0.975)). The simulation above checks that promise empirically: draw 1,000 samples of 100, build an interval from each, and count how many contain the real population mean. This is the best way to understand what "95% confidence" really means.

The bootstrap is the second method. It resamples the one observed sample with replacement 1,000 times, computes the mean each time, and takes the 2.5th and 97.5th percentiles. It needs no normality assumption; the sample stands in for the population. Part G then repeats intervals across several sample sizes to show that width shrinks with 1/sqrt(n): to halve the width you need four times as many observations.

Question 1: Welch's t-test. The project creates Cost_Per_User and labels companies with fewer than 1,000 users as "Small". t.test(..., var.equal = FALSE) runs Welch's test, which compares two means without assuming the groups have equal variance. It adjusts the degrees of freedom with the Welch-Satterthwaite formula. This is the right default, since small and large companies almost certainly differ in spread.

Question 2: hypertension. The data has binary predictors (male, smoker, BP medication, diabetes) and continuous ones (age, cholesterol, systolic and diastolic BP, BMI, heart rate, glucose), with a 0/1 Risk response. Two tests stand out:

  • chisq.test(table(bpmeds, risk)) is a chi-square test of independence. It compares observed counts in each cell of the 2 by 2 table with the counts expected if medication and risk were unrelated (row total times column total divided by grand total). For 2 by 2 tables R applies Yates' continuity correction by default, which makes the test slightly conservative.
  • t.test(glucose ~ risk) compares mean glucose between risk groups.

The project also fits lm(risk ~ age + sysbp + bmi + heartrate + glucose). A linear model on a 0/1 outcome is called a linear probability model. It is easy to read, but it can predict probabilities below 0 or above 1 and its residuals cannot be normal. Logistic regression (glm(..., family = binomial)) is the standard tool here. The "top 3 predictors" ranking fits one simple regression per variable and sorts by adjusted R squared, which finds the strongest single correlates but ignores overlap between them (systolic and diastolic pressure carry much of the same information).

Question 3: SMS spam. Messages are read with read.delim(..., sep = "\t", header = FALSE) and tokenised with tidytext::unnest_tokens, which splits text into one word per row; stop words such as "the" are removed with an anti-join. The most interesting analysis is a smoothed spam-to-ham ratio:

spam_ham_ratio <- sms_words %>%
  count(type, word) %>%
  pivot_wider(names_from = type, values_from = n,
              values_fill = list(n = 0)) %>%
  mutate(ratio = (spam + 1) / (ham + 1),
         total_occurrence = spam + ham) %>%
  filter(total_occurrence > 5) %>%
  arrange(desc(ratio)) %>%
  head(10)

Adding 1 to both counts is Laplace (add-one) smoothing. Without it a word seen only in spam would have an infinite ratio. This ratio is the core intuition of a Naive Bayes spam filter, which multiplies such per-word likelihood ratios together (in practice, adds their logs) to score a whole message.

The spam proportion is estimated from a random sample of 300 with the Wald interval p +/- 1.96 * sqrt(p(1-p)/n). With p near 0.13 and n = 300 that is acceptable, but for small samples or proportions near 0 or 1 the Wilson interval (prop.test) has much better coverage.

A real bug worth learning from. The one-sided length test reads:

t.test(length ~ type, data = sms_data,
       alternative = "greater")

With a formula, R orders groups by factor level, and factor() sorts levels alphabetically: ham then spam. alternative = "greater" therefore tests "mean of ham is greater than mean of spam", the opposite of the stated hypothesis. Because spam is in fact longer, this test returns a p-value near 1, and the write-up's interpretation ("a low p-value confirms spam is longer") does not match the code. The fix is alternative = "less", or relevelling with factor(type, levels = c("spam", "ham")). It is a common trap with one-sided tests in R.

Key Design Decisions and Trade-offs

  • One long document. Everything lives in a single Rmd, matching the exam format. Libraries are loaded again in many chunks, which is harmless but noisy. The midterm project's later refactor into helpers.R plus a report shows the alternative.
  • Classical and resampling side by side. Showing a z-interval, a bootstrap interval and an empirical coverage check together is a strong teaching choice, because it validates theory against simulation.
  • Population available. Because the "population" is just the full file, coverage could be verified directly. In real work the truth is unknown, which is exactly why the coverage simulation is valuable as a lesson.

Challenges and How They Were Solved

  • Messy headers. janitor::clean_names() standardised Cost P/M and similar names.
  • Missing values in health data. Regression chunks use na.omit() on the selected columns; this silently drops rows, so different analyses in Question 2 can use different subsets.
  • Reproducibility. Seeds are set before each sampling step (42, 99, 100). However, setwd("D:/Computational Statistic/Final Project") hard-codes a Windows path, so the document will not knit on another machine without edits. The later midterm rework solved this with a project-root finder.

Security and Performance Notes

The SMS corpus includes real phone numbers inside spam messages; it is public research data, but it should not be republished in new contexts. The datasets are small, so performance is not a concern; the 1,000-iteration simulations finish in seconds.

Distance Conversion Tool (PaceLab)

At a Glance

This repository started as a 78-line interactive R script that converted kilometres to miles for a university course. It was then rebuilt into PaceLab, an R package that reads GPX files from running, cycling and hiking apps and reports accurate distance, kilometre and mile splits, pace, elevation gain and a GPS data quality report. It solves a real problem: GPS recordings contain spikes, clock glitches and jitter that inflate distance and climbing, and most apps never show why. PaceLab shows raw and cleaned numbers side by side and documents every rule, through an R API, a Shiny dashboard and a REST API.

How It Works (Simple Version)

Picture a running coach with a notebook of GPS dots, one per second. Some dots are obviously wrong: one teleports a kilometre away and back, one has a timestamp from the future, two are exact copies. The coach crosses out each bad dot and writes why in the margin, but never moves a dot. Then the coach walks along the remaining dots with a measuring tape that understands the Earth is round, marks the exact moment each kilometre and mile was passed, and counts real hills while ignoring the tiny wobble of the altimeter. That is PaceLab: parse, clean, measure, split, summarise.

The original converter still exists at tag v0-coursework. It used a repeat loop with readline() and the approximate factor 0.621371. The rebuilt convert_distance() is vectorised and uses exact definitions (1 mile = 1609.344 m by the 1959 international agreement).

Deep Dive

GPX parsing (R/gpx.R). GPX is an XML format: a <gpx> root holding <trk> tracks, each with <trkseg> segments of <trkpt lat=".." lon=".."> points that contain <ele> and <time>. Different apps use different XML namespaces, so the XPath queries use local-name() to match elements regardless of namespace prefix. Segments matter: a device starts a new segment after a pause or signal loss, and no distance should be counted across that gap.

Great-circle distance (R/geo.R). The shortest path between two points on a sphere is an arc of a great circle. The haversine formula computes it stably for small distances, where the older spherical law of cosines suffers from rounding error:

haversine_m <- function(lat1, lon1, lat2, lon2,
                        radius = EARTH_RADIUS_M) {
  to_rad <- pi / 180
  dlat <- (lat2 - lat1) * to_rad
  dlon <- (lon2 - lon1) * to_rad
  h <- sin(dlat / 2)^2 +
    cos(lat1 * to_rad) * cos(lat2 * to_rad) * sin(dlon / 2)^2
  h <- pmin(pmax(h, 0), 1)
  2 * radius * asin(sqrt(h))
}

h is the haversine of the central angle (haversine(x) = sin squared of x/2). Clamping h to the range 0 to 1 matters for antipodal points, where floating-point rounding can push it to 1.0000000001 and make asin return NaN. The radius is the IUGG mean Earth radius, 6,371,008.8 m, computed as (2a + b) / 3 from the WGS84 ellipsoid axes. The code comment notes that a sphere with this radius stays within about 0.5% of the true ellipsoidal distance, well below typical GPS error. Because the function uses vector arithmetic, step_distance() computes every step of a 100,000-point track in one call by pairing lat[-n] with lat[-1] (all points except the last, against all except the first).

GPS cleaning (R/clean.R). The cleaner applies five rules in a fixed order and records a reason for each rejection. Two are especially clever:

  • time_spikes() finds an isolated clock glitch: a timestamp later than its next neighbour while the previous neighbour is earlier than that next one. "The neighbours agree, the point does not." Detecting this before the ordering check means one bad stamp cannot invalidate everything after it.
  • flag_speed_spikes() is a small state machine. It keeps an anchor (the last good point) and rejects any point that would require a speed above the sport limit (run 12 m/s, ride 30 m/s, hike 7 m/s; generous on purpose). But a real relocation, for example after a tunnel, also looks like a spike. So rejected points are held in pending, and if relock_points (default 3) of them agree with each other at a plausible speed, the receiver has genuinely moved: they are restored and a new segment starts at the jump, so the jump adds no distance. If the run of good points before the jump was shorter than 3, the earlier run is treated as the glitch instead, which handles the classic bad first fix at latitude 0, longitude 0.

If more than a quarter of the time steps go backwards, the file was probably exported in reverse, so it is sorted by time first. The stress tests found that a reversed GPX file originally lost all of its points; this rule is the fix.

Splits with interpolation (R/splits.R). A one-second GPS step rarely lands exactly on the 1 km mark. Assigning the whole step to one split would make split times jitter. Instead the code builds cumulative distance and interpolates the time at which each boundary was crossed:

crossing_times <- function(cum_m, t, targets) {
  first <- !duplicated(cum_m)
  stats::approx(cum_m[first], t[first], xout = targets,
                rule = 2, ties = "ordered")$y
}

approx() is linear interpolation. Removing duplicated cumulative distances (standing still) makes the boundary time the first moment the runner reached it. The last, shorter split is kept and marked partial, and it ends at the final timestamp, so split times always add up to elapsed time. Pace is seconds per unit; pace_consistency() reports the coefficient of variation (standard deviation divided by mean, in percent) of the full splits, and split_trend() interpolates the time at exactly half the distance to label a run as negative split (faster second half), positive or even within a 1% band.

Elevation (R/metrics.R). Summing every positive elevation difference wildly overstates climbing, because barometric and GPS altitude jitter by a metre or two each second. On the synthetic sample the naive sum gives 2,214 m of climbing against a true 48 m. PaceLab applies an 11-point running median (stats::runmed), which removes spikes without blurring real slopes as a moving average would, and then a hysteresis counter: climbing is only committed once the trace has reversed by at least 3 m from its extreme. Hysteresis is the same idea as a thermostat that switches on at 19 degrees and off at 21 so it does not flicker. The result on the sample is 55 m.

Untrusted input everywhere. GPX files reveal where people live and train, and XML parsers are a classic attack surface. parse_gpx() enforces a byte limit and a point limit, rejects any document containing <!DOCTYPE (scanning the whole buffer, because a DOCTYPE can follow a very long comment), and parses with libxml2's NONET option so the parser can never fetch a URL. Rejecting DOCTYPE blocks both XXE (XML External Entity attacks, where an entity reads a local file or a URL) and "billion laughs" entity expansion, where nested entities explode into gigabytes of text.

The REST API (R/api.R). Endpoints are GET /health, GET /convert and POST /analyze. Two hardening details stand out. First, every endpoint sets parsers = "octet" so the body is read as raw bytes. The code comment explains why: plumber's default parser set includes rds, which would call R's unserialize on attacker-supplied bytes, a deserialisation vulnerability. Second, a stress test found that a %00 (NUL byte) in a query string crashed plumber before any handler ran. The fix is a pre-route hook:

neutralise_nul <- function(req) {
  qs <- req$QUERY_STRING
  if (length(qs) == 1L && grepl("%00", qs, ignore.case = TRUE)) {
    req$QUERY_STRING <- gsub("%00", "%EF%BF%BD", qs,
                             ignore.case = TRUE)
  }
  invisible(NULL)
}

It swaps the NUL for U+FFFD, the Unicode replacement character, so the value stays invalid and validation returns a clean 400. It never silently turns 1%002 into 12. Status codes are deliberate: 413 for oversized bodies, 415 for the wrong content type, 422 for well-formed requests whose GPX is unusable, and a generic 500 that never echoes internal details.

Dashboard and export. The Shiny app deletes the temporary upload file right after reading it, and the CSV export runs csv_safe(), which prefixes a quote to any text cell starting with =, +, -, @, tab or carriage return. That blocks CSV formula injection, where a spreadsheet would execute a cell like =HYPERLINK(...). Leaflet is vendored, so no CDN is contacted.

Packaging. The Dockerfile is two-stage: the build stage restores renv.lock from Posit Package Manager binaries and installs the package, then the runtime stage copies only the installed library, runs as a non-root pacelab user, and uses tini as PID 1. In Linux, PID 1 does not get default signal handlers, so without tini a docker stop waits 10 seconds and then kills R; the stress tests found exactly that delay. A HEALTHCHECK probes whichever service is running.

Key Design Decisions and Trade-offs

  • Remove, never move. Cleaning only deletes points with a reason. Smoothing coordinates would reduce jitter (the cleaned sample is still 2% long), but it would make results harder to audit. The README lists optional smoothing on the roadmap, reported separately.
  • Sphere, not ellipsoid. Vincenty's ellipsoidal formula is more exact but iterative and slower; 0.5% is below GPS noise.
  • Only xml2 as a hard dependency. Shiny, plumber and ggplot2 are in Suggests, so the analysis core installs light.
  • Generous speed limits. Conservative thresholds risk keeping some bad points, but they never delete a real sprint.

Challenges and How They Were Solved

The commit history tells the rebuild story: refactor the coursework converter into a package core, add GPX parsing and cleaning, add Shiny and plumber, then add Docker and CI, then adversarial stress tests. The README reports that two rounds of stress testing (bench/stress.R, bench/stress-services.R) found five defects the normal suite missed, including the NUL byte crash, the reversed file losing all points and the 10-second container shutdown. Each fix has a regression test.

The dashboard caps uploads at 25 MB and 250,000 points, the API at 10 MB. Not included: authentication, rate limiting and TLS, which the README says belong in a reverse proxy. Project_01: Password Strength Checker

How It Works (Simple Version)

You type a password into a masked box. The app sorts each character into one of five bins (lowercase, uppercase, digits, spaces, everything else), counts how many bins are non-empty, and turns that 0 to 5 score into a progress bar, a verdict and a list of tips. It is like a checklist at a gym: "did you do legs, arms, back, core, cardio?" It counts variety, not effort.

Architecture

 Browser  <-- websocket -->  Streamlit server
                                 |
                   reruns password_checker.py
                   top to bottom on every input
                                 |
            st.text_input(type="password") -> pw
                                 |
                          analyze(pw)
               counts, score 0..5, remark text
                                 |
     st.progress, st.metric columns, tips list

Streamlit's execution model is unusual: there are no callbacks. Every time a widget changes, the whole script reruns from the top, and the widget calls return their current values.

Deep Dive

The whole program is one file, Project_01/password_checker.py. The core function:

def analyze(pw: str):
    lower = sum(c in string.ascii_lowercase for c in pw)
    upper = sum(c in string.ascii_uppercase for c in pw)
    digits = sum(c in string.digits for c in pw)
    spaces = pw.count(" ")
    special = len(pw) - lower - upper - digits - spaces
    strength = sum([lower>0, upper>0, digits>0,
                    spaces>0, special>0])
    ...
    return lower, upper, digits, spaces, special, strength, remark

sum() over a generator of booleans works because Python's bool is a subclass of int (True == 1). The "special" count is computed by subtraction, so it is "everything else". A side effect worth knowing: string.ascii_lowercase only covers a to z, so accented letters such as e with an acute accent, or any non-Latin script, are counted as special characters.

The UI calls st.progress(strength/5), shows verdicts from "Very bad" to "Very strong", and lists tips such as "Use at least 12 to 16 characters". Note that length only appears as a tip; it does not affect the score. A 4-character password like aA1! scores 4/5, while a 30-character lowercase passphrase scores 1/5.

Key Design Decisions and Trade-offs

The honest footer, "Checks composition only; does not validate against breached-password lists", shows awareness of the limits. Modern guidance (NIST SP 800-63B) actually discourages composition rules and recommends length plus screening against known breached passwords. Password strength is better estimated as entropy, the number of guesses an attacker needs. A naive estimate is length * log2(alphabet size), but real attackers use dictionaries and patterns, which is why tools such as zxcvbn model common words, keyboard walks and substitutions.

Challenges and How They Were Solved

The README references a requirements.txt and a repository name (Password_Strength_Checker) that do not exist in this repo, so a fresh clone needs pip install streamlit by hand. The README's roadmap lists the natural next steps: an entropy estimate, a Have I Been Pwned k-anonymity check (send only the first 5 characters of the SHA-1 hash, compare suffixes locally), pytest tests and CI.

Security and Performance Notes

The input uses type="password" so it is masked on screen, but it is still sent to the Streamlit server over its websocket. The README correctly warns not to type real passwords into the public Codespaces demo. Performance is trivial: four linear passes over a short string.

At a Glance

This began as a July 2025 lab report: install NASM on Ubuntu under WSL 2 and build three tiny programs (hello, add, star). Rebuilding them exactly as written exposed an executable stack, a calling convention violation, an oversized memory load and programs that exited successfully even when output failed. The repository is that lab rebuilt as a reproducible systems and binary hardening project, plus asm-hexdump, a roughly 300-line syscall-only clone of hexdump -C -v tested byte for byte against reference implementations.

How It Works (Simple Version)

A CPU only understands numbered instructions that move numbers between a few tiny storage slots (registers) and memory. Assembly is the human-readable spelling of those instructions. A program that wants to print text cannot touch the screen itself; it fills specific registers with "I want service number 1 (write), on file 1 (the terminal), from this address, for this many bytes" and then executes syscall, which is like ringing a bell for the operating system kernel. The kernel does the work and leaves a result in a register.

When assembly calls a library function like printf, both sides must follow a contract (the calling convention) about which registers carry arguments and how the stack must be arranged. Break the contract and things may still work by luck, which is exactly what happened in the original lab.

Deep Dive

Registers. x86-64 has sixteen 64-bit general-purpose registers: rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, r8 to r15. Each has smaller views: eax is the low 32 bits of rax, ax the low 16, al the low 8. A rule used constantly in this code: writing a 32-bit register such as mov edi, 1 zeroes the upper 32 bits of rdi. That is why the programs write mov eax, SYS_exit instead of mov rax, ...; the encoding is shorter and the result is identical. rsp is the stack pointer, rip the instruction pointer.

Linux system calls. On x86-64 Linux, the syscall number goes in rax and up to six arguments go in rdi, rsi, rdx, r10, r8, r9. The syscall instruction switches to the kernel. On return, rax holds the result, or a negative error code from -4095 to -1 (the negated errno). The CPU itself overwrites rcx (with the return address) and r11 (with the saved flags), so those two are always clobbered. include/linux.inc defines the numbers: read 0, write 1, open 2, close 3, exit 60. The file notes these are x86-64 specific; i386 and arm64 use different numbers.

hello.asm shows the whole pattern in a few lines:

default rel
section .rodata
msg:        db "Hello, World!", 10
msg_len     equ $ - msg

section .text
global _start
extern write_all
_start:
    mov     edi, STDOUT_FILENO
    lea     rsi, [msg]
    mov     edx, msg_len
    call    write_all
    mov     edi, EXIT_OK
    test    rax, rax
    jz      .exit
    mov     edi, EXIT_FAILURE
.exit:
    mov     eax, SYS_exit
    syscall

db emits bytes and 10 is the newline. $ - msg is the current address minus the label, so the assembler computes the length. _start is the real entry point the kernel jumps to; there is no main because there is no C runtime. default rel makes [msg] a RIP-relative address, which matters for position independence (below).

Short writes and error handling (src/io.asm). write(2) is allowed to write fewer bytes than requested, for example to a pipe or when a signal arrives. The original lab ignored the return value. write_all loops until everything is written, retries EINTR (interrupted by a signal), and reports a zero-byte result as -EIO instead of spinning forever:

write_all:
.loop:
    test    rdx, rdx
    jz      .done
    mov     eax, SYS_write
    syscall             ; kernel preserves rdi/rsi/rdx
    test    rax, rax
    js      .failed
    jz      .no_progress
    add     rsi, rax    ; skip what was written
    sub     rdx, rax
    jmp     .loop
.failed:
    cmp     rax, -EINTR
    je      .loop
    ret                 ; rax = -errno

test rax, rax ANDs the register with itself to set flags without storing anything; js jumps if the sign flag is set (negative result, an error) and jz jumps on zero. The programs now exit 1 when stdout is full (>/dev/full) or closed; the originals exited 0.

The System V AMD64 calling convention. When one function calls another, Linux follows the System V ABI (Application Binary Interface):

Role Registers
Integer/pointer arguments 1 to 6 rdi, rsi, rdx, rcx, r8, r9
Return value rax (and rdx for 128-bit)
Callee-saved (must be preserved) rbx, rbp, r12, r13, r14, r15, rsp
Caller-saved (may be clobbered) rax, rcx, rdx, rsi, rdi, r8 to r11
Variadic calls al = number of vector registers used
Stack rsp must be a multiple of 16 at each call

Note the fourth argument differs: rcx for functions but r10 for syscalls, because syscall destroys rcx. asm-hexdump uses the callee-saved registers on purpose: rbx is the read cursor, rbp the bytes left, r12 the input file descriptor, r13 the file offset, r14 the bytes collected in the current line and r15 the bytes pending in the output buffer, so they survive calls to the helpers.

The alignment bug. call pushes an 8-byte return address. So if rsp is 16-aligned at the call, it is 16k + 8 when the callee starts. The original add.asm called printf straight from main without adjusting, so rsp % 16 == 8 at the call. That is a violation; it only crashes if the callee uses an instruction that requires alignment (such as movaps on SSE registers), and this glibc path did not. The fixed main:

main:
    sub     rsp, 8          ; rsp % 16: 8 -> 0
    mov     esi, [num1]     ; 32-bit load of a dd value
    mov     edx, [num2]
    mov     ecx, esi
    add     ecx, edx
    lea     rdi, [fmt]
    xor     eax, eax        ; al = 0 vector regs (variadic)
    call    printf wrt ..plt
    test    eax, eax
    js      .failed
    xor     edi, edi        ; fflush(NULL)
    call    fflush wrt ..plt

The same fix also corrects an operand-size bug: num1 is declared with dd (4 bytes), but the original did mov rax, [rel num1], an 8-byte load that also read num2. And fflush(NULL) is called before returning, because when stdout is a file or pipe it is fully buffered, so a write error would otherwise happen silently inside exit().

Rather than hoping a misaligned call crashes, tests/abi_probe.asm proves alignment. The test binary is linked with -Wl,--wrap=printf, which redirects calls to printf into __wrap_printf and makes the real one available as __real_printf:

__wrap_%1:
    lea     r11, [rsp + 8]  ; r11: caller-saved, never an argument
    test    r11b, 15
    jnz     misaligned
    jmp     __real_%1 wrt ..plt

On entry rsp + 8 should be 16-aligned. r11 is chosen because it is scratch and never carries an argument, so jumping on to the real function leaves every argument register (including al) untouched. A known-bad copy of the original code, security/misaligned_call.asm, must make this probe exit 70.

Process entry and the stack. At _start the kernel has laid out argc at [rsp], then the argv pointers. So asm-hexdump reads argc from [rsp] and argv[1] from [rsp + 16]. It detects the argument - with cmp word [rdi], '-': a 2-byte compare of the dash and its NUL terminator. The die routine can be reached by jmp from any call depth, so it starts with and rsp, -16 to force alignment before calling helpers.

put_hex and bit tricks. To print a number in hex, you need the digit count. bsr rax, rdi (bit scan reverse) returns the index of the highest set bit; shifting it right by 2 (divide by 4, since each hex digit holds 4 bits) and adding 1 gives the digit count. cmovb (conditional move if below) raises it to the minimum width without a branch. Digits are then filled from the right by masking the low nibble (and r9d, 0x0f) and indexing the "0123456789abcdef" table.

asm-hexdump buffering. Reading and writing one byte at a time would cost two syscalls per byte. The tool reads 4 KiB chunks into inbuf, copies bytes into a 16-byte line accumulator (a hexdump line can span two reads, or many short reads from a pipe), formats a line when 16 bytes are collected, and appends it to a 4 KiB outbuf. reserve_line flushes only when fewer than 96 bytes remain, the longest possible line. Error messages come from a packed table of records (errno byte, length byte, text) instead of a pointer table. The comment explains why: a static PIE has no dynamic loader to apply relocations, and pointers in .rodata would need them.

ELF hardening. ELF is the Linux executable format. Its program headers tell the kernel how to map the file into memory with what permissions.

  • NX / non-executable stack. PT_GNU_STACK declares whether the stack may be executed. Every object needs a .note.GNU-stack section, or GNU ld assumes the worst. The original add linked with the warning "missing .note.GNU-stack section implies executable stack" and got RWE. The repo adds a NONEXEC_STACK macro to every file, and the linker flag --error-execstack makes a missing note a build failure.
  • PIE and ASLR. A Position Independent Executable can be loaded at any address, so ASLR (address space layout randomisation) can move it each run, making memory addresses unpredictable to an attacker. That requires RIP-relative addressing (lea rsi, [msg] with default rel) instead of absolute addresses, and calling library functions through the PLT (call printf wrt ..plt). The PLT (procedure linkage table) is a small stub table that jumps through the GOT (global offset table), which the dynamic loader fills with real library addresses. The original used -no-pie to silence the link error, which gave up ASLR.
  • RELRO. With -z relro -z now, the loader resolves every symbol at startup (BIND_NOW) and then makes the GOT read-only, so an attacker with a write primitive cannot overwrite a function pointer there.
  • Static PIE. hello, star and asm-hexdump use ld -pie --no-dynamic-linker: position independent, but with no interpreter. The Makefile passes -z norelro for them, with the reasoning that RELRO is applied by the dynamic loader they do not have, so the header would only make checkers report protection that never happens.

scripts/check-elf.sh enforces all of this with readelf: ELF64 x86-64, ET_DYN with DF_1_PIE, GNU_STACK exactly RW, no writable and executable LOAD segment, no TEXTREL, plus per-policy checks for interpreter and RELRO. The gate is itself tested against binaries that must fail it. The Python tests go further at run time: they read the kernel's real [stack] permissions from /proc, confirm the PIE load address changes across runs, and assert each program's exact syscall set with strace.

Key Design Decisions and Trade-offs

  • No libc for three programs. Raw syscalls make every instruction visible and the binaries tiny, at the cost of writing write_all and an errno table by hand. add keeps libc on purpose, to teach the calling convention.
  • Make warnings errors at every layer. nasm -w+all -Werror, ld --fatal-warnings --error-rwx-segments -z text: insecure code cannot be built quietly.
  • Preserve history. The first commits transcribe the original programs verbatim, so git log -p src/ shows each fix. The original PDF is kept unchanged with an errata table.
  • Compare against a compiler. docs/compiler-output.md shows that GCC -O2 emits the same sub rsp, 8 at the top of main, and uses a tail call (jmp __printf_chk@PLT) in a helper so no alignment adjustment is needed there.

Challenges and How They Were Solved

The errata in report/README.md list what re-testing found. Two documentation claims were wrong: star prints three lines (*, **, ***), not ******, and garbage output is never caused by a "missing NUL terminator", because write(2) takes an explicit length. Four code issues were real: the executable stack, the missing stack header on hello (kernels before 5.8 treat that as "everything readable is executable"), the misaligned printf call and the 8-byte load. Running on macOS was another challenge: Apple Silicon cannot run Linux x86-64 binaries natively, so a Dockerfile builds under linux/amd64 emulation, where tests that need a real kernel (stack permissions, ASLR, strace, gdb) are skipped; CI runs them all natively and treats skips as failures.

Security and Performance Notes

The security demos (make security-demo) build each insecure variant next to its hardened twin: execstack-bad gets an rwxp stack mapping, execstack-good gets rw-p; whereami-nopie loads at 0x401000 every run while the PIE moves. make stress runs about 2,900 seeded cases (2,067 input sizes, six byte patterns, 300 piped inputs, a 16 MiB file) against a Python reference and the system hexdump -C -v.

This chapter covers nine projects about protecting computers and moving packets between them. Automating InfoSec (WinSecKit)

At a Glance

Automating InfoSec started as four graded Windows security labs from a graduate course (Pace University, CYB 631). It grew into WinSecKit, a PowerShell module with nine commands. The module reads Windows event logs for signs of attack, audits a host against a small hardening baseline, signs scripts, and writes the results to a self-contained HTML report. It is for defenders who want repeatable, tested checks instead of one-off console commands. The repository also documents a real incident: a leaked encryption key in its own git history, which was purged and then guarded against.

How It Works (Simple Version)

Think of a building with a security guard and a building inspector. The guard watches the visitor log. If one visitor fails to badge in five times in five minutes, or someone tears pages out of the log, the guard raises an alarm. That is the detection half: Windows writes an event for every logon failure, account creation and log wipe, and WinSecKit reads those events and flags suspicious patterns.

The inspector walks the building with a checklist: are the fire doors shut, is the alarm switched on? That is the baseline half. WinSecKit checks six settings (firewall on, SMBv1 off, PowerShell logging on, and so on). It reports which ones fail, and if asked, it fixes them and checks again to prove the fix worked.

Both halves hand their results to a report writer, which produces one HTML page you can open offline or email.

Deep Dive

Windows event logs. Windows records security-relevant actions as numbered events in named logs. Each event has an ID, a timestamp, a machine name, a message and structured data fields. The project's detections depend on six of them:

Event ID Log Meaning
4625 Security An account failed to log on
4720 Security A user account was created
4732 Security A member was added to a security-enabled local group
4104 Microsoft-Windows-PowerShell/Operational PowerShell script block logged
7045 System A new service was installed
1102 Security The audit log was cleared

The comment at the top of Data/detections.psd1 warns that 4104 and 7045 are not in the Security log. A query against the wrong log returns nothing, and a detection that returns nothing looks like a pass. That is why Test-SecurityDetection matches on both Id and LogName.

MITRE ATT&CK. ATT&CK is a public catalogue of attacker techniques, each with an ID. For example T1110 is Brute Force and T1070.001 is Clear Windows Event Logs. Mapping each detection to a technique tells an analyst what the attacker was likely doing, not only which event fired.

Detections as data. Each rule is a PowerShell data file (.psd1) entry, so adding a rule never means changing code. The strategy field picks one of three evaluators: Presence (any matching event is a finding), Threshold (N events in a time window, grouped by a field) and Content (the message matches a regex). Here is the content rule for suspicious script blocks:

@{
    Id             = 'WSK0004'
    LogName        = 'Microsoft-Windows-PowerShell/Operational'
    EventId        = @(4104)
    Strategy       = 'Content'
    PatternList    = @(
        '-enc(odedcommand)?\s',
        'FromBase64String',
        'DownloadString',
        'IEX\s*\(',
        'System\.Net\.WebClient',
        'Bypass\s+-Scope',
        'HiddenWindowStyle|-w\s+hidden'
    )
    Severity       = 'High'
    Technique      = 'T1059.001'
}

These patterns are the fingerprints of a "download cradle": PowerShell code that fetches a payload from the internet (DownloadString, WebClient) and runs it in memory (IEX, short for Invoke-Expression), often hidden behind Base64 encoding (-enc, FromBase64String).

The sliding window. The brute-force rule (WSK0001) fires when one account has five or more failed logons inside five minutes. A naive approach buckets time into fixed five-minute blocks, but then a burst of three at 10:04 and three at 10:06 lands in two buckets and is missed. The code uses a two-pointer sliding window over sorted timestamps instead:

$times = @($group.Group.TimeCreated | Sort-Object)
$window = [timespan]::FromMinutes($det.WindowMinutes)
$start  = 0
for ($end = 0; $end -lt $times.Count; $end++) {
    while (($times[$end] - $times[$start]) -gt $window) {
        $start++
    }
    $inWindow = $end - $start + 1
    if ($inWindow -ge $det.MinimumCount) {
        ConvertTo-WinSecKitFinding -Detection $det `
            -Count $inWindow -FirstSeen $times[$start] ...
        break   # one finding per group
    }
}

$end walks forward through each event; $start is dragged forward whenever the gap between the two exceeds five minutes. The number of events between the pointers is always the count inside some five-minute window ending at $end. This is O(n) per group after sorting.

The host baseline. Data/baseline.psd1 defines six controls of three check types: Registry (a value under HKLM equals an expected number), FirewallProfile (Domain, Private and Public profiles enabled) and FirewallRule (an enabled inbound Block rule exists for a protocol and port). The Windows registry is a hierarchical database of system settings; HKLM is the machine-wide hive. SMBv1 is the original Windows file-sharing protocol, unencrypted and the transport the EternalBlue exploit used, so WSB0003 requires SMB1 = 0.

A private function, Test-WinSecKitControl, is shared by both the audit command and the remediation command. The comment explains why: "the audit and the remediation can never disagree about what compliant means." Invoke-SecurityBaseline calls it before acting and again after, and a remediation that does not flip the verdict is reported as failed.

Code signing. Authenticode is Microsoft's code-signing format: a hash of the script is signed with a certificate's private key and appended to the file. Invoke-ScriptSigning signs .ps1, .psm1 and .psd1 files and supports -WhatIf. An optional RFC 3161 timestamp server proves when the file was signed, so the signature stays valid after the certificate expires.

The report. Export-SecurityReport builds HTML with a StringBuilder and passes every value through [System.Net.WebUtility]::HtmlEncode. Event messages contain attacker-controlled text (a username in a failed logon can be anything), so unencoded output would turn the report into a cross-site scripting vector.

Lab 4 artifacts. The confidentiality lab used AES to encrypt a password with ConvertFrom-SecureString -Key. The original repo committed the key next to the ciphertext. The replacement script generate-lab4-artifacts.ps1 generates a fresh random key with RandomNumberGenerator and a throwaway demo secret on each run, and .gitignore plus a pre-commit hook block the output from being committed.

Key Design Decisions and Trade-offs

  • Rules as data. Detections and controls live in .psd1 files with a SchemaVersion. The trade-off is a small interpreter in code (three strategies, three check types) instead of arbitrary logic per rule.
  • Pure evaluation. Keeping Test-SecurityDetection free of I/O makes it testable everywhere. The cost is that records must be collected in memory before evaluation, because threshold rules need to see all events for a group.
  • Blank CIS IDs. The CIS Benchmarks (Center for Internet Security's hardening guides) require registration to download. The author chose to leave every CisId empty rather than guess, writing: "An unverified ID is worse than no ID: it looks authoritative and cannot be checked."
  • No domain controls. AD LDS, Group Policy and domain password policy were part of Lab 3 but need an Active Directory domain. CI only has standalone Windows runners, so those controls are left out instead of being stubbed or reported as passing.

Challenges and How They Were Solved

The engineering notes name a pattern: gates that report clean while skipping their inputs. It happened three times.

  1. PSScriptAnalyzer reported "clean across 26 files" after two scripts were added under .github/. Get-ChildItem -Recurse does not enter dot-directories without -Force. Fixed with -Force and an explicit .git filter; the count became 28.
  2. The Windows PowerShell 5.1 test leg passed with 63 tests while PowerShell 7 ran 88. Two test files referenced $IsWindows, which does not exist in 5.1, so Pester's discovery under StrictMode threw and dropped them silently. Fixed by keying on $env:OS, failing on FailedContainersCount, and asserting that Windows-tagged tests ran.
  3. gitleaks (a secret scanner) failed with four real findings because fetch-depth: 0 pulled the unpurged main. Narrowing the scan would have turned it green. The author purged main instead.

The countermeasure is tools/gate-coverage.psd1, which sets a minimum input count for each gate, and Assert-GateCoverage.ps1, which fails the build when a gate processes fewer:

# Was 26 while .github/scripts was invisible to the linter;
# is 28 with it. A floor has to be tight enough to fail on
# the actual historical bad value.
'PSScriptAnalyzer.Files' = 28
'Pester.Tests'           = 80
'Pester.WindowsTagged'   = 20
'Gitleaks.Commits'       = 30

Other notes record smaller bugs. One: Status -eq 'Valid' on an Authenticode signature also requires the certificate to chain to a trusted root, which a self-signed lab certificate never does, so signing was never idempotent. The fix splits "is this file signed by this certificate and unmodified" from "is the signer trusted". Another: a git filter-repo purge by path missed copies under an older folder layout whose name contained spaces. Verification became content-based: every blob in history is grepped for the key bytes.

Security and Performance Notes

  • The incident response followed the standard sequence: contain (rotate credentials), eradicate (rewrite history), redact (black out two report figures at bitmap level), prevent (gitignore, filename guard, gitleaks in a pre-commit hook and CI).
  • gitleaks drops path-only rules when useDefault = true is set, and a raw 16-byte AES key has no text pattern to match. Filename detection was moved to tools/Test-ForbiddenPath.ps1.
  • CI runs with permissions: contents: read, the least privilege a workflow needs to check out code.
  • Detection holds all records in memory. For very large logs, use Get-SecurityEventRecord -MaxEvents to bound the input.

How It Works (Simple Version)

Picture a chalkboard that is never fully erased. The AWS lab is Communication and Network Security, WinSecKit's detections are Security Operations, and the HTTP header scanner is Security Assessment and Testing.

The Matrix effect in script.js keeps one integer per column, drops[i], the row where that column's next character goes:

function drawMatrix() {
    ctx.fillStyle = "rgba(0, 0, 0, 0.05)";
    ctx.fillRect(0, 0, canvas.width, canvas.height);
    ctx.fillStyle = "#00FF00";
    ctx.font = `${fontSize}px monospace`;
    drops.forEach((y, index) => {
        const text = letters.charAt(
            Math.floor(Math.random() * letters.length));
        const x = index * fontSize;
        ctx.fillText(text, x, y * fontSize);
        if (y * fontSize > canvas.height &&
            Math.random() > 0.975) {
            drops[index] = 0;
        }
        drops[index]++;
    });
}
setInterval(drawMatrix, 50);

The 5 percent opaque black fill is the whole trick: a character fully fades after roughly 60 frames (about three seconds). The random reset with probability 0.025 once a column passes the bottom staggers the columns so they do not fall in lockstep. On resize, the canvas is resized, the font size is recomputed as max(innerWidth / 50, 12) and initializeDrops() rebuilds the column array.

The typewriter appends one character of "CISSP" every 150 ms with setTimeout, then waits one second and restarts.

Deployment. .github/workflows/jekyll-gh-pages.yml is GitHub's stock Pages workflow: checkout, configure-pages, jekyll-build-pages, upload, deploy. Jekyll passes a plain HTML site through unchanged.

Key Design Decisions and Trade-offs

  • No framework keeps the page instant to load and trivial to host.
  • setInterval is simpler than requestAnimationFrame but keeps drawing when the tab is hidden. requestAnimationFrame would pause automatically and save battery.
  • The script writes the title with innerHTML +=. With a fixed string this is harmless; with user input, textContent would be the safe choice.

Challenges and How They Were Solved

The commit history shows iterative tuning of styles.css and script.js. The visible fix in the code is responsiveness: the font size and column count are derived from window width and recomputed on every resize, so the effect does not leave gaps or overflow when a phone rotates.

Security and Performance Notes

The page has no inputs and makes no network requests, so its attack surface is effectively nil. Canvas work is proportional to the number of columns (about 50), which is cheap.

At a Glance

How It Works (Simple Version)

Imagine an office building (the VPC) with one floor (the subnet) and one office (the EC2 instance). The floor has a guard at the stairwell with a printed list (the network ACL). He checks every person in both directions against the list, and he has no memory, so someone leaving after a meeting needs their own line on the list. The office door has a receptionist (the security group) who remembers who came in, so anyone she let in can leave freely.

There is no front door key for administrators at all. Instead, a phone in the office (the SSM Agent) dials out to a help desk (AWS Systems Manager), and the admin talks through that call. Nothing outside can knock on the office door to get a shell.

A camera at the building entrance (VPC Flow Logs) records every visitor who was let in or turned away. A smoke detector (CloudWatch alarm) watches CPU load and pages someone (SNS email) when it stays high.

Deep Dive

VPC, subnet, route table. A VPC (Virtual Private Cloud) is a private IP address space inside AWS, here 10.20.0.0/16 (65,536 addresses). A subnet is a slice of it bound to one availability zone (a single data centre group), here 10.20.1.0/24. A subnet is "public" only because its route table sends 0.0.0.0/0 (every destination not otherwise known) to an internet gateway. network.tf builds exactly that, with map_public_ip_on_launch = false so only the lab instance gets a public address on purpose.

The default security group. Every VPC is created with a default security group that allows all traffic between its members. aws_default_security_group with no rule blocks takes ownership of it and empties it, so nothing can fall back to it by accident.

Stateful versus stateless filtering. This is the core concept of the lab. A stateful firewall keeps a connection table: when it allows an outbound packet, it records the 5-tuple (protocol, source IP, source port, destination IP, destination port) and automatically allows the matching reply. Linux iptables with the conntrack module (-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT) works this way, and so do AWS security groups. A stateless filter judges every packet alone, with no memory, so replies need their own rules. AWS network ACLs are stateless.

Security group rules in security.tf are minimal. There is no TCP or UDP ingress at all:

# For ICMP rules, from_port is the ICMP type and
# to_port is the ICMP code.
resource "aws_vpc_security_group_ingress_rule" "admin_echo_request" {
  security_group_id = aws_security_group.instance.id
  ip_protocol       = "icmp"
  from_port         = 8
  to_port           = -1
  cidr_ipv4         = var.trusted_admin_cidr
}

resource "aws_vpc_security_group_egress_rule" "https" {
  security_group_id = aws_security_group.instance.id
  ip_protocol       = "tcp"
  from_port         = 443
  to_port           = 443
  cidr_ipv4         = "0.0.0.0/0"
}

ICMP (Internet Control Message Protocol) carries diagnostic messages; ping sends type 8 (echo request) and expects type 0 (echo reply). ICMP has no ports, so AWS reuses the port fields for type and code. A CIDR (Classless Inter-Domain Routing) block like 198.51.100.7/32 names an address range; /32 means exactly one address.

Network ACL rule ordering. NACL rules are evaluated from the lowest number upward, and evaluation stops at the first match. The rebuild places the optional deny at rule 90, below the allows at 100 and 110:

resource "aws_network_acl_rule" "in_deny_icmp" {
  count = local.icmp_deny_source == null ? 0 : 1

  network_acl_id = aws_network_acl.public.id
  egress         = false
  rule_number    = 90
  rule_action    = "deny"
  protocol       = "icmp"
  icmp_type      = -1
  icmp_code      = -1
  cidr_block     = local.icmp_deny_source
}

local.icmp_deny_source comes from a map keyed by the variable nacl_icmp_mode: allow yields null (no rule created, because count = 0), deny_admin yields the admin CIDR, and deny_all yields 0.0.0.0/0. One variable flips the lab between three experiments.

Ephemeral ports and reply rules. When the instance opens an HTTPS connection, the kernel picks a random source port from its ephemeral range (net.ipv4.ip_local_port_range, 32768 to 60999 on Amazon Linux 2023). The server replies to that port. Because the NACL is stateless, it needs inbound rule 120 allowing TCP 32768 to 65535. Starting at 32768 keeps 22 (SSH) and 3389 (RDP) out of the allowed range. Similarly, rule In 110 allows ICMP echo replies so the instance's own outbound pings work, and Out 120 lets the instance answer the admin's pings.

IMDSv2. The Instance Metadata Service at 169.254.169.254 hands an EC2 instance its configuration, including temporary credentials for its IAM role. IMDSv1 answers a plain GET. That is dangerous: a server-side request forgery (SSRF) bug, where an attacker tricks the app into fetching a URL, can read the credentials. IMDSv2 requires a session token obtained by a PUT with a custom header first, which most SSRF primitives cannot send:

metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required" # IMDSv2 only
  http_put_response_hop_limit = 1
  instance_metadata_tags      = "disabled"
}

The hop limit of 1 sets the IP TTL of the token response to 1, so the reply cannot cross a second network hop, such as into a container on the host.

IAM and Session Manager. IAM (Identity and Access Management) is AWS's permission system. A role is an identity with no password that a trusted entity can temporarily assume, and its trust policy says who may assume it. The instance role trusts ec2.amazonaws.com and has only the AWS-managed AmazonSSMManagedInstanceCore policy, which lets the SSM Agent register and carry Session Manager traffic. Administration happens with aws ssm start-session; there is no port 22 and no key pair.

Flow logs and confused-deputy protection. VPC Flow Logs record every flow's source, destination, ports, protocol (1 = ICMP, 6 = TCP) and ACCEPT or REJECT. The delivery role trusts vpc-flow-logs.amazonaws.com, but with two conditions:

condition {
  test     = "StringEquals"
  variable = "aws:SourceAccount"
  values   = [local.account_id]
}
condition {
  test     = "ArnLike"
  variable = "aws:SourceArn"
  values   = ["arn:${local.partition}:ec2:${var.aws_region}:..."]
}

A "confused deputy" is a trusted service tricked into acting for the wrong customer. Pinning aws:SourceAccount and aws:SourceArn means only flow logs in this account can use the role. Its write policy is limited to the one log group.

KMS and the alarm. The log group and SNS topic are encrypted with a customer-managed KMS key with rotation enabled. A comment in monitoring.tf explains why the cheaper AWS-managed aws/sns key could not work: CloudWatch can only publish to an encrypted topic if the key policy grants cloudwatch.amazonaws.com permission, and an AWS-managed key's policy cannot be edited. The alarm fires when CPUUtilization > 70 for 2 of 3 one-minute datapoints.

Tests without credentials. tests/security_controls.tftest.hcl uses mock_provider "aws" so terraform plan runs offline. Ten assertions check things like http_tokens == "required", the only ingress rule being ICMP type 8 from the admin CIDR, and the deny rule number being lower than the allow. A mutation check (moving the deny to rule 130, setting IMDS optional) made three runs fail, as intended.

Key Design Decisions and Trade-offs

  • Session Manager instead of SSH. No inbound management port removes the most-attacked service. The cost is a dependency on outbound HTTPS and the AWS CLI plugin.
  • Public IP kept. The lab must test ICMP from the admin's own machine over the internet. Checkov flags public IPs (CKV_AWS_88); the skip is documented inline.
  • Documented Checkov skips. CKV_AWS_352 flags every ICMP NACL rule because ICMP has no from_port. Rather than weaken rules, each skip carries a reason.
  • Variable validation as guardrails. trusted_admin_cidr rejects 0.0.0.0/0; cpu_alarm_threshold must be 1 to 100; flow log retention must be a value CloudWatch accepts.

Challenges and How They Were Solved

From docs/original-lab.md and the README:

  • The NACL deny that never denied. In the console lab, rule 51 was meant to deny ICMP but was saved as "All traffic / Allow". Rule 1 already allowed everything, so even a correct deny at 51 would never be reached. The rebuild uses rule 90, and a test fails if the order changes.
  • Stateless means replies too. The original report claimed outbound pings would still work after an inbound ICMP deny. On a NACL they would not, because the echo reply arrives as new inbound traffic. deny_all mode exists to demonstrate this.
  • Self-ping blamed on AWS. Pinging the instance's own public IP failed, which the report blamed on an AWS limitation. Screenshots show it failed while the security group allowed only SSH and worked once ICMP was allowed: the reply arrives from the public IP and is filtered like any other sender.
  • An alarm that could never fire. The threshold was > 10000 on a percentage metric. Validation now rejects values above 100.
  • Detailed monitoring is not the CloudWatch agent. Detailed monitoring changes EC2 metric resolution from 5 minutes to 1 minute; the agent is separate software for OS metrics.

Security and Performance Notes

  • The README's "What I Tested" table separates static proof (format, validate, test, TFLint, Checkov: 121 passed, 0 failed, 7 documented skips) from live proof. Live checks are honestly marked "Not yet validated in live AWS".
  • Running cost is roughly two US cents per hour. terraform destroy removes everything except the KMS key, which enters a 7-day pending deletion window.
  • Traffic to the Amazon DNS resolver, IMDS and Time Sync is not filtered by NACLs, so no rules are needed for them.

HTTP Hardening Check (Nmap NSE)

At a Glance

http-hardening-check is an Nmap script that judges the security headers, cookies and CORS behaviour of a web service against a policy, instead of only listing them. Each weakness becomes a finding with a severity, evidence, a fix and a CWE/OWASP/ASVS reference. Each service gets a 0 to 100 score and a letter grade. A companion Python package, hhc-report, turns Nmap's XML into JSON, CSV, Markdown, HTML and SARIF and can fail a CI build. It is for security engineers and DevOps teams who want header regressions caught automatically.

How It Works (Simple Version)

A home inspector does not just note that a smoke detector exists; she presses the test button. Nmap's bundled http-security-headers script notes that a header exists. This project presses the button. A site that sends Strict-Transport-Security: max-age=0 has the header, but max-age=0 tells browsers to forget the HTTPS-only rule, so this script reports hsts-disabled.

For each web port, the script sends one GET request carrying a fake Origin header from a site that cannot exist. It reads every response header, checks each against the policy, subtracts points for each problem and prints a grade. If the server copies the fake origin into its CORS response and also allows credentials, the script knows any website on the internet could read logged-in users' data, and reports that as HIGH.

Deep Dive

The Nmap Scripting Engine. Nmap discovers hosts and open ports. NSE lets Lua scripts run against what it found. A script declares a portrule (when to run) and an action (what to do). Here portrule = shortport.http runs it on any port Nmap identifies as HTTP. action returns a structured stdnse.output_table() (which becomes XML elements under -oX) plus a human-readable string. The script is organised as a pure Engine table of parsing and judging functions plus a thin Nmap runtime; a test hook (HHC_TEST_EXPORT) exposes Engine to the Lua unit tests.

HSTS is judged only over TLS, because browsers ignore it on plain HTTP. On port 80 the finding that matters is no-https-redirect.

CSP evaluation is the most careful part. Engine.parse_csp splits a header on commas (several policies) and semicolons (directives), lowercasing tokens. csp_policy_weaknesses then applies browser rules. script-src falls back to default-src. 'unsafe-inline' is ignored by browsers when a nonce ('nonce-...') or hash ('sha256-...') is present, so it is only a finding without one. 'strict-dynamic' makes browsers ignore host and scheme sources, so broad sources like *, https: and data: only count without it. base-uri does not fall back to default-src, so its absence is a separate finding. When several policies are present, a resource must satisfy all of them, so a weakness is real only if every policy has it:

function Engine.csp_weaknesses(policies)
  if #policies == 0 then return {} end
  local result = csp_policy_weaknesses(policies[1])
  for i = 2, #policies do
    local w = csp_policy_weaknesses(policies[i])
    for id in pairs(result) do
      if not w[id] then result[id] = nil end
    end
  end
  return result
end

This is a set intersection: start with the first policy's weaknesses, then drop any that a later policy closes. CSP in a <meta http-equiv> tag is also extracted from the body, with HTML entities decoded.

Framing follows browser precedence: CSP frame-ancestors overrides X-Frame-Options. For X-Frame-Options, DENY and SAMEORIGIN protect, conflicting repeated values are ignored, and ALLOW-FROM is reported because current browsers ignore it.

Cookies. Engine.cookie_kind classifies names: anything containing csrf or xsrf is a CSRF token, which the double-submit pattern requires JavaScript to read, so a missing HttpOnly is not a finding. Names matching sess, sid, auth, token, jwt and similar are session cookies, judged strictly.

CORS probe. Every request carries Origin: https://hardening-check.invalid. The .invalid top-level domain is reserved and can never resolve. If the server echoes it in Access-Control-Allow-Origin with Access-Control-Allow-Credentials: true, any attacker site can make authenticated cross-origin reads: cors-reflected-credentials, HIGH.

Scoring.

A score starts at 100 and loses points per finding, floored at 0. The grade caps stop a site with one HIGH problem from earning an A just because everything else is fine. PASS or FAIL is decided separately by the policy's fail_on severity.

Policies. policies/baseline.json, strict.json and owasp-asvs-l1.json set fail_on, HSTS minimums, exposure probing, skipped IDs and severity overrides. Engine.apply_policy rejects unknown keys and finding IDs with result: ERROR, so a typo such as "hsts_min" can never silently weaken a scan.

Exposure probes (opt-in). With exposure=true, the script requests sensitive paths (/.git/HEAD, /.env, /server-status) and one TRACE. Soft-404 servers answer every path with 200, so it uses Nmap's soft-404 calibration plus content signatures and never copies bodies into reports.

The reporter. hhc-report parses Nmap XML into a model. Each finding gets a stable fingerprint: a SHA-256 of target, ID, path and detail with digits replaced by #, so a version bump from nginx 1.24 to 1.25 is not a "new" finding. With --baseline main.json, only new fingerprints fail the gate. The CSV writer neutralises formula injection:

# A cell starting with one of these is a formula in Excel,
# LibreOffice and Google Sheets. Prefixing a quote makes it
# inert text (OWASP CSV injection).
FORMULA_START = ("=", "+", "-", "@", "\t", "\r", "\n", "|")

def safe_cell(value: Any) -> Any:
    if isinstance(value, str) and value.startswith(FORMULA_START):
        return "'" + value
    return value

A header value like =HYPERLINK(...) copied from a hostile server would otherwise execute when an analyst opens the CSV. SARIF (Static Analysis Results Interchange Format) 2.1.0 output is validated against the official schema.

The lab. lab/docker/nginx/lab.conf defines three virtual hosts on one nginx. hardened.lab redirects HTTP to HTTPS and sends a complete header set, including Set-Cookie "__Host-session=lab; Path=/; Secure; HttpOnly; SameSite=Lax". weak.lab sends every header with a weak value, plus Access-Control-Allow-Origin $http_origin with credentials, "the classic CORS misconfiguration". spa.lab answers every path with index.html to exercise soft-404 handling. lab/server.py adds nine Python targets for edge cases.

Key Design Decisions and Trade-offs

  • One GET per port. The request budget is tiny and documented, so the scan is safe against production. The cost is that only one page is judged; headers set on other routes are missed.
  • Browser semantics over string matching. Combining CSP policies, honouring nonces and strict-dynamic, and letting frame-ancestors override X-Frame-Options mean fewer false positives, at the cost of a more complex engine with dedicated unit tests.
  • Deprecated headers as INFO. HPKP, Expect-CT and X-XSS-Protection are reported but cost no points, since browsers have removed support.
  • No TLS checks. Cipher and certificate analysis is left to Nmap's ssl-enum-ciphers and ssl-cert.

Challenges and How They Were Solved

  • Version 1 arguments. v2 removed headers, brief and host. Instead of silently ignoring them, the action emits a warning naming the replacement.
  • Slow non-responders. The README notes that a port that accepts but never answers takes about the timeout plus 15 seconds, because Nmap's HTTP library retries over TLS. This is documented rather than hidden.
  • Docs drifting from code. A Lua unit test checks that docs/checks.md and the JSON schema list exactly the script's 48 checks.
  • Robustness. The stress suite covers 14 status codes, redirect loops, duplicate and oversized headers, 30 cookies and 9,000 random parser inputs.

Security and Performance Notes

  • The GitHub Action runs action/guard.py first. It validates targets against a hostname regex (no URLs, options or shell characters), validates ports and severity, and resolves every target. Unless allow-public-targets: true is set, every address must be loopback, private (RFC 1918 or ULA) or link-local, so the action cannot be pointed at the internet by accident.
  • No payloads, credentials or state-changing methods are sent. Exposure probes never copy response bodies into reports.
  • The HTML report has no JavaScript and escapes hostile input.

UFW and iptables from first principles. Linux filters packets in the kernel with Netfilter. iptables (and its successor nftables) is the user-space tool that loads rules into Netfilter. Rules live in tables (filter for allow/deny, nat for address translation) and chains (INPUT for packets addressed to this machine, OUTPUT for packets it sends, FORWARD for packets routed through it). Each packet is checked against a chain's rules in order. The first rule that matches decides with a target such as ACCEPT or DROP, and if none match, the chain's default policy applies. A typical stateful host firewall looks like:

iptables -P INPUT DROP
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED \
  -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j ACCEPT

That snippet illustrates the concept and is not from the repo. UFW ("Uncomplicated Firewall") generates rules like these. ufw enable sets a default deny for incoming and allow for outgoing traffic, and inserts its own chains (ufw-before-input, ufw-user-input and so on) with conntrack rules so replies are allowed. ufw allow OpenSSH uses an application profile from /etc/ufw/applications.d that maps the name to TCP 22.

Fail2ban. Fail2ban tails log files (such as /var/log/auth.log) and matches lines with regex filters. When an IP fails too often inside a time window, a jail runs an action, normally inserting an iptables or nftables rule that drops that IP for a ban period. It is the same sliding-window idea as WinSecKit's brute-force detection, but it responds instead of only reporting. Ubuntu's package enables the sshd jail by default.

Key Design Decisions and Trade-offs

  • Modules over shell commands. Using apt, ufw and service modules makes every task idempotent and reports changed only when something actually changed.
  • Single play. Simple to read; roles would make it reusable across projects.
  • Upgrade everything. dist upgrades patch quickly but can pull in a new kernel that needs a reboot. The playbook does not check /var/run/reboot-required or reboot.

Challenges and How They Were Solved

The commit "Fix baseline playbook (UFW + fail2ban tasks)" corrected the firewall and Fail2ban tasks. Reading the current playbook closely shows two things worth knowing:

  • Task order and lockout risk. UFW is enabled before the OpenSSH allow rule is added. With default-deny incoming, there is a window where new SSH connections would be refused. Ansible's existing SSH session usually survives because conntrack already tracks it as established, but a dropped connection in that window would lock the controller out. Swapping the two tasks removes the risk.
  • README scope. The README promises "SSH hardening", but no task edits sshd_config (for example PasswordAuthentication no or PermitRootLogin no). That remains to be built.

Security and Performance Notes

  • Fail2ban plus UFW reduces brute-force noise, but key-only SSH authentication is the stronger control.
  • Real addresses and usernames belong in a private inventory or Ansible Vault, not a public repo.
  • Ansible connects to hosts in parallel (5 forks by default), so the baseline scales to many servers.

Deep Dive

Probes with honest failure. Every data source (Defender, firewall, SMB, registry) is read once through Invoke-StateProbe, which classifies failures instead of hiding them:

try {
    @{ Available = $true; Data = (& $ScriptBlock) }
} catch {
    $message = $_.Exception.Message
    $reason = 'Error'
    if ($_.Exception -is [System.UnauthorizedAccessException] -or
        $message -match 'access (is |was )?denied|0x80070005') {
        $reason = 'AccessDenied'
    } elseif ($message -match 'not supported on this platform|
              Invalid class|Invalid namespace') {
        $reason = 'NotSupported'
    }
    @{ Available = $false; Reason = $reason; Error = $message }
}

A missing BitLocker module on Windows Home becomes NOT_APPLICABLE; a non-elevated session becomes ERROR. Neither is counted as passing. This is the same honesty principle as WinSecKit's gate coverage.

The controls. Highlights, explained:

  • LLMNR (Link-Local Multicast Name Resolution) lets Windows ask the whole local network "who is FILESERVER?" when DNS fails. Any machine can answer, so tools like Responder impersonate the server and capture password hashes. The control checks the policy EnableMulticast = 0 under HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient.
  • SMB signing adds a cryptographic signature to file-sharing packets so a man-in-the-middle cannot relay or alter them.
  • LSA protection (RunAsPPL) runs the Local Security Authority, which holds credentials in memory, as a protected process so tools like Mimikatz cannot read it.
  • Script block logging, module logging and transcription make PowerShell activity visible (event 4104, as in WinSecKit), and removing the PowerShell 2.0 engine closes a downgrade path that bypasses that logging.
  • Defender exclusions. Get-ExclusionRisk flags exclusions that are drive roots, wildcards, user-writable staging folders (Temp, Downloads, Public), LOLBins (legitimate binaries attackers abuse, such as mshta.exe, rundll32.exe, regsvr32.exe) or executable extensions. An attacker who can drop a file into an excluded folder runs unscanned.

Remediation handlers are data. Remediation.psm1 maps control IDs to handler kinds:

$script:Handlers = @{
  'WIN-DEF-001' = @{ Kind = 'MpPreference';
      Property = 'DisableRealtimeMonitoring';

The Allowed list is used during rollback: a value read from a backup file that the setting could never have had is refused, so a tampered backup cannot push arbitrary values.

The remediation loop in Invoke-SecurityRemediation runs, per finding: ShouldProcess (with ConfirmImpact = 'High', PowerShell prompts unless -Confirm:$false); read the current state; write it to backup\security-backup-<timestamp>.json before changing anything; apply; read back; and record Applied or Failed. If the read-back disagrees, the detail reads "Group Policy, MDM or Defender tamper protection may control this setting." Firewall verification reads the effective policy, so a GPO override shows up as a failure instead of a false success.

PackageManager.psm1 validates the catalog, resolves categories from -Mode, -Only, -Include and -Skip, detects packages by exact winget ID, and decodes winget's HRESULT exit codes into names via Get-WingetExitDescription. Key Design Decisions and Trade-offs

  • Assessment and remediation are separate commands. Reading is always safe; writing is explicit.
  • Only immediately verifiable settings are automated. Changes that need a restart (UAC, LSA protection), risk data (BitLocker) or often break developer tools (ASR rules, controlled folder access) are never applied automatically; the report gives manual guidance.
  • No overall score. The summary gives counts per status and FAIL counts per severity, avoiding a single number that hides context.
  • References checked against sources. NIST SP 800-53 Rev. 5 and ATT&CK IDs were verified; CIS item numbers were left out because they change between benchmark versions and could not be checked against a licensed copy.

How It Works (Simple Version)

Imagine three towns in a row, each with a post office. Every 30 seconds, each post office shouts to its neighbours: "I can deliver to these streets, and this many towns away." Deep Dive

Routing basics. A router forwards packets by looking up the destination IP in its routing table and choosing the longest matching prefix. Connected routes appear automatically for each configured interface. Everything else must come from static routes or a routing protocol. Before RIP, Router0 knows only 192.168.0.0/24 and 172.168.0.0/24, so a ping from PC0 to 192.168.10.3 returns "Destination Host Unreachable" from 192.168.0.1. The report correctly reads that as Router0 having no route.

The report also lists a ping from PC0 to Router1's near interface (172.168.0.2) failing before RIP. The echo request reaches Router1 through PC0's default gateway, but Router1 has no route back to 192.168.0.0/24, so the reply is dropped. Routing must work in both directions.

RIP. RIP (Routing Information Protocol) is a distance-vector protocol: each router advertises its whole table to neighbours, adding one to each hop count. The metric is hop count, and 16 means unreachable, so RIP networks are limited to 15 hops. Updates go every 30 seconds. Cisco's administrative distance for RIP is 120 (lower is more trusted; OSPF is 110). Loop prevention uses split horizon (do not advertise a route back out the interface it was learned on) and route poisoning (advertise a failed route with metric 16).

RIPv1 versus RIPv2. RIPv1 is classful: its updates carry no subnet mask, and it broadcasts to 255.255.255.255. RIPv2 is classless: it carries masks, multicasts to 224.0.0.9, and supports authentication. The lab's configuration, from the report:

Router(config)# router rip
Router(config-router)# version 2
Router(config-router)# no auto-summary
Router(config-router)# network 192.168.0.0
Router(config-router)# network 172.168.0.0
Router(config-router)# end
Router# copy running-config startup-config

network statements in RIP are classful. They select which interfaces send and listen for RIP and whose connected networks get advertised; they do not take a mask. 172.168.0.0 is a Class B address (first octet 128 to 191), so the statement matches every interface in 172.168.0.0/16. Router1's network 172.168.10.0 is converted by IOS to 172.168.0.0 as well. no auto-summary stops RIPv2 from collapsing subnets into their classful network at boundaries, which would break discontiguous designs. copy running-config startup-config saves RAM config to NVRAM so it survives a reboot.

Verification. show ip route rip lists learned routes marked R, with [120/n] showing administrative distance and hop count. After all three routers are configured, the report shows PC0 reaching Router1, Router2 and PC3.

Key Design Decisions and Trade-offs

  • RIP for teaching. RIP is simple to configure and observe. OSPF (link-state, cost-based) converges faster and scales further, and is what the current CCNA emphasises.
  • Fiber between routers. Purely a Packet Tracer cabling choice; it does not change routing behaviour.

Challenges and How They Were Solved

The report's step 6 walks through each failed ping and explains why it failed before RIP was enabled, a good troubleshooting habit. One addressing detail is worth flagging: the WAN links use 172.168.0.0/24 and 172.168.10.0/24. The RFC 1918 private block is 172.16.0.0/12 (172.16.0.0 to 172.31.255.255), so 172.168.x.x is public address space owned by someone else. It works inside a simulator, but on a real network it would hijack those destinations. 172.16.0.0/24 and 172.16.10.0/24 would be the correct private choice.

Security and Performance Notes

  • RIPv2 without authentication accepts updates from any neighbour, so a rogue device can inject routes. ip rip authentication mode md5 with a key chain mitigates this, and passive-interface stops RIP updates from being sent onto LANs that have only hosts.
  • RIP's 30-second updates and hold-down timers make convergence after a failure take minutes, not seconds.

Inter-VLAN Routing via Router-on-a-Stick

At a Glance

This mini-lab splits one switch into two isolated networks (VLAN 10 "USERS" and VLAN 20 "SERVERS") and routes between them through a single router port. It is practice for a larger multi-VLAN office project and covers the core CCNA switching skills: creating VLANs, assigning access ports, building an 802.1Q trunk and configuring router sub-interfaces. The repo contains the .pkt file, a PDF lab report, a topology illustration and a screenshot.

How It Works (Simple Version)

A switch with VLANs is like one office building split into two companies with separate locked floors. People on floor 10 cannot walk to floor 20. To pass a note between them, you send it down the single shared lift (the trunk) to the mailroom (the router). Each note carries a coloured sticker (the VLAN tag) saying which floor it came from. The mailroom reads the sticker, swaps it for the other floor's colour, and sends it back up the same lift.

Architecture

              Router4 (ISR 4331)
              Gi0/0/0  (no IP, trunk)
               |-- .10  dot1Q 10  192.168.10.1/24
               '-- .20  dot1Q 20  192.168.20.1/24
                    |

             Fa0/1 |          | Fa0/2

                 PC0          PC1
         192.168.10.10    192.168.20.20

Deep Dive

VLANs. A switch normally forms one broadcast domain: an ARP broadcast from any port reaches all ports. A VLAN (Virtual LAN) divides one physical switch into several logical switches. Ports in VLAN 10 only exchange frames with other VLAN 10 ports. Each VLAN is its own Layer 2 network and needs its own IP subnet. To move traffic between VLANs, a Layer 3 device (a router or multilayer switch) must route it.

Access and trunk ports. An access port belongs to one VLAN and sends untagged frames, because PCs do not understand tags. A trunk carries many VLANs over one link by inserting an IEEE 802.1Q tag into each Ethernet frame: 4 bytes after the source MAC, holding a 12-bit VLAN ID (1 to 4094). The native VLAN (VLAN 1 by default) travels untagged on a trunk.

Switch configuration (from the report, reformatted one command per line):

vlan 10
 name USERS
vlan 20
 name SERVERS
interface Fa0/1
 switchport mode access
 switchport access vlan 10
interface Fa0/2
 switchport mode access
 switchport access vlan 20
interface Gi0/1
 switchport mode trunk
 switchport trunk allowed vlan 10,20
 switchport nonegotiate

switchport nonegotiate disables DTP (Dynamic Trunking Protocol), so the port will not negotiate trunking with whatever is plugged in. That closes the "switch spoofing" attack, where a host pretends to be a switch to become a trunk and see every VLAN. allowed vlan 10,20 prunes all other VLANs from the trunk.

Router-on-a-stick. The router's one physical interface is split into logical sub-interfaces, one per VLAN:

interface Gig0/0/0
 description Trunk to Switch3
 no shutdown
interface Gig0/0/0.10
 encapsulation dot1Q 10
 ip address 192.168.10.1 255.255.255.0
interface Gig0/0/0.20
 encapsulation dot1Q 20
 ip address 192.168.20.1 255.255.255.0

encapsulation dot1Q 10 tells the router that frames tagged 10 belong to .10, and frames it sends out .10 get tag 10. Each sub-interface IP is that VLAN's default gateway. The physical interface has no IP; it only needs no shutdown.

Packet walk. PC0 pings 192.168.20.20. That is outside its subnet, so PC0 ARPs for its gateway 192.168.10.1 and sends the frame untagged into Fa0/1. The switch tags it VLAN 10 and sends it up the trunk. The router receives it on .10, looks up 192.168.20.0/24 (a connected route on .20), rewrites the Layer 2 header and sends it back down tagged 20. The switch strips the tag and delivers it out Fa0/2. Verification uses show vlan brief, show interfaces trunk, show ip interface brief and show ip route connected.

Key Design Decisions and Trade-offs

  • ROAS versus a Layer 3 switch. Router-on-a-stick needs one router port, so it is cheap. But all inter-VLAN traffic crosses one link twice (up and back down), which caps throughput at that link's speed. A multilayer switch with SVIs (Switch Virtual Interfaces, interface vlan 10) routes in hardware and scales better.
  • Static host addressing keeps the lab focused; DHCP with ip helper-address is planned for the follow-up project.

Challenges and How They Were Solved

The report says all objectives were met without configuration errors, and it lists typical failure points to check (trunk mismatches, gateway errors). One mismatch is in the repository itself: the README describes configs/, report/ and packet-tracer/ folders, but all files sit at the top level and no running-config text files exist. The commands are only in the PDF.

Security and Performance Notes

  • Native VLAN 1 is left at its default. Moving the native VLAN to an unused ID and pruning VLAN 1 from trunks defends against double-tagging VLAN hopping.
  • With no ACLs on the sub-interfaces, USERS can reach SERVERS on every port. The follow-up project plans ACL enforcement.

Rapid PVST+ Campus Lab

At a Glance

This Packet Tracer lab builds a redundant Layer 2 campus: two distribution switches and two dual-homed access switches, with loops on purpose. Rapid PVST+ (Cisco's per-VLAN version of Rapid Spanning Tree) blocks the loops while keeping backup paths ready, and each distribution switch is root for a different VLAN to spread the load. Access ports are hardened with PortFast and BPDU Guard, demonstrated by plugging in a rogue switch that gets shut down. The repo includes screenshots and a PROJECT_OVERVIEW.md that audits the README against the actual files.

How It Works (Simple Version)

Ethernet frames have no expiry counter. If switches are wired in a loop, a single broadcast circles forever and multiplies until the network melts down (a broadcast storm). Spanning tree is like closing some roads in a town so that there is exactly one route between any two houses, while keeping the closed roads ready to reopen if a bridge collapses. The switches elect a "town centre" (the root bridge), every switch keeps its cheapest road towards it open, and every other redundant road is blocked. Rapid PVST+ runs a separate election per VLAN, so VLAN 10 and VLAN 20 can have different town centres and use different roads.

Architecture

         SW1 (3560) ======= Gi0/1 ======= SW2 (3560)
      root VLAN 10                     root VLAN 20
     Fa0/1 Fa0/2  Fa0/3            Fa0/1 Fa0/2  Fa0/3
       |    |       \               /    |     |
       |    |        \             /     |     |
       |    |         \           /      |     |
     Fa0/23 Fa0/24   Fa0/21   Fa0/21  Fa0/23 Fa0/24
       \    /          |         |       \    /
        SW4 (2960) ----+         +------ SW3 (2960)
        Fa0/1  Fa0/10                    Fa0/1
         |        |                        |
        PC1    SW5 (rogue,               PC0
     10.10.10.21  err-disabled)       10.10.10.11

SW3 uses SW2 links (Fa0/23-24) as primary and Fa0/21 to SW1 as its cross link. SW4 is the mirror image.

Deep Dive

STP from first principles. Switches exchange BPDUs (Bridge Protocol Data Units) every 2 seconds. Each switch has a Bridge ID: a priority (default 32768) plus its MAC address. The lowest Bridge ID becomes root. Every non-root switch picks one root port, the port with the lowest total path cost to the root (cost 19 for FastEthernet, 4 for Gigabit). Each segment gets one designated port that forwards towards it. Every remaining port is blocked.

PVST+ and the system ID extension. In PVST+, the priority field is split: a 4-bit priority in steps of 4096 plus a 12-bit VLAN ID. That is why the screenshots show SW1's root priority as 24586 (24576 + VLAN 10) and SW2's as 4116 (4096 + VLAN 20). spanning-tree vlan 10 root primary is a macro that sets the priority to 24576, or lower than the current root if needed. That explains why SW2 ended up at 4096: it had to beat whatever root was already elected.

Rapid STP (802.1w). Classic STP moves a port through listening and learning states, each 15 seconds (the forward delay), so recovery takes 30 to 50 seconds. RSTP adds port roles: alternate (a pre-computed backup root port) and backup. On point-to-point links it uses a proposal/agreement handshake to move a designated port to forwarding immediately. When a root port fails, the alternate port takes over almost at once. The lab claims under 10 seconds of ping loss.

Global edge configuration, applied on every switch:

spanning-tree mode rapid-pvst
spanning-tree portfast default
spanning-tree portfast bpduguard default
SW1(config)# spanning-tree vlan 10 root primary
SW2(config)# spanning-tree vlan 20 root primary

portfast default makes every access port an edge port that skips the listening and learning states, so PCs get connectivity instantly. bpduguard default puts any PortFast port that receives a BPDU into err-disabled: a host never sends BPDUs, so receiving one means someone plugged in a switch. That stops a rogue switch from triggering a topology change or claiming root.

Evidence of load balancing. On SW3 in VLAN 10, the root is SW1, reached through Fa0/21 (Root FWD, cost 19), with Fa0/23 and Fa0/24 Alternate Blocking. In VLAN 20 the root is SW2, reached through Fa0/23, with Fa0/24 and Fa0/21 blocked. So SW3 sends VLAN 10 traffic up one link and VLAN 20 traffic up another, which is the point of per-VLAN roots. SW4's show interfaces status shows Fa0/10 (TO-SW5) as err-disabled after the rogue SW5 was connected.

Trunks are 802.1Q, mode on, native VLAN 1, allowed VLANs 10 and 20, as shown in SW2's show interfaces trunk.

Key Design Decisions and Trade-offs

  • Individual trunks instead of EtherChannel. The README notes some 2960 Packet Tracer images do not support EtherChannel. With EtherChannel (LACP), parallel links bundle into one logical link that STP does not block, doubling usable bandwidth.
  • Root placement on distribution switches. Placing roots by design, not by lowest MAC, keeps the access layer from ever becoming root.
  • Global defaults over per-port config. portfast default and bpduguard default apply to all access ports automatically, so a newly patched port is protected without extra commands.

Challenges and How They Were Solved

PROJECT_OVERVIEW.md is an honest audit of the repo and lists 14 issues. The main ones:

  • Root Guard is claimed but not shown. No config or screenshot demonstrates spanning-tree guard root. Root Guard would block a downstream port that receives a superior BPDU, protecting root placement.
  • Configs are missing. The README promises sanitised per-device configs, but config/ holds only an empty readme.txt.
  • Broken image and paths. The README topology image is hotlinked from an expired LinkedIn CDN URL (HTTP 403 now), and the paths pkt/ and /configs do not match the real folders (pkt file/, config/).
  • No failover capture. The sub-10-second convergence claim lacks the continuous-ping screenshot.
  • Only VLAN 10 has hosts, so VLAN 20 forwarding is proven only by STP output.
  • Asymmetric root priorities (24576 versus 4096), harmless but untidy.

Security and Performance Notes

  • BPDU Guard is the key Layer 2 security control here. Recovering an err-disabled port requires removing the rogue device and running shutdown then no shutdown, or configuring errdisable recovery cause bpduguard.
  • Native VLAN 1 on trunks is a hardening gap; a dedicated unused native VLAN (for example 999) is best practice.
  • RSTP convergence on point-to-point full-duplex links is typically sub-second; Packet Tracer timing is approximate.

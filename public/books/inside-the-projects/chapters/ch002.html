2 spoonstill, a Batch Film Renderer in Rust

This chapter covers the largest project in the book: a Rust workspace that turns a folder of photographs and narration into one finished MP4 video. It is worth reading slowly, because the interesting part is not only the code. It is also the method around the code: a numbered decision log, benchmarks taken on real hardware, and tests that exist to stop a rule from being broken. By the end you should understand how FFmpeg can be driven safely and predictably from Rust at the scale of hundreds of scenes.

spoonstill

At a Glance

spoonstill is a batch renderer for narrated photo films. You give it still images and, for each one, a voice recording, a line of text, or nothing. It produces one MP4 in which every still slowly zooms or pans (the "Ken Burns" effect) and each scene lasts exactly as long as its narration. It is built for people making narrated photo essays, audiobook chapters with artwork, lecture slides with voiceover, or vertical Shorts made from a photo set. The problem it solves is the tedium of doing this by hand in a timeline editor: at 500 scenes, aligning every picture to every sentence is hours of dragging, and spoonstill computes all of that alignment instead.

The program has two front ends that share one engine: a command line tool called still, and a desktop window called spoonstill built with Tauri 2. The design rule is "if the CLI cannot do it, it does not exist", so the window is only a thin layer over the same library calls.

How It Works (Simple Version)

Imagine you are making a slideshow for a family dinner. You have 40 photos and you want to say a sentence or two about each one. Doing it by hand, you would record your voice for photo 1, time how long it lasted, set photo 1 to stay on screen exactly that long, add a slow zoom so it does not look frozen, then do the same for photo 2, and so on. Then you would join everything together and hope the volume is even.

spoonstill does each of those steps for you, in this order:

  1. Read the folder. It looks at what you gave it. 001.jpg and 001.m4a share the number 001, so they belong to the same scene. 002.jpg with 002.txt means "read this text aloud over photo 2".
  2. Check everything first. Before doing any slow work it opens every file with ffprobe (FFmpeg's inspection tool) and reports every problem at once: a broken JPEG, an empty MP3, two recordings for one photo.
  3. Get the narration ready. Recordings are converted to one standard audio format and made equally loud. Text lines are sent to a neural voice service, which returns speech. Then the length of each piece of audio is measured precisely.
  4. Make one small video per scene. For each photo, FFmpeg is told: "make exactly N frames, zooming from here to there, with this audio underneath". N comes from the measured audio length.
  5. Check each small video. It is opened again and every property (size, colour format, frame count) is compared against a fixed checklist. Only a video that passes is kept.
  6. Glue them together. The small videos are joined end to end without re-encoding, like taping film reels together.
  7. Check the final film, then delete small videos from older runs that are no longer needed.

The trick that makes it fast the second time: each small video is named after a fingerprint of everything that went into it. If you fix a typo in scene 12 and render again, only scene 12 has a new fingerprint, so only scene 12 is rebuilt. The other 39 are reused.

How the pieces talk at run time:

  • CLI to app: plain function calls such as spoonstill_app::render_project(&options, &cancel, &on_event). Progress comes back as FilmEvent values passed to a callback.
  • Window to app: the JavaScript calls invoke("render_project", ...), which runs a Rust #[tauri::command]. That command calls the same render_project on a blocking thread and streams FilmEvents back to the webview through an ordered Tauri Channel.
  • App to media: Rust calls that eventually build an FfmpegCommand (an argument vector) and spawn a child process.
  • Media to FFmpeg: operating system processes, with arguments passed as a list, stdin used for a graceful "quit", stdout used for -progress key/value lines, and stderr retained in full for diagnostics.
  • TTS to the voice service: edge-tts is a Python program that talks to Microsoft's speech endpoint over a websocket. spoonstill never speaks that protocol itself.

Deep Dive

This section walks the pipeline from bottom to top: first the pure maths in spoonstill-core, then the FFmpeg boundary, then audio, captions and voices, then the orchestration and concurrency, and finally the two front ends and the build system.

Timing: from seconds of speech to a frame count

Everything starts with one question: a narration is 3.717 seconds long and the video runs at 30 frames per second, so how many frames should the scene have? The answer lives in crates/spoonstill-core/src/timing.rs, which the author's own learning notes call "the single most load-bearing calculation in the program".

pub fn frames_for_duration(seconds: f64, fps: u32) -> u32 {
    if !seconds.is_finite() || seconds <= 0.0 || fps == 0 {
        return 1;
    }
    let exact = seconds * f64::from(fps);
    let frames = (exact - 1e-9).ceil();
    // Saturating rather than `as u32`, which would wrap a
    // nonsense duration into a small frame count ...
    if frames >= f64::from(u32::MAX) {
        u32::MAX
    } else {
        (frames as u32).max(1)
    }
}

Three decisions are packed into these lines:

  • Round up, never down (decision D-022). Rounding down would cut the last syllable of nearly every scene. Instead, the audio is padded with silence up to the next whole frame.
  • Subtract a tiny epsilon before ceil. Floating point numbers (the f64 type, which stores decimals approximately) mean 4.0 * 30.0 might come out as 120.00000000000001. A plain ceil would turn that into 121 frames. The 1e-9 is far smaller than one audio sample, so it can never swallow a real frame.
  • Saturate instead of casting blindly. as u32 on a huge float would wrap around to a small, plausible-looking number. Saturating makes a nonsense input produce an obviously nonsense output.

The same file has samples_for_frames, which returns the exact number of audio samples at 48,000 samples per second that fill a given number of frames. For the reference case, 112 frames at 30 fps is 179,200 samples. Using an integer sample count means FFmpeg's audio trim is told atrim=end_sample=179200 instead of a rounded decimal like atrim=0:3.733333. The sample rate 48 kHz divides evenly by 24, 25, 30, 50 and 60, so every common frame rate gets an exact answer.

Geometry: output sizes and the prescale canvas

crates/spoonstill-core/src/geometry.rs defines Aspect (16:9, 9:16, 1:1), Resolution names (720p to 2160p, also called 4k), and OutputSpec. A resolution number always means the short edge, so "4K vertical" is 2160x3840. The constant PRESCALE_FACTOR = 3 says the still is first scaled onto a canvas three times the output size in each axis. For 1080p that canvas is 5760x3240, and for 4K it is 11520x6480.

Why three? The answer is a measurement in ffmpeg-findings.md section 1. FFmpeg's zoompan filter rounds its zoom factor per frame. If the canvas is too small, two consecutive frames round to the same zoom and the motion visibly "steps". The author rendered a 10% zoom over 300 frames at different prescale sizes and counted unique frames with FFmpeg's mpdecimate filter:

Prescale height Unique frames of 300 Duplicates
1x output 188 37%
2x output 280 7%
3x output 300 0%
6x output 300 0%

Three times is both the floor (below it, stepping) and the ceiling (above it, only slower). The same section also disproved a claim from the planning documents that a big prescale was "a memory trap": peak memory moved only 8% across a 6x range. It is a CPU cost.

OutputSpec::new also refuses sizes past 4K, because the resulting H.264 "level" (a tag that tells players the maximum stream complexity to expect) would exceed what players honour. The limit is expressed as MAX_MACROBLOCKS = 36_864, where a macroblock is the 16x16 pixel tile H.264 works on.

Motion: the Ken Burns filter graph

crates/spoonstill-core/src/motion.rs is described by its own header as "the whole reason the project has measurements". It produces the FFmpeg filter graph string for one scene. A filter graph is FFmpeg's mini language for chaining image and audio operations, written as comma-separated filters. The emitted chain is:

scale=<3*W>:<3*H>:force_original_aspect_ratio=increase:out_range=tv,
crop=<3*W>:<3*H>,
zoompan=z='<f(on)>':x='<expr>':y='<expr>':d=<N>:s=<W>x<H>:fps=<FPS>,
setparams=range=tv:color_primaries=bt709:color_trc=bt709:colorspace=bt709,
setsar=1,
format=yuv420p

Each position fixes a failure that was reproduced first:

  • Cover-fit before zoompan (D-034). scale with force_original_aspect_ratio=increase plus crop makes the canvas fill the target shape exactly. Since the canvas is never smaller than the output aspect, the moving window can never slide off the picture and show black edges.
  • The frame count is structural (D-030). The still is fed once, with no -loop flag, and zoompan is told d=N (emit N output frames per input frame). The command also gets -frames:v N. Section 2 of the findings shows why: the common form -loop 1 with d=N and no duration limit produces frames forever. A reference project had recorded this as a "five-hour hang". The author measured it at 8,400 frames in 25 seconds and still accelerating. It was never hung; it was succeeding forever.
  • setsar=1 is last before format (D-033). SAR is "sample aspect ratio", the shape of one pixel. A 1999x1001 source picks up a SAR of 30007:30000 during scaling, and an early setsar does not survive zoompan. A segment with the wrong SAR is still joined by FFmpeg without any warning, which is how corrupted films happen.
  • setparams and out_range=tv (D-037). JPEGs use "full range" colour (values 0 to 255) while video normally uses "TV range" (16 to 235). Without pinning, the encoder writes yuvj420p, a different pixel format, and two segments from differently ranged sources join with exit code 0 and visibly different colour.

The pan and zoom expressions are where the "cannot walk off the image" guarantee becomes structural rather than clamped:

fn axis_expr(axis: Axis, motion: MotionSpec, frames: u32) -> String {
    let (ax, ay) = motion.anchor.fractions();
    let p = progress_expr(frames);

    let fraction = match (axis, motion.kind) {
        (Axis::X, MotionKind::PanRight) => p,
        (Axis::X, MotionKind::PanLeft) => format!("1-{p}"),
        (Axis::Y, MotionKind::PanDown) => p,
        (Axis::Y, MotionKind::PanUp) => format!("1-{p}"),
        (Axis::X, _) => expr_num(ax),
        (Axis::Y, _) => expr_num(ay),
    };

    match axis {
        Axis::X => format!("({fraction})*(iw-iw/zoom)"),
        Axis::Y => format!("({fraction})*(ih-ih/zoom)"),
    }
}

In zoompan, iw is the input width, zoom is the current zoom factor and on is the output frame number. The expression iw-iw/zoom is exactly the legal range of the window's left edge at that zoom: 0 puts it flush left, the full value puts it flush right. Because fraction is either a constant anchor between 0 and 1, or progress_expr, which is min(on/(frames-1),1), the result can never leave the image. No clamp is needed because nothing can go out of range. Two smaller details matter too: progress_expr returns the literal 0 for a one-frame segment so FFmpeg never divides by zero, and expr_num formats every number with {:.6} so a European locale can never write 0,1 instead of 0.1.

A pan also needs room to travel, so pans run at a fixed zoom of 1 + amount. At zoom 1 the legal travel is zero.

Deterministic motion. If you do not choose a move, one is derived from the scene's identity with MotionSpec::seeded. The seed is a hash of the project name, the scene index and the hash of the image bytes. Three different bit ranges of that 64-bit seed pick the move kind (6 options), the anchor (9 options), and the amount (0.08 to 0.12). Because it is a pure function of stable inputs, a re-render is byte-identical and the cache stays valid.

A later decision, D-153, added a second seed rule MotionSeed::V2 that leaves out the scene index and uses "how many earlier scenes use this same photo" instead. Under V1, moving scene 8 to the front changed the index of every scene after it, which changed every move and forced a full re-encode. Under V2 a reorder is free. The old rule is frozen and stays the default for projects that do not opt in, so films already made never change. still new writes motion_seed: v2 into new projects.

Hashing: why not Rust's built-in hasher

crates/spoonstill-core/src/hash.rs implements FNV-1a, a simple 64-bit non-cryptographic hash, by hand. The reason is written in the header: Rust's DefaultHasher does not promise the same output across compiler versions, and RandomState reseeds per process. Using it for cache keys would build a program that works, and then silently invalidates every cached segment after a compiler upgrade.

There are two field-combining variants, and the story of why tells you a lot about this codebase. fnv1a_fields separates fields with the byte 0x1f. That was safe while the fields were paths and hex digests. Then subtitles arrived, and subtitle text comes from the operator's .txt files. 0x1f is not whitespace, so it survives text cleanup, and two different sets of captions could hash to the same key (D-118). The fix was fnv1a_prefixed, which writes each field's length as 8 bytes before the field. A boundary stated as a count cannot be faked by data.

The project model and validation

crates/spoonstill-core/src/project.rs defines SceneId, AudioSource, SceneDraft, SceneSpec, and a long ProblemKind enum. AudioSource is the heart of the model: every scene has exactly one of a recording file, a line of text to speak (TTS), or a silent duration (D-020). A scene with both a recording and a text file is not ambiguous: the recording is the narration, and the text becomes its caption.

validate_drafts checks everything that needs no disk access and returns a Validation holding every Problem found, each tied to its scene. Limits such as MAX_SCENE_SECONDS = 3600 and MAX_SCRIPT_BYTES = 256 KiB are here too.

crates/spoonstill-core/src/path_safety.rs decides whether a path an operator wrote in a manifest stays inside the project folder. It compares canonical paths component by component, not strings (so /proj-evil is not inside /proj). It also gives the same error whether or not an outside file exists, so the error message cannot be used to probe the disk. The actual call to canonicalize comes in through a RealPath trait, which keeps core free of I/O and lets the tests run with a fake table on both macOS and Windows.

Other core modules:

  • captions.rs: subtitle themes (classic, boxed, band, card, punch, minimal), placement, and cues(), which splits text into timed caption cues with a minimum of 0.9 seconds each and at most 60 per scene. Every theme measurement is a fraction of the frame, so a theme looks the same at 720p and 4K.
  • language.rs: guesses the language from the writing system (Devanagari means Hindi, Han with kana means Japanese, and so on). This only applies when the operator named no voice, so a Hindi line is not sent to an English voice that returns silence.
  • chapter.rs: cuts a whole chapter of prose into scene-sized pieces (described below).
  • diagnostics.rs: the Event type and Diagnostics trait every layer logs through, plus redact for secrets.
  • remedy.rs: a structured "what is wrong and what fixes it" value that the window turns into an Install button.

Cutting a chapter into scenes

chapter.rs solves a real workflow problem the author had: writing a novel chapter and wanting a new picture every three to five seconds. Cutting by hand into 001.txt, 002.txt was most of the work. The algorithm treats every gap between words as a possible cut and gives it a cost: 0 after a full stop, 1 after a semicolon or dash, 2 after a comma, 3 before words like "and" or "then", 25 anywhere else, plus 20 for leaving a dangling "the" or "of". There is also a cost for every second a piece falls outside the target pacing. Joining the end of one sentence to the start of the next is refused outright.

The cheapest set of cuts is found as a shortest path over word positions, a form of dynamic programming. With n words and at most w words per piece, it runs in O(n*w), microseconds for a chapter. Lengths are estimated at 16.3 characters per second, a number measured from the author's own 431 lines (30,391 characters over 1,868 seconds of speech). The real length is only known after the line is spoken and measured.

The process boundary: spoonstill-media/src/command.rs

This is the only file in the workspace allowed to start a process. A test, tests/no_shell_strings.rs, reads the crate's own source and fails if any other module constructs a process or reaches for sh -c or cmd /c. FfmpegCommand is a builder that holds a program path and a Vec<OsString> of arguments. OsString is used instead of String because file names on both platforms can contain bytes that are not valid UTF-8.

Why does this matter so much? Because a shell string turns data into code. One of the test fixtures is literally named ünïcode spaced 名前.jpg, and others contain $(pwd) and backticks. Passed as separate arguments, these are just file names. Concatenated into a shell command, they are one quote away from running something.

Other details of command.rs:

  • Raw stderr is always kept, capped at the last 256 KiB per child so a damaged file cannot exhaust memory. Interesting FFmpeg failures do not always announce themselves as errors.
  • Cancellation is graceful, then forced (D-045). quit() writes q to FFmpeg's stdin, which tells it to finish the file cleanly. If it has not exited within a grace period, kill() follows. Stdin is used instead of a signal because there is no portable way to send SIGINT to a child on Windows.
  • Adaptive polling (D-149). Rust's standard Child has no timed wait, so waiting means checking repeatedly. The gap between checks is clamp(time_waited / 8, 1 ms, 20 ms). A fixed 20 ms poll had made still validate on 200 scenes take 11.82 seconds, because each 23 ms probe was noticed at 40 ms. With proportional backoff plus concurrent probes it dropped to 1.31 seconds.
  • Every command is logged in a paste-ready form, so when scene 147 fails, the operator (or developer) can run the exact command by hand.

tools.rs finds ffmpeg and ffprobe. It never hands Command::new a bare name. A Mac app launched from Finder inherits launchd's minimal PATH, which has no Homebrew directory, so a bare ffmpeg would fail for every photo. locate searches the places package managers install to and returns an absolute path. The pair is resolved once per run and cloned into each worker, so a 500-scene batch cannot run half on one FFmpeg build and half on another.

probe.rs wraps ffprobe -of json with a timeout from the very first call, parses the JSON with serde_json into ProbeResult and Stream, and has probe_counting_frames, which decodes the whole file and counts frames instead of trusting the header. Section D-179 records that 9 of 10 probe timeouts seen on a network share were read-after-write delays, so a failed probe is retried once instead of simply given a bigger timeout.

Rendering one scene: spoonstill-media/src/scene.rs

render_scene is "M1's whole product in miniature". Its order is fixed by D-042:

render to a temporary path beside the destination
  -> ffprobe validate (frames, duration, size, codec, SAR, colour)
    -> atomic rename into the real segment path
      -> the caller records success

Inside render_scene_inner, step by step:

  1. Probe the image for its SourceGeometry and probe the normalized audio for its duration. Duration is measured, never estimated (D-021).
  2. Compute frames, duration and pad with the timing functions.
  3. Use the requested motion or derive the seeded one from the image's content hash.
  4. Build the filter string and the expected SegmentProfile, then log a "scene resolved" event with every number, including the full filter string.
  5. Draw caption bands to temporary raw RGBA files if subtitles are on.
  6. Run FFmpeg, writing to a .partial file.
  7. Validate. On any failure the partial file is deleted, so nothing half-written can be mistaken for a finished segment.
  8. Rename into place.

The FFmpeg invocation itself is built with argument vectors. A trimmed excerpt of run_ffmpeg:

let audio_chain = format!(
    "[1:a]aresample={SAMPLE_RATE},apad,\
     atrim=end_sample={samples},asetpts=N/SR/TB[a]");
// ...
command
    .arg("-filter_complex")
    .arg(&graph)

        .quality_args(&request.encode.preset, request.encode.crf))

The audio chain resamples to 48 kHz, pads with silence (apad), cuts at the exact sample count (atrim=end_sample=), and resets timestamps to start at zero (asetpts). Input 0 is the still and input 1 is the narration. Each caption cue is a further rawvideo input, laid on top with FFmpeg's core overlay filter after the motion chain. The -movie_timescale line is the most recent fix in the history (D-206): MP4 stores each track's length in an "edit list" using a movie clock that defaults to 1,000 ticks per second. A 119-frame segment of 3.966667 seconds was declared as 3.966 seconds. On the author's 800-scene film, 52 segments each lost 0.67 ms, the joined 4K film came out 38 ms short, and the final length assertion correctly refused it. Setting the movie clock to the same 90,000 ticks as the video track fixed it.

The segment profile: exit code 0 is not validation

profile.rs pins every property a segment must have: container MP4, codec H.264 High profile, pixel format yuv420p, TV range, BT.709 colour, SAR 1:1, a 90 kHz video timescale, and AAC-LC stereo 48 kHz at 192 kbps. assert_matches_profile compares each field against the ffprobe output and returns a list of Mismatch { field, expected, actual }.

The reason is section 5 of the findings: concatenating a SAR 30007:30000 segment between two 1:1 segments with stream copy gave exit code 0, no warning, and a film declaring SAR 1:1 throughout. Sixty frames had the wrong geometry, silently. So "FFmpeg did not complain" is not evidence (D-041), and the profile module is the thing that complains. The 90 kHz timescale was chosen because it divides evenly by 24, 25, 30, 50 and 60.

Joining: spoonstill-media/src/concat.rs

Segments are joined with FFmpeg's concat demuxer and -c copy, which copies compressed data without re-encoding. That is only safe because every segment was already proven identical in format. The concat list is a text file FFmpeg parses, which makes it the one place in the codebase where a string format is unavoidable. Instead of escaping operator file names, is_safe_list_name only allows ASCII letters, digits, -, _ and ., which is the shape of spoonstill's own generated segment names. An operator's spelling never reaches the list.

After the join, the film is probed and checked: its video must be within one frame of the sum of the segment frame counts, and its container may run up to one AAC frame (1024 samples, 21.3 ms) longer because of AAC "priming" samples. If the film is short, stopped_at walks the per-segment frame counts to name which segment the join stopped at. This came from D-178: a segment written to a network share had an intact header over an incomplete picture, and the old error message blamed the film, the one file that was not at fault.

Atomic writes: atomic.rs

Every artifact is written to a temporary name beside its destination, then renamed. A rename within one filesystem is atomic (it happens completely or not at all), while a rename across filesystems is really a copy that can be interrupted. Temporary names look like .film.mp4.partial-<pid>-<counter>.mp4. The counter comes from a global AtomicU64, because two workers in one process can target the same cached audio file at the same moment. The extension is preserved because FFmpeg picks its output format from it. The cleanup function only deletes files matching that exact pattern, because the film's destination may be the operator's Downloads folder, and a looser rule could delete a stranger's file.

Audio: one shape for every source

spoonstill-media/src/audio.rs turns every audio source into the same artifact: 48 kHz stereo 16-bit PCM in a WAV file (PCM means uncompressed samples). PCM instead of AAC avoids two generations of lossy compression, at the cost of disk (about 2.9 GB for 500 scenes of 30 seconds). The cache can always be rebuilt; lost quality cannot.

Loudness is measured in LUFS (Loudness Units relative to Full Scale, the EBU R128 broadcast standard for perceived loudness). Edge TTS lands around -24 LUFS and a phone recording around -12, so a mixed film would be uneven. The target is -16 LUFS with a true-peak ceiling of -1.5 dBTP. The analysis pass runs FFmpeg's loudnorm filter only to measure, and silencedetect to find where speech starts and stops. The correction is then a single linear gain:

fn gain_db(analysis: &Analysis) -> Option<f64> {
    let loudness = analysis.loudness?;
    let wanted = LOUDNESS_TARGET_LUFS - loudness;
    let allowed = analysis
        .peak
        .map_or(f64::INFINITY, |peak| {
            TRUE_PEAK_CEILING_DBTP - peak
        });
    let gain = wanted.min(allowed)
        .clamp(-MAX_GAIN_DB, MAX_GAIN_DB);
    (gain.abs() >= 0.05).then_some(gain)
}

The gain is the smaller of "what loudness asks for" and "what the peak allows", capped at plus or minus 24 dB so a recording made with the microphone muted does not become a wall of hiss. Gains under 0.05 dB are skipped. The comment explains why loudnorm is not used to apply the change: in single-pass mode it compresses dynamics, which changes how speech sounds and depends on FFmpeg's version. A plain volume= filter moves every sample equally and is byte-identical run to run.

Synthesized speech has its leading and trailing padding trimmed; the operator's own recording never is, because "your padding is a decision and a provider's is an artifact". Silence is a real PCM file of an exact sample count, so a silent scene takes exactly the same path through the renderer as a narrated one. The normalization profile string pcm_s16le/48000/2/-16lufs/v2 is part of every audio cache key, so changing the profile misses the cache.

Captions drawn in Rust

spoonstill-media/src/caption.rs exists because Homebrew's default ffmpeg formula no longer includes libass or libfreetype, so the subtitles and drawtext filters do not exist on the very FFmpeg the README tells users to install. Rather than require a special build, spoonstill draws the text itself into RGBA pixels and asks FFmpeg only for overlay, which every build has.

The pipeline per cue is: wrap to the frame width, shrink if it still does not fit, draw the shadow, the backdrop, the outline (the glyph mask dilated), then the fill. Fonts are compiled into the binary with include_bytes!: three weights of Inter and three of Noto Sans Devanagari, both under the SIL Open Font License. Embedding them means a theme looks identical on every machine. fontdue rasterizes individual glyphs, and harfrust (a Rust port of the HarfBuzz text shaper) decides which glyphs to use. Shaping matters for Hindi: a conjunct like स + ् + त becomes one shape, and the vowel sign ि is drawn to the left of the consonant it follows.

Performance work here is a good example of the project's method (D-130). An audit asked for benchmarks, and drawing one 4K caption took 604 ms, with cost growing with the fourth power of resolution. Two algorithmic fixes brought it to 62 ms:

  • Dilation (growing the text mask to make an outline) now uses a sliding-window maximum with a monotonic deque: a queue that only holds indices whose values could still be the maximum, so each pixel is pushed and popped once and the pass is O(width) per row.
  • Box blur (for the shadow) now keeps a running sum: consecutive windows differ by one sample at each end, so each pass is O(area) instead of O(area * radius).

The old slow versions are kept in the tests as the definition of correct, and the new output is asserted byte-identical.

Hardware encoders: run it, do not trust the list

hardware.rs detects GPU encoders such as NVIDIA's NVENC (h264_nvenc), AMD's AMF, Windows Media Foundation, Intel Quick Sync and Apple's VideoToolbox. The key lesson is in its header table. On a Windows machine with an RTX 3060 and an AMD Radeon, ffmpeg -encoders listed seven H.264 hardware encoders, and only four could actually encode. The list reports what FFmpeg was compiled with, not what the machine can do. So each candidate is run: it encodes a few small yuv420p software frames from a synthetic source within a 30 second limit. Encoders that only accept frames already on the GPU are correctly reported unusable, because spoonstill's filter graph always produces CPU frames.

VideoEncoder::quality_args translates x264's settings for each encoder, because -crf 18 means nothing to most of them. NVENC gets -rc vbr -cq 18 -b:v 0 with the preset translated to its own p1 to p7 scale; AMF gets constant QP on all frame types; VideoToolbox takes a 1 to 100 quality scale that runs the other way.

Is the GPU worth it? Section 12c of the findings measured that at 4K the encoder is only 14% of a scene's time on macOS (22.7% on Windows), because the work is the CPU filter graph and the 11520x6480 prescale canvas. GPU encode gives 1.2 to 1.67x and saves zero memory. Since v0.1.20 (D-199) the control surfaces nevertheless pick a working graphics encoder by default through spoonstill_app::tooling::default_encoder, with an off switch in Settings, still doctor --graphics off, or the SPOONSTILL_GRAPHICS environment variable. The library itself still means libx264 when no encoder is named, so every test that pins a film's exact bytes keeps describing the same film. Hardware encodes also get a different cache key, while the software key string is unchanged from before, so old caches still hit.

Text to speech: spoonstill-tts

The Provider trait has a small contract: id, availability (ready, or missing with a Remedy), voices, default_voice, install, and speaking one line to one file. A provider does not choose the output format (everything is normalized afterwards), does not decide scene length (that is measured), and does not cache (the caller's key covers text, provider, voice, settings and profile).

The Edge provider (edge.rs, the largest file in the crate) spawns the Python edge-tts tool through spoonstill_media::command rather than reimplementing Microsoft's protocol in Rust, because that endpoint is reverse-engineered, uses a clock-skew-based anti-abuse token, and changes. Some notable choices:

  • Text goes in a file, never on the command line, passed with --file. Long text could exceed the OS argument limit, arguments are visible to every process through ps, and above all the command line is logged into diagnostics bundles. The operator's script should never end up in a bug report.
  • Failures are classified before they are retried. Every edge-tts failure ends with a Python exception on the last stderr line. NoAudioReceived and Invalid voice are permanent; aiohttp and websocket errors are transient and retried with growing pauses. An unrecognized error defaults to permanent, which avoids retrying a bad request three times slowly.
  • Timeouts scale with line length. Measured: a short line takes about 0.6 seconds, 5,980 characters took 37.6 seconds (about 6.3 ms per character). A fixed 90 second limit would wrongly call a long paragraph on a slow link a dead network.
  • Long lines are split (split_line) and the pieces are joined.
  • Speaking twice does not produce identical bytes (two runs differed in 5,916 bytes), which is why the raw speech is cached beside the normalized artifact: re-normalizing must never mean re-speaking.

pace.rs handles throttling, a problem found in production logs. A 431-scene render sent 335 lines in three and a half minutes and then every connection to the speech service was refused. Later, at a fifth of the rate, a Windows machine was cut off after about 390 lines. The conclusion (D-195, D-199) is that the service limits a count, not a rate. The Pace rules are process-wide: at most two requests in flight, starts at least 1.2 seconds apart, and after a refusal a cool-down that starts at 15 seconds, doubles up to 120, and resets on the first success. A refusal streak is waited out for up to an hour once the process has spoken anything (and much less if it never has, because that looks like a blocked network). Meanwhile the segment pool keeps encoding everything already spoken. The arithmetic lives in a Schedule type that takes the clock as an argument, so it is tested without sleeping, and a Gate with a Mutex and Condvar wraps it for real threads.

Orchestration and concurrency: spoonstill-app

spoonstill-app/src/film.rs is still render. Its phases:

import      every problem at once; nothing renders on any error
lock        one render per project at a time
audio pool  each scene -> (normalized path, measured duration)
render pool each scene -> validated segment, N at a time
concat      stream copy, then assert the film's profile and length
sweep       remove superseded segments

Two pools, not one (D-044). Audio work is network and I/O bound; rendering is CPU and memory bound. They have separate limits. Originally they ran as two separate phases, which left encoders idle while narration was being fetched. D-146 overlapped them with pool::pipeline, which starts rendering a scene as soon as that scene's audio is ready.

The pool is built on plain threads, not an async runtime. The comment in pool.rs gives the reason: the unit of work is a child process that runs for seconds, so there is no I/O concurrency problem to solve, and std::thread::scope lets workers borrow the caller's data without wrapping everything in Arc. The core of the simple pool:

std::thread::scope(|scope| {
    for _ in 0..workers {
        scope.spawn(|| loop {
            if cancel.is_requested() {
                return;
            }
            let index = next.fetch_add(1, Ordering::SeqCst);
            let Some(item) = items.get(index) else { return };

            let value = work(index, item);

            if let Ok(mut slot) = results.lock() {
                slot[index] = Some(value);
            }
        });
    }
});

Each worker claims the next index with an atomic counter (fetch_add), does the work without holding any lock, and only locks the results vector to drop its value into the slot for that index. Results therefore come back in input order regardless of which worker finished first, so --jobs 8 and --jobs 1 produce the same film byte for byte. Cancellation stops admitting new items; work in flight stops through FFmpeg's own quit-then-kill ladder. Items never started are reported as NotAdmitted with a reason (Cancelled or EarlierFailure), a distinction added after a single failed narration was reported as five scenes "cancelled" when nobody had cancelled anything (D-174).

pipeline_in is the two-stage version. Producers run stage one (audio) and push finished items into a VecDeque inside a Mutex, guarded by a Condvar that wakes consumers. A live count of running producers is the only signal that no more work is coming, because an empty queue "right now" says nothing. If stage one fails, an AtomicBool stops further narration from being bought for a film nobody will get. D-199 added an admission order: scenes whose narration is already cached go first, so the encoders stay busy while throttled lines wait.

How many workers? default_jobs() is half the cores, capped at 4. Findings section 10a measured the speedup on twelve 1080p scenes: 1.00x at one job, 1.55x at two, 1.83x at three, 1.85x at four and only 1.92x at eight, because x264 already uses about 2.7 cores per worker. capacity.rs (D-144) then caps by memory. Its model is 192 MB + 36 bytes per prescale pixel per worker, which sits above every measurement (369 MB at 720p, 768 MB at 1080p, 2,630 MB at 4K), and a render may plan to use 70% of total RAM (total rather than available, so two runs pick the same number). This module was written after a Windows machine froze on start with four 4K workers.

The render lock (D-113). Two renders of the same project would interleave segments. The lock is the operating system's, via std::fs::File::try_lock on .spoonstill/render.lock. The file's existence means nothing and it is never deleted. A kernel lock cannot go stale, because the OS releases it when the process dies. One related Windows bug is worth knowing: LockFileEx refuses a handle opened only for append, so a different lock (on the activity log) had failed on every Windows write for five releases without anyone noticing, because its failure was tolerated by design (D-135). The fix was to open the file read/write, and the lesson was that "a lock whose failure is survivable must still be a lock whose failure is loud".

The segment cache key (D-043, D-107). segment_key hashes, with length-prefixed fields: the image content hash, the narration's own audio cache key, the frame count, the motion descriptor and seed, the output geometry, the encoder settings, the pinned pixel format, colour space and timescale, and each subtitle field. Nothing about paths, scene IDs or the machine is included. The narration key was added after a nasty bug: the key once included the frame count but not the audio itself, so re-recording a line at the same length reused the old segment, and the film had the operator's previous take while reporting success.

The audio cache (app/src/audio.rs) keys by content too:

Source Key
Recording hash(file bytes, normalization profile)
Silence hash("silent", sample count, profile)
TTS hash(text, provider, voice, settings, profile)

The cache is a directory of content-named files with no index database, so it can be inspected with ls. Superseded segments are swept after a render unless --keep-cache is set (D-109).

Import, ingest and arrange

import/ turns a folder into a project. settings.rs loads project.yaml with serde_yaml_ng (the maintained fork of the deprecated serde_yaml). rows.rs either reads a CSV manifest with the csv crate or pairs files by stem (D-050). Then core validation runs, paths are resolved with resolve_within, and every file is probed. Each stage adds to one problem list, so still validate reports everything at once. Extensions are only a hint: a .jpg that is really a PDF is caught by ffprobe.

A strict rule: project.yaml is an input, and the renderer never writes to it (D-013). Machine state lives in the hidden .spoonstill/ folder, which can be deleted at any time. Per-run choices such as --voice are overrides that never touch the file.

ingest.rs (D-080) copies the operator's files in under numbered names. Its rules: copy, never move; never overwrite (numbering continues past the highest existing number); skip and count unusable files instead of failing. Pairing is natural-sort positional (IMG_2 before IMG_10) after matching names. Copies are made beside the destination and renamed in, because of D-120: on APFS fs::copy is an instant clone so the problem is invisible, but on a FAT32 volume an interrupted copy of a 400 MB photo left 232 MB at 001.jpg.

arrange.rs (D-100) implements still move and still remove. Because the scene number is the order, moving a scene means renaming files. Renames happen in two passes through temporary "parked" names that encode what they were doing, so recover can finish or undo an interrupted renumber the next time the project is read (D-121). This came from a real disaster: a killed still remove left files under dotfile names the scanner ignored, and validate reported "1566 scenes, no problems" over a project that had 2000. A move only renames scenes whose numbers change, so swapping two neighbours in 431 scenes is four renames, not 862. Removed scenes go to removed/; nothing is ever deleted. picture.rs (D-194) adds placing, swapping and undoing a picture on a specific scene, journalled the same way.

State and diagnostics: spoonstill-state

Despite a module comment that still describes SQLite, there is no database yet; the crate description says "No SQLite yet, that is M3". What exists:

  • logs.rs: every run appends JSON Lines (one JSON object per line) to .spoonstill/logs/, rotated at 8 MiB with five files kept. JSON Lines is append-only, so a crash loses at most the last line. Values pass through redact before being written. write_bundle packages logs plus environment details into one text file for bug reports, with a header that tells the user plainly it contains their paths.
  • runs.rs: a machine-wide runs.csv in the OS config folder, so "what went wrong just now" can be answered without knowing which project folder to look in. Failures here are silent by design, because a render must never fail over a spreadsheet. Values starting with =, +, -, @ or a tab are defused, because spreadsheets execute those as formulas even after stripping CSV quotes (D-122). This was verified with folders named =1+1 and @SUM(A1:A9).

The CLI: spoonstill-cli/src/main.rs

still uses clap's derive API. Its subcommands: new, add, import-chapter, picture, remove, move, validate, render, render-scene, voices, subtitles, resolutions (alias formats), doctor, licences, and diagnostics export|where. Ctrl-C uses the ctrlc crate to set the shared Cancel flag, because a hand-written signal handler would need unsafe, which the workspace forbids, and would not cover Windows console events. Render progress arrives as FilmEvents; the Planned event prints how many workers were chosen and whether memory, not cores, decided it.

The desktop window: apps/desktop

The Tauri 2 shell is "the review grid of D-051, and nothing more". Tauri apps have a Rust backend and a system webview frontend; the frontend calls Rust functions by name through IPC (inter-process communication). src/main.rs registers about 40 commands (validate_project, add_media, import_chapter, voices, preview_voice, subtitle_preview, render_project, cancel_render, and others). Every one translates arguments into a spoonstill-app call and returns a serializable view. There is no filter string, FFmpeg argument, duration maths or cache key in the shell.

Security is tight by construction:

  • The capability file grants only core:default, window dragging and the open-file dialog. There is no filesystem scope at all.
  • open_film and reveal_project take no path arguments. They can only open the film this window just rendered, so the webview cannot name an arbitrary file.
  • The asset protocol (used to show thumbnails) starts with an empty scope, and a project's folder is granted at runtime only when it is opened.
  • The content security policy is script-src 'self', which forbids inline scripts.

render_project runs the blocking render inside tauri::async_runtime::spawn_blocking and sends progress through a Channel<ProgressView>. The cancel flag lives in Rust managed state, not in the webview, so reloading the page cannot lose track of a running render. A guard object (ActiveRender::claim) releases the "a render is running" slot on every exit path; it used to be cleared by a line after handle.await?, which ? skipped on a panic, leaving the window convinced a render was running forever (D-115).

The UI itself is ui/index.html, ui/styles.css and ui/app.js, about 4,900 lines with no framework and no build step. The dialog plugin is invoked by name (invoke("plugin:dialog|open")) because there is no bundler to import its npm package. Screens are home, then a project with tabs for scenes, voice, subtitles, output and render. The Subtitles preview is drawn by the real Rust rasterizer, not imitated in CSS. Because a webview fails silently, tests/ui_contract.rs checks that every el("id") in the JavaScript exists in the HTML and that every invoke("cmd") is a registered command, and make ui runs node --check plus a smoke script on app.js.

Build system, tests and release

  • Workspace Cargo.toml: resolver 3, edition 2024, rust-version = 1.94, shared version 0.1.25. unsafe_code = "forbid" and clippy::all = "deny" apply to every crate. Release builds use thin LTO and one codegen unit. rust-toolchain.toml pins 1.94.0.
  • Dependencies are few: about a dozen third-party crates at runtime, and spoonstill-core has none. Each Cargo.toml explains its dependencies in comments (for example, harfrust was chosen over rustybuzz because the latter was declared unmaintained in a RustSec advisory).
  • Makefile targets: test, lint (clippy with warnings denied, rustfmt check, actionlint for workflows, shellcheck for scripts, node --check for the UI), fixtures (synthesizes test media with FFmpeg, including odd.jpg, truncated.jpg, zero_byte.mp3, vbr_lying_header.mp3 and the Unicode-named file), gates, demo, tts-live, brand, clean.
  • Exit gates: scripts/m0-gates.sh, m1-gates.sh and m2-gates.sh (the last is 82 KB of shell) render real media and assert real properties: 8 + 8 + 23 = 39 checks.
  • Rule-enforcing tests: architecture.rs (layering), no_shell_strings.rs, motion_matrix.rs (durations x frame rates x aspects x source shapes x hostile paths), segment_integrity.rs, hardware_report.rs (checks both directions: usable encoders encode, unusable ones fail), cited_decisions.rs (every D-nnn cited in code exists), readme_claims.rs (the README's counts are derived from the tree), release_assets.rs, and edge_retry.rs (retries through a real process boundary with a fake edge-tts).
  • CI (.github/workflows/ci.yml) runs six jobs per push: cargo audit --deny warnings, macOS and Windows builds with fmt, clippy and full tests rendering real media, both installers executed for real, and the gates on a machine without the voice service, to prove a missing provider fails loudly instead of silently producing silence.
  • Release (release.yml): a tag must match the versions in Cargo.toml and tauri.conf.json; the CLI is built for macOS Apple Silicon, macOS Intel and Windows, smoke-tested and architecture-checked; the Tauri app is bundled as a universal .dmg and an NSIS .exe installer; checksums are generated; the publish job asserts the exact set of expected assets before undrafting.
  • Installers (scripts/install.sh, install.ps1) verify SHA-256 checksums, install to the user's own folder with no admin rights, clear the macOS quarantine attribute, and offer to install FFmpeg through Homebrew or winget.

Key Design Decisions and Trade-offs

  • FFmpeg as a child process, not linked bindings (D-011). The alternatives were rust-ffmpeg C bindings (described as maintenance mode with painful cross-platform builds) and ffmpeg.wasm (an order of magnitude slower, about a 4 GB ceiling, no hardware encode). A child process is isolated, easy to log and paste, and cancellable. The cost is that every result must be validated from outside, which the segment profile does.
  • Reimplement the ffmpeg-sidecar pattern instead of depending on it (D-012). The crate auto-downloads FFmpeg by default (rejected: shipped builds must be pinned), has no timeout on ffprobe, and its typed stderr parsing was something the project had already decided not to trust. The result was a smaller module than the estimated 600 lines.
  • CLI first, GUI as a thin adapter (D-010). A headless CLI over 500 scenes can be tested in CI; a webview cannot. The trade-off is that every feature costs a CLI surface first, but nothing can only be done in the window.
  • zoompan over time-based scale+crop (D-031). The planning documents suggested scale+crop would avoid zoom quantization. Measured, zoompan was 7.7x faster and used half the memory, because scale with eval=frame re-runs a lanczos resample on the whole canvas every frame. The 3x prescale had already fixed quantization.
  • Per-scene segments plus stream-copy concat (D-040). This enables resume and caching, and the join costs I/O, not encoding. The alternative, studied in editly, renders every frame in one Node process with no segments, so no resume. editly's frame-server approach is recorded as the escape hatch if motion ever needs more than FFmpeg filters can express.
  • Hard cuts only for now. Transitions with xfade are on the roadmap but deferred until measured at 500 scenes, because overlapping segments would break the simple "segment length equals narration length" model.
  • Draw captions in Rust. It costs about 1,900 lines and two font families in the binary, but subtitles work on the stock Homebrew FFmpeg.
  • Threads instead of async. No runtime dependency and no "function colouring" (the way async spreads through every signature), for work that is a handful of long-running processes.
  • No state database yet. Resume already works through content-addressed files, so the planned SQLite state.db is explicitly "not load-bearing for correctness", only a future reporting index.
  • Edge TTS as a development provider. It is free and good enough, but it rests on a reverse-engineered endpoint, so the design reserves a bring-your-own-key provider (ElevenLabs, with keys in the OS keychain via keyring-rs, D-014) for any sold build. That provider is not written yet.
  • Unsigned builds and no bundled FFmpeg (D-062). The FFmpeg used in development is a GPL build that cannot be shipped with a proprietary product; a custom LGPL build is required first. The licence for spoonstill's own code is not chosen yet.

Challenges and How They Were Solved

The project's PROCESS.md states one rule above all: reproduce it before believing it, fix it, then prove the test fails without the fix. Many of the fixes below came with a test that was first run against the broken code.

  • The five-hour "hang": measured as unbounded output from -loop 1 with d=N. Solved by making the frame count structural (d=N plus -frames:v N, no loop flag).
  • Wrong SAR and colour range passing silently through concat: solved with the fixed filter tail and a per-field profile assertion on every segment and on the final film.
  • A fixture that could not exhibit its own bug: odd.jpg was first generated at 1998x1000, which is even, so the odd-dimension SAR test would have passed for the wrong reason. Findings section 8b documents the three deliberate steps needed to make a truly odd fixture, and the tests now assert the fixture still has the hazard.
  • The cache that returned your previous take (D-107): the narration's own key was added to the segment key.
  • Caption text colliding with the hash separator (D-118): switched to length-prefixed hashing.
  • The interrupted renumber that hid 433 photos (D-121) and the removal that kept half a scene (D-203): journal-in-the-filename parking plus recover.
  • A Windows file lock that never worked (D-135): open with read/write access, and make tolerated failures visible.
  • A 4K render freezing a Windows PC (D-144): memory-derived worker count.
  • The voice service cutting off after about 350 lines (D-195, D-199): process-wide pacing, cool-down, waiting out refusals, and admitting cached scenes first so encoders stay busy.
  • Hindi rendered as boxes (D-157): Inter's missing-glyph box (which literally says "NO GLYPH") was drawn per character. Fixed by embedding Noto Sans Devanagari and adding a real shaper, while proving three Latin captions render byte-identically before and after.
  • The export "hidden in the folder" (D-178): it was actually four failed renders leaving invisible .partial- files and a segment on a network share with an intact header but incomplete picture. The fix made the join name the segment it stopped at and made sure a failed export leaves nothing invisible.
  • The film 38 ms short (D-206): MP4's default movie timescale of 1,000 rounding each segment's declared length. Fixed with -movie_timescale 90000.
  • Tests that passed by checking nothing (D-153, D-154): a resume gate killed a process that had already exited, and another gate reported PASS while running no command for three sessions. The lesson recorded: "a gate count is not evidence that every gate ran."
  • Parallel AI sessions corrupting each other's tests: the AI Model/claude/plan.md review found that tests used a fixed scratch folder that was deleted on entry, so two terminals running tests at once could make results lie in either direction. It ranked fixing test isolation first, before any other work.

Security and Performance Notes

Security.

  • unsafe is forbidden in every crate.
  • No shell is ever involved in running FFmpeg or edge-tts; this is enforced by a test that reads the source.
  • Manifest paths are canonicalized and contained, with one generic error for anything outside, so errors cannot be used to probe the filesystem.
  • The concat list, the only text format FFmpeg parses, only accepts names spoonstill generated.
  • The Tauri window has no filesystem scope, path-free open commands, a runtime-granted asset scope and a strict CSP.
  • The narration text is passed to edge-tts through a file, never an argument, so it does not appear in ps or in logs. Diagnostics are redacted before being written.
  • CSV output is defused against formula injection.
  • cargo audit runs on every push; one advisory (unsafe-libyaml unmaintained, RUSTSEC-2024-0449) is recorded with the reason it is not swapped yet.
  • Installers verify SHA-256 checksums and need no admin rights. Releases are not code-signed yet, which the README explains openly.

Performance. Every number below is a measurement from ffmpeg-findings.md or the decision log:

Question Measured answer
Best prescale 3x output: 0 duplicate frames, about 761 MB
zoompan vs scale+crop 1.08 s vs 8.32 s for 4 s of 1080p
Worker speedup flattens at 3 to 4 workers
Memory per worker 768 MB at 1080p, 2,630 MB at 4K
Encoder share of a 4K scene 14% (macOS), 22.7% (Windows)
Caption at 4K 604 ms reduced to 62 ms, same bytes
still validate, 200 scenes 11.82 s reduced to 1.31 s
Second render of an unchanged project encodes nothing

The scaling principle (D-002) is that n=500 is the design point: something fine at 5 scenes but quadratic at 500 is a defect. The author stress-tested the voice and pool changes on a real 431-scene project and on a synthetic one forty times larger.

How to Run It

From the repository README and Makefile:

# Prerequisites: FFmpeg, and optionally the edge-tts voice tool
brew install ffmpeg              # macOS
winget install Gyan.FFmpeg       # Windows
still voices --install           # or: pipx install edge-tts

# Build from source
git clone https://github.com/VijaysinghPuwar/spoonstill.git
cd spoonstill
cargo build --release -p spoonstill-cli     # -> target/release/still
cargo run   --release -p spoonstill-desktop # the window
# Make a project, check it, render it
still new ~/holiday ~/Pictures/trip/*.jpg ~/Voice\ Memos/*.m4a
still validate ~/holiday
still render ~/holiday --out ~/holiday.mp4

# Options
still render ~/holiday --out ~/film.mp4 --subtitles boxed
still render ~/holiday --out ~/short.mp4 --aspect shorts \
  --resolution 1080p
still doctor            # what is installed, which GPU encoders work
still move ~/holiday 8 1
# Developer loop
make fixtures   # synthesize test media
make test       # cargo test --workspace
make lint       # clippy, fmt, actionlint, shellcheck, node --check
make gates      # the 39 milestone exit gates

A warning from the README: building and running the gates fills target/ quickly (37 GB on the author's machine). make clean removes it.
